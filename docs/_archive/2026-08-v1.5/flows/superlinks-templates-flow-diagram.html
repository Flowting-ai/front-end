Super Links — Page-by-Page Reference

Companion to flows/agents-flow-diagram.html, flows/chats-projects-flow-diagram.html and flows/tasks-flow-diagram.html, same schema — the agent-sharing surface: generating a public/credit-metered link to a persona, the sender's management table, the recipient's accept flow, and the unrelated "Template" preview-link feature this doc exists partly to disentangle from it.

V1.5 — Built fresh from current source this session. The first real finding here is a naming collision, not a UX bug: the codebase has two completely separate "shareable link" systems that both get called a "link" in the UI and both live partly under a route literally named template/Templates in one case. This doc untangles them (§00) before documenting Super Links proper (§01–§04). Also flags one unused/dead component (§01) and one directly verified access contradiction between Super Link's own marketing copy and the app's auth middleware (§04).

00Entities — two unrelated "link" systems

Worth stating plainly before anything else, because the naming actively invites confusion: this codebase has two independent sharing mechanisms that share no components, no API module, and no data shape. They are not two views of one primitive.

FeatureWhat it actually isWhere it lives
Super Link
(this doc)		A credit-metered, revocable public URL to chat with one specific persona/agent — the visitor gets a live conversation, billed to the sharer's credit budget.src/lib/api/persona-shares.ts, /agents?tab=super-links, /agent/configure/sharing, /share/[id]
"Template"
(unrelated — not covered further)		A revocable public URL to a static, model-written HTML document (a dashboard/report an agent produced) — the visitor gets a read-only sandboxed <iframe>, no chat, no credit metering visible to them.src/app/api/template/[uuid]/route.ts, src/app/(app)/template/[uuid]/page.tsx, backend /templates/{id} and /templates/{id}/html

The overlap is entirely superficial: both are a /​<segment>/[uuid] route that resolves a token to something a logged-in org member can view, and both can be revoked by their creator (a 410 on the Template route, an is_active:false/expiry check on the Super Link route). Everything else — the payload, the viewer experience, the backend table, the revoke UI — is different. The Template route's own document comment even says its sandbox headers exist so "charts, filters and drill-downs" in model-generated HTML keep working; that has nothing to do with chatting with an agent.

This is also distinct from Chat Sharing (see chats-projects-flow-diagram.html §04, /chat-shares/[shareId]) — sharing one finished conversation transcript for another Souvenir user to view/copy. Chat Sharing, Super Links, and Templates are three separate share-a-URL features built independently, not three configurations of one shared "share" primitive. The one structural similarity worth naming is that Chat Sharing and Super Links both went through a near-identical design evolution (a card/chart "dashboard" mockup that never shipped, superseded by a plainer table-based tab inside an existing settings page) — see §01's dead-component note below.

Input

  • GET /persona-shares/dashboard?window=7|30|90 (fetchDashboard) — summary tile numbers plus a daily credit series for the sparkline; refetched whenever the 7d/30d/90d range control changes.
  • listShares() → GET /persona-shares populates the "My Superlinks" table (every share this user created, both link and email type, though only share_type: 'link' rows are what this doc calls a Super Link).
  • listReceived() → GET /persona-shares/received populates "Shared Superlinks" only once that sub-tab is actually selected — not prefetched with the rest of the tab.
  • The est. cost stat tile is computed client-side (credits_this_month / 1,000,000 × 3) — a hardcoded $3/M-credit rate, not a value the dashboard endpoint itself returns.

Edge cases

  • gap A whole design of this feature was built and never wired up. src/templates/SuperLinks/index.tsx (plus its supporting SuperLink/LinksSidePanel/SuperLinkRow/SuperLinksEmpty components) is a complete stat-card + chart + master-detail dashboard — but nothing in src/app imports it. The page that actually ships (agents/page.tsx) reimplements the same stat tiles and chart concept inline with a plain SettingsTable instead of the LinksSidePanel master list. SuperLinkRow/SuperLinksEmpty/SuperLinkDrawer ARE still used by the live page; only the top-level SuperLinks template and its LinksSidePanel shell are orphaned. Worth deleting or explicitly marking as a design reference, since a future edit to the unused file will silently do nothing.
  • The stat-tile row and chart are hidden entirely (not zero-stated) when the sender has zero outgoing links — isEmpty gates the whole block, not just the table below it.
  • sparkData deliberately falls back to an all-zero flat line (never fabricated activity) when the backend's daily series has fewer than 2 points — an explicit inline comment calls out this as an "honest placeholder" choice.
  • "Most active agent" is a client-side ranking by recipient count over whatever page of shares was already fetched — there's no backend "top agent" endpoint being called.

Input

  • Overview — 4 StatCards, a TokenBudgetBar, and a 7-day Sparkline of dailyTokens — all derived from the one PersonaShare row already in memory, no separate fetch on open.
  • Sessions — one SessionRow per share.recipients entry (id, time, messages, tokens, status), separated by dividers; header line states the count plus unique-user count.
  • Settings — editable credit limit (inline edit → Save/Cancel), a Pause switch, and a two-step "Revoke link" confirm (button → inline danger card → "Yes, revoke").

Edge cases

  • "Runs out in ~N days" under the credit-limit field is computed from (limit − used) / average-daily-usage — silently omitted (not zero, not "∞") when average daily usage is 0, e.g. a brand-new link with no traffic yet.
  • Pausing is modeled as a boolean toggle bound to status === 'paused', but SuperLinkStatus is actually a 4-value type (active | paused | limit-reached | revoked) — the Switch has no way to represent or clear a limit-reached state; only Settings' separate Revoke action can move a link out of that state.
  • ESC-to-close and body-scroll-lock are both scoped to exactly the drawer being open (mount/unmount effects), so there's no idle listener when no link is selected.

Navigation

Not applicable — closes back to §01's table; no further drill-down page.

Floating panels & Help

Missing / Unused / Hidden

  • backend-ready-but-unused The 4-value SuperLinkStatus type (active | paused | limit-reached | revoked) has no UI path to reach or explicitly clear limit-reached. The Settings tab's Pause switch only toggles between active/paused (bound to status === 'paused'); limit-reached can apparently only be set server-side (link hit its credit cap) and the only way out of it from this UI is the unrelated Revoke action, which destroys the link rather than resetting it — e.g. after raising the credit limit, there's no "reactivate" affordance shown for a limit-reached share. — SuperLinkDrawer Settings tab / SuperLinkStatus type.
  • Nothing else found in this section beyond the status-value gap above (no dead components, no {false &&}, no orphaned routes specific to the Drawer).

03Generating a link/agent/configure/sharing, and /agents/published

Two different screens can generate the same kind of Super Link, both wrapping the same createShare call — one during normal editing, one right after a fresh publish.

Layout sketch — SharingTab (agent/configure/sharing)

souvenir.app/p/your-agent-a8b2c3
Generate link

Input

  • SharingTab is one of 5 tabs on the agent Configure shell (Instructions/Profile/Knowledge/Connectors/Sharing); it loads existing shares for the repo (listShares().filter(s => s.persona_repo_id === repoId && s.is_active)) and splits them into the one link-type share and any number of email-type shares.
  • Credit limit input defaults to Math.floor(planMax / 2) and is clamped to [1, planMax] — planMax comes from getShareTokenLimit(user.planType) (src/lib/plan-config.ts), so the ceiling is plan-gated, not a flat constant.
  • Shares are explicitly repo-scoped, not version-frozen — an inline comment states the backend always resolves to whichever version is currently published, so republishing an agent silently carries its existing Super Link forward rather than orphaning it.

Edge cases

  • Generating (or sending an email invite) is blocked with a toast if the agent has never been saved (!repoId) or if the open version isn't the currently published one (publishedVersionId !== versionId) — you cannot mint a Super Link for a draft.
  • Turning the Super Link toggle off while a live link exists calls handleRevokeLink immediately rather than just hiding the UI — an inline comment explains this deliberately, so the org doesn't keep being billed for a link the panel makes it look like you turned off.
  • note Visibility (private/team) sharing is present in the data model (Visibility = 'private' | 'team', setPersonaVisibility) but its UI section is deliberately hidden per an inline "hide, don't delete" comment — agents are private-only for now. Not a Super Link concern directly, but it lives in the same tab and is worth knowing isn't currently reachable.
  • /agents/published (the post-publish confirmation screen) duplicates a slimmer version of the same Super Link generate/revoke UI inline, reading and writing the exact same persona-shares API — a user can generate a link from either screen and it's the same underlying share.

Navigation

Publish → /agents/published?repoId=...&versionId=..., which offers "Back to Library," "Use this Agent" (opens /chat with the persona pre-attached via a sessionStorage handoff key), and — only while no Super Link exists yet — "Configure Sharing" back into SharingTab.

Save & Publish

Every Super Link/email-invite action (createShare, revokeShare) writes immediately — there is no draft state and no separate "Save version" step for sharing changes, confirmed by an inline comment on the page's own publish handler ("Sharing actions... are saved immediately to the API — no dirty data to flush").

Floating panels & Help

Not applicable — inline form sections, no floating panel.

Missing / Unused / Hidden

  • disabled The Saved/Unsaved + Live/Unpublished status badges under the tab strip are permanently disabled via {false && (anyDirty || publishedVersionId != null || (!!repoId && !!versionId)) && (...)}, with an inline comment reading "Hidden for now." This isn't unique to the Sharing tab — the identical hardcoded-false block is duplicated across all five Configure tabs (Instructions, Profile, Knowledge, Connectors, Sharing), so any Super Link generation happening while badge state would have shown "Unsaved"/"Unpublished" gives the user no such feedback today. — src/app/(app)/agent/configure/sharing/page.tsx:258 (same pattern at profile/page.tsx:500, knowledge/page.tsx:599, connectors/page.tsx:293, instructions/page.tsx:1414).
  • backend-ready-but-unused Visibility (private/team) sharing is fully wired end-to-end in state and API (Visibility type, setPersonaVisibility, load/save handlers) inside SharingTab.tsx but its rendered section is deliberately commented out per an inline "hide, don't delete" note ("hidden, not removed... so it can be re-shown later without rebuilding it") — already called out narratively in this section's Edge cases above; restated here as a structured entry since it fits backend-ready-but-unused exactly. — src/app/(app)/agent/configure/components/SharingTab.tsx:336-340 (state/handlers at lines 92-123, 187-192).

04Accepting a link/share/[id]

The recipient-facing preview/accept screen — and the one place this doc found a real, verified contradiction between what the product says and what it does.

Layout sketch
img
Agent name — "Shared by {name} ({email})"
Prompt preview — truncated to 200 chars
Model · Temperature · Credits available · Expires
Decline
Accept & copy agent

Input

  • getSharePreview(id) → GET /persona-shares/{id} returns a PersonaSharePreview: persona name/description/prompt/model/temperature/image, sharer name+email, expiry, and credit_remaining.
  • The visible prompt is client-truncated to 200 characters (truncatePrompt) — the full stored prompt is never shown pre-accept.

Edge cases

  • gap This is NOT actually reachable without a Souvenir account, despite both places that advertise Super Links saying exactly that ("chat without a Souvenir account," "no account needed to chat with your agent" — SuperLink/index.tsx's own default description, and SuperLinkSection on /agents/published). Verified in src/proxy.ts: the app-wide middleware redirects any request with no Auth0 session straight to /auth/login for every path except a short explicit allowlist (/auth/*, /api/*, the org-invite landing page, onboarding routes). /share/[id] is not on that allowlist, so a logged-out visitor clicking a Super Link is bounced to sign-in/sign-up before ever seeing this preview — and the accept action itself is explicit about the same thing ("Accepting adds a copy of this agent to your account"). The actual behavior is closer to "invite a new or existing Souvenir user to your agent" than "let anyone chat, no account."
  • 410 (expired/revoked) and 404 (not found) collapse to two nearly identical "link not found"/"link expired" cards — as designed, not a bug, but there's no distinction shown between "revoked by the sender" and "hit its own expiry timestamp," both surface as the same copy.
  • A 402 on accept ("no credits remaining") is a toast only, not a state change — the page stays on the preview screen rather than re-rendering to reflect that the link is now practically dead.
  • Accepting freezes a copy of the persona at that moment — it doesn't grant ongoing access to the sender's live, still-editable version, so later edits the sender makes never propagate to an accepted copy.

Navigation

Accept → acceptShare(id) creates a new persona VERSION owned by the recipient (AcceptShareResponse) → toast → redirect to /agents after 1.2s (not straight into the new agent's chat or editor). Decline → root route.

Save & Publish

One-shot: POST /persona-shares/{id}/accept. The resulting copy is explicitly read-only per an inline comment ("Received agents are read-only — go to the agents list, not the edit page").

Floating panels & Help

Not applicable — a single centered card, no panel.

Missing / Unused / Hidden

  • orphaned-route (hidden behavior mismatch) /share/[id] is effectively unreachable without an existing Auth0 session, despite Super Link's own marketing copy ("chat without a Souvenir account," "no account needed to chat with your agent" — SuperLink/index.tsx's default description and SuperLinkSection on /agents/published) promising the opposite. src/proxy.ts's app-wide middleware redirects any unauthenticated request to /auth/login for every path except a short allowlist (/auth/*, /api/*, org-invite landing, onboarding), and /share/[id] is not on it — so the route this page documents is, for a logged-out visitor, a dead end that bounces to sign-in before this UI ever renders. Restated here as a structured entry (already documented narratively above and in this section's own Proposed changes).

Proposed changes

  • proposed Fix the copy, not just the flow — grammarly-onboarding-survey.md (Personalization Clarity — a mismatch between what a product tells you and what it does erodes trust faster than being upfront about a limitation). The "no account needed" framing is a real, verifiable mismatch with proxy.ts's own gate gap documented above — either add /share/[id] (and its onward accept step) to the public allowlist so the copy becomes true, or rewrite the copy to say what actually happens ("Recipients sign in or create a free account to add this agent"). Backend: partial — making the copy accurate is a frontend-only text change; actually enabling true no-account access would require the preview/accept endpoints to support an unauthenticated or guest-session path, which is a backend/auth decision, not something the frontend can do alone.
