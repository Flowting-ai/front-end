## 3. Thread A — Team → Organization flattening

The back-end already did this (five migrations, ending in `flatten_teams_into_organizations` — `Team`/`TeamEditor`/`TeamViewer`/`TeamInvite`/`PersonaTeam` tables dropped, everything reparented onto `Organization`). The front-end has an existing, detailed plan for this at `docs/organizations/team-to-org-flattening-migration-plan.md` — this thread absorbs it.

**Governing rule for all of Thread A (set by the user 2026-08-20): only wire up what the back-end already exposes. Never invent replacement UX for a capability that has no back-end route.** Where a team-scoped feature has no org-scoped or project-scoped equivalent anywhere in the back-end, the correct action is deletion with no replacement — not a redesigned version of it. Flag the resulting capability gap; don't fill it.

**services/organizations/router.py was read in full this session — this is the authoritative, current route list** (openapi.yaml is still stale, don't use it):
`GET/POST /`, `GET/PATCH/DELETE /{id}`, `POST /{id}/transfer-owner`, `GET /{id}/settings` (+PATCH), `GET /{id}/plan` (+`/pool-cap` PATCH, Enterprise-only, +`/usage` → `by_member`, +`/enterprise-usage`), `GET /{id}/pool-status`, `GET /{id}/members` (+`/admins`, `/regular`, `/{member_id}/role` PATCH, `/{member_id}` DELETE) — **no member-cap endpoint exists**, `GET/POST /{id}/connectors` (+`/{slug}` PATCH/DELETE, `/catalog`, `/{slug}/used-by`, `/{slug}/accounts` GET/POST, `/accounts/{account_id}` PATCH/DELETE), `GET/POST/PATCH/DELETE /{id}/connections/{slug}` (+`/link`), `GET/POST/DELETE /{id}/projects/{project_id}/members(/{member_id})` — **flat, no team_id in path**, `POST/DELETE /{id}/invites(/{invite_id})` — **one flat org-level invite, `InviteRequest{emails, role, project_id}`, no team grant fields at all**, `GET /{id}/audit`. ## 6. Thread D — Project/Chat/Persona visibility staleness

Found while working Thread A, not part of the original scope: the same rename that hit Team hit **Project** too, and the frontend never caught up. Confirmed directly against `services/projects/schemas.py`/`service.py`: the real backend fields are `organization_id` and `visibility: "private"|"org"` — `Project.team_id` and the `"team"` visibility value don't exist on the backend at all.

- **✅ Fixed — committed `d15f61a`.** `lib/api/projects.ts` was still parsing a `team_id` field and a `"team"` visibility value the backend has never sent since the flattening migration — every project's shared/private status silently normalized to "private" regardless of its real backend value. Worse, the **share flow was completely inert**: the "Share" modal's Team option derived its list from org-context's `teams` (permanently empty per A3b), so it rendered greyed out with "No teams available" and clicking it did nothing — no project could be shared through the UI at all, in any org. Fixed with the same technique as A1 (correct the parsing, keep the output shape) so the ~10 other consumers of `ApiProject`/`ApiProjectSummary` (sidebar filtering, the projects list, Slack channel mapping, chat sharing) didn't need touching — their private/shared boolean is correct immediately. The share modal itself needed a real fix: removed the team-picker (there's only one organization to share with) and wired Save straight to the current org id, relabeled "Team" → "Shared" to match the spec's own vocabulary.
- **✅ Chat fixed — committed `319647c`, `7dcf944`.** `lib/api/chat.ts`'s `BackendChat`/`normalizeChat` had the identical bug as pre-fix Project: `visibility`/`team_id` were read straight off the raw backend fields with no `"org"→"team"` translation, so every `chat.visibility === 'team'` check (publish badges, read-only gating on `LeftSidebar`/`ChatHistoryItem`/`chats/page.tsx`) was silently always false. Fixed the same way as Project: translate at the API boundary, keep `Chat.visibility`/`team_id` output names unchanged. `setChatVisibility()` fixed to send `{visibility: 'org'|'private', organizationId}` matching `SetVisibilityRequest`. The share flow itself was also inert the same way Project's was: `ChatShareOverlay.tsx`'s "pick a project" dropdown grouped shareable projects by team via `orgTeams` (permanently empty), which — once the Project fix made `project.teamId` correctly non-null — started silently dropping every shared project out of the picker entirely (the exact "fix makes previously-dead code newly reachable" trap A3c's `ProjectTeamPanel` fix hit first). Flattened to a single project list, no team grouping. Also removed `project/[id]/page.tsx`'s `projectTeam`/`orgTeams.find(...)`-fed `TeamChip` — permanently `undefined` for the same reason, rendered nothing, no replacement needed (there's only one org to show).
- **✅ Persona fixed — committed `228886d`, `b00eb66`.** Different shape of bug than Chat/Project: `lib/api/personas.ts`'s `team_ids: string[]` was never a real backend field, even before the flatten (confirmed via `services/persona/schemas.py` — `PersonaRepoResponse` has only `visibility`/`organization_id`, no team list, ever). So `teamIds` was always `[]`, and `SharingTab.tsx`'s "share to which teams" checkbox-picker derived its list from `useOrg().teams` (permanently empty) — the "Team" visibility option was unconditionally disabled with "No editable teams" for every user, in every org: **agent sharing was completely inaccessible from the UI**, same severity class as the invite/project-sharing bugs found earlier in Thread A. Fixed by translating `visibility` the same way as Chat/Project, collapsing the fictional `teamIds: string[]` to "at most one org id" (`repo.organization_id ? [repo.organization_id] : []`) so existing `.includes()`/`.length` consumers (`personasForTeamContext`, `agents/page.tsx`'s team-count badge) needed no changes, and replacing `SharingTab`'s team-picker dropdown with a single Private/Shared toggle keyed off `orgId` (same pattern as Project's share modal). `setPersonaVisibility()` now takes a single org id, matching `SetVisibilityRequest`.
