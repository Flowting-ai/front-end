## 3. Thread A — Team → Organization flattening

The back-end already did this (five migrations, ending in `flatten_teams_into_organizations` — `Team`/`TeamEditor`/`TeamViewer`/`TeamInvite`/`PersonaTeam` tables dropped, everything reparented onto `Organization`). **Governing rule for all of Thread A (set by the user 2026-08-20): only wire up what the back-end already exposes. Never invent replacement UX for a capability that has no back-end route.** Where a team-scoped feature has no org-scoped or project-scoped equivalent anywhere in the back-end, the correct action is deletion with no replacement — not a redesigned version of it. Flag the resulting capability gap; don't fill it.

## 6. Thread D — Project/Chat/Persona visibility staleness

Found while working Thread A, not part of the original scope: the same rename that hit Team hit **Project** too, and the frontend never caught up. Confirmed directly against `services/projects/schemas.py`/`service.py`: the real backend fields are `organization_id` and `visibility: "private"|"org"` — `Project.team_id` and the `"team"` visibility value don't exist on the backend at all.

- **✅ Fixed — committed `d15f61a`.** `lib/api/projects.ts` was still parsing a `team_id` field and a `"team"` visibility value the backend has never sent since the flattening migration — every project's shared/private status silently normalized to "private" regardless of its real backend value. Worse, the **share flow was completely inert**: the "Share" modal's Team option derived its list from org-context's `teams` (permanently empty per A3b), so it rendered greyed out with "No teams available" and clicking it did nothing — no project could be shared through the UI at all, in any org. Fixed with the same technique as A1 (correct the parsing, keep the output shape) so the ~10 other consumers of `ApiProject`/`ApiProjectSummary` (sidebar filtering, the projects list, Slack channel mapping, chat sharing) didn't need touching — their private/shared boolean is correct immediately. The share modal itself needed a real fix: removed the team-picker (there's only one organization to share with) and wired Save straight to the current org id, relabeled "Team" → "Shared" to match the spec's own vocabulary.
- **✅ Chat fixed — committed `319647c`, `7dcf944`.** `lib/api/chat.ts`'s `BackendChat`/`normalizeChat` had the identical bug as pre-fix Project: `visibility`/`team_id` were read straight off the raw backend fields with no `"org"→"team"` translation, so every `chat.visibility === 'team'` check (publish badges, read-only gating on `LeftSidebar`/`ChatHistoryItem`/`chats/page.tsx`) was silently always false. The share flow itself was also inert the same way Project's was: `ChatShareOverlay.tsx`'s "pick a project" dropdown grouped shareable projects by team via `orgTeams` (permanently empty), which — once the Project fix made `project.teamId` correctly non-null — started silently dropping every shared project out of the picker entirely (the exact "fix makes previously-dead code newly reachable" trap A3c's `ProjectTeamPanel` fix hit first). Also removed `project/[id]/page.tsx`'s `projectTeam`/`orgTeams.find(...)`-fed `TeamChip` — permanently `undefined` for the same reason, rendered nothing, no replacement needed (there's only one org to show).
- **✅ Persona fixed — committed `228886d`, `b00eb66`.** Different shape of bug than Chat/Project: `lib/api/personas.ts`'s `team_ids: string[]` was never a real backend field, even before the flatten (confirmed via `services/persona/schemas.py` — `PersonaRepoResponse` has only `visibility`/`organization_id`, no team list, ever). [repo.organization_id] : []`) so existing `.includes()`/`.length` consumers (`personasForTeamContext`, `agents/page.tsx`'s team-count badge) needed no changes, and replacing `SharingTab`'s team-picker dropdown with a single Private/Shared toggle keyed off `orgId` (same pattern as Project's share modal). `setPersonaVisibility()` now takes a single org id, matching `SetVisibilityRequest`. Also fixed `chat-personas.ts`'s `fetchSelectableChatPersonas`: it derived `teamIds` from `persona.teamIds` (now correctly non-empty) and fed them to `fetchPersonaOwnerMap`/`listTeamPersonaShares` — a team-scoped route with nothing left behind it — which would have started 404ing on every shared persona once `teamIds` stopped being permanently empty.
