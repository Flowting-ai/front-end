# Connectors v1.5 — Migration Plan (Old Connectors → ConnectorLibraryV1)

**Status:** First pass built and typechecked (2026-08-27); a real backend-contract crash found in live testing the same day led to a significant correction — see "§0a — the Team vs Organization finding" below, it changes how §5's Gap #2/#3/#7 should be read. §6's open decisions are parked as gaps (not resolved) per user instruction — implementation proceeds against the default assumptions listed there. See "Build log" at the bottom for what's shipped, what's still unverified, and gaps #11–#14 discovered only once real API code was read during implementation.

**Scope:** Front-end only, per instruction. This is a **full UI replacement**, not a redesign of the existing pages: every pixel of the current connectors experience is retired and rebuilt to match `may-day-final/src/stories/teams/ConnectorLibraryV1.stories.tsx` (all 22 states) 1:1. Nothing from the old visual design is preserved. What **is** preserved, deliberately, is the old system's business logic and edge-case handling — OAuth mechanics, polling, optimistic-update/revert, pagination rules, StrictMode guards, error-message surfacing — re-expressed through the new components. Section 4 is the edge-case-by-edge-case carry-over list; do not treat "full UI replacement" as license to drop any of it.

**Source of truth for the new design:** `d:\WJP Souvenir\may-day-final\src\stories\teams\ConnectorLibraryV1.stories.tsx` (`Teams/Connectors/Connector Flow V1`, states `S1`–`S22` + `EndToEndFlow`).

**Source of truth for current behavior:** two existing pages that this replaces (see the naming-flip callout immediately below — the route paths are *not* what their surface names suggest).

## 0. Read this first — the two old pages, and why the route names are misleading

There are two entirely separate, almost code-sharing-free implementations today. Both are retired by this migration. Route paths and on-screen purpose are swapped from what you'd guess:

| Route | What it actually is | Audience | Key file |
|---|---|---|---|
| `/connectors` (`src/app/(app)/connectors/page.tsx`, 1924 lines) | **Org admin connector management** — "Org access" / "Shared accounts" tabs, connector-level org ON/OFF toggle, member request approve/deny, org-owned shared account CRUD | Admins get the full tabbed UI; everyone else gets a stripped-down `MemberBrowseView` (browse + "Request access") | org-scoped, gated on `useOrg().currentUserRole` |
| `/settings/connectors` (`src/app/(app)/settings/(shell)/connectors/page.tsx`, 1823 lines) | **Personal connectors page** — "My Connectors" / "Workspace Connectors" tabs, OAuth/API-key connect flow, per-connector tool-permission modal | Every signed-in user, role has no effect on behavior (only shows/hides a link to the admin page above) | user-scoped |

These two pages share almost no code (only `useConnectorBrowse`/`CategoryFilter`/`Pagination`, `connectorCategory`, `toConnector`, `isMcpProviderConnector`, `springs`). They use **different backend object models** for what looks like the same idea ("an account"): the personal page's own link is a `UserConnection`-shaped thing driven by `entry.linked`/`entry.workspace_linked` booleans, while the org page's shared accounts are a distinct `OrgConnectorAccount` object (camelCase, `expectedVersion` optimistic concurrency, admin-only CRUD).

**This split does not exist in the new design.** `ConnectorLibraryV1` is one page, one account list per connector, with a `visibility: 'shared' | 'private'` field on each account rather than two disjoint systems. That consolidation is the single biggest structural decision in this migration — see §2.

## 0a. The "Team vs Organization" finding — a real backend crash, found in live testing, that goes deeper than the original research

**What happened:** the first build (above) typechecked clean but crashed at runtime — `listConnectors()` threw a `ZodError` on `accounts[0].scope`, "expected one of \"personal\"|\"shared_org\"", for any account that actually existed on a real org. The whole catalog fetch failed, so the page silently rendered "No connectors found." with no visible error (the toast fired but was easy to miss). This is why `/connectors` showed nothing on first click-through.

**Root cause, confirmed by reading `back-end/services/connectors/schemas.py`, `service.py`, and `back-end/services/organizations/router.py`/`schemas.py` directly — not inferred, not guessed:** connector sharing is scoped to a **Team** sub-entity living inside an organization, not to the organization directly. This is live, actively-exercised backend logic (`service.py`'s `list_user_connectors` does real repository joins against team membership — `list_team_connections_for_user`, `can_edit_team` — not vestigial code), and it predates this migration entirely: **both old pages would have hit the identical crash against this same backend**, for any org that actually had a shared account. It just happened to surface now because building this migration was the first time anyone exercised that path against live data in this session.

Concretely, the real contract vs. what `front-end/src/lib/api/connectors.ts` and `org-connectors.ts` assumed:

| | What the code assumed | What the backend actually sends/expects |
|---|---|---|
| Scope literal | `"personal" \| "shared_org"` | `"personal" \| "shared_team"` (`AccountScope` in `schemas.py`) |
| Shared account's org field | `organization_id` / `organization_name` (singular) | `team_ids` / `team_names` (**plural** — one shared account can be attached to several teams at once) |
| "Attached to N other X" field | `attached_slugs: string[]` (connector slugs) | `team_ids: list[UUID]` (teams, not connector slugs — this field never meant what the old FE comment said it meant) |
| Org-level approve/deny gate | `POST/GET/PATCH/DELETE /organizations/{id}/connectors[/{slug}]` | **Does not exist on the backend at all.** The real gate is `/organizations/{id}/teams/{team_id}/connectors[/{slug}]` — every one of `requestOrgConnector`/`setOrgConnectorStatus`/`listOrgConnectorRequests`/`removeOrgConnector` was calling a 404. |

**Also found, not previously known to either front-end file:** `ConnectorCatalogEntry` carries two fields the FE schema never modeled — `org_enabled: bool | null` and `personal_access_status: 'pending'|'approved'|'denied'|null` — and the backend exposes a *third*, entirely separate personal-request family (`/organizations/{id}/connectors/{slug}/personal-request`, `.../personal-requests`) that gates whether a member can even create their own *private* link to a connector, orthogonal to team-shared sharing. Neither is wired up by this migration (out of scope for the immediate fix) — flagged for awareness.

**This also broke a second, unrelated feature the same way:** `src/app/(app)/agent/configure/components/ConnectorsTab.tsx` (the agent-configure "Connectors" tab, not part of this migration) filtered on `scope === 'shared_org'` too — meaning workspace/shared connector accounts have likely never shown up there either, for the same root cause. Fixed as a mechanical side-effect of correcting the shared schema (see Build log), since leaving it broken would have failed the app-wide typecheck.

**Fix applied (front-end only, per scope):**
- `lib/api/connectors.ts` — corrected `scope` enum, renamed `attached_slugs`→`team_ids` on the embedded org-account schema, renamed `organization_id`/`organization_name`→`team_ids`/`team_names` on `ConnectorAccountOption`, added the two new `ConnectorCatalogEntry` fields (unused for now, just modeled).
- `lib/api/org-connectors.ts` — rewritten: `OrgConnectorAccount` uses `teamIds` not `attachedSlugs`; the whole request/approve/deny family now targets the real `/organizations/{id}/teams/{teamId}/connectors[/{slug}]` routes and requires a `teamId`; added `listOrgTeams`.
- New `lib/useDefaultTeam.ts` — since the new design's Setup screen has **no team picker at all** (just a flat Shared/Private choice), and inventing one is a real product decision I won't make unilaterally (same standing principle as every other gap in this doc), "Shared" auto-targets the org's team when there is exactly one (the common case — functionally equivalent to "org-wide" sharing for a single-team org). When there are zero or multiple teams, "Shared" is disabled in `SetupModal` with an honest, specific explanation instead of guessing which team to use.
- Three other call sites broke from the same rename and were fixed as mechanical follow-through: `ConnectorsTab.tsx` (agent-configure), `src/app/(onboarding)/onboarding/connectors/page.tsx` (dead code — not reachable from the current onboarding flow per `docs v1.5/onboarding-v1.5-flow.md` — fixed to keep the app typechecking, not given design attention), and `connectors.test.ts` (whose own fixture had encoded the wrong `shared_org` value — see the Build log for why that's notable).

**What's still genuinely uncertain, flagged rather than papered over:** the exact mechanics linking a freshly-approved `TeamConnector` request to the `OrganizationConnectorAccount` created immediately after (in `useConnectorSetupFlow.connectShared`) are inferred from the response schemas and route list, not verified against every line of `service.py`'s implementation. If a newly-shared account doesn't show up under the expected team after a real click-through, that's the first place to check — not a sign the whole approach is wrong.

**Read §5's gap table with this in mind:** Gap #2 ("no visibility field") is now more precisely "visibility exists but is Team-scoped, and the source design has no UI for picking a team" — still the single biggest blocker, just for a more specific reason. Gap #3's "surface: organization" should read "surface: team" (`ConnectorUsedByEntry.surface`'s real backend comment says `# "team"`). Gap #7's default assumption now correctly targets the real per-team endpoint rather than a 404.

**CORRECTION 2026-08-27, later same day — §0a's framing above got the *direction* of the fix backwards.** The user pointed at the actual target-architecture spec (Superhuman Docs "New Architecture" overview, Workspace Model v2 / Project & Chat Model / Billing & Credits) — read directly, not assumed. Its "Key invariants" table states outright: **"Connections are workspace-wide — never scoped by project or member."** The target architecture has no Team entity at all — Projects replace Teams as the sole organizing unit under a single flat Workspace, and Owner/Admin/Member roles only gate admin/billing, not product access or connector visibility.

This means the new Figma design's flat Shared/Private toggle (no team picker) was **correct all along** — it's not an oversight the design needs to grow a team-selector for. The mismatch is the opposite of what §0a concluded: the **current backend** (`TeamConnector`, `team_ids`, `scope: "shared_team"`) is itself legacy code that predates this target architecture and hasn't been migrated to match it yet — not something the frontend should be building permanent scaffolding around.

**What this changes:**
- The real fix is a **backend migration**: make connector `scope` genuinely workspace-wide (e.g. `"personal" | "shared"`, no team indirection) so the API matches both the target spec and what the frontend design already assumed. This is *not* "rebuild a Teams settings page" (§0's framing in `settings-v1.5-pages-audit.md` needs the same correction — creating more Team-management UI moves the product away from where it's headed, not toward it).
- `lib/useDefaultTeam.ts` and the `teamId` threading through `useConnectorSetupFlow.connectShared`/`SetupModal` (built earlier today) are a **working stopgap against the current, soon-to-be-superseded backend shape** — left in place since they function against what actually exists right now, but they should be **deleted, not extended,** once connections go workspace-wide. Don't build further Team-aware UI on top of them.
- Gap #2 in §5 should be read as: the backend needs to finish a migration it's already implicitly headed toward (per the org's own target-architecture doc), not that the frontend design is missing a control it should have.
- The equivalent "just create a team to unblock everything" recommendation in `docs v1.5/frontend-backend-requirements.md`'s closing summary and `docs v1.5/settings-v1.5-pages-audit.md`'s §0 is corrected in those files directly — see their own 2026-08-27 correction notes.

## 1. The consolidation decision (read before implementing anything)

The new design's `ConnectorDetail` screen (S19) groups every account under one connector into three panels — **Attention** (needs reconnect) → **Shared** → **Private** — using one `Account` shape:

```ts
interface Account {
  id, connectorId, connectorName, nickname, email
  visibility: 'shared' | 'private'
  status: 'connected' | 'reconnect_required'
  dependencies: string
  permission?: PermissionMode   // 'always' | 'ask' | 'blocked'
  ownerId?: string              // only present on private accounts
}
```

This single shape has to absorb both of the old system's account types:

| Old concept | Old object | Maps to new `Account` as |
|---|---|---|
| Personal connector link (`entry.linked`) | Implicit — a boolean flag + `entry.tools` on the catalog entry, not a standalone account row | `visibility: 'private'`, `ownerId: currentUser.id` |
| Org shared account (`OrgConnectorAccount`) | Standalone object, `scope` hardcoded `'shared_org'`, admin-managed | `visibility: 'shared'` |
| Workspace-visible shared account, as seen by a non-admin member (`ConnectorAccountOption`, `scope='shared_org'`) | Read-only projection already returned to any member via `listConnectors()`'s `account_options` field | `visibility: 'shared'`, read-only unless `can_manage` |

**What has no home in the new design at all:** the old org-admin page's connector-level "Org ON/OFF" toggle and its member-request approve/deny queue (`OrgAccessTab`, `PermissionRequestStatus: 'pending'|'approved'|'denied'`). None of the 22 states show a pending-approval account state, an approve/deny action, or a page-level admin/member branch. This is flagged as **Open Decision 1** below — do not silently drop it or silently invent a screen for it; it needs a product call.

### 3c. Icon strategy — a real decision point, not just a port

The new design imports `ConnectorIcon` from `@strange-huge/icons/connectors` (`<ConnectorIcon id="notion" size={40} />`) — the package subpath is already installed in `front-end/node_modules` but **is not imported anywhere in front-end today**. Front-end instead resolves connector logos through `toConnector(entry).logo`, a backend-hosted-image-first pipeline (`logo_url`/`icon_url` from Pipedream → bundled `CONNECTOR_LOGO_MAP` SVG/PNG fallback → letter-tile fallback in the consuming card).

These are fundamentally different strategies: `ConnectorIcon` is a hardcoded per-id icon baked into the icon package (returns `null` — no fallback — for an id it doesn't recognize), while `toConnector().logo` is data-driven off whatever the backend returns and covers the full ~150-connector live catalog today.

**Recommendation:** hybrid — try `ConnectorIcon` first (matches the new design exactly for the common/curated connectors it covers), fall back to the existing `toConnector(entry).logo` chain for anything `ConnectorIcon` returns `null` for. This mirrors the story file's own pattern (it special-cases `shopify` with a manual letter badge because `ConnectorIcon` doesn't cover it). Confirm with design/`@strange-huge/icons` maintainers how many of the live catalog's ~150 slugs `ConnectorIcon` actually covers before committing to "icon-package-only."

## 4. Edge cases to carry over verbatim (do not silently drop these while re-skinning)

These are the load-bearing behaviors buried in code comments across both old pages. None of them are visible in the story file (which is a static-data Storybook mock), so they are the easiest things to lose in a "1:1 UI" rebuild. Preserve every one:

**OAuth / connect flow** (`useConnectFlow` → power the new `Setup` component):
- Native MCP connectors (`isMcpProviderConnector`) navigate the **current tab** (`window.location.href`), never a popup — their OAuth callback redirects back to the app's own domain, so a popup would trap the app inside itself.
- Non-MCP popups are opened **without** `noopener` deliberately — `noopener` breaks the later `popup.location.href =` assignment in some browsers.
- A closed popup is **not** immediately treated as cancellation. The long poll aborts and a short 12s "grace window" poll runs first (Pipedream's hosted success screen often stays open after the account is actually linked) — only report "cancelled" if that grace poll still comes back empty.
- 5xx errors prefer the raw backend detail (`ApiError.rawMessage`, e.g. "Multiple connected accounts found...") over a generic message; other errors use the friendly generic text.
- Exponential backoff polling (2s → 4s → 8s → … capped at 30s) with `AbortController`-based cancellation on unmount/reconnect; `AbortError` is swallowed silently, never toasted.
- React StrictMode double-mount guard: reset `abortedRef.current = false` on every effect setup, not just once — otherwise dev-mode's mount→cleanup→mount leaves every async handler silently bailing.
- Per-tenant OAuth (Shopify-style BYOA, `oauthNeedsInitFields`): the credential form's fields get POSTed as `init_data` on the link call, **not** PATCHed as credentials — this is a different code path from plain `api_key` connectors even though both show the same form UI.

**Tool permissions** (→ power the new `AccountDetail` Permissions tab):
- Optimistic local update on every permission change, reverted to the last server-confirmed `baselineTools` on failure — never leave the UI showing a permission that didn't actually save.
- Long-tail connectors return an empty `tools` array on the list endpoint (payload-size optimization) — lazily backfill via `getConnector(slug)` the first time the detail view opens, and fail silently if that backfill errors (the account is still manageable, just without a tool list).
- "Allow all" is a single PATCH with every tool's slug, not N sequential PATCHes.

**Catalog & pagination** (→ power the new `Connections`/`Catalog` view):
- "Connected"/"Enabled" accounts always render in full, never paginated; only the "Available"/disconnected set paginates, on its own page counter — mixing the two into one paginated list was an explicit prior bug class ("pagination chops the mixed enabled/disabled list arbitrarily").
- Search/list-context changes reset both category and page; a category-only change resets only the page.
- Workspace/shared account lists are intentionally left unpaginated ("shared accounts are few").

**Org-shared account management** (→ power the new `AccountDetail` Settings/Access tabs where an account is shared):
- Optimistic concurrency: every PATCH to a shared account sends `expectedVersion` (from the last-fetched `version`) and updates local `version` from the response — do not drop this even though the new UI has no visible version indicator.
- Disable/remove confirmation must account for one shared account being attached to multiple connectors (`attached_slugs`) — the old cross-connector count logic (`new Set(accounts.flatMap(a => a.attached_slugs)).size`) is the only place this "shared account, multiple connectors" relationship is computed; reuse it wherever the new Remove modal needs to describe blast radius.

**Icons/rendering:**
- Grid layouts must use `minmax(0, 1fr)` columns, never a bare `1fr` — a bare `1fr` computes as `minmax(auto, 1fr)` and lets one long unbroken name push the whole row wider than the container.
- Card action buttons are absolutely positioned bottom-right so cards of uneven content height still align across a row (already true of the new `ConnectorCatalogCard`'s own layout — verify it, don't reintroduce the old bug if a custom wrapper is built around it).
