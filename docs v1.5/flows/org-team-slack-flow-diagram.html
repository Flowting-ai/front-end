00Entities, roles, and the /org → /settings redirect map

One org/workspace context (src/context/org-context.tsx) backs every page in this doc. It exposes orgId, org, members/membersLoading, orgRole (raw backend value) and currentUserRole (a same-value convenience field, 'admin' | 'member'), a caps capability object, and two readiness flags (orgReady, orgRoleResolved) that pages gate their initial redirect/skeleton on.

Role (org-level)What it actually grants
AdminFull organization control — billing, payment methods, invoices, subscriptions, topups, invites, member management, connectors. Any number of admins per org, all equal.
MemberBaseline access through assigned projects only. Cannot change org settings or manage other members.

note The backend also has an owner value and the UI still ships editor tokens/glyphs (RoleBadge's WorkspaceRole type is 'admin' | 'editor' | 'member') — but per an explicit comment in the Members page, "Team has no backend route left at all", so a member's displayed role is always folded down to just Admin or Member (owner → Admin, everything else → Member) with no separate Editor tier reachable in practice. See §06 for where the editor/team-role UI still lives unused.

Nearly everything historically at /org/* is now a redirect shim. Concretely:

Missing / Unused / Hidden

  • Orphaned routes: /org, /org/general, /org/members, /org/activity, /org/analytics — all render nothing but a client-side redirect stub (src/app/(app)/org/*), targeting /settings/general, /settings/general, /settings/members, /settings/activity, and /settings/analytics respectively.
  • Backend-ready-but-unused: the backend's owner role value and the UI's editor role tier (RoleBadge's WorkspaceRole type, src/types/teams.ts) are both received/typed but never surfaced distinctly — per an explicit code comment on the Members page, "Team has no backend route left at all," so every role folds down to just Admin or Member.
  • Duplicate dead guard logic: src/app/(app)/org/layout.tsx and src/app/(app)/settings/(shell)/(org)/layout.tsx implement the identical admin-only redirect check — one of the two is pure redundant surface area now that the routes it guards are stub-only.

Proposed changes

  • proposed Once nothing else could plausibly still deep-link to the old /org/general//org/members//org/activity//org/analytics paths (bookmarks, emailed links, external docs), collapse the redirect stubs into real server-side redirects (or delete them) rather than a client component mount + useEffect + blank render on every visit — today's version costs a full extra render cycle and a flash of nothing for every stale link.

Input

  • Members table columns: Member (avatar + name/email, "Invite sent" badge when inviteStatus === 'invite_sent'), Role (inline dropdown), Actions (Remove/Withdraw with a blur-swap confirm-in-place, no modal).
  • Stats row: total members, admin count, pending-invite count — all derived client-side from the same members array, not separate endpoints.
  • Search filters across name, email, role, org-role, and team-membership names (client-side, over the already-loaded list).
  • The Role dropdown's two options (Admin/Member) and their one-line descriptions come from a single ROLES_INFO array also consumed by the "Roles & Permissions" info modal — the dropdown copy and the modal copy structurally cannot drift apart.

Edge cases

  • The sole remaining admin cannot open the Role dropdown on their own row at all — blocked client-side with an explanatory toast ("You're the only admin — promote someone else before changing your own role") rather than letting them pick Member, confirm a downgrade modal, and then get rejected by the backend. Every other admin→member change (on someone else's row, or when ≥2 admins exist) goes through a confirm modal first.
  • A pending-invite row (inviteStatus === 'invite_sent') cannot have its role managed or be removed via the normal path — its Actions column instead shows "Withdraw", which calls the invite-specific revoke endpoint (falling back to the plain remove-member call only if invite metadata is missing on an optimistic row).
  • Every mutation (role change, remove, invite, revoke) is optimistic with rollback on failure, and is versioned through a ref-backed bump counter so a slow, superseded background resync of the members list can never clobber a newer local edit.
  • note A one-off effect silently patches the signed-in user's own display name to the backend if it's currently empty or the literal string "Someone" — a self-healing step, not something the page ever surfaces to the user.
  • Invite validation (already-a-member, domain-restriction) runs client-side first, so a batch of pasted emails can partially fail before any network call — InviteModal flags each bad email inline as a red chip with its reason on hover/title, and only sends the emails that pass both checks.

Not applicable — a single page, no sub-navigation. The Usage page's "Manage members" action (§04) links here.

02Invite flow — org-invite vs team-invite/org-invite/[id], /team-invite/[id], /onboarding/team/[id]

These are not the same flow wearing two names. They're two different links, doing two different jobs, that happen to both exist because of how the backend emails invites vs. how an already-signed-in click resolves.

RouteWho reaches itWhat it does
/org-invite/[inviteId]a logged-out visitor clicking the emailed invite linkstatic "You're on the list!" landing — no API call at all. Just two buttons (Sign up / Sign in), both carrying returnTo into Auth0 so the visitor lands back on the real invite screen once authenticated.
/team-invite/[inviteId]the post-login return leg (or a direct hit once already authenticated)pure redirect stub — immediately replace()s to /onboarding/team/[inviteId], the actual acceptance flow. Renders nothing itself.
/onboarding/team/[inviteId]authenticated visitor, real invite idScreen 1 — "Join a workspace": workspace card (name, member count, avatar stack) + Join button.
/onboarding/team/[inviteId]/profilebrand-new users only, right after JoinScreen 2 — "Create your profile": first/last name, role, tone — then on to the shared Slack-modal landing.

fixed /org-invite/[id] used to also fetch GET /org-invite/{id} to render a personalized card and pick Sign-in vs Sign-up — but that endpoint requires an authenticated caller, so it always failed for the logged-out visitor this exact page exists to serve, replacing the whole card (including both auth buttons) with a "couldn't be found" error. The fix documented inline in the file dropped the data dependency entirely: this screen's only job is routing into Auth0, and the personalized card now renders one step later on /onboarding/team/[inviteId], where the same endpoint succeeds naturally because the visitor is authenticated by then.

Layout sketch — the 3 real screens in sequence
1 · /org-invite/[id] (logged out)
"You're on the list!" — Sign up / Sign in
2 · /onboarding/team/[id]
Workspace card — name, N members, avatar stack, Join
3 · .../profile (new users only)
First/last name, Role, Style → Slack-modal landing
/team-invite/[id] is not shown — it renders nothing, it only forwards from step 1's returnTo into step 2

Input

  • Screen 1's Join button does two things atomically in sequence: acceptTeamInvite(inviteId) then updateOnboarding({ onboarding_completed: true }) — same contract the old flow's "Accept invite" button had.
  • Routing after Join branches on whether the user was already onboarded (captured before the mutations run, so a stale post-mutation read can't flip the branch): already-onboarded users skip straight to ${WELCOME_ROUTE}?slack=1; brand-new users go to the profile screen first.
  • The profile screen also runs in a second, undocumented "standalone" mode: if [inviteId] in the URL is actually a teamId (an already-onboarded user redirected here post-accept) the invite context 404s, and saving sends the user straight to /chat instead of the Slack landing.

Edge cases

  • The profile screen deliberately has no Back button — the invite is deactivated the instant Join succeeds, so a Back-then-re-Join would 404 "Invite not found" rather than re-accept. There's nothing left to reconsider once membership is already committed.
  • If the signed-in user already has first name, last name, and an onboarding role set, the profile screen auto-redirects to /chat without ever rendering the form — covers a user who completes onboarding via some other path before reaching this screen.
  • A 410 from acceptTeamInvite surfaces as "This invite has expired" via toast; other failures show the raw API message.
  • Non-"ready" invite-context states (loading / expired / not_found / error) render through a single shared InviteStateScreen on both screens — same gradient-card look, so a hard refresh at any point in the flow degrades identically.
  • Tone is collected inline here as a third dropdown (defaulted to "Balanced") rather than the self-signup flow's dedicated full-screen tone step — an invited member otherwise never gets asked their tone preference at all until they happen to visit Settings → Account later.

Navigation

Join (already onboarded) → ${WELCOME_ROUTE}?slack=1. Join (new user) → /onboarding/team/[inviteId]/profile → (standalone mode) /chat, or (invite mode) ${WELCOME_ROUTE}?slack=1.

Save & Publish

Profile screen saves via two parallel calls — updateUser({ first_name, last_name }) and updateOnboarding({ user_role, ai_tone }) — followed by a forced refreshUser() so the "already complete, skip me" check above never reads stale pre-save data if this screen is somehow revisited.

Floating panels & Help

Not applicable — full-screen step flow, no side panels.

Missing / Unused / Hidden

  • Orphaned/dual-purpose route: /team-invite/[inviteId] renders nothing itself — it is a pure redirect stub that immediately replace()s to /onboarding/team/[inviteId], the route that does the real work.
  • Hidden mode, not a separate route: /onboarding/team/[inviteId]/profile secretly runs in an undocumented "standalone" mode when [inviteId] is actually a teamId rather than an invite id (an already-onboarded user redirected here post-accept) — the invite context 404s silently and saving routes to /chat instead of the Slack landing, with no UI distinction shown to the user that they're in a different code path.

Proposed changes

  • proposed The 3-hop redirect chain (/org-invite → Auth0 → /team-invite → /onboarding/team) works but is easy to break silently if any one ROUTE constant drifts — worth a lightweight integration test that walks the chain end-to-end rather than relying on each file's own comments to keep them in sync.

Input

  • listAudit(orgId, { limit: 100 }) — one flat fetch, filtered/searched entirely client-side afterward (action-type dropdown built from the distinct actions actually present, plus a free-text search across actor/target/action).
  • Action badges are colored by regex-matching the raw action string's family: red for removed/deleted/unlinked/denied/revoked, green for created/added/accepted/published/linked/granted/approved, yellow for requested/sent/pending, blue for role/cap/ownership/status/settings changes, neutral otherwise.

Edge cases

  • gap The audit API has no role-aware filtering server-side — it always returns the full org's log. Non-admin scoping (members only see rows where they're the actor) is done entirely client-side by filtering on actorEmail === user.email after the full fetch. A non-admin's browser therefore always receives the whole organization's audit trail even though the UI only shows them their own slice.
  • Backend timestamps are UTC and often lack a trailing Z — a shared parseServerDate normalizes this so relative times ("3h ago") don't come out negative from a local-time misparse.

Input

  • "Monthly Limits" and "Active members" stat cards read straight from plan/members in org context — real numbers, no derivation.
  • note The "Credit usage by feature" chart (Chat/Slack/Brain split) is not a real per-day, per-feature time series — the backend only exposes one org-wide credit total per cycle. The chart apportions that real total across the selected date range and a fixed feature-mix ratio (68% Chat / 20% Slack-labeled "assistants" / 12% Brain) using deterministic (non-random) per-bucket weights, so it's stable across re-renders but not a measured breakdown. The caption under the chart states this plainly rather than letting the bars imply more precision than they have.
  • "Utilisation" (share of active members who've spent ≥1 credit this cycle) is likewise a substitute for a Figma-specified "20% utilisation" figure that has no direct backend equivalent — computed from real per-member creditUsed, just not the exact metric the design called for.
  • Top users list is sorted by real per-member creditUsed descending, capped at 4, with "Manage members" (→ Members page) appearing only when the list is actually truncated.

Edge cases

  • fixed An Enterprise/custom-contracted org's monthly price never lands on one of the fixed Teams $50–$2000 tiers, so a naive lookup silently showed $0. The page now derives the Enterprise price from the projected invoice minus overage instead.
  • Per-member creditUsed includes "utility" work (auto-titling, summarization, memory extraction) that's metered for visibility but never actually charged — so member totals will usually sum to slightly more than the org-level "Monthly Limits" total, not less. The page spells this out in a footnote under the Top Users list rather than leaving the mismatch looking like a tracking bug.

  • Workspace install (SlackConnectModal): a permissions-disclosure card ("Souvenir will be able to: establish a connection… send scheduled summaries… read channel names and members…") → "Accept and Connect" opens Slack's OAuth install in a new tab, then polls getOrgSlackStatus/getSlackStatus every 3s (3-minute timeout) until the bot reports installed, closing itself and toasting success the moment it does.
  • Per-project channels (/souvenir-slack, admin-only): lists every Workspace/Shared project the user can see (explicitly excluding Personal-visibility projects, even though they carry the same teamId stamp — a plain teamId check would otherwise leak other members' private projects into this admin list), each row either showing its existing mapped channel or an inline create form (name + Public/Private toggle).
  • Person-level identity link (/slack/link): reached via a Slack /connect slash command, not from the app UI. Binds the Slack member's identity to their Souvenir account, then hands them to a second Slack consent screen for a user-level token — without that second token Souvenir can only ever read Slack as the bot, never search or post as the person.
  • Sidebar surface (FlatSidebarSlackConnector): a single row, "Souvenir in Slack" — shows "Add" when not connected (fires onAdd) or an external-link glyph when connected (fires onClick, presumably to /souvenir-slack); has a collapsed icon-only variant with a tooltip for the rail-collapsed sidebar state.

Edge cases

  • Deleting a project's Slack channel is confirmed via a plain window.confirm (not the app's own modal system) warning that the channel will be archived in Slack and unlinked from the project — same for removing the whole org's Slack installation ("all project channels stop working").
  • Removing the org's Slack installation re-fetches status afterward and throws a client-side error ("Slack is still connected. Please try disconnecting again.") if the backend didn't actually clear it — doesn't just trust the DELETE call's 2xx.
  • /slack/link's page state is decided synchronously at first render from URL params (a fresh ?state= deep link → "linking"; a Slack consent-screen return leg via ?authorized=1 → "linked"; neither → "missing") specifically so the linking POST effect never has to call setState synchronously during mount — and that POST is guarded against React 18 StrictMode's dev-mode double-invoke via a ref.
  • note A 400 from the link POST is shown as a specific, actionable message ("This link is invalid or has expired. Run /connect in Slack to get a fresh one.") rather than a generic error — the deep link is single-use and short-lived by design.
  • gap SlackChannelMappingRow is a fully built, styled component (channel name + a project-picker dropdown + a remove button) with no live usage anywhere in the app — both real channel-mapping surfaces (the General page's inline card, §05, and the dedicated /souvenir-slack page) implement their own bespoke row markup instead of using it. Likely superseded during the V1.5 restructure and left behind.
