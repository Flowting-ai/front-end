00Entities & the phase machine

"Tasks" isn't a separate mode inside /brain — it's simply what the rest of the app calls a Brain thread (sidebar says "New task", the library's Tasks tab lists them). /brain is the one canvas for running a thread; everything else — /brain/threads, /brain/chats — are legacy redirect stubs into /chats?filter=tasks.

Everything on screen is driven by one 12-value Phase state machine (src/templates/Brain/lib/phase.ts), mirrored into a ref so streaming callbacks always read the latest value:

  • disabled confirming-pins has a transition-table entry but no rendering branch — src/templates/Brain/lib/phase.ts declares the phase and src/app/(app)/brain/page.tsx sets it (~line 1949), but no JSX in the transcript switches on this value; restating §00's own gap note here as a structured entry — it's effectively a phase that can be entered but never visibly rendered.
  • verified clean No dead components in this family — grepped for zero-usage exports: LoopCancelledCard and LoopFailedCard are both re-exported from src/templates/Brain/index.tsx (lines ~43–46) and rendered in src/app/(app)/brain/page.tsx (lines ~3536, 3816, 3830); BreathingDot (src/components/BreathingDot/index.tsx) is used elsewhere in the app but confirmed absent from Brain (see §02); StepStatusIcon is a local, actively-used helper inside LoopHistoryCard.tsx (lines ~21, 62, 164). None are orphaned exports.

Backend: ready — the frontend already knows phase==='stuck' regardless of whether a prompt payload came with it; the fallback needs no new data, just a rendering change for the case where a prompt object is absent.

Input

  • Query: id → the thread to load; new=1 → force a fresh thread; fromSchedule → links a schedule-originated prompt (see §06).
  • With no id, thread history is considered "loaded" immediately (empty-state, no fetch needed).
  • Persona chip picker fetches once per open (guarded by a ref), rendered as a dropdown sized min(520px, 100vw − 32px), filtered to owned agents only (same underlying filter as the rest of the app — see the Agents doc's known gap about workspace-visibility exclusion).

Edge cases

  • note Brain computes its own context-usage percentage (totalChars / (modelInputLimit × 4)) independently from how /chat computes the same-looking ring — worth verifying the two are meant to diverge before treating them as consistent.
  • The "New" sidebar button's active/selected state uses an exact path+query match (pathname === '/brain' && no id param), not a prefix check — deliberate, per an inline comment, so it doesn't light up while viewing an existing thread.

02Task execution — animations & statesduring phase: 'executing'

The part of this doc that's really about motion and feedback, not routes.

Input — the live state shapes

  • liveToolCalls: Record<id, {status: 'streaming'|'executing'|'complete'|'failed', tool_call}> — entries created/updated by SSE events (tool_calls_streaming, tool_executing, tool_complete), rendered via an activity feed: spinner while streaming/executing, checkmark on complete.
  • toolProgress — a separate single live-progress object (e.g. a document being generated), which can also flip a matching tool-call entry to failed on an error status.
  • Reasoning reuses the same ReasoningBlock component as regular Chat, wrapped as BrainReasoningStack — auto-opens while thinking, otherwise user-toggleable, with a word-cycling collapsed trigger.

Edge cases — the Stop fix, and what it didn't fully close

  • fixed handleStop now filters out only liveToolCalls entries still streaming/executing (keeping already-settled ones visible) and nulls toolProgress — previously these kept spinning forever after Stop.
  • gap StepStatusIcon (the per-step icon inside a LoopHistoryCard) treats 'executing' exactly like 'pending'/'upcoming' — a plain static open ring, no spinner — even though the Scheduled Tasks detail view does pass a live status: 'executing' for an in-progress run. That history card silently shows "not started" for a run that's actually live.
  • gap Only 3 of the 6 StepStatus values (failed/complete/executing) get a distinct header color on LoopHistoryCard; pending/upcoming/skipped fall back to plain gray if ever passed as the card-level status — currently nothing does, so this is latent, not yet visibly broken.
  • Historical/archived turns never pass isStreaming to their reasoning block (defaults false) — correct, since a past turn shouldn't re-animate, but worth knowing if you're auditing "why doesn't this replay."

Navigation / transitions

Phase transitions are driven by SSE events (content → streaming, error → failed) and two user actions: Stop → cancelled, and the Pause card's own Cancel → cancelled.

Proposed changes

  • proposed Give executing steps a spinner, not the same static ring as pending — labor-perception-bias.md, this whole corpus's single most directly-applicable finding (up to a 15% lift in perceived value from visible labor, and its core thesis is literally "does this look like it's actually doing something?"). 05In-task Questionsinline, during execution

A real, dedicated clarifying-question mechanism — distinct from connector permission/connect prompts, which stay connector-specific.

Layout sketch — inline clarification card
Clarifying question

Input

  • Two SSE event families trigger it: a generic user_prompt (kinds: choice/input/confirm/permission) and a dedicated questions/question_prompt event emitted specifically by the Brain ask_user tool, carrying a list of question objects (id, question text, type, options, entity).
  • Rendered by ClarificationCard (wrapping the same QuestionCard used elsewhere in the app, e.g. Agent Configure's help system) — inline in the transcript's input slot, never a modal.
  • Response types: single-choice (radio), multi-choice (checkboxes), free text, or yes/no (synthesized automatically when the payload provides no options).

Edge cases

  • Multiple questions step through one at a time with an "N/M" pagination chip, accumulating answers keyed by question id before a single combined response is sent.
  • The stream genuinely blocks while waiting — per an inline comment, without this handling the stream would stall on heartbeats until a 300-second server-side prompt-gate timeout. Send/Skip are disabled (clarificationInFlight) until the answer POSTs.
  • A second, related but distinct fallback exists: StuckCard ("Brain cannot proceed without human input") for open-ended blockers that aren't a structured question — free-text "provide context" or Cancel. See §00's gap note: this only renders when a prompt object is actually present; otherwise the stuck phase shows nothing.

Navigation

After the last question in a batch, one combined response POSTs and the phase returns to thinking — execution resumes automatically, no page navigation involved.

Save & Publish

One respondToPrompt(promptId, {response: {answers}}) call per question batch — not saved incrementally per question.

Floating panels & Help

Not applicable — inline in the main transcript, not a panel.

Missing / Unused / Hidden

Nothing found in this section — no dead code, disabled branches, orphaned routes, or unused backend fields specific to the clarifying-question/ask_user mechanism itself were found. The one adjacent gap (stuck-with-no-prompt rendering nothing) belongs to §00, where it's catalogued as a structured entry.

Proposed changes

  • proposed Name the actual pending question in any re-engagement notification — linkedin-retention-triggers.md (Singularity Effect / Benefit-Focused Messaging — LinkedIn's own case study cites contextual, personalized prompts converting roughly 5× better than generic ones). No re-engagement trigger exists today if the user navigates away while blocked; if one is added, it should reference the real question ("Souvenir needs to know: which timezone should this run in?") rather than a generic "your task needs attention." Backend: needs backend work — there's no notification/push infrastructure of any kind for this path (no websocket, push-subscription, or device-token system anywhere). The only delivery channels that exist at all (email, and a Slack DM) are hardwired to scheduled-automation run failures specifically, not to a chat/task waiting on ask_user — and the timeout path itself currently just logs and does nothing else. This is a build-from-near-scratch item, not a wiring job.
  • proposed A real, honest countdown as the 300-second prompt-gate window closes — uber-eats-scarcity.md (Positive Scarcity — urgency framing is ethical only when tied to a genuinely real constraint, unlike Uber Eats' own critiqued cases). The stream already blocks toward a real server-side timeout with nothing communicating this to the user; surfacing it as it approaches is the textbook honest use of urgency this case study distinguishes from manufactured pressure. Backend: ready — the 300s window is a fixed constant, and the SSE prompt event arrives right as the wait begins, so the frontend's own receive-timestamp is a reliable countdown start. Minor gap: the constant isn't echoed inside the SSE payload itself, so if it's ever made configurable server-side the frontend would silently drift out of sync — worth adding a timeout_seconds/expires_at field to that event as a small follow-up, but not a blocker today.
  • See §00's proposal for the related stuck-with-no-prompt blank-render gap — the same underlying "the user needs to act and nothing tells them" failure, one step further along the same flow.

06Scheduled Tasks/brain/schedules

Creation and editing are conversational, not direct form submissions — a real, deliberate design choice worth knowing before you go looking for a POST endpoint that doesn't exist.

Layout sketch
All
New schedule
Schedule card — name, "Daily • 9:00 AM (America/Chicago)", active/paused badge, run count, success rate, drift warning if the deployed timer disagrees with the stored schedule
Schedule card

Input

  • List/detail read from real REST endpoints (GET /automations, GET /automations/{id}) — only the mutation side is unusual (below).
  • The create/edit modal collects exactly 3 things: Name, Instructions (free text), Frequency (Daily/Weekly tabs, day-of-week, time, IANA timezone — defaulted from the browser) — no target persona/model field exists at all.

Edge cases

  • note Creation has no direct create endpoint — confirmed by an inline comment ("local — no create/update endpoints available yet"). Saving the modal instead builds a natural-language prompt ("I want to create a schedule called…") and navigates into a Brain chat so the Task agent itself creates the schedule conversationally. Editing works identically — an update-style prompt, back into the linked chat, not a direct PATCH of the fields you just edited.
  • gap parseFrequency (which round-trips the backend's human-readable cadence sentence back into the modal's structured fields) can't recognize every possible cadence — e.g. "Every 5 minutes" — and silently falls back to modal defaults instead of surfacing the real value.
  • No "target agent/persona was deleted" handling exists, because the Automation/AutomationDetail types don't reference a persona field at all — that failure mode simply isn't modeled client-side.
  • Repeated run failures show per-run in the run history (traceback stripped to just the exception message) — there's no "N consecutive failures" banner or auto-pause behavior.

A 409 on resume (no future run computable) surfaces as a "Failed to resume schedule" toast rather than a silent failure.

Save & Publish

Only the operational fields (active/paused, name, summary) persist directly. Content (instructions, frequency) only ever changes via the conversational round-trip above — there is no "Save" button that writes those fields straight to the backend.

Proposed changes

  • proposed Escalate visually after N consecutive failures, with one concrete action — amber-alert-ux.md (Habituation — repeated identical signals get tuned out — and Actionability — give recipients something concrete to do). Failures currently show per-run in history only, with no "N consecutive failures" banner or auto-pause gap; a distinct treatment on the schedule card itself plus a direct "Review and fix" action into the linked chat turns a quietly-decaying automation into something the user can actually act on. Backend: partial — better than it looks: this exact streak calculation already exists server-side (used internally to decide when to auto-pause and email the owner at 3 consecutive failures), it's just never included in the API response. Serializing that already-computed number onto the schedule detail/list response is a small addition, not new logic.
  • proposed Say so when parseFrequency can't match the exact cadence, instead of silently substituting modal defaults — grammarly-onboarding-survey.md (Personalization Clarity — a silent mismatch between what a user said and what the system shows erodes trust more than an honest "we didn't quite get that"). gap already documented above.   • proposed A small "Next run in 3h" teaser on each schedule card — spotify-wrapped-psychology.md (Curiosity Gap). Cards show cadence, run count, and success rate today but nothing forward-looking; a low-effort, low-stakes teaser builds a mild pull to check back, the same lever Spotify Wrapped uses on a much bigger stage. Backend: ready — a computed next_run_at field already exists on both the list and detail schedule responses (recalculated fresh on every read, so it can't drift from the actual cron), it just isn't surfaced on the card today.
