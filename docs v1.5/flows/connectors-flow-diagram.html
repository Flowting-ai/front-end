00Entities & the one-page model

"Connectors" used to be two almost code-sharing-free pages — an org-admin page at /connectors and a personal page at /settings/connectors — with two different backend object shapes for what looked like the same idea ("an account"). A full UI-replacement migration (docs v1.5/connectors-v1.5-migration-plan.md) collapsed both into one experience, ConnectorsExperience, mounted at both routes. There is now one account list per connector, with a visibility: 'shared' | 'private' field on each account rather than two disjoint systems.

EntityShape
ConnectorCatalogOne row per connector slug (Gmail, Slack, …): authMode (oauth2|api_key), tools[], apiKeyFields[], linked, and connections[] — every account, private or shared, that exists for this connector across the viewer's visibility.
ConnectorConnection ("account")One authorized login: scope: 'personal'|'shared', owned (only the linker may manage it), inUse (the one account per connector that chats/automations actually resolve to — a person can hold several, the rest are "parked"), connected/status, and a sparse permissions[] list (a tool with no entry defaults to 'ask').
ConnectorTool / AccountToolThe catalog describes what a tool is once; the account decides what it does about each tool (allowed/blocked/ask). Two Gmail accounts can be permissioned completely differently.

A single account can be shared with the whole workspace or kept private — sharing is "just a flag flipped on the row afterwards," per an inline comment in useConnectorSetupFlow.ts: the credential is always vaulted under whoever authorized it, connecting shared is not a structurally different flow from connecting private.

note The live backend still scopes sharing to a Team sub-entity inside an organization (scope: 'personal'|'shared_team'), not to the workspace directly — discovered via a real runtime crash during the migration (a ZodError on accounts[0].scope the first time a real shared account was fetched). The target architecture the org has since pointed at states connections should be workspace-wide with no Team indirection at all. The current frontend types this doc describes (AccountScope = 'shared' in connectors.ts, i.e. team-indirection already erased at the FE layer) reflect that target shape; a useDefaultTeam.ts/team-resolution stopgap existed during the migration to bridge the gap against the pre-migration backend and was flagged in the plan doc as something to delete once the backend catches up, not extend further.

Missing / Unused / Hidden

  • note useDefaultTeam.ts is a live stopgap explicitly marked for deletion, not extension. It exists solely to bridge the erased Team-indirection type (AccountScope) against the pre-migration backend's actual scope: 'personal'|'shared_team' shape. It is real, called code — not dead — but the migration plan is explicit it should be deleted once the backend adopts workspace-wide scoping, and any future PR that instead builds more logic on top of it would be extending something already flagged as debt.

Proposed changes

No proposal here — this section is glossary, not a page. See §08 for the standing backend-gap ledger this whole doc is built against.

Input

  • Query: ?q= pre-fills the search box — the welcome page's "Connect Slack" quick action links here as /connectors?q=slack. The one other query param, ?tab=, only ever reflects the currently-open account sub-view (permissions/access/settings), written by a router.replace effect, not a user-set filter.
  • Catalog fetch is not one call: personal/shared visibility for the signed-in user comes from listLinkedConnectors() (paginates via GET /connectors?linked=true); the "Connected" vs "All connectors" split inside the Catalog subcomponent additionally calls listConnectors({linked:false, ...}) or a search query for the browse grid, independently paginated 10/page.
  • Toolbar: three view tabs (All/Connected/Not connected), a debounced (300ms) search box, and a sort menu — alphabetical only (Name A–Z / Z–A). No "Recommended" mode exists: an inline comment notes the backend orders GET /connectors by slug with no curation field, so a fake "Recommended" would just be an alias for arrival order.

Edge cases

  • note The personal catalog endpoint is an intentional allowlist, not a browse-everything view — GET /connectors's member_catalog_view filters to org_enabled | team_approved | personal_approved | personally_linked by design. A regular member genuinely cannot browse the full ~150-slug catalog through any endpoint they call; only an admin's separate unfiltered listOrgCatalog() fetch (merged in via mergeCatalogs) sees everything. This is deliberate access control per the migration doc's Gap #15, not a bug — but it does mean a non-admin member and an admin looking at the same page can see genuinely different catalogs with no visible explanation of why.
  • gap Follow-on to the above: an admin who discovers a not-yet-enabled connector through the full catalog and tries a Private connect can still 403 (ensure_member_can_link applies the same gate to admins, no role exception) — SetupModal has no "enable this connector for the org first" step, since the source Figma design never had one. Connecting Shared works around it (it itself is one of the gating conditions), so this only bites one specific path.
  • Connected and available connectors deliberately use separate pagination (connected renders in full, always; only "All connectors" paginates) — the plan doc calls out mixing them into one paginated list as an explicit prior bug class ("pagination chops the mixed enabled/disabled list arbitrarily").
  • Search/view changes reset to page 1 and re-fetch a fresh cursor chain; a category-only change (not applicable here — no category filter is currently wired into this specific toolbar, unlike the older ConnectorBrowse hook it reuses elsewhere) would reset only the page per the preserved-edge-case list.
  • Loading state is 8 skeleton ConnectorCatalogCards in state="loading" — a real skeleton, not a spinner.

03Setup / Reconnect modalS11, S18

Where the bulk of the old system's real edge-case handling landed, carried over verbatim per the migration doc's §4 checklist rather than re-derived from the new visual design.

Layout sketch

Connect Gmail — "Choose access before authorizing."
Account name (optional) — you@company.com
Who can use it?
◉ Shared — everyone in this workspace can use it
○ Private — only you can use it
Cancel

Input

  • Fields shown depend on authMode: plain OAuth2 shows only the name + visibility choice; api_key connectors (and per-tenant OAuth like Shopify's client-id/secret, needsOAuthInitFields) additionally render one input per apiKeyFields entry, secret fields as password inputs.
  • Visibility (Shared/Private) is only offered on fresh connects (not reconnects) and only when orgId is non-null — "Shared" is locked with a "Needs a workspace" badge otherwise.
  • Zapier-provider connectors skip the credential form entirely (isZapierProviderConnector) — they're always hosted, so needsForm is forced false regardless of authMode.

Edge cases — the load-bearing OAuth mechanics

  • Native MCP connectors (isMcpProviderConnector) navigate the current tab (window.location.href), never a popup — their OAuth callback redirects back to Souvenir's own domain, so a popup would trap the whole app inside itself. If the user asked to name/share the account on an MCP connect, that choice is dropped with an explicit toast ("Finish authorizing Gmail, then set its name and sharing from the account's settings") rather than silently lost, since nothing survives the full-page navigation to apply it to.
  • Non-MCP popups are opened without noopener deliberately — noopener leaves the popup stuck at about:blank in some browsers once the code later assigns popup.location.href.
  • A closed popup is not immediately cancellation. The long exponential-backoff poll (2s→30s, 120s timeout) aborts and a short 12s "grace window" poll runs first, because Pipedream's hosted success screen often stays open after the account is actually linked — only report "cancelled" if that grace poll also comes back empty. Zapier is the one exception: it never flips linked until a completeZapierLink POST with the postMessage-delivered auth id, so a closed Zapier popup is treated as cancellation immediately.
  • 5xx errors surface the raw backend detail (ApiError.rawMessage) instead of a generic message — e.g. "googledrive is not available in your organization — request access from an admin first" is materially more actionable than "backend returned 500."
  • React StrictMode double-mount guard: abortedRef.current resets to false on every effect setup, not just once — otherwise dev-mode's mount→cleanup→mount sequence leaves it stuck true and every async handler silently bails ("click Connect, nothing happens").
  • The row a fresh link "belongs to" is computed as the owned account not already known before the flow started (knownAccountIds) — never assumed to be "whichever row is handy." Re-authorizing an account already on file produces no new row, so naming/sharing choices made in that case are explicitly not silently applied to some other row; the flow says so via toast instead ("re-authorized the account you already had — set its name and sharing from that account's settings"). An inline comment notes this exact guess is "what turned a private account shared" in an earlier version.

Navigation

On success: closes, calls onConnected, parent re-fetches (fetchAll) and shows a success toast. On Cancel: fully aborts the poll and closes any orphaned popup via cleanup — the Cancel button itself is only disabled during the brief window the flow is actually writing the name/sharing PATCH (state === 'submitting'), specifically so a user who closed the external OAuth tab isn't stuck watching "Waiting for auth…" with no way out until the poll times out.

Save & Publish

Naming and sharing are edits to the row the link just produced, applied as a follow-up updateAccount PATCH after the OAuth/API-key link itself succeeds — not part of the link call. If that follow-up PATCH fails, the account is still linked and usable; the toast says exactly what didn't save ("connected, but saving its sharing failed... set it from the account's settings") rather than implying the whole connect failed.

Floating panels & Help

A centered modal, not a panel — dismiss-on-backdrop-click except while submitting.

Proposed changes

  • proposed Surface the grace-window poll as a distinct state, not silently reused "Waiting for auth…" copy. The 12-second grace poll that runs after the popup closes is functionally a second, shorter wait with different semantics (last chance before declaring cancellation) but shows the identical "Waiting for auth…" button label as the long poll before it — a user who closed the popup on purpose sees the exact same UI as one who's mid-authorization, with no signal that a countdown to "cancelled" has begun. A brief distinct label ("Checking if that finished…") would make the two states legible without changing any timing logic. Backend: ready — purely a frontend state-label change; the grace-window logic and its timing already exist exactly as needed.

Missing / Unused / Hidden

Nothing found in this section. Re-checked ConnectorPrompts.tsx and useConnectorSetupFlow.ts directly for no-op handlers and TODO stubs — the only "no-opener"-adjacent hits are the deliberate, documented decision not to pass noopener to window.open (already covered inline above), not disabled/dead code.

Input

  • Permissions tab: joins the connector's flat tool list with the account's sparse permission list, grouped into Read-only / Write sections purely on the frontend (tool.group, derived from read_only). Long-tail connectors return an empty tools[] on the list endpoint (a payload-size optimization) — the detail view lazily backfills via getConnector(slug) the first time it opens, with a dedicated skeleton (PermissionsTabSkeleton) while that resolves, and fails silently (keeps an empty list) if the backfill itself errors.
  • Access tab: answers "Is this the account Gmail runs through?" directly, then a Shared/Private VisibilityRow choice below it.
  • Settings tab: a single editable label field plus the Remove action.

Edge cases

  • Every permission change is optimistic with revert-on-failure: the UI flips immediately, a baselineRef holds the last server-confirmed state, and any PATCH failure snaps the UI back to that baseline rather than leaving a permission shown that didn't actually save.
  • "Set all" on a Read-only/Write group is one PATCH with every tool key in that group, not N sequential PATCHes — preserved from the old system per the migration doc.
  • gap Tool grouping (Read-only/Write) has no backend field. ToolEntry.read_only is a per-tool boolean the frontend buckets into two hand-maintained group labels (ConnectorTool.group in connectors.ts) — there's no server-side "group" or "category" concept beyond that one flag, so any future grouping richer than a binary read/write split would need new backend work, not just a frontend remap (migration doc Gap #4).
  • gap Shared accounts have zero tool-permission storage on the backend at all — the shared-account update endpoint accepts no permissions field (Gap #11, marked "Highest" severity alongside the visibility gap below). The Permissions tab still renders for a shared account, but every control is disabled with a tooltip ("Tool permissions for shared accounts aren't supported yet") — a deliberate choice to show a disabled-and-explained control rather than a live-looking one that silently no-ops.
  • gap Changing an account's visibility after creation has no backend field at all (Gap #2/#8) — Save access on the Access tab is wired to a real updateAccount({shared: ...}) PATCH in the current code, which is a step ahead of what the migration doc describes as unsupported; worth re-confirming against a live backend whether that PATCH's shared field actually persists post-migration or whether this is aspirational code shipped ahead of backend support.
  • gap Private accounts can't be renamed after creation (Gap #13) — UpdateConnectorRequest/updateAccount's label field is real in the current schema and the Settings tab's label input is not disabled for private accounts in the code read for this doc, which again reads as ahead of the gap the migration doc records; if the backend genuinely still rejects a label PATCH on a private account, the UI currently has no guard for that specific 4xx and will likely surface it as a generic "Failed to update label" toast rather than the asymmetric-but-honest explanation the migration doc originally specified.
  • note Shared OAuth accounts have no re-authorize-in-place path (Gap #14) — creating a new shared account is possible, but PATCHing an existing OAuth-based shared account's credentials is not (only api_key-auth shared accounts support in-place credential PATCH). A team's expired shared Slack/Notion connection genuinely cannot be fixed without deleting and recreating the account, which changes its id.

Navigation

Back → Connector detail (§02). Remove (Settings tab) → Remove modal (§05), rendered by the parent orchestrator rather than this component.

If the current PATCH genuinely rejects a private-account rename, a read-only field with a short note beats a Save button that silently does nothing. Backend: unclear — needs a live check against the current backend to know whether Gap #13 is actually still open or already closed by the schema shown in connectors.ts; this proposal only applies if it's still open.

07Cross-cutting: Context Rail & Agent Configure

Two other surfaces show connector state without being the Connectors page. Kept brief here — see tasks-flow-diagram.html §03 for the Context Rail's full layout and animation spec.

Context Rail (Brain)

  • The rail's "Connectors" section (ContextRailConnector[], in src/templates/Brain/ContextRail.tsx) is purely a display of what the current/latest turn actually touched — an "Active" group (used by the latest turn) and a dimmed "Previously used" group, exactly mirroring the rail's Pins/Files sections. A colored dot on each row reads the connector's status: green for connected, red for failed — this is turn-scoped connector-usage telemetry, structurally distinct from the Connectors page's own account-level connected/needsReconnect status, and the two should not be conflated even though both render a status dot.
  • This is read-only — the rail has no connect/reconnect affordance of its own; a failed connector here has to be fixed from the Connectors page or the chat-embedded prompt (§06), not from the rail itself.

Agent Configure — Connectors tab

  • ConnectorsTab.tsx is a per-agent allow/block list, not a connect flow — it lists every connector already linked (personal or workspace) and toggles a per-agent blocked_connectors array on the agent's version (setVersionBlockedConnectors/unblockVersionConnector), entirely separate from the account-level tool permissions in §04.
  • Two labeled sections — "Workspace connectors" (shared org accounts) and "Personal connectors" (the viewer's own links) — each a ConnectorRow toggle. A real conflict rule is enforced client-side: note a connector should only ever be usable through one scope per agent, never both a personal and a workspace account simultaneously.
