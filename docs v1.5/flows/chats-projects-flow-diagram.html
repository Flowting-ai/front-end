00Entities

A Chat is a single conversation thread — standalone, or living inside a Project. Chat visibility is just three states now: private (default), team (the frontend's leftover name for "shared" — a chat shared with specific people, not org-wide), and archived (one-way, no unarchive endpoint exists). Sharing a chat and sharing a persona (Super Link, in the Agents doc) are unrelated systems.

A Project has three visibility types: Personal (owner only), Workspace (every org member automatically — no manageable list), Shared (an explicit, owner-or-collaborator-managed list). Set once at creation, immutable after. Pins and Highlights are both message-level, cross-chat features rendered as global side panels rather than pages of their own — Pins save a copy of a message's content; Highlights save a specific text selection within one.

The entry point into a fresh chat from anywhere in the app.

02Chat/chat

The standalone chat surface. Two remount layers protect against stale state: an outer ChatPageInner key={`chat-${newChatEpoch}`} (a true remount, belt-and-suspenders in case the router serves the route from cache) and an inner synchronous reset for the common case.

Layout sketch
Chat title / share button (if canManage && orgId)
Message list — empty state shows the composer centered mid-page for a brand-new chat
Composer — model ▾ · Add-agent/attach menu · web-search toggle · input · send
Content isn't width-capped the way Configure's 714px column is — the message list/composer run the full available width of the chat panel.

Input

  • Query: id (chat id), msg (a message id to scroll to), share (presence-only — auto-opens the Share overlay).
  • isNewChat = !activeChatId && !hasMessages && !initialPrompt — the tri-state driving new-vs-existing UI.
  • Per-chat settings (web search, attached persona) load from localStorage souvenir_chat_<chatId> whenever chatIdFromUrl changes — not part of the remount key, so switching between two existing chats via a useLayoutEffect URL-sync (not a remount) still gets fresh settings without losing other page state.

Edge cases

  • Sending with no chat id yet just sets local state (initialPrompt, hasMessages=true) — no id exists until the stream's first RUN_STARTED event.
  • Switching away mid-stream doesn't abort it — streams are tracked in a global registry independent of navigation; only UI updates for the now-unfocused stream are gated.
  • Page reload mid-conversation relies on a documented "reload-interrupted-stream recovery path" plus a message refresh.

04Chat Sharingshare overlay + /chat-shares/[shareId]

Two halves: the sharer's overlay (on /chat) and the recipient's read-only accept page. The backend dropped the old editable/read-only "mode" and project-target columns entirely — every share today is uniformly "view read-only, then optionally fork your own copy."

Input

  • Sharer side: the overlay button only renders when chatId && canManage && orgId. Tabs: "Share" (multiselect org members, one POST /chat-shares call per person) and "Active shares" (GET /chat-shares?chat_id=, revoke via DELETE).
  • A deep link /chat?id=<id>&share=1 (built by both the sidebar's "Share" menu item and the Chats-list row's share action) auto-opens the overlay on load.
  • Recipient side (/chat-shares/[shareId]): GET /chat-shares/{shareId} on mount returns the chat title + full message transcript in one shot.

Edge cases

  • A cancellation guard (a local cancelled flag checked in every branch) protects against a fast shareId1 → shareId2 navigation letting a stale response overwrite the newer share's content.
  • gap A revoked/deleted share and a share that never existed both 404 into the exact same "not found" screen — there's no distinct "this was unshared while you were viewing it" message, just a generic error and a "Go back" button.
  • Separately, if a chat that was already shared with you (not owned) needs its own copy, there's a different, unrelated "Create a copy" action directly on /chat for read-only chats you can already see — that calls copyChat(), not the fork-from-share endpoint below.

08Project chat/project/[id]/chat/[chatId]

Same composer engine as standalone chat, scoped to a project, with three separate persistence channels for state carried in from the hub page.

Input

  • Per-chat settings (web search, persona): localStorage souvenir_project_chat_<chatId>.
  • A pending persona chip dropped on the hub page just before navigating here: sessionStorage project-chat-pending-persona, read once then removed.
  • Pending file attachments carried the same way: window.__pendingProjectChatFiles.
  • Highlights reload per chat via an effect keyed on activeChatId — loadForChat(activeChatId), or clearHighlights() for the "new chat" sentinel route.

Edge cases

  • Remount key: project-chat-<projectId>-<chatId>-<resetEpoch> — the epoch counter bumps on a dedicated sidebar "quick add" event for that project. This is the documented fix ensuring switching chats doesn't leave the previous chat's messages, share overlay, highlights, or settings on screen — all four were bleeding across chats before the key included all three identifiers plus the epoch.

Navigation

Same navigation shape as standalone Chat (§02) — chat-id adoption on first send, sidebar New Chat resets — scoped to this project's chat list instead of the global one.

Save & Publish

Same as standalone Chat — every send is the persistence event; settings save to the project-scoped localStorage key on change.

Floating panels & Help

Highlights (§10) is scoped to activeChatId here specifically — switching chats reloads the panel's contents via the effect above rather than via a full remount of the highlight sidebar itself (that sidebar is a single app-wide instance, not per-chat).

Input

  • Created from a chat message's hover action bar (not a dedicated flow) — pins the full message content as a copy, not a live reference, with title = first 80 chars up to the first newline, category hardcoded to "Quote" (no picker), plus auto-extracted tags from any "tags" content block in that message.
  • A cross-tree pin:insert CustomEvent (fired on "Insert" click or drag-drop) is picked up by whichever chat composer is currently mounted, adding the pin as an @mention chip — the exact same event-bridge pattern reused (independently, not shared code) by the Agents picker elsewhere in the app.

Edge cases

  • Pinning the same message twice is a client-side no-op — a messageId duplicate check bails before the API call even fires.
  • Deleting a folder does not delete its pins — they're unassigned back to "All Pins," matching the confirm modal's own copy.
  • gap If a pin's source chat is later deleted, the pin's content survives (it was always a stored copy) but its chat name was never actually captured at creation time, and "Show in chat" navigates to a chat id that may no longer resolve — no defensive check exists for either.
  • note A `PinFolder` type is reused for typing inside the agent-configure Test Chat panel (`testChatFolders`) but is dead/unwired there — Pinboard is not actually integrated into that composer.

Navigation

"Show in chat" → /chat?id=<chatId>&msg=<messageId> (the msg param from §02's Input list is what this jump relies on).

Save & Publish

Optimistic insert with a temp id, then POST /pins/message/<messageId>; reconciles or rolls back with a toast. Folder CRUD is its own set of immediate calls (POST/PATCH/DELETE /pins/folders...), with folder names validated non-empty, ≤255 chars, case-insensitive-unique.

Floating panels & Help

Pinboard is itself one of the floating-panel-style surfaces in this doc's schema — no further nested panel exists inside it beyond the Organize overlay shown above.

Highlight card — sticky-note style, 5-line clamp, hover: Copy / Open in chat / Delete
Panel: 332px wide, app-wide singleton (not remounted per chat)

Input

  • Filter dropdown: "This chat" (default, needs a chat_id — the backend has no all-chats endpoint) vs. "All highlights" (fans out one GET /highlights?chat_id= call per known chat in parallel, silently swallowing per-chat failures).
  • color_index is assigned automatically, round-robin over 4 colors — never user-chosen.

Edge cases

  • note Creating a highlight calls PATCH /highlights — an odd HTTP verb for what's semantically a create, likely an intentional upsert-style backend design, but worth knowing if you're cross-referencing the API contract.
  • Editing an existing highlight is not implemented — only create/read/delete exist.
  • Deleting is a soft-delete (PATCH /highlights/{id}) behind a confirm modal ("This highlight will be permanently removed").
  • The literal string "new" as a chat id is explicitly excluded from highlight loads to avoid a 422 from the backend.
  • gap If the source message is deleted, the highlight persists server-side and still shows as a card, but its inline mark can no longer render (needs the message present) and "Jump" has no verified fallback beyond the message container. No explicit access-revocation handling either — a chat you've lost access to just silently contributes zero highlights rather than erroring.

Navigation

"Open in chat" (Jump): same-chat scrolls directly; cross-chat navigates first, then polls the DOM (up to 20×250ms, twice — once for the message, once for the mark) before scrolling. "Copy" is clipboard-only, no navigation, no API call.

Save & Publish

Optimistic create/delete against the API described above, with rollback + toast on failure — same pattern as Pins.

Floating panels & Help

Highlights is itself a floating-panel-style surface — no further nested panel.
