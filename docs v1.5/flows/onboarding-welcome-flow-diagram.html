00Entities, route map & the two live flows

"Onboarding" isn't one flow in this codebase — it's two independently-maintained flows sharing one route prefix. The v1.5 rebuild (docs v1.5/onboarding-v1.5-flow.md) was built to supersede the previous team-onboarding implementation, but the previous implementation's files, context provider, and proxy exemptions were never deleted — both are mounted by the same layout (src/app/(onboarding)/layout.tsx wraps every child in both OnboardingProvider and WorkspaceOnboardingProvider) and both are still reachable by URL. This doc covers the live, current-entry-point flow in depth (§01–§07) and flags the legacy surface only where it's still structurally load-bearing (§07's invite tree, and the still-present but now-unreachable-from-the-new-flow hello/account-type/plans/tone/import pages, which this pass did not re-document since src/proxy.ts's determineNextOnboardingPath() — the server-side gate — never routes a new user into them).

Everything in the live flow is driven by two lightweight React contexts mounted at the shared layout, not a state machine — there is no phase graph the way Brain has one:

  • WorkspaceOnboardingContext (src/context/workspace-onboarding-context.tsx) — the v1.5 flow's only state: workspaceName, workspaceSize, firstName, lastName, role, tone, inviteEmailList, inviteEmailDraft, entryFlow: "create" | "join" | null. Pure client memory — a hard refresh mid-flow loses every unsaved field (see §08).
  • OnboardingProvider — backs only the legacy pages; the live flow's pages never call useOnboarding().

Server-side truth lives entirely on GET /users/me. src/proxy.ts's determineNextOnboardingPath() derives the correct live-flow step from exactly two backend signals — see §08 for the full gate and its one documented false-positive risk.

  • On mount, sets entryFlow: "create" in context — this is purely so the profile step's Back button later knows to return here rather than to /onboarding/join (A2's screen 1).

Edge cases

  • note The 4-bucket size picker doesn't map 1:1 onto the backend's 3-value role_fit enum (just_me | small_team | large_team) — flagged in-code as "a reasonable guess, not a confirmed contract": just_me→just_me, 10+→large_team, and both 1-5 and 5-10 collapse to small_team.   • gap GET /users/me never returns an org id (no such field in the response schema — user.orgId is always null client-side). Next has to call listOrganizations() first to tell "already has a workspace" apart from "doesn't yet" before deciding whether to createOrganization() or updateOrg() — without that lookup, clicking Back then Next again would re-call createOrganization() and 400 with "You already belong to an organization."
  • note No plan/billing step exists anywhere before this screen, unlike the legacy team flow (which created the org only after a Stripe checkout) — org creation now happens unconditionally, with no payment gate at all. Flagged in-code as needing backend confirmation, not silently assumed correct.
  • A save failure here (workspace name/role_fit PATCH) is non-fatal — toasts an error but still advances to the profile step; the name can be fixed later in Settings.
  • Leaving with unsaved input (name typed or size changed from default) triggers the shared useLeaveGuard — see §08 for its two independent mechanisms.

  • fixed Role and Tone are typed in on this screen but deliberately not sent from it. The backend's update_onboarding (services/users/repository.py) silently flips onboarding_completed=true the instant user_role + ai_tone + role_fit are all set on the account, independent of which request set the last one. Since role_fit is already set by the workspace step (§02), a version of this page that PATCHed Role/Tone immediately would complete onboarding right here — and did, in a real, dated bug: the proxy's already-onboarded re-entry gate then bounced the subsequent navigation to /onboarding/invite straight to /, skipping the invite screen entirely. The fix is frontend-only: Role/Tone stay in WorkspaceOnboardingContext and are sent together with onboarding_completed: true from the invite step's own finish call instead (§05), so all three gating fields land in the same request as the explicit completion flag.
  • An explicit refreshUser() runs before navigating away, kept as a defensive backstop for a returning user whose user_role/ai_tone were already set by some other path (e.g. the legacy flow) before role_fit landed — though the comment is candid that this alone doesn't prevent the bug above, since it's the proxy's live check, not the client's cached auth state, that actually gates re-entry.
  • Back branches on entryFlow: /onboarding/workspace if the user arrived via A1, /onboarding/join if via A2 — this branch itself is a documented fix for an earlier version that hardcoded the A1 destination regardless of entry path.

Next → /onboarding/invite (both entry cases converge here). No Skip on this screen — only Role and Tone are optional, First/Last name still gate the button.

A1/A2 shared, dot 3 of 3 — and the only step with a 3-button footer (Back / Skip for now / Next), since inviting is fully optional. This is where onboarding actually completes; there is no separate route for the flow spec's "screen 5" ("Into the app" + Slack modal) — that's the /welcome handoff in §06.

Layout sketch

← Back

Input

  • A chip-input email list: typed text is parsed on Enter/comma/blur; pasting a comma- or newline-separated block commits the whole batch immediately. Each entry is format-checked (^[^\s@]+@[^\s@]+\.[^\s@]+$ — a shape check, not a deliverability check) and deduped case-insensitively against both the committed list and the rest of the same paste.
  • Invalid and duplicate entries in a batch each get their own distinct toast, singular vs. plural copy depending on count.
  • State (committed chips and whatever's still sitting un-committed in the input) lives in WorkspaceOnboardingContext, not local useState — specifically so clicking Back to profile/workspace and then Next again doesn't silently drop a partially-typed address, a documented behavior a plain local-state version used to have.

Edge cases

  • Skip and Next each track their own loading flag (a single shared boolean previously showed Skip's spinner on the Next button — the wrong button — a documented, since-fixed bug).
  • note Sending invites and completing onboarding are independent outcomes with independent toasts: an invite-send failure ("no workspace was found for your account" if orgId never resolved, or the backend's own verbatim error, e.g. "X is already a member") does not block completion — the user still lands in the app.
  • No org id resolved at all (the workspace step's org-create likely failed silently) is explicitly detected and surfaced as its own toast, rather than the invite silently no-op'ing.
  • Both Skip and Next call the same finish() → updateOnboarding({ user_role?, ai_tone?, onboarding_completed: true }); if the backend response's completed flag isn't true, an error toast fires and navigation does not proceed — this is the one hard-stop in the entire live flow.
  • The Continue navigation is an intentional full window.location.href handoff (not a router push) — leaveGuard.bypass() is called immediately before it specifically to suppress the leave-guard's own beforeunload prompt for this one navigation, distinct from a real accidental unload.

07The other invite tree/onboarding/team/[inviteId]

A second, independently-built "accept a workspace invite" implementation that is not the same code as §03's /onboarding/join — both are live, both call overlapping backend contracts, and nothing in the routing determines which one a real invite link actually points a user at.

Input

  • Own context (team-invite-onboarding-context), own UI (_components/invite-ui.tsx's InviteStateScreen for loading/error/expired states), own workspace-join card component — visually and structurally similar to §03's card but a separate implementation, not a shared component.
  • An in-code comment describes this as replacing an even older 4-screen version (invite → join → profile → confirm), on the grounds that the "join" pass-through step made no API call and the old "confirm" screen duplicated the Slack-modal landing with its own bespoke treatment.

Edge cases

  • The workspace card's Join button here does two things atomically that §03's does sequentially across two screens: acceptTeamInvite(inviteId) and updateOnboarding({ onboarding_completed: true }) in one handler.
  • note Already-onboarded users are branched explicitly: wasAlreadyOnboarded is captured from user.onboardingCompleted before the mutations run, and if true, the user skips the profile step entirely and goes straight to ${WELCOME_ROUTE}?slack=1 — this is the one documented, correct handling in this whole doc of "an already-onboarded user joining a second workspace," a case §03's A2 screen doesn't appear to special-case at all (it always routes to /onboarding/profile next, which would re-collect a name that's already on file).
  • A 410 on accept surfaces as "This invite has expired." specifically, not a generic error.
  • src/proxy.ts carries a dedicated isTeamInviteOnboarding exemption (pathname.startsWith(ONBOARDING_TEAM_BASE_ROUTE)) letting an already-onboarded user back into this specific route tree, since the rest of /onboarding/* is otherwise blocked for onboarded users (see §08) — no equivalent exemption exists for /onboarding/join, reinforcing that the two were built and are maintained separately rather than as one reused flow.

Navigation

New user: Join → /onboarding/team/[inviteId]/profile (this tree's own profile step, not /onboarding/profile) → the shared ${WELCOME_ROUTE}?slack=1 landing. Already-onboarded user: Join → straight to ${WELCOME_ROUTE}?slack=1. Back (on the initial screen) → /chat, not a logout, unlike §03's Back.

Save & Publish

Covered above — accept + completion fire together, not staged across steps the way §03/§05 split them.

Missing / Unused / Hidden

Proposed changes

08Re-entry gating, refresh mid-flow & already-onboarded users

Two independent gates are meant to agree exactly, and the code says so explicitly in a comment: src/proxy.ts (server-side, runs on every request) and src/components/shared/OnboardingGuard.tsx (client-side, runs in the app shell).

Edge cases

  • gap The proxy's step-inference has one documented, unresolved false-positive risk, called out directly in-code: since user_role is now optional at the profile step, determineNextOnboardingPath() instead infers "profile step done" from first_name/last_name being non-empty on /users/me. Auth0 sometimes auto-populates first_name to the account's raw email on signup (existing, separately-documented behavior in auth-context.tsx) — this function can't distinguish that placeholder from a real name, so such a user could be silently routed past /onboarding/profile straight to /onboarding/invite without ever being asked their actual name. The comment explicitly recommends a dedicated profile_completed flag as the real fix, not the current name-field inference.
  • A positive-only cache (onboardedCache, 60s TTL, keyed by Auth0 sub) means an onboarded result never needs a fresh /users/me round-trip for a minute — safe because "onboarded" is treated as monotonic (an account never un-onboards) — but every un-onboarded request still pays a live fetch, since that state changes mid-flow and must never be served stale.
  • The leave-guard (§02/§04/§05, shared via step-shell.tsx's useLeaveGuard) covers both a real page unload (beforeunload) and the browser Back/Forward buttons (a pushState/popstate trick, since Next's App Router has no first-party navigation-block hook) — but deliberately does not intercept the step's own in-flow Back/Next buttons, which use router.push and never fire popstate.
