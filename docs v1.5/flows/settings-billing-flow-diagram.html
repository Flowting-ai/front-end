Settings & Billing — Page-by-Page Reference

Companion to flows/tasks-flow-diagram.html, flows/agents-flow-diagram.html and flows/chats-projects-flow-diagram.html, same schema — the previously-undocumented Settings shell: personal Account/Usage, workspace General/Members/Plans & Billing/Usage (Analytics), Help & Legal, plus the five orphaned pages (AI, Security, Notifications, Preferences, Files) that still exist behind no nav link at all.

V1.5 — Built fresh from current source this session, grounded against docs v1.5/settings-v1.5-pages-audit.md (the prior read-only audit) and re-checked page-by-page against the live component code rather than trusted verbatim — a few of that doc's claims (route labels, exact field wiring) are restated here in the same visual format as the other three flow docs; nothing in the audit was found to be materially stale for the pages this doc covers. This pass leans on what's real vs. decorative more than the other three docs — Settings is the single area of the app with the most components that render, look finished, and either save nowhere or save to nowhere real (a localStorage-only model-tier picker, a fully-built but statically-disabled "Workspace defaults" card, a wired-but-unreachable ownership-transfer flow, five orphaned full pages with zero incoming links). Each is called out where it appears rather than glossed over.

+ light UX proposals — A handful of Proposed changes sections are included only where a real, groundable gap was found in the code itself (not sourced from an external case-study corpus, unlike the Tasks doc) — plain proposed items with no citation, since no ux research/ pass exists for this feature area yet.

00Shell, nav & entities

The shell lives at src/app/(app)/settings/(shell)/layout.tsx, pairing a fixed 294px SettingsSidebar with a scrollable content pane. Nearly every page in the "new nav" set uses the same two structural pieces: SettingsPageShell (title/description header + centered content column, default max-width 1114px, optional back-button) or a page-local re-implementation of the same card/row visual language (border var(--neutral-200), radius 16, shadow 0px 2px 2.8px 0px rgba(82,75,71,0.12)) — Account, Security, Notifications, Files and Preferences all hand-roll their own SettingsCard/CardSection locals rather than sharing one component, so the visual language is consistent but not literally the same code path everywhere.

Input — the group-visibility logic

  • Until useOrg().orgReady resolves, the whole nav renders as one atomic SettingsNavSkeleton block (PERSONAL + WORKSPACE + HELP shape) rather than assembling section-by-section — a deliberate choice per an inline comment, to avoid WORKSPACE visibly popping in underneath PERSONAL once org/role data arrives.
  • WORKSPACE only renders at all when orgId && orgRole === 'admin' — a plain member of an org sees just PERSONAL + HELP, identical to an individual account with no org.
  • The account-menu credits/plan line is computed from several independent signals: isTeamUser (org membership or roleFit or a cached billing snapshot), orgHasPlan (a real subscription/pool vs. a zeroed starter object), and orgHasSelectedPlan (distinct — true only once a real Teams/Enterprise plan is chosen, not just because the org's founder-grant starting balance is nonzero). The role badge is deliberately gated on orgReady && orgId, not just orgId, specifically to avoid a "Member" badge flashing before the real "Admin" role resolves.

Edge cases

  • gap /settings/teams is a live 404. Per the prior audit's §0 (independently re-confirmed against SettingsSidebar.tsx's own code comment, which explicitly notes Connectors — and by extension Teams — "has no home in the new Figma frame"): the entire Teams CRUD UI was deleted, but LeftSidebar.tsx's org-admin section still links to the dead route. This is a real backend architecture question (Team is being phased out in favor of flat Workspace/Project, per the audit's cited target-architecture doc), not something this frontend doc can resolve — flagged here because it's directly adjacent to Settings' own org-admin surface.
  • note "Usage" is used as a label for two different pages depending on section — SETTINGS_USAGE_ROUTE (personal, §02) under PERSONAL and ORG_ANALYTICS_ROUTE (workspace, §07) under WORKSPACE — same icon asset, genuinely different data and page.
  • The nav's own "New" vs. active-item highlighting uses a prefix match for WORKSPACE items (pathname === href || pathname.startsWith(href + '/')) so a sub-route like Plans' /confirmation still highlights "Plans & Billing" — but an exact match for PERSONAL/HELP items.

01Account/settings/account

Personal profile — the one settings page wired into a real dirty-tracking guard, and the clearest example in this whole area of a control that looks live but writes to nothing on the backend.

Layout sketch
Profile card — avatar (65px circle, hover "Change" overlay) · First Name · Last Name · Role (read-only) · Email (read-only) · Edit Profile / Save changes
Personalisation — Style (Direct/Balanced/Warm, saves immediately) · Default Model (Advanced/Standard/Basic, localStorage only)
Danger Zone — Delete account (disabled, "Coming soon")

Input

  • Profile picture — click-to-upload only while an explicit "Edit Profile" mode is toggled on; rejects non-images and files over 8MB, then downscale/center-crops client-side to a 256×256 JPEG and base64-encodes it as a data URL before it's ever sent anywhere.
  • First Name / Last Name — wired to real first_name/last_name fields via updateUser(). Figma's field label ("Full Name" for the first input) was deliberately corrected to "First Name" in the shipped copy since the underlying field and placeholder both say "first name."
  • Role / Email — both permanently disabled; Role reads roleDisplayLabel(user.onboardingRole) (set once at onboarding), Email is billing/notification contact info. No edit-role surface exists anywhere in the app.
  • Personalisation — Style: Direct/Balanced/Warm, backed by the same 3-value TONE_API_MAP onboarding itself uses. Commits immediately via updateOnboarding({ai_tone}) on click (no separate Save), with an optimistic set-then-revert-on-failure pattern and a toast on error.
  • Personalisation — Default Model: Advanced/Standard/Basic. gap The component's own inline comment states plainly there is no backend field for a per-user default-model preference anywhere in the codebase — this control persists to localStorage only (key souvenir:settings:default-model-tier) and does not feed into pickDefaultModel() or any real chat-creation path. It is a fully rendered, fully interactive control that changes nothing about what model any future chat actually uses.

Edge cases

  • note Avatar upload is itself a workaround: PATCH /users/me's profile_picture field is a plain string URL, not a multipart upload endpoint (contrast: the org logo on General, §03, does accept a real file). The compressed image is disguised as a "URL" — functional today, but fragile (no size cap enforced server-side beyond the client's own 8MB gate, no CDN, no asset lifecycle).
  • Baseline resync is done as an in-render reset keyed on a composite profileKey string (name + avatar) rather than a useEffect, specifically so a fresh server value after Save doesn't fight in-flight typing — a subtle but correct pattern worth preserving if this page is ever refactored.
  • gap Delete account is deliberately inert. Figma shows the Danger Zone button enabled with no "Coming soon" badge; the shipped code overrides that on purpose — handleDeleteAccount's body is empty (a bare // TODO: open confirmation dialog comment), the button is hard-disabled, and it's badged "Coming soon." There is no DELETE /users/me-equivalent that does a real purge — the one that exists (see §11) just flips active=False. The frontend's refusal to expose this as a working button is the correct call, not an oversight.

Navigation

Not applicable — no sub-navigation on this page; leaving it while dirty is intercepted by the guard described below.

Save & Publish

  • Name and avatar changes are batched behind one explicit "Edit Profile" → "Save changes" gesture, gated on isDirty (name or avatar changed from baseline) — this is the one page in the whole nav wired into the dirty-tracking guard (useNavGuard): leaving with unsaved name/avatar edits triggers the shared "Unsaved profile changes" confirm modal, and a beforeunload listener catches a hard refresh/close too.
  • Style and Default Model are excluded from that dirty-check by design — they already commit (or persist) immediately, so there's nothing pending to warn about when navigating away.

Floating panels & Help

Not applicable — no panels on this page.

Missing / Unused / Hidden

  • disabled Default Model picker is fully interactive but writes only to localStorage. Key souvenir:settings:default-model-tier; never read by pickDefaultModel() or any chat-creation path — the component's own inline comment states no backend field exists. — src/app/(app)/settings/(shell)/account/page.tsx (Personalisation section).
  • disabled Delete account button is hard-disabled with an empty handler. handleDeleteAccount body is a bare // TODO: open confirmation dialog before proceeding comment; button is badged "Coming soon" on purpose (Figma shows it enabled). — src/app/(app)/settings/(shell)/account/page.tsx:480.
  • backend-unused Account deletion on the backend is a soft active=False deactivate, not a real purge — the frontend correctly never exposes a working "delete" call against it.

Proposed changes

  • proposed Either wire the Default Model picker to a real per-user preference once one exists, or mark it "Coming soon" the same way Delete account already is — right now it's the one control on this page that behaves inconsistently with the page's own otherwise-careful "don't fake a save against a contract that doesn't exist" stance (a stance the code's own comments state explicitly for this exact field, yet the control still renders as if it does something).

03General/settings/general (workspace, owner/admin)

The largest single settings file in the app (1385 lines) — workspace identity, org-level AI behavior, domain restrictions, and the Danger Zone, plus two features that are fully built and entirely unreachable.

Layout sketch
Workspace Identity — logo upload (512×512 JPEG, real file upload), name, URL slug + live preview, read-only Workspace ID + copy
Org-level AI instructions — textarea, 3000-char cap, "Overrides personal" badge, Clear/Save
Allowed email domains — add/remove pill list
Workspace defaults — default chat/agent visibility (built, but statically disabled)
Slack channel mapping — shown only if Slack connected; per-channel project-ID text input
Danger Zone — Archive workspace (stub) · Delete workspace (real, type-to-confirm)

Input

  • Workspace Identity — logo upload IS a real file upload (contrast with Account's data-URL workaround, §01) since PATCH /organizations/{id} accepts a real file; compressed to 512×512 JPEG client-side first. Name and URL slug with a live souvenir.ai/workspace/{slug} preview. Workspace ID is read-only with a copy button.
  • Org-level AI instructions — a 3000-character textarea with a live counter and an "Overrides personal" badge (i.e. this instruction wins over any individual member's own personalisation from §01). Its Save has a real integrity safeguard: it trusts only the server's own echoed value to confirm success, not the request payload — and surfaces an error if the two don't match, specifically to catch a silent backend drop rather than showing a false "saved."
  • Allowed email domains — an add/remove pill list, held client-side as a local array and only committed to the backend on explicit Save.
  • Slack channel mapping — only rendered at all if Slack is connected; a raw text-input per channel to map it to a project ID (no picker UI).

Edge cases

  • gap Workspace defaults card — fully built, permanently off. Default chat/agent visibility dropdowns have complete state, a loader, and a working save handler, all wrapped in a static {false && (...)} — with no comment anywhere explaining why. This is inert code sitting in a shipped page, not a stub; someone made a late call to hide it and didn't leave a trail.
  • note Archive workspace looks real, isn't. The button renders enabled (matching Figma) but its click handler is a pure stub that toasts "not available yet" — there's genuinely no archive endpoint in lib/api/organization.ts to call yet, per an inline comment. Delete workspace, by contrast, is fully real: type-the-workspace-name-to-confirm, then a real deleteOrg call.
  • gap Ownership-transfer flow is complete and unreachable. Full state and handlers (handleOpenTransfer, handleTransferOwnership) exist in this file, calling the real transferOrgOwnership API — but no button or UI in the current render tree ever triggers them. The backend and the frontend logic both already work; only the trigger is missing.
  • note The Danger Zone's own destructive-action gate (canDeleteOrg) checks caps.canManageOrg, which is true for both admin and owner — there's no owner-only distinction on archiving or deleting the entire workspace, even though that's the single most destructive action on the page. Compare Members (§04), where several actions genuinely are owner-only.
  • No useSettingsGuard/useNavGuard wiring on this page at all — every section has its own inline Save button instead of one page-level dirty state, so there is no "unsaved changes" warning if you navigate away mid-edit on any of these cards.

Navigation

Not applicable — a single page, no sub-routes; the "Manage caps" link elsewhere on Plans & Billing (§05) points into Members (§04), not here.

Save & Publish

Each section (Identity, AI instructions, domains) saves independently via its own inline button — there is no single page-level "Save all" and no shared dirty-tracking guard across sections.

Floating panels & Help

Not applicable — no panels; Danger Zone actions use inline confirm affordances rather than modals except for the type-to-confirm Delete workspace flow.

Missing / Unused / Hidden

  • disabled Correction to this doc's own wire sketch: "Allowed email domains" is not actually live. A full re-read of the source past what the prior audit checked shows the entire domains card — pill list, add/remove, Save — is wrapped in a static {false && (...)}, identical in shape to the already-documented Workspace defaults block. An adjacent code comment confirms both blocks are intentionally "temporarily disabled" and lists both line numbers. There is currently no way to manage allowed email domains from the UI at all, contrary to how this feature reads elsewhere in the app's own docs/audit trail. — src/app/(app)/settings/(shell)/(org)/general/page.tsx:1126-1239 (comment at :409 confirms intent, referencing both dead blocks).
  • disabled Workspace defaults card — fully built, permanently off. Default chat/agent visibility dropdowns, loader, and save handler all wrapped in {false && (...)}, same pattern and same explaining comment as the domains card above. — src/app/(app)/settings/(shell)/(org)/general/page.tsx:1242 (comment at :409).
  • disabled Archive workspace button is a stub. Renders enabled, but the click handler only toasts "not available yet"; a nearby comment states no archive endpoint exists in lib/api/organization.ts yet, and another TODO notes "no backend enforcement exists yet — wire once archived is [added]". — src/app/(app)/settings/(shell)/(org)/general/page.tsx:643.
  • dead-code Ownership-transfer flow is complete and unreachable. handleOpenTransfer/handleTransferOwnership and their state exist and call the real transferOrgOwnership API, but no button or menu item in the current render tree ever invokes them — effectively dead code despite being fully wired to a live backend call.
  • backend-unused canDeleteOrg gates the entire Danger Zone (including full workspace delete) on caps.canManageOrg, true for both admin and owner — an owner-only distinction the backend role model could support is simply not read/enforced here.

Proposed changes

Layout sketch

Input

  • Stat row — total members, admin count, pending invites.
  • Members table — collapsible search, per-row role control and actions.
  • Role editing — the owner can manage anyone except the owner themself; a plain admin can only manage members whose role is already member, never another admin. Pre-validates locally (already-a-member, disallowed domain) before any network call, and reports back per-email success/failure so only genuinely-sent invites clear from the chip list.

05Plans & Billing/settings/plans (workspace, owner/admin)

The org-level plan/payment/invoice surface, plus a /plans/confirmation sub-route for the post-Stripe return trip. Explicitly built as a single-source-of-truth page — everything renders off getOrgPlan()'s one response, with no merge against a separately-loaded billing snapshot and no business-default fallback papering over a still-loading state.

Layout sketch — Teams (non-Enterprise) tier
Plan card — price, active/canceling badge, Upgrade/Cancel/Resume (owner-only; non-owner sees "Request plan change")
Credits Remaining card — Buy credits, View usage
Payment — card brand/last4/expiry, "Manage on Stripe" (opens Stripe-hosted portal, no in-app card-edit form)
Admin permissions panel (owner only) — top-up / manage payment / view invoices toggles
Invoice history table — "Export all" opens Stripe-hosted PDFs in new tabs

Input

  • Enterprise tier — gradient hero (next billing date, monthly fee, remaining credits, progress bar, overage/projected-invoice badges), a stat row (shared credits, credits remaining, seats, a "Manage caps" link into Members §04), and an owner-only Overage spend limit card with an edit modal (non-owners get a "Request change" toast in its place, not a dead control).
  • Teams (non-Enterprise) tier — Plan card (owner-only Upgrade/Cancel/Resume; non-owners get "Request plan change") and a Credits Remaining card (Buy credits modal, View usage link into §02).
  • Payment section — visible to the owner, or an admin with the explicit canManagePayment permission. Card brand/last4/expiry rendered via CardBrandLogo (a small set of hand-drawn inline SVGs — Visa, Mastercard, Amex, Discover, Diners, JCB, UnionPay, plus an "unknown" generic-card fallback). "Manage on Stripe" opens the Stripe-hosted billing portal — there is no in-app card-edit form, by backend design.
  • Admin permissions panel (owner-only) — three real toggles (top-up / manage payment / view invoices) that gate what the same page shows to a non-owner admin, plus a static "Change plan — Owner only" row.
  • Invoice history — a table plus "Export all," which opens every invoice's Stripe-hosted PDF/URL in new tabs. There is no backend-generated export file.
  • Buy More Credits modal — four fixed top-up packs plus a custom amount field.

Edge cases

  • gap "Recharge below $X" threshold is captured, never sent. The Buy More Credits modal's auto-recharge input holds a real value in component state, but it is never sent to any API call — no backend field for an auto-recharge threshold exists at all. The control looks fully functional.
  • gap "Edit payment method" pencil icon is a no-op. In the same modal, its onClick just calls onClose() — it doesn't open any edit flow. The real path to changing a card is the separate "Manage on Stripe" button elsewhere on the page (openBillingPortal(), a real POST /stripe/portal call).
  • note The client deliberately recomputes true overage/remaining figures rather than trusting the backend's own overage_usd field directly — that field is server-side capped at the owner's overage limit for invoicing purposes and would otherwise silently under-report once usage exceeds the cap. If this page's math and an invoice's math ever look inconsistent, that divergence is expected, not a bug — documented in-code with an explicit comment.
  • ENTERPRISE_INTERMAX (2_147_483_647, i.e. int32 max) is used as an effective "no limit" sentinel for Enterprise credit displays — worth knowing if a raw number like that ever surfaces somewhere it shouldn't.
