## 24. Provider Pattern

> Context makes data available to a whole subtree without prop drilling. Split contexts by how often they change; for high-frequency state, reach for a store such as Zustand.

### Definition
A **provider** is a component that owns a value (state, config, a service) and exposes it to every descendant through React Context. Consumers read it with a hook (`useTheme()`), without the value being threaded through each intermediate component's props.

Context is a **delivery mechanism**, not a state manager. It answers "how does this value reach deep components?", not "how is it updated efficiently?". Every consumer re-renders when the context value changes by reference, which is the source of most provider problems.

### Key properties

**1. Providers are Client Components**
- `createContext`, `useState` and `useContext` / `use(Context)` need `"use client"`. Server Components cannot read context.
- Put the provider in its own client file and wrap `{children}`; children passed from a Server Component stay server-rendered.

**2. Place providers as deep as possible**
- Wrap only the subtree that needs the value (principle 6). A provider at the root forces everything under it to be considered for client re-renders when the value changes.
- Truly global values (theme, session, locale) belong in the root layout.

**3. Split by change frequency**
- Static or rarely changing (theme, locale, feature flags, current user) in one context.
- Frequently changing (form values, selection, live counters) in another, or not in context at all.
- Split **state** from **dispatch/actions**: components that only trigger actions then do not re-render on state changes.

**4. Consumers go through a typed hook**
- Never export the raw context. Export a hook that throws a clear error when used outside the provider.

### When to use what
| Situation | Use |
|---|---|
| A value used by many components, changes rarely | Context |
| A value used by one subtree, changes often | Local state plus composition (`children`) |
| Server data shared across the page | Fetch in Server Components; dedupe with `React.cache` (principle 6) |
| Fast-changing client state read by many distant components | Zustand (or `useSyncExternalStore`, Jotai) |
| Server cache of API data on the client | TanStack Query / SWR |
| Shareable, bookmarkable state | URL (`searchParams`) |

### Practical patterns in Next.js (TypeScript)

**Typed context with a safe hook**
```tsx
// context/theme-context.tsx
"use client";
import { createContext, use, useMemo, useState, type ReactNode } from "react";

type Theme = "light" | "dark";
type ThemeValue = { theme: Theme; setTheme: (t: Theme) => void };

const ThemeContext = createContext<ThemeValue | null>(null);

export function ThemeProvider({ initial, children }: { initial: Theme; children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>(initial);
  const value = useMemo(() => ({ theme, setTheme }), [theme]);
  return <ThemeContext value={value}>{children}</ThemeContext>;
}

export function useTheme() {
  const ctx = use(ThemeContext);
  if (!ctx) throw new Error("useTheme must be used inside <ThemeProvider>");
  return ctx;
}
```
In React 19 `<Context>` can be rendered directly as the provider (`<Context.Provider>` is still supported), and `use(Context)` replaces `useContext` and may be called conditionally. With the React Compiler on, the `useMemo` is optional, but a stable value reference is still the goal.

**Split state from actions**
```tsx
const CountStateContext = createContext<number>(0);
const CountActionsContext = createContext<{ inc: () => void } | null>(null);

export function CountProvider({ children }: { children: ReactNode }) {
  const [count, setCount] = useState(0);
  const actions = useMemo(() => ({ inc: () => setCount((c) => c + 1) }), []);
  return (
    <CountActionsContext value={actions}>
      <CountStateContext value={count}>{children}</CountStateContext>
    </CountActionsContext>
  );
}
```
A button that only calls `inc` reads the actions context, whose value never changes, so it does not re-render when `count` does.

**Compose providers in one client file, wrap `children`**
```tsx
// app/providers.tsx
"use client";
export function Providers({ children }: { children: ReactNode }) {
  return (
    <ThemeProvider initial="light">
      <QueryProvider>{children}</QueryProvider>
    </ThemeProvider>
  );
}
// app/layout.tsx (Server Component)
<body><Providers>{children}</Providers></body>
```
Server Components passed as `children` stay on the server even though the provider is a client component.

**Per-request Zustand store (App Router safe)**
```tsx
// stores/cart-store.ts
import { createStore } from "zustand/vanilla";
export type CartState = { items: string[]; add: (id: string) => void };
export const createCartStore = (init: Partial<CartState> = {}) =>
  createStore<CartState>()((set) => ({ items: [], add: (id) => set((s) => ({ items: [...s.items, id] })), ...init }));

// stores/cart-provider.tsx
"use client";
import { createContext, use, useRef } from "react";
import { useStore } from "zustand";

const CartContext = createContext<ReturnType<typeof createCartStore> | null>(null);

export function CartProvider({ children, initial }: { children: ReactNode; initial?: Partial<CartState> }) {
  const ref = useRef<ReturnType<typeof createCartStore>>(null);
  if (!ref.current) ref.current = createCartStore(initial);
  return <CartContext value={ref.current}>{children}</CartContext>;
}

export function useCart<T>(selector: (s: CartState) => T): T {
  const store = use(CartContext);
  if (!store) throw new Error("useCart must be used inside <CartProvider>");
  return useStore(store, selector);
}
```
A module-level store would be shared between users on the server. Creating the store per request and handing it down through context avoids cross-request leaks, and selectors (`useCart((s) => s.items.length)`) re-render a component only when that slice changes.

### Rules of thumb
1. **Context for low-frequency, wide-reach values** (theme, locale, session, flags).
2. **Split by change rate**, and split state from actions.
3. **Keep the value reference stable** (`useMemo` or the React Compiler); never pass a fresh object literal inline in a provider whose parent re-renders often.
4. **Wrap `{children}`**; do not render the whole subtree inside the provider component.
5. **Export a hook, not the context**, and throw outside the provider.
6. **High-frequency state goes to a store with selectors**, not context.
7. **Prefer composition over context** when only two or three levels are involved.
8. **Initialise from the server**: pass server data into the provider as props rather than refetching on the client.

### Anti-patterns
- One giant `AppContext` holding user, theme, cart, modals and form state; every change re-renders every consumer.
- Putting mouse position, scroll offset, typing state or timers in context.
- An inline value (`value={{ a, b }}`) rebuilt on every provider render.
- Using context to avoid passing props two levels, when `children` would do.
- A module-level Zustand or Redux store on the server, shared between requests and users.
- Reading `window` or `localStorage` during provider render, causing hydration mismatches.
- Providers that fetch data on mount in a Client Component what a Server Component could pass in.
- Consumers that destructure the whole context when they need one field.

### Industry best practices
- **Colocate providers with their feature** and mount them at the lowest common ancestor; keep only global concerns in the root layout.
- **Provide a safe default or throw**: a typed hook with an explicit error beats a silent `undefined`.
- **Memoise provider values**, or rely on the React Compiler, and verify with React DevTools "Highlight updates".
- **Use selectors with stores** (`useStore(store, s => s.x)`) so components subscribe to slices; use `useShallow` when selecting multiple fields.
- **Create stores per request** in Next.js and initialise them with server-fetched data; do not mutate a module-level store from Server Components.
- **Handle persistence and hydration** deliberately: Zustand `persist` needs `skipHydration` or a client-only rehydrate step to avoid server/client mismatches.
- **Keep server state out of context and client stores** when a query library exists; let TanStack Query or SWR own cache, retries and invalidation.
- **Order providers by dependency** (a provider that reads another goes inside it) and compose them in one `Providers` file.
- **Test with a custom render helper** that wraps the providers, and test the hook error path.
- **Document each context**: what it holds, update frequency, and who may write to it.
- **Avoid nested identical providers** unless you intend to override for a subtree (theme override, form scopes).

### Things to avoid
- Context as a replacement for a state library under high update rates.
- Mixing unrelated concerns in one context to "save providers".
- Mutating context values in place instead of updating state.
- Exposing `setX` for everything; expose intent-named actions.
- Using `"use client"` on the layout just to mount a provider; extract a small `Providers` client component.
- Relying on `React.memo` to stop context-driven renders (it does not).
- Storing derived values in context; derive them in consumers or selectors.
- Reading context in a Server Component (not possible) or working around it with globals.
- Putting secrets or server-only objects in a provider value; it serialises to the client.

### Checklist
- [ ] Each context has one concern and a documented update frequency.
- [ ] State and actions are split where consumers differ.
- [ ] Provider value is stable; no inline object literals.
- [ ] A typed hook guards against use outside the provider.
- [ ] Providers sit as deep as their consumers allow; the layout stays a Server Component.
- [ ] High-frequency state uses a store with selectors, created per request.
- [ ] No server-only data or secrets in provider values.
