## 22. Container / Presentation

> One component fetches data and holds state; the other is a pure render function of props. Swap the data source without touching the UI.

### Definition
A **container** knows where data comes from (a server fetch, an API client, a store, a URL) and what happens on events. A **presentational** component knows only how to draw what it is given and how to report user intent through callbacks. The container passes data down; the presentational component passes events up. This is principle 13 applied at the component boundary.

Dan Abramov, who popularised the split, later noted it is not a rule: hooks and Server Components give the same separation with less ceremony. Treat it as a **separation of concerns**, not as two mandatory file types.

### Key properties

**1. Presentation is a pure function of props**
- Same props, same output. No fetching, no router, no context reads, no global store in a presentational component.
- Everything it needs arrives as props: data, loading/empty/error flags (or slots), and `onX` callbacks.

**2. The container owns data and behaviour**
- It fetches, derives, handles mutations, and decides what to pass down.
- It stays thin: no markup beyond wiring.

**3. The data source is swappable**
- Real API, mock, fixture or Storybook args all feed the same presentational component.
- Moving from `fetch` to a Server Action, SWR or TanStack Query changes the container only.

**4. Testing splits cleanly**
- Presentation: render with props in Storybook or a unit test, covering every state (loading, empty, error, long text, many items).
- Container: test data wiring with mocked data functions; no pixel assertions.

### How this maps onto the App Router
| Role | Typical form | Server or client |
|---|---|---|
| Container | `page.tsx`, `layout.tsx`, or an async Server Component that awaits data | Server (default) |
| Container (interactive) | A client component using a custom hook (`useAgents()`), SWR or TanStack Query | Client |
| Presentation | A plain function component taking typed props | Server-safe if it has no state; client if it needs one |

The server container is the modern default: it fetches next to the data, ships no fetch code to the browser, and passes serialisable props down. A client container is for live data (polling, websockets, optimistic UI).

### Practical patterns in Next.js (TypeScript)

**Server container, presentational child**
```tsx
// app/(app)/agents/page.tsx   container: fetch + assemble, no markup
import { listAgents } from "@/lib/data/agents";
import { AgentList } from "@/components/AgentList";

export default async function Page() {
  const agents = await listAgents();
  return <AgentList agents={agents} />;
}
```
```tsx
// components/AgentList/index.tsx   presentation: props in, JSX out
import type { Agent } from "@/lib/types";

type Props = { agents: Agent[] };

export function AgentList({ agents }: Props) {
  if (agents.length === 0) return <p className="text-muted-foreground">No agents yet.</p>;
  return (
    <ul className="divide-y">
      {agents.map((a) => (
        <li key={a.id} className="py-2">{a.name}</li>
      ))}
    </ul>
  );
}
```
A function prop cannot cross from a Server Component to a Client Component (except a Server Action). If the view needs interaction, make that part its own client leaf (principle 12).

**Client container with a hook**
```tsx
"use client";
import { useAgents } from "@/hooks/useAgents";
import { AgentList } from "./AgentList";
import { AgentListSkeleton } from "./AgentListSkeleton";

export function AgentListContainer() {
  const { data, error, isLoading } = useAgents();
  if (isLoading) return <AgentListSkeleton />;
  if (error) return <p role="alert">Could not load agents.</p>;
  return <AgentList agents={data ?? []} />;
}
```
The hook is the real container logic; the component is glue. Hooks replace the class-based containers of the original pattern.

**Presentation states as a discriminated union**
```tsx
type ListState =
  | { status: "loading" }
  | { status: "error"; message: string }
  | { status: "ready"; items: Agent[] };

export function AgentListView({ state }: { state: ListState }) {
  switch (state.status) {
    case "loading": return <AgentListSkeleton />;
    case "error": return <p role="alert">{state.message}</p>;
    case "ready": return <AgentList agents={state.items} />;
  }
}
```
Impossible combinations (`loading` and `error` at once) cannot be expressed, and Storybook gets one story per state.

**Storybook with plain props**
```tsx
// AgentList.stories.tsx
export const Empty: Story = { args: { agents: [] } };
export const Many: Story = { args: { agents: Array.from({ length: 50 }, makeAgent) } };
```
No providers, no network mocking: that is the payoff of the split.

### Rules of thumb
1. **Presentation imports no data layer.** If it imports `fetch`, a store, `useRouter` or a context, it is a container.
2. **Pass data, not sources.** Props are values (`agents`), not fetch functions or store handles.
3. **Server container first.** Reach for a client container only when the data must change in the browser.
4. **Split on the second reason to change**, not by default. A 20-line component that fetches and renders needs no split.
5. **Model every state** (loading, empty, error, ready) as props or a union so each can be rendered in isolation.
6. **Keep containers boring.** Logic worth testing belongs in a hook or a plain function.

### Anti-patterns
- Splitting every component into `FooContainer` and `FooView` files out of habit, doubling the file count for no gain.
- A presentational component that quietly reads context or the router, so it breaks in Storybook.
- Containers that contain markup and styling, defeating the separation.
- Passing the entire fetched entity or a query object down "just in case" instead of the fields the view needs.
- Making a whole page a client container to fetch data a Server Component could fetch.
- Presentational components holding server data in `useState` copies.

### Industry best practices
- **Prefer hooks for logic reuse and Server Components for data**; keep class-era "container classes" out of new code.
- **Type the presentational contract tightly** with explicit prop types and discriminated unions for state; export the prop type for stories and tests.
- **Keep presentational components server-safe by default** (no hooks, no browser APIs) so they render in either environment.
- **Keep UI-only state** (open/closed, hover, active tab) inside the presentational component; it is not "data" and does not belong in the container.
- **One story per state** in Storybook (loading, empty, error, overflow, long text); use stories as the visual regression suite.
- **Name callbacks by intent** (`onSelect`, `onRetry`), not implementation (`setSelected`).
- **Use Suspense and `loading.tsx` for initial loading UI** in server containers, so the presentation needs no `isLoading` prop for the first load.
- **Do the mapping from API shape to view model in the container** (or a mapper function), so API changes do not ripple into the UI.
- **Colocate** the view, its stories and its tests; keep the container next to the route that needs it.
- **Avoid contract drift**: generate API types from the schema (OpenAPI or similar) and map them to view props in one place.

### Things to avoid
- Fetching inside presentational components "just this once".
- A container layer that only forwards props unchanged (an empty wrapper).
- Passing plain function props from a Server Component to a Client Component (not serialisable).
- Passing whole ORM or database rows (with secrets or extra fields) across the server/client boundary.
- Duplicating loading and error rendering in every container; centralise it with `Suspense` plus `error.tsx` or a shared state component.
- Prop drilling more than three levels to reach a presentational leaf; use composition or a provider (principle 24).
- Testing presentation through the network (MSW) when props would do.
- Mocking at the wrong level: mock the data function the container calls, not the presentational component.

### Checklist
- [ ] Each view renders correctly from props alone, in Storybook, with no providers.
- [ ] Containers hold no layout or styling beyond wiring.
- [ ] Every state (loading, empty, error, ready) has a story.
- [ ] Server container by default; a client container is justified by live data.
- [ ] Props are typed, minimal and serialisable when they cross the server/client boundary.
- [ ] Swapping the data source requires no change to the view file.

### In this codebase
- `src/app/(app)/**/page.tsx` files are the natural server containers; `src/components/<Name>/` folders hold the views.
- Several pages are client components that fetch through `src/lib/api/*`; those are client containers and are candidates to move data fetching to a Server Component where the data is not live.
- Check that components in `src/components/` do not import from `src/context/` or `src/lib/api/` directly; the ones that do are containers in disguise.
