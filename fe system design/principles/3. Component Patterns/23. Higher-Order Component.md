## 23. Higher-Order Component

> A function that takes a component and returns an enhanced one, injecting behaviour (auth, analytics, error handling) uniformly.

### Definition
A Higher-Order Component (HOC) is a function `(Component) => EnhancedComponent`. It wraps the input, adds behaviour or props around it, and renders it. `withAuth(Page)`, `withAnalytics(Button)` and `withErrorBoundary(Widget)` are typical shapes.

HOCs were the main reuse mechanism before hooks. Today they are a **niche tool**: hooks cover logic reuse, Server Components cover data and auth, and composition (`children`) covers wrapping. A HOC still earns its place when behaviour must wrap the **whole component from outside** (an error boundary, a provider, a render-time gate) and you want to apply it uniformly.

### Key properties

**1. Behaviour is injected from outside**
- The wrapped component stays unaware of the concern; it receives extra props or is simply gated.
- Good fits: error boundaries (which must be class components), page-view analytics, feature-flag gates, legacy class-component interop.

**2. Props pass through untouched**
- A HOC must forward every prop it does not consume, and must not silently rename or drop any.
- Injected props should be clearly named or namespaced to avoid collisions with the caller's props.

**3. The static contract is preserved**
- The enhanced component keeps the wrapped component's prop types (minus injected ones) and a useful `displayName` for DevTools.

**4. Composition order matters**
- `withA(withB(C))` differs from `withB(withA(C))`. The outer HOC runs first on the way in.

### Where HOCs sit in the App Router
| Need | Prefer | HOC? |
|---|---|---|
| Reuse stateful logic | Custom hook | No |
| Auth on a route | Server-side check in `layout.tsx` / `page.tsx` / data layer, plus `proxy.ts` for early redirects | No |
| Wrapper UI (layout, chrome) | Composition with `children` | No |
| Error boundary around a client widget | `error.tsx` per segment, or a boundary wrapper | Sometimes |
| Cross-cutting client behaviour (analytics, flags) on many components | Hook, or a HOC when wrapping from outside is needed | Sometimes |

HOCs are client-side in practice: they run during render and typically need hooks or classes, so they live in `"use client"` files and cannot add client behaviour to a Server Component.

### Practical patterns in Next.js (TypeScript)

**Typed HOC that injects a prop and forwards the rest**
```tsx
"use client";
import type { ComponentType } from "react";
import { useFlag } from "@/hooks/useFlag";

type Injected = { flagEnabled: boolean };

export function withFlag<P extends Injected>(Component: ComponentType<P>, flag: string) {
  function WithFlag(props: Omit<P, keyof Injected>) {
    const flagEnabled = useFlag(flag);
    return <Component {...(props as P)} flagEnabled={flagEnabled} />;
  }
  WithFlag.displayName = `withFlag(${Component.displayName ?? Component.name ?? "Component"})`;
  return WithFlag;
}
```
The caller's props are `Omit<P, "flagEnabled">`; the wrapped component additionally receives `flagEnabled`.

**Guarding without a HOC: the server-side check**
```tsx
// app/(app)/billing/page.tsx
import { redirect } from "next/navigation";
import { getSession } from "@/lib/auth/session";

export default async function Page() {
  const session = await getSession();
  if (!session) redirect("/login");
  return <BillingView user={session.user} />;
}
```
For authentication and authorisation this replaces a `withAuth` HOC: it runs on the server, cannot be bypassed by client code, and ships no JS. Repeat the check in every Server Action and Route Handler; never rely on a client-side guard or on `proxy.ts` alone.

**Error boundary as a wrapper**
```tsx
"use client";
import { Component, type ComponentType, type ErrorInfo, type ReactNode } from "react";

class Boundary extends Component<{ fallback: ReactNode; children: ReactNode }, { failed: boolean }> {
  state = { failed: false };
  static getDerivedStateFromError() { return { failed: true }; }
  componentDidCatch(error: Error, info: ErrorInfo) { reportError(error, info); }
  render() { return this.state.failed ? this.props.fallback : this.props.children; }
}

export function withErrorBoundary<P extends object>(C: ComponentType<P>, fallback: ReactNode) {
  return function Wrapped(props: P) {
    return <Boundary fallback={fallback}><C {...props} /></Boundary>;
  };
}
```
Where a segment boundary exists, prefer `error.tsx`; use the wrapper for widgets that must fail independently inside a page.

**Prefer a wrapper component when it is enough**
```tsx
// Same effect as withAnalytics(Page), with no HOC
export function TrackedPage({ name, children }: { name: string; children: ReactNode }) {
  usePageView(name);
  return <>{children}</>;
}
```

### Rules of thumb
1. **Hook first.** If the behaviour is logic (state, effects), write a hook; if it wraps UI, write a component taking `children`. Use a HOC only when neither fits.
2. **Never create a HOC inside render.** Apply it once at module scope; otherwise a new component type is created every render and state is lost.
3. **Forward all props** and type the injected ones separately from the caller's.
4. **Set `displayName`** (`withX(Name)`) for readable DevTools and error stacks.
5. **Do security on the server.** A HOC guard is UX, not protection.
6. **Keep a HOC to one concern**; stack several rather than building one that does everything.

### Anti-patterns
- `withAuth` as the only auth control on a route; the data is still reachable through the API or a Server Action.
- Applying a HOC inside a component body or a `map` (`const Enhanced = withX(C)` in render).
- A HOC that silently overrides a prop with the same name as an injected one.
- Deep HOC pyramids (`withA(withB(withC(withD(X))))`): wrapper hell in DevTools, unclear order, hard to type.
- Using a HOC to share what a custom hook shares more simply.
- Mutating the wrapped component instead of wrapping it.

### Industry best practices
- **Choose hooks, then composition, then HOCs** for new code; the React docs teach hooks and composition as the primary reuse tools.
- **Keep refs working**: in React 19 `ref` is a regular prop for function components, so it passes through `{...props}`; for older code, use `forwardRef`.
- **Copy static members** (`hoist-non-react-statics`) when wrapping components that expose statics.
- **Type with generics**: `P extends object`, and `Omit<P, keyof Injected>` for the public props when the HOC supplies props itself.
- **Name HOCs `withX`**, keep each in its own file, and test forwarding, injection and `displayName`.
- **Authorise on the server in the data layer** (a `verifySession()` helper called by pages, actions and handlers); use `proxy.ts` only for optimistic redirects.
- **Use class wrappers only for error boundaries** (`componentDidCatch`) and report errors to your telemetry from there.
- **Keep cross-cutting HOCs pure**: no hidden network calls or side effects outside effects.
- **Prefer a render prop or slot** when the wrapped component should decide how the injected value is displayed.
- **Document injected props and ordering rules** at the top of the HOC file.
- **Measure before wrapping everything**: each wrapper is an extra component in the tree and another place for bugs.

### Things to avoid
- Wrapping Server Components with a client HOC (it forces client rendering or fails to compile).
- Relying on a HOC to hide protected UI as a security measure.
- Prop collisions: injecting a prop the caller may also pass, without naming or documenting it.
- Losing `ref`, `displayName`, statics or generics through the wrapper.
- Copying props into state inside the HOC.
- Using HOCs to pass data a hook could read in the component that needs it.
- Re-creating the enhanced component on every render.
- Mixing several concerns (auth, analytics, theming) in one HOC.

### Checklist
- [ ] A hook or composition was considered and rejected for a stated reason.
- [ ] The HOC is applied at module scope, not in render.
- [ ] All unconsumed props are forwarded; injected props are typed and documented.
- [ ] `displayName` is set.
- [ ] No security decision depends on the HOC alone; the server re-checks.
- [ ] The HOC lives in a `"use client"` file when it uses hooks or classes.
- [ ] Wrapping order is documented where more than one HOC is stacked.
