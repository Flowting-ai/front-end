## 25. Compound Components

> Sub-components share implicit state while the consumer controls layout. Like `<select>` and `<option>`: the parts only make sense together, and they coordinate through context.

### Definition
A compound component is a **family of components** exported together (`Tabs`, `Tabs.List`, `Tabs.Trigger`, `Tabs.Content`). The root owns state (which tab is active, whether the menu is open) and shares it with the parts through context. The consumer decides **which parts to render, in what order and with what markup**, without wiring props between them.

This is how Radix UI, Base UI, Headless UI and shadcn/ui stay flexible: behaviour and accessibility live in the family, structure and styling stay with the caller.

### Key properties

**1. Implicit state sharing**
- The root holds state; parts read it from context. No `activeTab` or `onChange` threaded through every child.

**2. The consumer owns the layout**
- Parts can be reordered, omitted, wrapped or interleaved with other elements.
- Replaces a prop-heavy config API (`<Tabs items={[...]} showIcons stickyHeader />`).

**3. Parts are meaningful only inside the root**
- A part used outside its root throws a clear error from its context hook.

**4. Accessibility is built in**
- The family wires `role`, `aria-*`, ids, roving focus and keyboard handling so the consumer cannot forget them.

**5. Controlled and uncontrolled**
- Support both: `defaultValue` for uncontrolled use, `value` plus `onValueChange` for controlled use.

### Compound versus alternatives
| Approach | Good for | Cost |
|---|---|---|
| Config props (`items=[...]`) | Fixed, simple, data-driven lists | Prop explosion as variants grow |
| Boolean flags | Nothing past one or two | Mutually exclusive combos, boolean traps |
| Slots (`header`, `footer` props) | A few named regions with no shared state | No coordination between regions |
| **Compound components** | Coordinated state, flexible structure (tabs, accordion, menu, dialog, select) | More files, context boundary, client component |
| Render props | Exposing internal state to one custom child | Nesting, less readable |

### Practical patterns in Next.js (TypeScript)

**A compound component built with context (client file)**
```tsx
// components/Tabs/index.tsx
"use client";
import { createContext, use, useId, useState, type ComponentProps, type ReactNode } from "react";
import { cn } from "@/lib/utils";

type TabsCtx = { value: string; setValue: (v: string) => void; baseId: string };
const TabsContext = createContext<TabsCtx | null>(null);

function useTabs() {
  const ctx = use(TabsContext);
  if (!ctx) throw new Error("Tabs parts must be rendered inside <Tabs>");
  return ctx;
}

type RootProps = { defaultValue: string; value?: string; onValueChange?: (v: string) => void; children: ReactNode };

function Tabs({ defaultValue, value, onValueChange, children }: RootProps) {
  const [inner, setInner] = useState(defaultValue);
  const baseId = useId();
  const current = value ?? inner;
  const setValue = (v: string) => { if (value === undefined) setInner(v); onValueChange?.(v); };
  return <TabsContext value={{ value: current, setValue, baseId }}>{children}</TabsContext>;
}

function List({ className, ...rest }: ComponentProps<"div">) {
  return <div role="tablist" className={cn("flex gap-2 border-b", className)} {...rest} />;
}

function Trigger({ value, className, ...rest }: ComponentProps<"button"> & { value: string }) {
  const t = useTabs();
  const selected = t.value === value;
  return (
    <button
      role="tab"
      id={`${t.baseId}-tab-${value}`}
      aria-selected={selected}
      aria-controls={`${t.baseId}-panel-${value}`}
      tabIndex={selected ? 0 : -1}
      onClick={() => t.setValue(value)}
      className={cn("px-3 py-2 aria-selected:border-b-2", className)}
      {...rest}
    />
  );
}

function Content({ value, ...rest }: ComponentProps<"div"> & { value: string }) {
  const t = useTabs();
  if (t.value !== value) return null;
  return <div role="tabpanel" id={`${t.baseId}-panel-${value}`} aria-labelledby={`${t.baseId}-tab-${value}`} {...rest} />;
}

Tabs.List = List;
Tabs.Trigger = Trigger;
Tabs.Content = Content;
export { Tabs };
```
```tsx
// Consumer: owns the layout
<Tabs defaultValue="usage">
  <Tabs.List>
    <Tabs.Trigger value="usage">Usage</Tabs.Trigger>
    <Tabs.Trigger value="billing">Billing</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Content value="usage"><UsageChart /></Tabs.Content>   {/* may be a Server Component */}
  <Tabs.Content value="billing"><BillingTable /></Tabs.Content>
</Tabs>
```
Content passed as children can be a Server Component, so only the small interactive family ships client JS. A production tab list also needs arrow-key roving focus; prefer Radix or Base UI for that rather than rebuilding it.

**Compose over a library: wrap Radix with Tailwind**
```tsx
"use client";
import * as TabsPrimitive from "@radix-ui/react-tabs";
import { cn } from "@/lib/utils";

export const Tabs = TabsPrimitive.Root;
export function TabsList({ className, ...p }: React.ComponentProps<typeof TabsPrimitive.List>) {
  return <TabsPrimitive.List className={cn("inline-flex gap-1 rounded-md bg-muted p-1", className)} {...p} />;
}
```
This is the shadcn/ui approach: the library provides state, ARIA and keyboard behaviour; the wrapper adds Tailwind classes and design tokens.

**Dot notation versus named exports**
`Tabs.List` is easy to discover, but a namespace object blocks tree-shaking of unused parts and cannot be used across the server/client boundary from a Server Component (a `"use client"` module exports client references; dot access on them from a Server Component does not work reliably). Named exports (`Tabs`, `TabsList`, `TabsTrigger`) are the safer default in the App Router and what shadcn/ui and Radix use.

### Rules of thumb
1. **Reach for compound components** when you have 3 to 5 flags, or parts that must coordinate (open state, selected item, ids).
2. **Name exports `Thing`, `ThingPart`** (`Dialog`, `DialogTrigger`, `DialogContent`) for tree-shaking and server/client safety.
3. **Own accessibility in the family**: roles, ids, labels, focus and keys come from the root and parts.
4. **Support controlled and uncontrolled** use.
5. **Fail loudly** outside the root with a descriptive error.
6. **Spread native props** (`ComponentProps<"div">`) onto each part and merge `className` with `cn`.
7. **Keep context private** to the family; export parts, not the context.
8. **Keep it client-side and small**: state in a `"use client"` file, content passed as `children`.

### Anti-patterns
- Cloning and injecting props into children with `React.Children.map` and `cloneElement` (breaks with wrappers and fragments; fragile).
- Requiring strict child order or count through runtime checks.
- A compound family for something with no shared state (a card with header and body needs only plain components).
- Reimplementing menu, dialog, combobox or tabs keyboard behaviour by hand.
- Parts that secretly depend on sibling markup or class names.
- Exposing the raw context so outsiders mutate internal state.
- Mixing config props and compound parts for the same thing (`<Tabs items=... >` plus `<Tabs.Trigger>`).

### Industry best practices
- **Start from an accessible headless library** (Radix UI, Base UI, Headless UI, React Aria) and style it; do not build focus traps, typeahead or roving tabindex yourself.
- **Use `useId`** for aria relationships (`aria-controls`, `aria-labelledby`) so ids are stable between server and client.
- **Follow WAI-ARIA Authoring Practices** for the pattern (tabs, accordion, combobox, menu) and test it with keyboard only and a screen reader.
- **Provide `data-state` and `data-*` attributes** (`data-state="open"`) so Tailwind can style states (`data-[state=open]:rotate-180`) without extra props.
- **Support `asChild` or a polymorphic `as`** (principle 26) on parts that must render as a different element, such as a link inside a menu item.
- **Keep the context value small and stable** (principle 24); store `value` and stable callbacks, not whole objects that change each render.
- **Make parts optional** where possible; a Dialog should work with or without a Title, but warn in development when an accessible name is missing.
- **Ship stories for each composition** (default, controlled, disabled, with long content) and a test per keyboard interaction.
- **Type parts with native props** and add only the extra props they need, so wrappers inherit `aria-*`, `data-*` and event handlers.
- **Prefer slots/children for content**, props for state and behaviour (`value`, `disabled`, `onOpenChange`).

### Things to avoid
- Dot-notation namespaces exported from a `"use client"` file and used from Server Components.
- `cloneElement` and `Children.map` for state sharing.
- Losing ARIA relationships when consumers reorder or omit parts.
- Hiding inactive content with `display: none` when it should be unmounted, or the reverse, without considering forms, focus and SEO (`forceMount` style options exist for this).
- Over-engineering: building a compound API before two real usages.
- Putting styles in the root that parts cannot override.
- Server-side state or data fetching inside the family; keep it presentational and interactive only.
- Forgetting `"use client"` on the module that holds the context.

### Checklist
- [ ] Parts share state through a private context, with a guard hook that throws outside the root.
- [ ] Controlled and uncontrolled modes both work.
- [ ] Roles, ids and keyboard behaviour match the WAI-ARIA pattern (tested with keyboard).
- [ ] Native props are spread and `className` is merged on every part.
- [ ] Named exports, no cross-boundary dot notation.
- [ ] State attributes (`data-state`) are exposed for Tailwind variants.
- [ ] Content passes as `children`, so Server Components can sit inside.
