## 26. Polymorphic Components

> One component renders as different elements through an `as` prop (or `asChild`). Correct HTML semantics, no class explosion, and TypeScript generics keep the props type-safe.

### Definition
A polymorphic component keeps one visual and behavioural identity but lets the caller choose the underlying element or component: a `Button` that renders as `<a>`, a `Link` from Next.js, or a `<div>`; a `Text` that renders as `<h2>`, `<p>` or `<label>`. Styling lives once; semantics are picked per use.

Two mechanisms exist:
- **`as` prop**: `<Button as="a" href="/docs">`. The component renders the element type you name.
- **`asChild` (Radix `Slot`)**: `<Button asChild><Link href="/docs">Docs</Link></Button>`. The component merges its props and classes onto its single child.

### Key properties

**1. Semantics follow meaning, not looks**
- A link that looks like a button must be an `<a>` (navigates), a button must be `<button>` (acts). `role="button"` on a `div` is not a substitute.
- Headings keep a correct outline (`h1` to `h6`) while sharing a visual scale.

**2. Styling is written once**
- Variants live in the component (`cva`); the element is a separate decision. No `ButtonLink`, `ButtonAnchor`, `ButtonDiv` duplicates.

**3. Props are type-safe per element**
- `as="a"` allows `href`; `as="button"` allows `type` and `disabled`; `as="div"` allows neither.
- TypeScript generics derive the allowed props from the chosen element.

**4. Refs and events still work**
- The `ref` and handlers reach the real DOM node, whichever element renders.

### `as` versus `asChild`
| | `as` prop | `asChild` / `Slot` |
|---|---|---|
| Call site | `<Button as="a" href="/x">` | `<Button asChild><Link href="/x"/></Button>` |
| Typing | Generic over `ElementType`; props follow the element | Child's own types apply; no generic needed |
| Custom components (Next `Link`, router links) | Works, but typing the custom component's props is harder | Natural: the child is already typed |
| Extra inner nodes (icon, spinner) | Easy | Needs `Slottable` or restructuring |
| Used by | Chakra, MUI, Primer, many in-house systems | Radix, shadcn/ui, Base UI (`render` prop) |

Pick one per design system and apply it consistently. In a Radix / shadcn / Next.js codebase, `asChild` is the usual choice; use a typed `as` for primitives with a small fixed set of elements (`Text`, `Heading`, `Stack`).

### Practical patterns in Next.js (TypeScript)

**Typed `as` prop with generics (React 19, `ref` is a normal prop)**
```tsx
import type { ComponentPropsWithRef, ElementType } from "react";
import { cn } from "@/lib/utils";

type TextOwnProps<E extends ElementType> = { as?: E };
type TextProps<E extends ElementType> = TextOwnProps<E> &
  Omit<ComponentPropsWithRef<E>, keyof TextOwnProps<E>>;

export function Text<E extends ElementType = "p">({ as, className, ...rest }: TextProps<E>) {
  const Component: ElementType = as ?? "p";
  return <Component className={cn("text-base text-foreground", className)} {...rest} />;
}

<Text>Paragraph</Text>
<Text as="label" htmlFor="email">Email</Text>      // htmlFor allowed
<Text as="a" href="/docs">Docs</Text>              // href allowed
<Text as="span" href="/docs">x</Text>              // type error: span has no href
```
`Omit<..., keyof OwnProps>` stops the element's props from clashing with the component's own. `ComponentPropsWithRef` includes `ref`, which is a regular prop in React 19; in older React use `ComponentPropsWithoutRef` plus `forwardRef`.

**`asChild` with Radix Slot and `cva`**
```tsx
import { Slot } from "@radix-ui/react-slot";
import { cva, type VariantProps } from "class-variance-authority";

const button = cva("inline-flex h-10 items-center rounded-md px-4 font-medium focus-visible:outline-2", {
  variants: { intent: { primary: "bg-brand text-white", ghost: "hover:bg-muted" } },
  defaultVariants: { intent: "primary" },
});

type Props = React.ComponentProps<"button"> & VariantProps<typeof button> & { asChild?: boolean };

export function Button({ asChild, intent, className, ...rest }: Props) {
  const Comp = asChild ? Slot : "button";
  return <Comp className={button({ intent, className })} {...rest} />;
}

<Button>Save</Button>
<Button asChild><Link href="/billing">Billing</Link></Button>   // real <a>, client-side navigation
```
`Slot` merges the parent's props, `className` and event handlers onto the child and forwards the ref.

**Heading with a semantic level separate from its size**
```tsx
type Level = 1 | 2 | 3 | 4;
const sizes: Record<Level, string> = { 1: "text-3xl", 2: "text-2xl", 3: "text-xl", 4: "text-lg" };

export function Heading({ level, size, className, ...rest }: React.ComponentProps<"h2"> & { level: Level; size?: Level }) {
  const Tag = `h${level}` as "h1" | "h2" | "h3" | "h4";
  return <Tag className={cn("font-semibold", sizes[size ?? level], className)} {...rest} />;
}
```
Visual size and document outline are independent: `<Heading level={2} size={4}>` is an `h2` that looks small.

### Rules of thumb
1. **Choose the element for meaning first**: navigation is `a`, action is `button`, outline is `h1` to `h6`.
2. **Default to the most common element** (`button`, `p`, `div`) and make `as` the exception.
3. **Constrain `as` when only a few elements make sense** (`as?: "h1" | "h2" | "h3"`), instead of `ElementType` for everything.
4. **Derive props from the element** with `ComponentPropsWithRef<E>` and omit the component's own keys.
5. **Merge, do not replace** `className` (`cn` / `tailwind-merge`) and chain event handlers.
6. **Static Tailwind class strings in variants**; never build class names by concatenation.
7. **Use `asChild` for routing links**, so the real Next.js `Link` keeps prefetching and client navigation.

### Anti-patterns
- `<div onClick>` styled as a button instead of rendering `button` or `a`.
- A `variant="link"` button that still renders `<button>` and calls `router.push`.
- `as: any` or `as: string` that disables type checking.
- Duplicate components per element (`ButtonLink`, `ButtonDiv`) sharing copied classes.
- `as={Link}` with unresolved `href` typing by casting everything to `any`.
- Nested interactive elements (`<a><button/></a>`), invalid HTML and a keyboard trap.
- `Slot` with more than one child or a text-only child (it needs exactly one element).

### Industry best practices
- **Prefer the native element** (`button`, `a`, `h2`) over ARIA roles on generic elements; add `role` only when no native element fits.
- **Type with generics and `ElementType`**, default the parameter (`E extends ElementType = "button"`), and test the type contract (`// @ts-expect-error` cases).
- **Use `React.ComponentProps<"button">`** (React 19) for non-generic wrappers so every native attribute and `ref` works.
- **Forward `ref`** to the rendered element; in React 19 pass it as a normal prop, and rely on `forwardRef` only for older React.
- **Preserve accessibility on swap**: `disabled` does not work on `<a>`; use `aria-disabled` plus `tabIndex={-1}` and block the click.
- **Document the semantics rule** in the design system: when to use link versus button, heading levels per page region.
- **Use `asChild` to avoid wrapper elements** (no extra `div` between a menu item and its link), keeping the DOM and focus order clean.
- **Keep the polymorphism shallow**: a primitive layer (`Text`, `Box`, `Button`) is polymorphic; feature components are not.
- **Watch the TypeScript cost**: deeply generic polymorphic types slow the compiler and produce unreadable errors; constrain them where you can.
- **Pair with `cva` and design tokens** so a single variant map yields consistent styles for every rendered element.
- **Lint for semantics**: `eslint-plugin-jsx-a11y` rules (`anchor-is-valid`, `click-events-have-key-events`, `no-static-element-interactions`).

### Things to avoid
- Making every component polymorphic by default; it widens the API and the type surface for no gain.
- Allowing `as` values that break the component's role (a `Button` as `ul`).
- Spreading arbitrary props onto the DOM element that are not valid for it, such as unknown boolean props producing React warnings.
- Using `as="a"` without `href`.
- Passing `as` as a dynamic string from user input (a rendering-injection risk when the value is not from a fixed allow-list).
- `Slot` children that do not forward `ref` or spread props (custom components must pass `...props` through to a DOM node).
- Heading levels chosen for size, producing a broken outline (`h4` before `h2`).
- Dynamic Tailwind classes assembled from the element name.

### Checklist
- [ ] The rendered element matches the meaning: link for navigation, button for action, correct heading level.
- [ ] `as` is typed from the element, with a sensible default and a constrained set where possible.
- [ ] Props not valid for the chosen element are a compile error.
- [ ] `ref`, `className` merge and event handlers reach the rendered node.
- [ ] Links use `asChild` (or `as={Link}`) so Next.js navigation and prefetch still work.
- [ ] Disabled links use `aria-disabled`, not the `disabled` attribute.
- [ ] No `any` in the polymorphic types.

### In this codebase
- `@radix-ui/react-slot` is installed and `Slot` / `asChild` appears in about 55 files under `src/`, so `asChild` is the established polymorphism mechanism; keep using it for Button and link-like primitives rather than introducing a second `as` convention.

- Audit clickable `div`s and `button` elements that call `router.push`; these should be links.
