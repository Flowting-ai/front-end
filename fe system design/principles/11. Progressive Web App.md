## 11. Progressive Web App

> A web app that installs, works offline and sends push: service worker + manifest + HTTPS. Higher engagement than the browser tab. Skips app-store distribution friction.

### Definition
A **PWA** is an ordinary website that uses a set of web platform features to behave like an installed app. It is not a separate technology or framework; it is a checklist of capabilities layered on top of the app you already have, and it **progressively enhances**: browsers that lack a feature still get a normal working site.

The three pillars from the one-liner:

| Pillar | What it gives | Provided by |
|---|---|---|
| **Manifest** | Installability: name, icons, start URL, display mode, theme colours | `app/manifest.ts` (Next.js built-in) |
| **Service worker** | Offline support, caching strategies, push and background features | `public/sw.js` ([principle 10](10.%20Service%20Workers%20and%20Caching.md)) |
| **HTTPS** | Required for service workers, push and install; also trust and security | Hosting / CDN / TLS certificate |

Together they enable: **installing** to the home screen or desktop with its own window and icon, **offline or flaky-network** behaviour, and **web push notifications** that re-engage users when the app is closed.

### On the claims
- **"Higher engagement than the browser tab":** published case studies from companies that shipped PWAs report increases in sessions, time on site and conversions. Those are vendor-reported and depend heavily on the product; engagement gains come mostly from push re-engagement, the home-screen icon and faster, more reliable loads, not from the PWA label itself. Measure your own before assuming them.
- **"Skips app-store distribution friction":** true for distribution: ship with a normal deploy, no review queue, no store fees on web payments, one codebase, instant updates. Two caveats: on **iOS** web push works only for apps **installed to the home screen** (iOS/iPadOS 16.4+), and PWAs have less access to device APIs than native apps. Discoverability through store search is lost unless you also publish a wrapped version where stores allow it.

### Key properties

**1. Installable**
Chromium browsers show an install prompt when the app has a valid manifest (name or short name, icons including 192 px and 512 px, `start_url`, a `display` of `standalone`/`minimal-ui`/`fullscreen`) and is served over HTTPS. Per the Next.js docs you can trigger install prompts without offline support, so the service worker is not what makes an app installable in current browsers; verify the exact criteria per browser, as they change. Safari uses "Add to Home Screen" from the share menu and reads the manifest plus Apple-specific meta tags.

**2. Reliable (offline and flaky networks)**
- A service worker can serve an **offline fallback page**, cached app shell assets, or previously fetched read-only data.
- "Works offline" must be defined per feature. A chat app that needs a live backend can show history it already has and a clear "you are offline" state, but cannot generate new answers. Do not promise more than the architecture delivers.

**3. Re-engageable (push notifications)**
- **Web Push** uses the Push API plus the Notifications API. The browser vendor's push service delivers the message; your service worker receives the `push` event and shows the notification, even when no tab is open.
- Needs: the user's explicit permission, a **subscription** stored on your server, and **VAPID** keys (a public/private key pair identifying your server).
- Supported in Chromium browsers, Firefox, Safari 16+ on macOS 13+, and iOS/iPadOS 16.4+ for home-screen-installed apps.

**4. App-like presentation**
- `display: "standalone"` removes browser chrome; `theme_color` and `background_color` colour the title bar and splash screen.
- Needs good safe-area handling (`viewport-fit=cover`, `env(safe-area-inset-*)`), touch targets, and no reliance on browser UI (back button, address bar).

**5. Linkable and updatable**
- It is still a URL. Deep links and shares keep working; updates ship on deploy with no store review.
- Updates have the lifecycle issues from [principle 10](10.%20Service%20Workers%20and%20Caching.md): version the caches and prompt users to reload.

### Practical patterns in Next.js (TypeScript)

**1. The manifest (built in)**
```ts
// app/manifest.ts
import type { MetadataRoute } from "next";

export default function manifest(): MetadataRoute.Manifest {
  return {
    name: "Souvenir",
    short_name: "Souvenir",
    description: "AI workspace",
    start_url: "/",
    scope: "/",
    display: "standalone",
    background_color: "#ffffff",
    theme_color: "#000000",
    icons: [
      { src: "/icons/pwa-192.png", sizes: "192x192", type: "image/png" },
      { src: "/icons/pwa-512.png", sizes: "512x512", type: "image/png" },
      { src: "/icons/pwa-maskable-512.png", sizes: "512x512", type: "image/png", purpose: "maskable" },
    ],
  };
}
```
Next.js serves this at `/manifest.webmanifest` and links it automatically. Provide **PNG** icons (192 and 512, plus a **maskable** one that survives circular cropping); SVG-only is not enough for installability everywhere. Use the viewport export for theme colour per scheme:
```ts
// app/layout.tsx
import type { Viewport } from "next";

export const viewport: Viewport = {
  themeColor: [
    { media: "(prefers-color-scheme: light)", color: "#ffffff" },
    { media: "(prefers-color-scheme: dark)", color: "#000000" },
  ],
  viewportFit: "cover",
};
```

**2. Service worker + registration**
Use the versioned, allow-list service worker and the production-only registration component from [principle 10](10.%20Service%20Workers%20and%20Caching.md), and serve `/sw.js` with `no-cache` and a strict CSP.

**3. An offline route**
```tsx
// app/offline/page.tsx   Server Component, static, precached by the service worker
export default function OfflinePage() {
  return (
    <main>
      <h1>You are offline</h1>
      <p>Check your connection. Anything you already opened is still available.</p>
    </main>
  );
}
```
Keep it static and dependency-free so it can be precached and rendered with no network.

**4. Install prompt UX (custom)**
```tsx
"use client";
import { useEffect, useState } from "react";

type BeforeInstallPromptEvent = Event & {
  prompt: () => Promise<void>;
  userChoice: Promise<{ outcome: "accepted" | "dismissed" }>;
};

export function InstallButton() {
  const [evt, setEvt] = useState<BeforeInstallPromptEvent | null>(null);

  useEffect(() => {
    const onPrompt = (e: Event) => {
      e.preventDefault();                          // hold the event; show our own UI
      setEvt(e as BeforeInstallPromptEvent);
    };
    window.addEventListener("beforeinstallprompt", onPrompt);
    return () => window.removeEventListener("beforeinstallprompt", onPrompt);
  }, []);

  if (!evt) return null;                           // not supported (e.g. Safari) or already installed
  return (
    <button onClick={async () => { await evt.prompt(); setEvt(null); }}>
      Install app
    </button>
  );
}
```
`beforeinstallprompt` is Chromium-only. For iOS Safari show short "Share, then Add to Home Screen" instructions, and detect standalone mode with `matchMedia("(display-mode: standalone)")`. Ask at a meaningful moment, not on first load.

**5. Web push, end to end**
1. Generate VAPID keys once (`npx web-push generate-vapid-keys`). Public key is exposed to the client (`NEXT_PUBLIC_VAPID_PUBLIC_KEY`); the **private key stays server-side only**.
2. After a user gesture (never on page load), request permission and subscribe:
```tsx
"use client";

async function enablePush(publicKey: string) {
  const permission = await Notification.requestPermission();
  if (permission !== "granted") return;
  const reg = await navigator.serviceWorker.ready;
  const sub = await reg.pushManager.subscribe({
    userVisibleOnly: true,
    applicationServerKey: urlBase64ToUint8Array(publicKey),
  });
  await saveSubscription(sub.toJSON());            // Server Action or API call
}
```
3. **Store the subscription per user and device in a database.** (The Next.js example keeps it in a module variable only to keep the demo short; that does not survive restarts or multiple instances and must not be copied.)
4. Send from the server with the `web-push` package, and handle expired subscriptions (HTTP 404/410 means delete it):
```ts
"use server";
import webpush from "web-push";

webpush.setVapidDetails("mailto:ops@example.com", process.env.NEXT_PUBLIC_VAPID_PUBLIC_KEY!, process.env.VAPID_PRIVATE_KEY!);

export async function notifyUser(userId: string, payload: { title: string; body: string; url: string }) {
  for (const sub of await getSubscriptions(userId)) {
    try {
      await webpush.sendNotification(sub, JSON.stringify(payload));
    } catch (err) {
      if ((err as { statusCode?: number }).statusCode === 410) await removeSubscription(sub.endpoint);
    }
  }
}
```
5. The service worker shows it and handles clicks:
```js
// public/sw.js (additions)
self.addEventListener("push", (event) => {
  const data = event.data?.json() ?? {};
  event.waitUntil(
    self.registration.showNotification(data.title ?? "Souvenir", {
      body: data.body,
      icon: "/icons/pwa-192.png",
      data: { url: data.url ?? "/" },
    })
  );
});

self.addEventListener("notificationclick", (event) => {
  event.notification.close();
  event.waitUntil(clients.openWindow(event.notification.data.url));
});
```
Every push must show a visible notification (`userVisibleOnly: true`); browsers penalise or revoke silent pushes.

**6. Security headers for the worker**
Serve `/sw.js` with `Content-Type: application/javascript`, `Cache-Control: no-cache, no-store, must-revalidate` and a strict CSP, as in [principle 10](10.%20Service%20Workers%20and%20Caching.md) and the Next.js PWA guide.

### Design rules specific to PWAs
- **Permissions are earned.** Ask for notification permission in context ("Notify me when my report finishes"), after the user has seen the value. A denied permission is hard to reverse, and prompting on load drives denials.
- **Notifications must be useful, rare and actionable**, with a deep link into the right screen. Give per-type controls and an easy off switch.
- **Be honest about offline.** Show connection state, queue user actions only where you can actually sync them, and say what is unavailable.
- **Installed apps share your auth.** A PWA uses the same cookies and storage as the site (per browser). Standalone windows may sandbox the OAuth/login redirect flow differently on some platforms; test Auth0 login and logout in installed mode.
- **Respect platform differences.** iOS: install is manual, push needs the installed app, storage can be cleared for unused PWAs, and some capabilities lag. Android/desktop Chromium: richest support.
- **Track installs and notification outcomes** (`appinstalled` event, display-mode standalone, push opt-in rate, notification click-through) to confirm the engagement claim.

### Rules of thumb
1. **Start with the manifest and HTTPS**: low cost, makes the app installable.
2. **Add a service worker only for a concrete need** (offline fallback, push). See [principle 10](10.%20Service%20Workers%20and%20Caching.md).
3. **Push is a product feature, not a toggle.** It needs a use case, a backend, permission UX and unsubscribe handling.
4. **Define offline per feature**, and test it.
5. **Progressive enhancement**: the web app must work fully with no manifest, no SW and no push support.
6. **Measure** installs, push opt-in and engagement against a browser-tab baseline.

### Anti-patterns
- Requesting notification permission on first load.
- Storing push subscriptions in memory (as in the docs demo) or not removing expired ones (404/410).
- Exposing the VAPID **private** key (only the public key is `NEXT_PUBLIC_*`).
- SVG-only or missing 192/512 PNG icons, and no maskable icon.
- A service worker that caches authenticated pages or API responses; stale or cross-user data in an installed app.
- Promising "works offline" when core features need the backend.
- Assuming iOS behaves like Android (install prompt, push without install).
- Silent pushes or notification spam, which leads to revoked permission.
- Forgetting to test login, logout and deep links in standalone mode.
- Building a PWA purely for the label, with no offline or push need.

### Checklist
- [ ] Served only over HTTPS (including preview and staging if testing push).
- [ ] `app/manifest.ts` exists with name, `short_name`, `start_url`, `display: "standalone"`, theme/background colours and 192/512 PNG icons (plus maskable).
- [ ] `viewport.themeColor` and safe-area insets handled; layout works in a standalone window with no browser chrome.
- [ ] Service worker per [principle 10](10.%20Service%20Workers%20and%20Caching.md): allow-list, versioned caches, `/sw.js` never long-cached, update prompt, kill switch.
- [ ] A static `/offline` page is precached and shown on failed navigations; offline behaviour is documented per feature.
- [ ] Install UX: `beforeinstallprompt` on Chromium, manual instructions for iOS; shown at a sensible moment.
- [ ] Push: VAPID keys generated, private key server-only, subscriptions stored per user and device in a database, expired ones pruned, permission asked in context, unsubscribe available.
- [ ] Push payloads contain no sensitive data and link to an authenticated screen (which re-checks auth).
- [ ] Auth login/logout and deep links tested in installed mode on Android, desktop and iOS.
- [ ] Lighthouse installability checks pass; Core Web Vitals do not regress ([principle 8](8.%20Core%20Web%20Vitals.md)).
- [ ] Install count, push opt-in and click-through tracked.

### In this codebase
Measured with a quick search of `src/`, `public/` and `next.config.ts` (not a full audit):
- **None of the PWA pieces exist yet**: no `app/manifest.ts`, no service worker, no PWA icons (`public/icons/` holds SVG logos and UI icons, no 192/512 PNGs), no `themeColor` viewport export, and no push subscription code.
- **Push needs backend work.** Storing subscriptions per user, sending notifications, and expiring them would need a backend endpoint and a trigger (for example "agent run finished", "report ready", "invite received"). Per the standing project rule the backend is not changed from the front-end work, so this must be agreed with the backend side first.
- Auth0 sessions and the Proxy auth/onboarding gate (`src/proxy.ts`) apply inside an installed app too; test the login redirect and logout in standalone mode.
- The CSP already allows `worker-src 'self' blob:`. HTTPS is a hosting matter and is not stated in the repo (see [principle 9](9.%20CDN%20and%20Edge%20Delivery.md)).
- A realistic first step is the **manifest and icons only** (installable, low risk), then an offline fallback page, then push if a concrete notification use case is agreed. Chat is streaming and per-user, so real offline chat is out of scope; "installable with a clean offline message" is the reasonable target.
