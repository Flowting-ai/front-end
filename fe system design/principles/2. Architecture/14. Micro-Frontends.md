## 14. Micro-Frontends

> Each team owns a vertical feature slice that a shell composes at runtime. Independent build, test and deploy cycles. Real coordination cost: not for a team of three or smaller.

### Definition
A micro-frontend architecture splits a large frontend into **independently built and deployed applications**, each owned end-to-end by one team (UI, data access, tests, release). A **shell** (or a routing layer) assembles them into one product for the user.

It is the frontend version of microservices, and it carries the same trade: **team autonomy in exchange for operational and consistency cost**. It solves an *organisational* scaling problem (too many teams blocking each other in one deploy), not a technical one.

### Key properties

**1. Vertical slices, not horizontal layers**
- Split by **business capability** (Checkout, Search, Account, Admin), each owning its whole stack. Never split by technical layer ("the header team", "the forms team").
- A slice has a clear URL space or a clear region of the page.

**2. Independent delivery**
- Own repo or own pipeline, own versioning, own deploy and rollback. A bug in one slice does not block another team's release.

**3. Composition strategy decides the cost**
| Strategy | How | Cost / risk |
|---|---|---|
| **Route-level (Multi-Zones)** | Separate Next.js apps each serve a set of paths behind one domain; a proxy or rewrite routes to the right zone | Simplest and most robust. Navigation between zones is a full page load |
| **Server-side composition** | Gateway or edge stitches HTML fragments from several services | Fast first paint; needs fragment contracts and caching rules |
| **Build-time (npm packages)** | Slices published as packages, shell installs them | Not independent: the shell must rebuild and redeploy to update |
| **Runtime (Module Federation)** | Shell loads remote bundles in the browser at runtime | Most flexible, most fragile: shared-dependency version skew, bigger bundles, harder SSR |
| **iframes** | Each slice in an iframe | Strong isolation, poor UX (sizing, focus, routing, accessibility) |
| **Web Components** | Slices expose custom elements | Framework-neutral; weak SSR and React-state ergonomics |

For Next.js, **start with Multi-Zones**: it is the officially documented approach and avoids runtime bundle sharing.

**4. Shared concerns need an explicit contract**
- Authentication/session, design tokens, analytics, error reporting and i18n must work identically across slices. Share them through a **design system package** (principle 15) and a single auth boundary, not by copy-paste.
- Communication between slices should be **URLs, events and well-typed props at the edges**, never shared mutable global state.

**5. Real coordination cost**
- Duplicated dependencies (several copies of React or UI libraries) bloat the page and hurt Core Web Vitals (principle 8).
- Inconsistent UX, version skew, cross-slice end-to-end testing and a platform team to maintain the shell are permanent costs.
- **Rule of thumb:** below roughly 3 to 4 teams (or a team of three or smaller), a well-structured monolith or monorepo (principle 17) wins.

### When to use it
| Use when | Avoid when |
|---|---|
| Many teams (rule of thumb 4+) block each other on one release train | One small team |
| Parts of the product have very different release cadence or risk (marketing vs checkout) | Features share heavy interactive state across the page |
| A large legacy app is being migrated piece by piece (strangler pattern) | You want micro-frontends mainly to "use different frameworks" |
| Acquisitions merged into one product surface | Core Web Vitals budgets are tight and cannot absorb duplicated bundles |

### Practical patterns in Next.js (TypeScript)

**Multi-Zones: one app per path set, one domain** (from the Next.js guide)
```ts
// next.config.ts   in the "blog" zone (not the default zone)
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  assetPrefix: "/blog-static",          // keeps this zone's /_next assets from colliding
};
export default nextConfig;
```
```ts
// next.config.ts   in the default (catch-all) zone: route blog paths to the blog zone
const nextConfig: NextConfig = {
  async rewrites() {
    return [
      { source: "/blog", destination: `${process.env.BLOG_DOMAIN}/blog` },
      { source: "/blog/:path+", destination: `${process.env.BLOG_DOMAIN}/blog/:path+` },
      { source: "/blog-static/:path+", destination: `${process.env.BLOG_DOMAIN}/blog-static/:path+` },
    ];
  },
};
```
- The default zone (catch-all) does not need an `assetPrefix`.
- Links **to another zone** must use a plain `<a>`, not `<Link>`: `<Link>` prefetches and soft-navigates, which cannot cross zone boundaries.
- If a zone uses Server Actions, set `experimental.serverActions.allowedOrigins` to the user-facing origin, because that domain serves several apps.
- Zones can live in one monorepo or separate repos; in separate repos, share code through (private) npm packages.
- Feature flags help release a cross-zone feature in unison (principle 18).

**Shared contract package (types and events)**
```ts
// packages/contracts/src/events.ts
export type CartEvent =
  | { type: "cart:item-added"; sku: string; qty: number }
  | { type: "cart:cleared" };

export const emitCart = (e: CartEvent) =>
  window.dispatchEvent(new CustomEvent("cart", { detail: e }));
```
Slices talk through typed, versioned events or URLs. Treat the contract like a public API (principle 15).

### Rules of thumb
1. **Earn it.** Adopt only when team count and release friction justify the cost.
2. **Split by business capability, vertically.**
3. **Prefer route-level composition (Multi-Zones)** over runtime bundle sharing.
4. **One session, one design system, one analytics setup** across all slices.
5. **Budget the bundle.** Measure total JS per route across zones; shared libraries must be deduplicated or accepted as cost.
6. **Version contracts.** Breaking a shared event or API shape is a cross-team incident.
7. **Test the seams**: cross-slice end-to-end tests for login, navigation and shared layout.
8. **Keep a platform owner** for the shell, routing and shared packages.

### Anti-patterns
- Micro-frontends for a team of three: you pay the cost with none of the benefit.
- Splitting by technical layer (a "header app", a "forms app").
- Different UI frameworks per slice for no business reason.
- Slices sharing mutable global state or reaching into each other's DOM.
- Several copies of React and the UI library loaded on one page.
- Using `<Link>` between zones (broken prefetch and navigation).
- No shared design tokens: each slice drifts visually.
- No owner for the shell: it becomes a bottleneck, recreating the monolith's coordination problem.

### Industry best practices
- **Start from team topology (Conway's law)**: align slices with team boundaries and business domains, then choose the technology.
- **Prefer a modular monolith first**; extract a micro-frontend only when release coupling is proven to hurt.
- **Define the contracts early**: URL structure, shared event names and payloads, shared design tokens, auth/session behaviour, and error reporting format. Version them.
- **Keep one shell responsibility**: routing, layout chrome, auth and global error handling. The shell contains no business logic.
- **Share as little as possible at runtime**: share the design system and a thin contract package; avoid shared stores and shared component libraries beyond the design system.
- **Deduplicate heavy dependencies** deliberately (React, router, UI kit) or accept the cost with a measured budget.
- **Give each slice its own CI/CD, error tracking project tag, feature flags and dashboards**, plus a shared view of end-to-end journeys.
- **Run cross-slice contract and smoke tests** in the shell's pipeline (login, navigation, checkout journey), because unit tests per slice cannot catch integration breaks.
- **Isolate styles** (CSS Modules, scoped Tailwind prefix, or Shadow DOM) so one slice cannot restyle another; share tokens, not selectors.
- **Plan navigation**: hard navigation between zones is acceptable if the journeys rarely cross; otherwise reconsider the split.
- **Use progressive rollout and versioned remotes** (canary a slice, pin shell-to-slice compatibility) to limit blast radius.
- **Own the platform**: a small team maintains the shell, templates, shared packages and documentation for new slices.

### Things to avoid
- Splitting before there is an organisational problem to solve.
- Sharing a global state store, or a global CSS file, across slices.
- Letting slices depend on each other's internals or import each other's code directly.
- Runtime Module Federation with unmanaged shared-dependency versions (singleton conflicts, double React).
- Differing build tools, Node versions and lint rules per slice with no platform support.
- One slice acting as the de facto shell for all the others.
- Treating the user's page as the integration test environment: shipping contract changes with no consumer tests.
- Authentication logic reimplemented in each slice.
- Measuring only per-slice performance; the user experiences the sum of all slices on a page.

### Checklist
- [ ] A written reason exists: which teams are blocked, and what independent delivery would unlock.
- [ ] Each slice maps to one business capability and one owning team.
- [ ] Composition method chosen deliberately (Multi-Zones by default for Next.js).
- [ ] Cross-zone links use `<a>`; `assetPrefix` set on non-default zones.
- [ ] Server Actions allowed origins configured for the shared domain.
- [ ] Shared auth, tokens, analytics and error reporting come from shared packages.
- [ ] Total per-route JS budget measured across slices; Core Web Vitals tracked per slice.
- [ ] Cross-slice contracts are typed and versioned; integration tests cover the seams.

### In this codebase
Measured with a quick scan:
- The app is a single Next.js application (one `package.json`, one `next.config.ts`) served as one deployable; the back-end is a separate repo-level project. There are no zones or federated remotes.
- A small team with one product surface is below the threshold where micro-frontends pay off. The right investment is modular structure inside one app (principles 12, 15, 17), not runtime composition.
- If a separate surface later needs its own cadence (for example a public marketing site or an embedded widget), a **second Next.js app in a monorepo** behind rewrites (Multi-Zones) is the lowest-risk first step.
