## 21. Frontend Security

> The browser is the first line of defence against XSS, CSRF and injection. Never `dangerouslySetInnerHTML` user content. Keep auth tokens in `httpOnly` cookies, not `localStorage`.

### Definition
Frontend security is the set of practices that stop attackers from running code in your users' browsers, acting as them, or reading data they should not see. Two facts frame everything:

1. **Anything shipped to the browser is public.** Client code, `NEXT_PUBLIC_*` variables, props passed to Client Components and RSC payloads are all readable. The browser is not a trust boundary for secrets or authorisation.
2. **The server must re-check everything.** Client-side checks are usability, not security.

The frontend's own security job is to prevent **injection** (XSS), **request forgery** (CSRF), **data leakage** and **supply-chain** compromise, and to send the right **headers** so the browser enforces policy.

### Key properties

**1. XSS: do not let attacker data become code**
- React **escapes** values rendered in JSX by default, so `{userText}` is safe.
- The escape hatches are the danger: `dangerouslySetInnerHTML`, `href`/`src` with `javascript:` URLs, `eval`, `new Function`, `innerHTML` via refs, and unsafe third-party widgets.
- **Never** render user-controlled or model-generated HTML with `dangerouslySetInnerHTML`. If rich content is unavoidable, **sanitise with an allow-list sanitiser** (DOMPurify) right before rendering, keep the config strict, and never concatenate user data into the sanitised output afterwards.
- Validate URLs before using them in `href` (allow only `http:`, `https:`, `mailto:`). Add `rel="noopener noreferrer"` to `target="_blank"` links.
- For markdown, use a renderer that does **not** allow raw HTML by default (for example `react-markdown` without `rehype-raw`), or sanitise the output.

**2. Auth tokens in `httpOnly` cookies, not `localStorage`**
- Anything in `localStorage` or `sessionStorage` (and any cookie readable by JS) can be stolen by **any** XSS on your origin. An `httpOnly` cookie cannot be read by JavaScript.
- Set session cookies with `HttpOnly; Secure; SameSite=Lax` (or `Strict`), a narrow `Path`, and a short, renewable lifetime. Use the `__Host-` prefix where possible.
- Keep tokens server-side: the browser holds an opaque session cookie; the server (or a backend-for-frontend) holds and uses the real access tokens. Use a vetted library (Auth0 SDK, Auth.js) instead of rolling your own.
- `localStorage` is fine for **non-sensitive preferences** (theme, sidebar state, recent items). It is never for credentials, tokens or personal data.

**3. CSRF: cookies are sent automatically**
- With cookie auth, a malicious site can make the victim's browser send authenticated requests. Defences:
  - `SameSite=Lax` or `Strict` cookies (blocks most cross-site POSTs).
  - **Server Actions** are POST-only and Next.js compares the `Origin` header with `Host` / `X-Forwarded-Host` and rejects mismatches. Keep `experimental.serverActions.allowedOrigins` narrow (and, if you self-host, make sure only trusted infrastructure can set `Host`). In 2026 a bypass (CVE-2026-27978) affected `origin: null` handling in Next.js 16.0.1 to 16.1.7; stay on a patched version.
  - For route handlers, **verify the Origin header and/or a CSRF token** yourself; never change state on `GET`.
- The built-in origin check is **not** authorisation.

**4. Authorisation lives on the server, close to the data**
- Every Server Action is a public POST endpoint that can be called directly. Authenticate and authorise **inside each action and route handler**, and verify the caller owns the resource (an ID from the client may refer to someone else's row).
- Proxy (`proxy.ts`, formerly middleware) is for optimistic redirects and headers, **not** the only authorisation layer.
- Follow the Next.js **Data Access Layer** pattern: a `server-only` module that checks the session, queries the database and returns minimal **DTOs**. Components never touch the database or `process.env` directly.
- Return only what the client needs. Do not pass whole database rows or objects with secrets as props to Client Components (they are serialised into the page).

**5. Validate and encode at the boundary**
- Treat all input (form data, query strings, headers, API responses) as untrusted. **Parse with a schema** (Zod) on the server, in every Server Action and route handler, even if the client validated too.
- Use parameterised queries / an ORM; never build SQL, shell commands or file paths from raw input.
- Encode output for its context: HTML (React does), attribute, URL, JS string, CSS.

**6. Content Security Policy and security headers**
- A **strict CSP** limits damage if XSS slips through: `default-src 'self'`; `script-src` with a per-request **nonce** and `'strict-dynamic'`; `object-src 'none'`; `base-uri 'self'`; `frame-ancestors 'none'`; `form-action 'self'`.
- Nonce-based CSP requires **dynamic rendering** (a fresh nonce per request), which disables static optimisation for those pages; the Next.js CSP guide generates the nonce in `proxy.ts`. A header-only CSP with `'unsafe-inline'` is weaker but compatible with static pages.
- Also send: `Strict-Transport-Security` (HTTPS only), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (disable unused features), and `X-Frame-Options` / `frame-ancestors` (clickjacking).
- Subresource Integrity for third-party scripts you cannot self-host.

**7. Secrets and environment variables**
- Only `NEXT_PUBLIC_*` variables are inlined into client JavaScript; everything else stays server-side. Never prefix a secret with `NEXT_PUBLIC_`.
- Mark server modules with `import "server-only"` so a Client Component importing them fails at build time.
- Rotate keys; keep them out of the repo, logs and error messages (principle 19: production errors are sanitised).

**8. Supply chain**
- Pin and audit dependencies (`npm audit`, Dependabot or Renovate, lockfile committed, `npm ci` in CI). Prefer fewer, well-maintained packages. Review postinstall scripts for new dependencies.
- Keep **Next.js and React patched**: framework CVEs (including Server Action and RSC issues) are real.

### Practical patterns in Next.js (TypeScript)

**Authenticated Server Action with validation and ownership check**
```ts
// app/actions/rename-project.ts
"use server";
import { z } from "zod";
import { getSessionUser } from "@/data/auth";     // server-only DAL
import { renameOwnedProject } from "@/data/projects";

const Input = z.object({ id: z.string().uuid(), name: z.string().trim().min(1).max(80) });

export async function renameProject(_prev: unknown, formData: FormData) {
  const user = await getSessionUser();            // 1. authenticate
  if (!user) return { error: "Unauthorised" };

  const parsed = Input.safeParse(Object.fromEntries(formData));   // 2. validate
  if (!parsed.success) return { error: "Invalid input" };

  const ok = await renameOwnedProject(user.id, parsed.data.id, parsed.data.name); // 3. authorise by ownership
  return ok ? { error: null } : { error: "Not found" };
}
```

**Server-only data access returning a DTO**
```ts
// data/projects.ts
import "server-only";
import { cache } from "react";

export const getProjectDTO = cache(async (userId: string, id: string) => {
  const row = await db.project.findFirst({ where: { id, ownerId: userId } });  // scoped to the owner
  if (!row) return null;
  return { id: row.id, title: row.title };        // minimal, no internal fields
});
```

**Safe HTML when rich content is unavoidable**
```tsx
import DOMPurify from "isomorphic-dompurify";

export function RichText({ html }: { html: string }) {
  const clean = DOMPurify.sanitize(html, { USE_PROFILES: { html: true }, FORBID_TAGS: ["style", "form"] });
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
}
```
Prefer **not** doing this at all. Render structured data (markdown AST, JSON) as components instead of strings of HTML.

**Safe links**
```tsx
function SafeLink({ href, children }: { href: string; children: React.ReactNode }) {
  const ok = /^(https?:|mailto:)/i.test(href);
  return ok ? <a href={href} target="_blank" rel="noopener noreferrer">{children}</a> : <span>{children}</span>;
}
```

**Session cookie settings (server)**
```ts
import { cookies } from "next/headers";

(await cookies()).set("session", opaqueId, {
  httpOnly: true, secure: true, sameSite: "lax", path: "/", maxAge: 60 * 60 * 8,
});
```

**Security headers in `next.config.ts`**
```ts
const securityHeaders = [
  { key: "Strict-Transport-Security", value: "max-age=63072000; includeSubDomains; preload" },
  { key: "X-Content-Type-Options", value: "nosniff" },
  { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
  { key: "Permissions-Policy", value: "camera=(), microphone=(), geolocation=()" },
  { key: "X-Frame-Options", value: "DENY" },
];
// export default { async headers() { return [{ source: "/(.*)", headers: securityHeaders }]; } };
```

**Strict CSP with a nonce (from the Next.js guide, outline)**
- Generate a nonce per request in `proxy.ts`, build the policy with `'nonce-…' 'strict-dynamic'`, set it on the request (`x-nonce`) and response headers, skip prefetches and static assets in the matcher, and force dynamic rendering for pages that need the nonce. In development, `'unsafe-eval'` is needed for React's debugging; not in production.

### Rules of thumb
1. **Treat the browser as hostile and public.** No secrets, no authorisation decisions.
2. **Never `dangerouslySetInnerHTML` untrusted content**; if forced, sanitise at render time.
3. **Tokens in `httpOnly; Secure; SameSite` cookies**; `localStorage` for preferences only.
4. **Authenticate and authorise in every Server Action and route handler.**
5. **Validate with a schema on the server**; parameterise queries.
6. **Use a Data Access Layer** with `server-only` and return DTOs.
7. **Send a CSP and the standard headers**; prefer nonce-based CSP.
8. **Patch and audit dependencies**, including Next.js itself.

### Anti-patterns
- Putting JWTs or API keys in `localStorage`, `sessionStorage`, or non-httpOnly cookies.
- `dangerouslySetInnerHTML={{ __html: userOrModelOutput }}` with no sanitiser.
- Authorisation only in the UI (hiding a button) or only in `proxy.ts`.
- Trusting an `id` from the client without scoping the query to the current user.
- Prefixing secrets with `NEXT_PUBLIC_` "to make it work".
- Passing entire database rows or objects containing tokens to Client Components.
- `'unsafe-inline'` and `'unsafe-eval'` in the production CSP without a plan to remove them.
- State-changing `GET` routes; CORS set to `*` with credentials.
- Rendering markdown with raw HTML enabled for user or model content.
- Ignoring dependency alerts and framework security releases.

### Industry best practices
- **Follow the OWASP Top 10 and ASVS** as the review baseline, and run a threat-modelling session for new features that handle money, identity or user content.
- **Apply defence in depth**: sanitise, CSP, `httpOnly` cookies, server checks and monitoring each assume the others may fail.
- **Use Trusted Types** (`require-trusted-types-for 'script'`) where browser support and your dependencies allow, to make DOM XSS sinks safe by policy.
- **Isolate untrusted content**: render model output, user HTML or third-party widgets in a sandboxed `iframe` (`sandbox` attribute, no `allow-same-origin` unless essential) on a separate origin where possible.
- **Handle model output as untrusted input** in AI applications: no HTML injection, no auto-following of links or running of code, confirm before tool actions with side effects, and defend against prompt-injection data exfiltration (for example images or links that encode secrets in URLs).
- **Rate-limit and bot-protect** sensitive routes (login, signup, password reset, expensive AI calls); return generic messages to avoid account enumeration.
- **Use short-lived sessions with rotation**, re-authentication for sensitive actions, and server-side logout that invalidates the session.
- **Configure CORS narrowly**: explicit origins, no wildcard with credentials, and only the methods and headers needed.
- **Protect uploads and redirects**: validate type, size and content server-side; allow-list redirect targets to prevent open redirects.
- **Use Subresource Integrity and a minimal third-party script list**; load analytics and tags through a consent-aware, CSP-restricted path.
- **Log security events** (failed logins, permission failures, CSP violation reports via `report-to`) and alert on anomalies.
- **Scan continuously**: dependency audit, secret scanning, SAST, and periodic penetration tests; publish a `security.txt` and vulnerability disclosure contact.
- **Minimise data**: collect, send and store only what is needed; make sure client logs, analytics events and error reports exclude personal data.
- **Keep the platform patched**: subscribe to Next.js and React security advisories and upgrade promptly.

### Things to avoid
- Rolling your own authentication, session handling or cryptography.
- Putting API keys, signing secrets or private URLs in client bundles, source maps or public repos.
- Shipping source maps publicly when they expose server-only code or secrets; restrict or upload them only to the error tracker.
- Disabling security features (`rejectUnauthorized: false`, CSP report-only forever, removing headers) to make a bug go away.
- Trusting client-supplied roles, prices, user IDs or feature flags.
- Using `postMessage` with `"*"` as target origin, or accepting messages without checking `event.origin`.
- Open redirects (`?next=` used without validation) and unvalidated `target="_blank"` links.
- Using `eval`, `new Function`, `document.write` and string-based `setTimeout`.
- Letting third-party scripts run with full page access when an `iframe` or a server-side integration would do.
- Verbose error responses that reveal stack traces, SQL or internal hostnames.
- Storing personal data in URLs, analytics events or client logs.
- Assuming "internal" or "behind login" means safe: authorised users can still be attackers or compromised.

### Checklist
- [ ] No tokens, secrets or personal data in `localStorage`/`sessionStorage`; session cookies are `HttpOnly; Secure; SameSite`.
- [ ] Each `dangerouslySetInnerHTML` is reviewed, minimal, and fed only constants or allow-list-sanitised content.
- [ ] Each Server Action and route handler authenticates, validates (schema) and checks resource ownership.
- [ ] Data access goes through a `server-only` layer returning DTOs; no direct `process.env` in components.
- [ ] No secret uses `NEXT_PUBLIC_`; only needed fields cross the server/client boundary.
- [ ] CSP (preferably nonce-based) plus HSTS, `nosniff`, `Referrer-Policy`, `Permissions-Policy`, frame protection are set.
- [ ] `serverActions.allowedOrigins` is narrow; the app runs a patched Next.js and React.
- [ ] Links from user data are scheme-checked and use `rel="noopener noreferrer"`.
- [ ] Dependencies are audited automatically (Dependabot/Renovate, `npm audit`) in CI.

### In this codebase
Measured with a quick scan of `src/` and `next.config.ts` (not a security audit):
- `next.config.ts` already sets `X-Frame-Options`, `Strict-Transport-Security` and a `Content-Security-Policy` whose `connect-src` is built from environment variables (backend, Auth0 tenant, analytics). That is a good base; `script-src` currently allows `'unsafe-inline'` (plus Google Tag Manager), so it does not yet use a nonce; moving to a nonce-based policy is the main CSP upgrade, at the cost of dynamic rendering.
- Authentication uses `@auth0/nextjs-auth0` (`src/lib/auth0.ts`), which keeps the session in server-managed cookies; no auth token write to `localStorage` was found by a simple search, but 36 files use `localStorage` for preferences. Re-check each key holds nothing sensitive (for example chat content or personal data).
- 11 `dangerouslySetInnerHTML` uses: the theme-init script (constant string), KaTeX output passed through `sanitizeKaTeX`, and code-highlight and Mermaid SVG output. `MermaidDiagram.tsx` and `CodeBlock.tsx` showed no `sanitize`, `DOMPurify` or `securityLevel` reference in a text search, so review those two first: their input originates from model output. `isomorphic-dompurify` is already installed.
- Cookies written from the client (`document.cookie`) are limited to non-sensitive flags (`souvenir_checkout_complete`, sidebar state), which is fine; they cannot be `httpOnly` by definition and must never carry credentials.
- No Server Actions were reviewed here; if added, apply the validated-and-owned pattern above. `server-only` is not yet used (see principle 6), so a Data Access Layer is a recommended next step.
