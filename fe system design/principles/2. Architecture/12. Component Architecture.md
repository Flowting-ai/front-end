## 12. Component Architecture

> UI is a function of state: `UI = f(state)`. Compose small, focused components into larger ones. Split when a component has two reasons to change; merge when two always change together.

### Definition
A component is a unit of UI with a clear contract (its props) and one responsibility. Larger screens are built by **composing** components, not by growing one component. Given the same props and state, a component renders the same output, so UI bugs reduce to "which state was it in?".

In the App Router there are two kinds of component, and the split is itself an architectural decision (see principle 6): **Server Components** (the default, no client JS) and **Client Components** (`"use client"`, for state, effects, events and browser APIs).

### Key properties

**1. Single reason to change**
- A component should change for one kind of reason: a visual change, a data-shape change, or a behaviour change, not all three.
- A component that fetches, formats, validates and renders is four reasons to change in one file.

**2. Split when there are two reasons to change**
- Signals: the file keeps growing; props are mostly passed through; two halves have separate state; one half needs `"use client"` and the other does not.
- Splitting along the server/client line is the most valuable split in Next.js: a server shell that fetches, plus a small client leaf that handles interaction.

**3. Merge when two always change together**
- Two components that are always edited in the same PR, never used apart, and pass many props between them are one component split too early.
- Premature abstraction costs more than duplication. Wait for the third use before extracting ("rule of three").

**4. Composition over configuration**
- Prefer `children` and slot props to a long list of boolean flags (`showHeader`, `hasFooter`, `compact`, `withIcon`...).
- A component with more than about 5 to 7 props, or mutually exclusive props, wants to be several components or a compound component.

**5. Stable, typed contracts**
- Props are the public API of a component. Type them explicitly, keep them small and serialisable where they cross the server/client boundary.
- Export a component and its prop type; keep internals private.

### Component layers
| Layer | Responsibility | Typical home | Server or client |
|---|---|---|---|
| Primitives | Styled, behaviour-free building blocks (Button, Badge, Divider) | `components/` or a design-system package (principle 15) | Server-safe where they hold no state |
| Composites | Primitives combined with local state (Dropdown, Modal, Tabs) | `components/` | Usually client |
| Feature components | A domain concept (ChatInput, AgentEditor, ConnectorCard) | `components/<Feature>/` | Mixed |
| Route components | `page.tsx`, `layout.tsx`: fetch data, assemble features | `app/` | Server by default |

Dependencies point **downwards only**: a primitive never imports a feature; a feature never imports a route file.

### Practical patterns in Next.js (TypeScript)

**Container (server) plus presentational (client leaf)**
```tsx
// app/(app)/projects/[id]/page.tsx   Server Component: fetch + assemble
import { getProject } from "@/lib/data/projects";
import { ProjectHeader } from "@/components/ProjectHeader";
import { FavouriteButton } from "@/components/FavouriteButton";

export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const project = await getProject(id);
  return (
    <>
      <ProjectHeader title={project.title} owner={project.owner} />
      <FavouriteButton projectId={project.id} initial={project.favourite} />
    </>
  );
}
```
```tsx
// components/FavouriteButton.tsx   Client leaf: the only part with state
"use client";
import { useState } from "react";

type Props = { projectId: string; initial: boolean };

export function FavouriteButton({ projectId, initial }: Props) {
  const [on, setOn] = useState(initial);
  return (
    <button aria-pressed={on} onClick={() => setOn((v) => !v)}>
      {on ? "Favourited" : "Favourite"}
    </button>
  );
}
```

**Compound components (composition instead of flags)**
```tsx
// Card with slots instead of showHeader / showFooter / compact booleans
export function Card({ children }: { children: React.ReactNode }) {
  return <section className="rounded-lg border p-4">{children}</section>;
}
Card.Header = function CardHeader({ children }: { children: React.ReactNode }) {
  return <header className="mb-2 font-medium">{children}</header>;
};
Card.Body = function CardBody({ children }: { children: React.ReactNode }) {
  return <div>{children}</div>;
};

// Usage: the caller decides the structure
<Card>
  <Card.Header>Usage</Card.Header>
  <Card.Body><UsageChart /></Card.Body>
</Card>
```

**Variants as data, not branching (Tailwind + `cva`)**
```tsx
import { cva, type VariantProps } from "class-variance-authority";

const button = cva("inline-flex items-center rounded-md font-medium focus-visible:outline-2", {
  variants: {
    intent: { primary: "bg-brand text-white", ghost: "bg-transparent hover:bg-muted" },
    size: { sm: "h-8 px-3 text-sm", md: "h-10 px-4" },
  },
  defaultVariants: { intent: "primary", size: "md" },
});

type Props = React.ButtonHTMLAttributes<HTMLButtonElement> & VariantProps<typeof button>;

export function Button({ intent, size, className, ...rest }: Props) {
  return <button className={button({ intent, size, className })} {...rest} />;
}
```
Tailwind v4 reads class names statically, so keep full class strings in the source (do not build them with string concatenation like `` `bg-${color}-500` ``). Use `tailwind-merge` when callers can override classes.

**Extract logic into hooks, not into more components**
```tsx
function useDebouncedValue<T>(value: T, ms = 250) {
  const [v, setV] = useState(value);
  useEffect(() => { const t = setTimeout(() => setV(value), ms); return () => clearTimeout(t); }, [value, ms]);
  return v;
}
```
A hook shares behaviour; a component shares structure. Use the one that matches what is being reused.

**Colocate**
```
components/ChatInput/
  index.tsx            # public export
  ChatInput.test.tsx
  useAttachments.ts    # private hook
  AttachmentChip.tsx   # private subcomponent
```
Keep a feature's parts together. Promote a file to a shared folder only when a second feature needs it.

### React Compiler note
`reactCompiler: true` memoises automatically, so manual `useMemo`/`useCallback`/`React.memo` are rarely needed. Component boundaries should follow responsibility, not "to avoid re-renders". Measure before adding manual memoisation.

### Rules of thumb
1. **One reason to change.** Name it in one sentence; if the sentence has "and", consider splitting.
2. **Server by default; client at the leaf** (principle 6).
3. **Compose with `children` and slots** before adding a boolean prop.
4. **Rule of three** before extracting a shared component.
5. **Dependencies point down**: primitives → composites → features → routes.
6. **Derive, don't sync.** If a value can be computed from props or state during render, compute it; do not copy it into more state or an effect.
7. **Colocate** tests, hooks and subcomponents with the feature.
8. **Keep props small and typed.** Pass IDs and minimal data, not whole entities.

### Anti-patterns
- God components: 800-line files that fetch, transform, validate, render and handle every interaction.
- Prop explosion: 15 props, many booleans, several mutually exclusive.
- Prop drilling through four or more layers (use composition, context for truly global values, or fetch lower in the tree).
- Copying props into state (`useState(props.value)`) and then trying to keep them in sync with an effect.
- Defining a component inside another component's body (it remounts on every render and loses state).
- `"use client"` on a whole feature because one child needs a click handler.
- Dynamic Tailwind class names built by string concatenation (they are not generated).
- Abstracting after one use, then bending the abstraction for each new caller.

### Industry best practices
- **Type props with a TypeScript interface or type, and extend native element props** (`React.ComponentProps<"button">`) so wrappers pass through `aria-*`, `data-*` and event handlers without re-declaring them.
- **Forward refs and spread rest props** on design-system primitives. In React 19, `ref` is a regular prop for function components, so `forwardRef` is no longer required.
- **Prefer function components and hooks**; use a class only for error boundaries.
- **Keep render pure**: no mutation of props, no reading or writing external mutable values, no side effects outside effects and event handlers. React Strict Mode double-invokes render to expose this.
- **Use stable, unique `key`s** (IDs, never array indexes for reorderable lists).
- **Handle every state a component can be in**: loading, empty, error, partial and success. Design them as props or slots, not as an afterthought.
- **Co-locate tests and stories** with the component; test behaviour through roles and text, not implementation details.
- **Name by role, not appearance** (`PrimaryAction`, not `BlueButton`; `UsageCard`, not `RoundedBox`).
- **Use `children`/slot props for layout flexibility** and keep the component unaware of its parent.
- **Lazy-load heavy, rarely used components** with `next/dynamic` or `React.lazy` (editors, charts, maps, diagram renderers).
- **Enforce structure with tooling**: ESLint (`react-hooks/rules-of-hooks`, `exhaustive-deps`), `eslint-plugin-react`, import-boundary rules, and the React Compiler's lint checks.
- **Document the contract** (props table, usage, accessibility notes) next to the component.

### Things to avoid
- Using array index as `key` on lists that reorder, insert or delete.
- Calling hooks conditionally, in loops or after an early `return`.
- Side effects (fetching, subscriptions, `localStorage` writes) during render.
- `useEffect` for things that belong in event handlers or derived values.
- Over-memoising by hand when the React Compiler is on, which adds noise and stale-closure bugs.
- Boolean traps in APIs (`<Dialog true false true />`); use named props or variants.
- Barrel files (`index.ts` re-exporting everything) in large feature folders; they hurt tree-shaking and build time.
- Premature generic components (`<DataTable>` with 40 options) before two concrete uses exist.
- Reading `window` or `document` at module scope or in render in components that also render on the server.
- Shared components that import app context or feature modules.

### Checklist
- [ ] Each component can be described in one sentence without "and".
- [ ] Page and layout files assemble; they hold no large inline UI.
- [ ] Interactive parts are small client leaves; display parts are Server Components.
- [ ] Variants use `cva` (or equivalent) rather than nested ternaries.
- [ ] No component defined inside another component.
- [ ] No state that is derivable from props or other state.
- [ ] Shared components exist because of three or more real uses.
- [ ] Props are typed, minimal and serialisable across the server/client boundary.
