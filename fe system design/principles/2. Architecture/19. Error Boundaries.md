## 19. Error Boundaries

> Catch render errors and show a fallback instead of a blank, crashed page. Wrap risky sections so failures stay isolated. Forward every caught error to Sentry.

### Definition
An **error boundary** is a React component that catches errors thrown while rendering its children (and in lifecycle methods and constructors below it) and renders a **fallback UI** instead of unmounting the whole tree. Without a boundary, one uncaught render error unmounts the nearest parent that has one, which can mean the entire app.

Errors fall in two groups (from the Next.js docs):
- **Expected errors** (validation failure, 404, failed request): part of normal operation. **Return them as values** or use `notFound()`, and show them in the UI. Do not throw.
- **Uncaught exceptions** (bugs, unexpected failures): **throw** them and let an error boundary handle them.

### What boundaries do not catch
React error boundaries do **not** catch:
- Errors in **event handlers** (use `try/catch` there).
- **Asynchronous** code outside rendering (timers, promises, `fetch` callbacks).
- Errors in the boundary itself.
- Errors during server-side rendering **after the response status was sent** (streaming): see below.

For async errors, catch them and either set state that renders the error, or rethrow inside render (for example `setState(() => { throw error })`), so a boundary sees it.

### Key properties

**1. Granularity: isolate failures**
- A boundary should enclose a **section whose failure can be survived**: a widget, a panel, a chart, a list. The rest of the page keeps working.
- Layers, from outermost to innermost:
  1. `global-error.tsx`: last resort, replaces the root layout.
  2. `app/error.tsx`: catches errors under the root layout.
  3. Segment `error.tsx`: per route area (dashboard, settings, chat).
  4. Component-level boundary (`unstable_catchError` or a class boundary) around risky widgets.

**2. Next.js file conventions**
- `error.tsx` creates a boundary around a **route segment's** `page` and its nested layouts. It must be a Client Component.
- It does **not** wrap the `layout.tsx` or `template.tsx` in the **same** segment. To catch errors in the root layout use `global-error.tsx`, which must render its own `<html>` and `<body>`.
- Props: `error` (with `digest`) and `unstable_retry()` (v16; it re-fetches and re-renders the children, including Server Components).
- `global-error.tsx` only appears in production builds.
- Error state clears on client navigation to a different route.

**3. Server errors are sanitised**
- Errors thrown in Server Components reach the client with a **generic message and a `digest`** in production, so sensitive details do not leak. Use the `digest` to find the matching **server-side log** entry.
- Client-side errors keep their original message.

**4. Streaming and status codes**
- If an error happens **after** streaming started, the HTTP status is already 200 and cannot change. The boundary shows its fallback in the stream. Check for errors before the first `await` or boundary where the status matters (principle 7).
- `notFound()` and `redirect()` work by throwing special errors; framework-aware boundaries (`error.tsx`, `unstable_catchError`) let them pass. A custom class boundary can accidentally swallow them.

**5. Always report**
- A boundary **hides** the error from the browser's global handlers, so nothing is reported unless the boundary reports it. Call your error tracker (Sentry or similar) from **every** boundary, including `global-error.tsx`.
- Include context: route, user id (not personal data), release version, and the `digest` for server errors.

**6. Good fallbacks**
- Say what happened in plain language, offer **Try again** (`unstable_retry`), and a way out (go home, contact support).
- Keep the fallback **simple and dependency-light**: a fallback that itself throws is worse than none.
- Make fallbacks accessible: a heading, focus moved to it, `role="alert"` where the failure is announced.

### Practical patterns in Next.js (TypeScript)

**Route-segment boundary that reports**
```tsx
// app/(app)/dashboard/error.tsx
"use client";

import { useEffect } from "react";
import * as Sentry from "@sentry/nextjs";

export default function DashboardError({
  error,
  unstable_retry,
}: {
  error: Error & { digest?: string };
  unstable_retry: () => void;
}) {
  useEffect(() => {
    Sentry.captureException(error);        // boundaries hide errors; report explicitly
  }, [error]);

  return (
    <div role="alert">
      <h2>We could not load the dashboard</h2>
      <p>Reference: {error.digest ?? "n/a"}</p>
      <button onClick={() => unstable_retry()}>Try again</button>
    </div>
  );
}
```

**Root-layout last resort**
```tsx
// app/global-error.tsx   must define html and body; replaces the root layout when active
"use client";

import { useEffect } from "react";
import * as Sentry from "@sentry/nextjs";

export default function GlobalError({
  error,
  unstable_retry,
}: {
  error: Error & { digest?: string };
  unstable_retry: () => void;
}) {
  useEffect(() => { Sentry.captureException(error); }, [error]);
  return (
    <html lang="en">
      <body>
        <h1>Something went wrong</h1>
        <button onClick={() => unstable_retry()}>Try again</button>
      </body>
    </html>
  );
}
```
Because it replaces the root layout, style it with self-contained CSS; global styles and fonts from the layout are not applied.

**Component-level boundary with `unstable_catchError`**
```tsx
// components/WidgetBoundary.tsx
"use client";

import { unstable_catchError, type ErrorInfo } from "next/error";

function Fallback(props: { name: string }, { error, unstable_retry }: ErrorInfo) {
  return (
    <div role="alert">
      <p>{props.name} is unavailable.</p>
      <button onClick={() => unstable_retry()}>Retry</button>
    </div>
  );
}

export const WidgetBoundary = unstable_catchError(Fallback);
```
```tsx
<WidgetBoundary name="Usage chart">
  <UsageChart />      {/* if this throws, only this panel shows the fallback */}
</WidgetBoundary>
```
`unstable_catchError` keeps `redirect()` and `notFound()` working, supports `unstable_retry`, and clears when the user navigates elsewhere. The name has an `unstable_` prefix, so expect the API to change and pin the Next.js version.

**Class boundary (framework-neutral) with a reset key**
```tsx
"use client";
import React from "react";

type Props = { children: React.ReactNode; resetKey?: string };
type State = { error: Error | null };

export class Boundary extends React.Component<Props, State> {
  state: State = { error: null };
  static getDerivedStateFromError(error: Error): State { return { error }; }
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    reportError(error, info.componentStack);          // forward to Sentry
  }
  componentDidUpdate(prev: Props) {
    if (this.state.error && prev.resetKey !== this.props.resetKey) this.setState({ error: null });
  }
  render() { return this.state.error ? <Fallback /> : this.props.children; }
}
```
Pass a key such as `pathname` as `resetKey` so the boundary clears when the user navigates, otherwise the fallback sticks.

**Expected errors as values, not exceptions**
```tsx
export default async function Page() {
  const res = await fetch(`${process.env.API_URL}/projects`);
  if (!res.ok) return <p role="alert">Could not load projects.</p>;   // expected: render it
  const projects = await res.json();
  return <ProjectList projects={projects} />;
}
```

**Event handler and async errors**
```tsx
async function onSave() {
  try { await save(); }
  catch (e) { Sentry.captureException(e); setError("Save failed"); }   // boundaries do not catch this
}
```

**Sentry setup for Next.js (outline)**
- Install `@sentry/nextjs` and run its wizard, which adds `instrumentation.ts`, `instrumentation-client.ts` and `sentry.*.config.ts`.
- Export `onRequestError` from `instrumentation.ts` so **server** render errors are captured (Next.js calls it for uncaught request errors).
- Upload source maps in CI so stack traces are readable (principle 18); tag events with the release.
- Scrub personal data before sending (`beforeSend`), consistent with principle 21.

### Rules of thumb
1. **Expected errors are values; bugs are exceptions.**
2. **At least three layers**: `global-error`, root or segment `error.tsx`, and boundaries around independent widgets.
3. **Every boundary reports** (and `global-error` too).
4. **Fallbacks are small, accessible and offer retry.**
5. **Reset on navigation** (framework boundaries do this; custom ones need a key).
6. **Catch event and async errors yourself.**
7. **Log the `digest` server-side** so a user's reference ID finds the log.
8. **Test fallbacks** by forcing a throw in tests and in a production build.

### Anti-patterns
- A single boundary at the very top: any error replaces the whole app.
- A boundary around everything at component level, so errors are silently swallowed and the page shows many broken-looking holes.
- Swallowing errors: `componentDidCatch` with only `console.error` and no reporting.
- Custom boundaries that catch `redirect()` or `notFound()` errors.
- A fallback that depends on the data or context that just failed.
- Throwing for expected failures (validation, "not found") instead of returning a result or calling `notFound()`.
- Assuming a boundary catches errors from event handlers or promises.
- Showing raw `error.message` to users (leaks internals; server messages are generic in production anyway).

### Industry best practices
- **Classify errors** (expected, recoverable, fatal) and handle each class one way across the codebase; document the convention.
- **Use typed result objects** (`{ ok: true, data } | { ok: false, error }`) at API and Server Action boundaries instead of throwing for expected failures.
- **Add context to reports**: release, route, user ID (not personal data), feature flags, breadcrumbs, and the server `digest`. Group and alert on new or spiking errors.
- **Scrub personal data** before sending (`beforeSend`), and never send request bodies or tokens.
- **Rate-limit and sample** reports to avoid flooding the tracker during an incident (a render loop can emit thousands of errors).
- **Offer recovery, not just apology**: retry, reload the section, go back, or contact support with the reference ID.
- **Use `loading.tsx` and Suspense together with `error.tsx`** so loading, failure and success each have a designed state.
- **Add `not-found.tsx`** (root and per area) and return correct HTTP status for missing resources.
- **Handle network failure explicitly**: timeouts, retries with backoff and jitter for idempotent requests, offline messages.
- **Reset boundaries on meaningful change**: route change, retry, or key change.
- **Run chaos checks**: force a throw in each boundary in tests, and verify the fallback in a production build (`global-error` only shows there).
- **Monitor real users**: error rate per release, crash-free sessions, and alert thresholds; review top errors weekly.
- **Keep error pages on-brand and accessible** with a clear heading, plain language, and focus moved to the message.
- **Show a safe message to users and a rich one to engineers**: user-facing text is generic; logs hold detail.

### Things to avoid
- Empty `catch {}` blocks and `catch (e) { console.log(e) }` as the only handling.
- Showing stack traces, SQL errors or raw API messages to users.
- Retrying non-idempotent requests (payments, creates) automatically.
- Retry loops without a limit or backoff.
- A fallback UI that fetches data or depends on the context that failed.
- One generic "Something went wrong" for every failure with no reference ID or next step.
- Catching an error, reporting it, and then continuing in a corrupt state.
- Reporting every expected 404 or validation failure as an exception (alert fatigue).
- Letting `error.tsx` swallow errors without reporting.
- Relying on `window.onerror` alone for React render errors.
- Forgetting server-side rendering errors, which never reach browser-based trackers.

### Checklist
- [ ] `app/global-error.tsx` exists, renders `<html>` and `<body>`, and reports.
- [ ] A root or segment `error.tsx` exists for each major area (app shell, settings, chat, dashboard).
- [ ] Risky or independent widgets (charts, editors, third-party embeds, markdown or diagram renderers) have their own boundary.
- [ ] Every boundary calls the error tracker with release and route context.
- [ ] `onRequestError` (or equivalent) captures **server** errors; `digest` is shown or logged.
- [ ] Fallbacks offer retry and a way out, and are keyboard and screen-reader accessible.
- [ ] Expected errors are handled as values or with `notFound()`.
- [ ] Event-handler and async errors are caught and reported explicitly.
- [ ] Fallbacks verified in a production build.
