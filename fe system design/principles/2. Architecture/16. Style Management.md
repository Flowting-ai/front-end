## 16. Style Management

> How you scope styles has real architectural consequences at scale. CSS Modules are the sane default. Benchmark runtime CSS-in-JS on mobile.

### Definition
Style management is the choice of **how CSS is authored, scoped, delivered and themed**. It affects: bundle size, render performance, Server Component compatibility, streaming, team ergonomics and how easily a design system can be maintained. CSS is global by nature; every approach is a different answer to "how do we stop styles leaking and colliding?".

### Approaches compared
| Approach | Scoping | Runtime cost | Server Components | Notes |
|---|---|---|---|---|
| **CSS Modules** (`*.module.css`) | Build-time, locally scoped class names | None | Works | Plain CSS; built into Next.js; the safe default for component styles |
| **Tailwind CSS** (utility classes) | Utilities in markup, no collisions | None (static CSS generated at build) | Works | Tokens in `@theme`; fast iteration; long class strings need `cva` / components |
| **Global CSS** | None (global) | None | Works | For resets, tokens, base typography only. Import from the root layout |
| **Zero-runtime CSS-in-JS** (vanilla-extract, Panda CSS, StyleX, Linaria) | Build-time extraction to static CSS | None | Works in principle | TypeScript-typed styles; extra build tooling |
| **Runtime CSS-in-JS** (styled-components, Emotion) | Styles generated in the browser/at render | Real: serialise and inject styles during render | Client Components only, needs a style registry | Costly on low-end mobile; adds JS; complicates streaming |
| **Inline `style={{}}`** | Per element | Low | Works | Good for truly dynamic values (e.g. a measured width or CSS variable); no pseudo-classes or media queries |
| **Sass** | Modules via `*.module.scss` | None | Works | Needs the `sass` package; mostly superseded by modern CSS (nesting, variables) |

### Key properties

**1. CSS Modules as the default**
- Locally scoped class names, zero runtime, plain CSS, compiled by Next.js with no extra configuration.
- Place a module next to its component; import it as `styles`. Works in Server and Client Components.

**2. Tailwind as an equally valid default in this stack**
- Tailwind v4 generates one static CSS file at build time: no runtime, small, cache-friendly, Server Component safe.
- Configure tokens in CSS (`@theme`), not in a JavaScript config file.
- Class names must appear **in full** in source files; Tailwind scans text, so `` `bg-${color}-500` `` is never generated.

**3. Runtime CSS-in-JS has architectural costs**
- Needs JavaScript to produce CSS on every render, adding main-thread work (hurts INP, principle 8) and bundle weight.
- Needs `"use client"`, a **style registry** and `useServerInsertedHTML` to work with SSR and streaming (see the Next.js CSS-in-JS guide).
- Result: less of the tree can be a Server Component.
- Decide with a **mobile benchmark**, not by habit: measure scripting time, INP and total JS on a mid-range Android profile with CPU throttling.

**4. Theme with CSS variables, not JavaScript**
- Light/dark and brand themes are variable remaps on `:root`, `.dark` or `[data-theme]` (see principle 15).
- Switching theme is then a class change, with no re-render of styled components. Set the theme in a tiny blocking script or a cookie before first paint to avoid a flash.

**5. Order, layers and specificity**
- Next.js concatenates CSS; import order matters. Keep global CSS in the root layout and component CSS beside components.
- Use CSS **cascade layers** (`@layer`) to make order explicit. Tailwind v4 already uses layers (`theme`, `base`, `components`, `utilities`), so unlayered custom CSS overrides utilities, which is a common surprise.
- Avoid `!important` and high-specificity selectors; they are architectural debt.

### Practical patterns in Next.js (TypeScript)

**CSS Module for a component**
```css
/* components/Panel/Panel.module.css */
.panel {
  border: 1px solid var(--color-border);
  border-radius: var(--radius-md);
  padding: var(--space-4);
}
.panel[data-tone="warning"] {
  border-color: var(--color-warning);
}
```
```tsx
// components/Panel/index.tsx
import styles from "./Panel.module.css";

export function Panel({ tone, children }: { tone?: "warning"; children: React.ReactNode }) {
  return <section className={styles.panel} data-tone={tone}>{children}</section>;
}
```
Prefer **data attributes** (`data-tone`) over conditional class-name concatenation for state-driven styling.

**Tailwind v4 setup (as used with Next.js)**
```js
// postcss.config.mjs
export default { plugins: { "@tailwindcss/postcss": {} } };
```
```css
/* app/globals.css */
@import "tailwindcss";

@theme {
  --color-brand: oklch(0.6 0.2 260);
  --font-display: "Inter", sans-serif;
}
```

**Dynamic values: CSS variable, not a generated class**
```tsx
<div
  className="w-(--progress) h-2 bg-brand"
  style={{ "--progress": `${percent}%` } as React.CSSProperties}
/>
```
Tailwind v4 accepts a variable directly in an arbitrary value (`w-(--progress)`), so a runtime number never needs a runtime stylesheet.

**Dark mode via a custom variant (class strategy)**
```css
@custom-variant dark (&:where(.dark, .dark *));
```
Then `dark:bg-gray-900` follows a `.dark` class on `<html>`, which the theme script sets before first paint.

**If you must use runtime CSS-in-JS (Next.js guide)**
1. Create a **style registry** that collects the rules rendered on the server.
2. Inject them with `useServerInsertedHTML` before the content that uses them.
3. Wrap the app in the registry from a Client Component.

Treat this as a cost to be justified with a benchmark.

### Decision flow
1. New component with its own look? **CSS Module** (or Tailwind utilities if the team uses Tailwind).
2. Visual language shared across components? **Tokens as CSS variables** (principle 15).
3. A value that changes at runtime (width, colour from data)? **Inline CSS variable**.
4. Typed, programmatic styles needed at scale? **Zero-runtime** (vanilla-extract, Panda, StyleX).
5. Need runtime CSS-in-JS? **Benchmark on mobile first**; accept `"use client"` and registry setup.

### Rules of thumb
1. **Zero-runtime by default** (CSS Modules or Tailwind). Runtime CSS-in-JS needs a measured reason.
2. **One primary approach per codebase.** A second one needs a boundary (for example "Tailwind for layout, modules for complex components").
3. **Tokens in CSS variables**; themes remap variables.
4. **Global CSS only for resets, tokens and base typography.**
5. **Never build Tailwind class names dynamically**; map to full class strings.
6. **Use data attributes for state variants**, not class-string concatenation.
7. **Control order with `@layer`**; avoid `!important`.
8. **Set the theme before first paint** to avoid a flash and layout shift (CLS).

### Anti-patterns
- Mixing three styling systems in one component.
- Adding runtime CSS-in-JS to an App Router app "because we know it", then marking pages `"use client"` to make it work.
- Building utility class names with template strings.
- Large global stylesheets with generic selectors (`.card`, `.title`) that collide.
- `!important` wars and deep selector chains.
- Per-component theme logic in JavaScript (`isDark ? ... : ...`) when a CSS variable would do.
- A flash of the wrong theme on load (theme applied after hydration).
- Inline styles for things that need `:hover`, `:focus-visible` or media queries.

### Industry best practices
- **Keep specificity flat**: single-class selectors, no nesting deeper than two or three levels, no IDs for styling.
- **Use modern CSS before reaching for JavaScript**: custom properties, `clamp()`, container queries (`@container`), `:has()`, logical properties (`margin-inline`), `color-mix()`, nesting, `@layer`.
- **Design mobile-first** and use fluid sizing (`rem`, `clamp()`) so layouts adapt without many breakpoints.
- **Use logical properties and `dir`-aware utilities** (`ps-4`, `me-2`) so right-to-left languages work without rewrites.
- **Load fonts with `next/font`** (self-hosted, `display: swap`, size-adjusted fallback) to avoid layout shift (principle 8).
- **Keep the critical CSS small**: split global from route-level CSS; remove unused CSS; check the generated stylesheet size after each Tailwind upgrade.
- **Lint styles**: Stylelint (or Biome) for CSS Modules; `prettier-plugin-tailwindcss` for class ordering; ESLint rules for Tailwind where adopted.
- **Use `cva` or a variant helper plus `tailwind-merge`** to resolve conflicting utilities predictably.
- **Prefer `:focus-visible`, `prefers-reduced-motion`, `prefers-color-scheme` and `forced-colors`** media features as first-class concerns.
- **Animate only `transform` and `opacity`** where possible, and avoid layout-triggering properties in animations.
- **Keep z-index on a named scale** (tokens such as `--z-modal`) instead of arbitrary numbers.
- **Record the styling decision** (ADR) including the benchmark result if CSS-in-JS was considered.
- **Benchmark on real mid-range mobile devices** (or CPU-throttled profiles) with the metrics that matter: scripting time, INP, LCP, total JS.

### Things to avoid
- Using `@apply` heavily to recreate a CSS-class system on top of Tailwind; prefer components.
- Arbitrary values (`w-[137px]`) scattered through markup instead of tokens.
- Styles that depend on DOM structure (`div > div > span`) and break when markup changes.
- Importing component CSS in the wrong order and relying on the accident.
- Global `*` selectors and element selectors for components.
- Pixel units for font sizes and spacing that should scale with user settings.
- Animating `width`, `height`, `top` or `left`, which triggers layout.
- Large, unscoped third-party CSS bundles imported globally.
- Mixing CSS-in-JS runtimes (two libraries) in one app.
- Theme flicker caused by applying the theme class after hydration.

### Checklist
- [ ] A single documented primary styling approach, and the allowed exceptions.
- [ ] No runtime CSS-in-JS unless a mobile benchmark justified it (and the result is recorded).
- [ ] Tokens are CSS variables; dark/brand themes remap variables.
- [ ] Theme is applied before first paint; no flash, no layout shift.
- [ ] No dynamically constructed Tailwind class names.
- [ ] Global CSS limited to resets, tokens, base typography.
- [ ] Cascade order is controlled by `@layer`; no unexplained `!important`.
- [ ] Stateful variants use data attributes or `cva`.
