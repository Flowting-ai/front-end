## 15. Design System & Library

> One source of truth for the visual language: components, tokens and guidelines. Tested once, reused everywhere. Treat it as a versioned public API.

### Definition
A design system is more than a component library. It has three layers that must stay consistent:

1. **Tokens**: named design decisions (colour, spacing, type, radius, shadow, motion), the single source of the visual language.
2. **Components**: accessible, tested building blocks built **only** from tokens.
3. **Guidelines**: when and how to use them (content, patterns, accessibility, do and don't).

The library is the code that ships layers 1 and 2. Because many features depend on it, it behaves like a **public API**: changes can break every consumer.

### Key properties

**1. Tokens in layers**
| Layer | Example | Purpose |
|---|---|---|
| Primitive | `--color-blue-600`, `--space-4` | Raw palette and scale; no meaning |
| Semantic | `--color-text-primary`, `--color-surface-raised`, `--color-border-focus` | Intent; what components use; swapped per theme |
| Component | `--button-bg`, `--input-border` | Optional per-component overrides |

- Components reference **semantic** tokens, never primitives and never hard-coded hex values. Dark mode then becomes a remap of semantic tokens, not a rewrite of components.

**2. Tested once, reused everywhere**
- Each component is tested for behaviour, keyboard use, focus, ARIA and visual states in one place (unit tests, plus Storybook or an equivalent for states).
- Consumers get an accessible component for free (principle 20) and do not re-implement it.

**3. Versioned public API**
- Follow semantic versioning: **patch** (fix), **minor** (additive, backwards compatible), **major** (breaking: renamed prop, removed variant, changed default).
- Deprecate before removing: keep the old prop for one minor, log a dev-only warning, then remove in the next major.
- Use a changelog (Changesets is the common tool in monorepos) so consumers see what changed.

**4. Constrained by design**
- The system provides the **right** options and makes the wrong ones hard: a closed set of `variant` and `size` values, not a free `className` for everything.
- Escape hatches (`className`, `asChild`) exist but are documented and limited.

**5. Governed contribution**
- A clear path to propose, review and add components, and a rule for when something is promoted from a feature into the system (principle 12's rule of three).

### Where the code lives
| Setup | When | Notes |
|---|---|---|
| In-app folder (`components/ui/`) | One app, small team | Cheapest. Keep it free of feature imports so it can be extracted later |
| Internal package in a monorepo (`packages/ui`) | Several apps share it | Atomic changes across apps (principle 17); consume as source via `transpilePackages` or ship compiled |
| Published private/public npm package | Many repos or teams | Real semver, release process, support burden |
| Copy-in model (shadcn/ui style) | Want ownership of the code | You own the files; no upstream upgrades, but full control |

### Practical patterns in Next.js (TypeScript, Tailwind v4)

**Tokens as CSS variables, exposed to Tailwind with `@theme`**
```css
/* styles/tokens.css (imported once from globals.css) */
@import "tailwindcss";

/* Primitives: raw scale */
:root {
  --blue-600: oklch(0.55 0.2 260);
  --gray-50: oklch(0.98 0 0);
  --gray-900: oklch(0.2 0 0);
}

/* Semantic: intent, remapped per theme */
:root {
  --surface: var(--gray-50);
  --text: var(--gray-900);
  --accent: var(--blue-600);
}
.dark {
  --surface: var(--gray-900);
  --text: var(--gray-50);
}

/* Expose semantic tokens as Tailwind utilities (bg-surface, text-text, bg-accent) */
@theme inline {
  --color-surface: var(--surface);
  --color-text: var(--text);
  --color-accent: var(--accent);
}
```
- In Tailwind v4 there is **no `tailwind.config.js` by default**; tokens live in CSS with `@theme`, and every token becomes a CSS variable too.
- Use `@theme inline` when a token's value references another variable that changes at runtime (as above for light/dark). Plain `@theme` emits the variable on `:root` and utilities read it through `var()`.
- Use `@source` to tell Tailwind to scan a package in a monorepo (for example `@source "../../packages/ui";`), otherwise its classes are not generated.

**A component built only from semantic tokens, with a closed API**
```tsx
// packages/ui/src/Button.tsx
import { cva, type VariantProps } from "class-variance-authority";
import { Slot } from "@radix-ui/react-slot";

const button = cva(
  "inline-flex items-center justify-center rounded-md font-medium " +
  "focus-visible:outline-2 focus-visible:outline-offset-2 disabled:opacity-50",
  {
    variants: {
      variant: {
        primary: "bg-accent text-white hover:opacity-90",
        ghost: "bg-transparent text-text hover:bg-surface",
      },
      size: { sm: "h-8 px-3 text-sm", md: "h-10 px-4" },
    },
    defaultVariants: { variant: "primary", size: "md" },
  },
);

export type ButtonProps = React.ButtonHTMLAttributes<HTMLButtonElement> &
  VariantProps<typeof button> & { asChild?: boolean };

export function Button({ variant, size, asChild, className, ...rest }: ButtonProps) {
  const Comp = asChild ? Slot : "button";
  return <Comp className={button({ variant, size, className })} {...rest} />;
}
```

**Export surface: one entry point, explicit exports**
```ts
// packages/ui/src/index.ts   everything not exported here is private
export { Button, type ButtonProps } from "./Button";
export { Dialog } from "./Dialog";
```
Only what `index.ts` exports is the public API. Deep imports into internals are a breaking-change hazard.

**Server/client awareness**
- Keep stateless primitives (Button, Badge, Card) free of `"use client"` so they can render on the server.
- Put `"use client"` only on components that need state or events (Dialog, Dropdown, Tabs). Do **not** add it to a barrel `index.ts`, or every export is pulled into the client bundle (principle 6).

**Component documentation as tests**
- Document each state (default, hover, focus, disabled, loading, error) in Storybook or a visual-regression suite; run accessibility checks (axe) against those stories in CI (principle 18).

### Rules of thumb
1. **Tokens first, components second.** No raw hex or pixel values in components.
2. **Semantic tokens in components**; primitives only inside the token files.
3. **Closed variant sets**; limit free-form `className` and style props.
4. **Version it**: semver, changelog, deprecation window.
5. **Accessible by default**: keyboard, focus ring, ARIA built into the component, tested once.
6. **No feature imports** inside the system: dependencies point one way (feature → system).
7. **Promote on the third use**, not the first.
8. **Measure adoption**: count raw `<button>` or custom colours that bypass the system.

### Anti-patterns
- A component library with no tokens (every component hard-codes its own colours).
- Theme by duplicating components (`ButtonDark`) instead of remapping semantic tokens.
- Breaking changes shipped as a minor or patch.
- A barrel file with `"use client"` that drags the whole library into every page.
- Components that import from feature code or from app-level context.
- Tailwind classes in a shared package not scanned by the app (missing `@source`), so styles silently vanish.
- "Just add a prop" for every request until a component has 30 props.
- Documenting only the happy path and no accessibility behaviour.

### Industry best practices
- **Adopt a clear token naming convention** (`category-property-role-state`, e.g. `color-text-muted`, `space-4`) and follow the Design Tokens Community Group format so tokens can move between design tools and code.
- **Keep design and code in sync**: tokens exported from the design tool (Figma variables) or generated into CSS by a script; never maintained twice by hand.
- **Build on accessible headless primitives** (Radix UI, Base UI, React Aria) and style them with your tokens.
- **Document with live examples** (Storybook or equivalent): every variant and state, usage guidance, accessibility notes, do and don't.
- **Add visual regression testing** (Chromatic, Playwright screenshots) on stories, and **axe checks** on each story.
- **Use semver with automated releases** (Changesets) and publish a changelog with migration notes; provide **codemods** for breaking changes.
- **Deprecate in steps**: mark `@deprecated` in TypeScript doc comments, warn in development only, remove in a major.
- **Support theming through tokens**, including dark mode, high contrast and density, without forking components.
- **Provide composition escape hatches** (`asChild`, slots, `className` merged with `tailwind-merge`) so teams do not fork components.
- **Set a contribution and governance model**: intake, review criteria (accessibility, tests, docs), and an owner.
- **Track adoption and drift** (lint rules against raw colours, usage analytics of components) and report coverage.
- **Keep the package small and tree-shakable**: ESM exports, `sideEffects: false`, per-component entry points, and no heavy dependencies in primitives.
- **Version and test against the framework versions you support** (React 19 and the Next.js version in use).

### Things to avoid
- Building a full design system before there are three real consumers; start with tokens and five to ten primitives.
- A design system maintained by a team that does not ship product code with it.
- Pixel-perfect copies of design files that ignore content length, localisation and accessibility.
- Tokens named for their value (`blue-500` used as "primary action"); name them by intent in the semantic layer.
- Exposing implementation details (internal class names, DOM structure) as the API.
- Letting the system depend on a CSS-in-JS runtime that forces client rendering for every component.
- Breaking changes without a migration path or a deprecation window.
- Treating the Figma file and the code as two sources of truth.
- Global CSS resets that leak into embedded or third-party content.
- Skipping documentation because "the stories are enough".

### Checklist
- [ ] Tokens are defined once, in layers (primitive → semantic), in CSS.
- [ ] Dark mode (or any theme) is a semantic-token remap, not component forks.
- [ ] Every component has tests for keyboard, focus, ARIA and each variant.
- [ ] Public API is one explicit entry point; internals are not importable.
- [ ] Semver and a changelog are followed; deprecations have a window.
- [ ] Stateless components carry no `"use client"`; no `"use client"` on barrel files.
- [ ] Tailwind `@source` covers any shared package that uses classes.
- [ ] Adoption is measured; raw colours and ad-hoc buttons are tracked and shrinking.
