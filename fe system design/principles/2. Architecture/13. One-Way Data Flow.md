## 13. One-Way Data Flow

> Data flows down through props; events flow up through callbacks. Every state change has a traceable cause. Controlled components simulate two-way binding without giving up the single direction.

### Definition
In React, a parent passes data to a child as props, and a child tells its parent something happened by calling a function the parent gave it. State has **one owner**; everything else receives a copy by props. The child cannot mutate the parent's data, so to find why a value changed you only look **up** the tree, to the one component that owns it.

In the App Router the flow has a longer path: **server → client → server**. Data is read on the server and flows down as serialisable props; user events flow up in Client Components and go back to the server via **Server Actions** (or route handlers); the server revalidates and new data flows down again.

```
 Server (read)  ──props──▶  Client component  ──state──▶  children
      ▲                          │ events (callbacks)
      └──── Server Action ◀──────┘   then revalidate, new props flow down
```

### Key properties

**1. State has a single owner**
- Keep each piece of state in exactly one place: the **lowest common ancestor** of the components that need it.
- If two siblings need it, lift it to their parent. If it is needed everywhere, consider context or a store (see below), not copies.

**2. Props down, callbacks up**
- Props are **read-only**. Never mutate a prop, and never mutate an object or array held in state; create a new one.
- A child reports intent (`onSelect(id)`); the owner decides what that means.

**3. Every change has a traceable cause**
- State changes only inside event handlers, effects or reducers. Reading the owner's setters tells you every way the state can change.
- With a reducer, the list of action types is the complete list of causes.

**4. Controlled components simulate two-way binding**
- A controlled input gets `value` and `onChange` from its owner. The DOM shows what state says, and typing updates state, so the loop closes through React, not behind its back.
- An uncontrolled input (`defaultValue`, read via `FormData` or a ref) is fine for simple forms; the rule is to pick one per field, never mix.

**5. Derive instead of duplicate**
- Anything computable from existing state or props is calculated during render, not stored.
- Duplicated state is the main way one-way flow breaks: two copies drift apart.

### Where state should live
| State kind | Home | Notes |
|---|---|---|
| Server data (lists, records) | Server Component fetch; cache layer on the client only if needed | Do not copy into `useState` |
| UI state local to one component (open, hover, draft) | `useState` in that component | Keep it low |
| UI state shared by siblings | Lift to nearest common parent | Pass value down, callback up |
| Shareable, bookmarkable state (filters, tab, page) | **URL** (`searchParams`, route segments) | Survives refresh, link-sharable, server-readable |
| Cross-tree app state (theme, current user, org) | Context provider at a deep boundary | Split by change rate; avoid one mega-context |
| Complex transitions | `useReducer` | Explicit, testable action list |
| Form state | `<form action>` + `useActionState`; controlled fields only when live validation needs it | |
| Server-fetched, client-refreshed data | TanStack Query / SWR | The library owns the cache; components subscribe |
| Persisted preferences | `localStorage` or a cookie, read once into state | Storage is a sink, not the source of truth during render |

### Practical patterns in Next.js (TypeScript)

**Controlled input, state owned by the parent**
```tsx
"use client";
import { useState } from "react";

export function SearchBox({ onSearch }: { onSearch: (q: string) => void }) {
  const [q, setQ] = useState("");                       // single owner
  return (
    <form onSubmit={(e) => { e.preventDefault(); onSearch(q); }}>
      <input value={q} onChange={(e) => setQ(e.target.value)} />  {/* controlled */}
      <button>Search</button>
    </form>
  );
}
```

**Events up, via a Server Action; fresh props down**
```tsx
// app/actions.ts
"use server";
import { revalidatePath } from "next/cache";

export async function renameProject(id: string, formData: FormData) {
  const name = String(formData.get("name") ?? "").trim();
  if (!name) return { error: "Name is required" };      // expected error as a value
  await db.project.update({ id, name });
  revalidatePath(`/projects/${id}`);                    // server re-reads, new props flow down
  return { error: null };
}
```
```tsx
"use client";
import { useActionState } from "react";
import { renameProject } from "@/app/actions";

export function RenameForm({ id, name }: { id: string; name: string }) {
  const [state, action, pending] = useActionState(renameProject.bind(null, id), { error: null });
  return (
    <form action={action}>
      <input name="name" defaultValue={name} />
      {state.error && <p role="alert">{state.error}</p>}
      <button disabled={pending}>Save</button>
    </form>
  );
}
```
The server is the source of truth. After the action, `revalidatePath` makes the Server Component re-render with the saved value, so there is no hand-copied client state to reconcile.

**Optimistic updates without a second source of truth**
```tsx
"use client";
import { useOptimistic } from "react";

export function Likes({ count, onLike }: { count: number; onLike: () => Promise<void> }) {
  const [optimistic, add] = useOptimistic(count, (c, n: number) => c + n);
  return <button onClick={async () => { add(1); await onLike(); }}>{optimistic}</button>;
}
```
`useOptimistic` layers a temporary value over the real prop; when the server responds the real prop replaces it.

**URL as state**
```tsx
// app/(app)/agents/page.tsx   Server Component reads the URL directly
export default async function Page({ searchParams }: { searchParams: Promise<{ q?: string }> }) {
  const { q = "" } = await searchParams;
  const agents = await listAgents({ query: q });
  return <AgentList agents={agents} />;
}
```
A filter in the URL needs no client state, survives refresh and can be shared as a link.

**Reducer for traceable transitions**
```ts
type Action = { type: "added"; item: Item } | { type: "removed"; id: string } | { type: "cleared" };

function reducer(state: Item[], a: Action): Item[] {
  switch (a.type) {
    case "added": return [...state, a.item];
    case "removed": return state.filter((i) => i.id !== a.id);
    case "cleared": return [];
  }
}
```
The `Action` union is the full, typed list of every way this state can change.

### Context without breaking the flow
- Context is still one-way (provider value flows down); it just skips intermediate props.
- Split contexts by **change frequency** (a theme that changes rarely vs. streaming chat state that changes constantly) so a fast-changing value does not re-render unrelated consumers.
- Keep the setter separate from the value (two contexts, or a stable dispatch) so components that only write do not re-render on every change.
- Put the provider as deep as possible and wrap `{children}` so server content stays server-rendered (principle 6).

### Rules of thumb
1. **One owner per piece of state**; lift only as far as needed.
2. **Never mutate** props or state; return new objects.
3. **Derive** values during render; do not store what you can compute.
4. **Use the URL** for state users may share, bookmark or refresh.
5. **Read on the server, write through Server Actions**, then revalidate.
6. **Prefer reducers** when state transitions have more than two or three causes.
7. **Choose controlled or uncontrolled per field**, and stick to it.
8. **Keep context small and split by change rate.**

### Anti-patterns
- `useState(props.x)` plus an effect to "sync" it (two sources of truth).
- Mutating state (`items.push(x); setItems(items)`): React sees the same reference and may not re-render.
- A child reaching into a parent's state through a shared mutable module variable or a ref.
- Fetching initial data in `useEffect` into local state when a Server Component could pass it as props.
- One giant context holding everything, re-rendering the whole tree on each keystroke or stream chunk.
- Switching an input between `value` and `defaultValue` (controlled/uncontrolled warning, lost input).
- Using `localStorage` as the live source of truth during render (hydration mismatches; two tabs disagree).
- Effect chains: effect A sets state that triggers effect B that sets state. Replace with one event handler or derived value.

### Industry best practices
- **Colocate state as low as possible**, then lift only when a second consumer appears.
- **Treat the server as the source of truth** for persisted data; keep client stores for UI state and short-lived caches.
- **Use a data-fetching cache library** (TanStack Query or SWR) for client-side server state instead of hand-rolled `useEffect` + `useState`; you get deduplication, caching, retries, invalidation and stale-while-revalidate.
- **Use immutable updates** (spread, `map`/`filter`, or Immer for deep structures).
- **Model state as a discriminated union** (`{ status: "idle" } | { status: "loading" } | { status: "error"; error } | { status: "success"; data }`) so impossible states cannot be represented.
- **Normalise relational client data** (by ID) when many components read the same entities, so one update changes every view.
- **Use `useSyncExternalStore`** (directly or through a store library such as Zustand) for external stores, so concurrent rendering stays consistent.
- **Select, don't subscribe to everything**: read the slice of a store a component needs, so unrelated updates don't re-render it.
- **Handle optimistic updates with rollback**, and reconcile with the server response.
- **Debounce or throttle** high-frequency events (typing, scroll, resize, streamed tokens) before they hit state or the network.
- **Make actions idempotent and cancellable** (`AbortController` for fetches, request IDs to ignore stale responses).
- **Log state transitions in development** (reducer actions, store devtools) so causes are traceable.
- **Revalidate after mutation** (`revalidatePath`/`revalidateTag`, or query invalidation) rather than patching several caches by hand.

### Things to avoid
- Storing the same server entity in several stores or contexts.
- Global stores for state that only one subtree uses.
- Imperative event buses and ad-hoc `window` events for ordinary parent/child communication.
- Race conditions from unguarded async effects (a slow response overwriting a newer one).
- Updating state in an effect solely to react to another state change.
- Passing setters through many layers instead of exposing a narrow callback (`onSelect`, `onSave`).
- Mixing sources of truth for one value (URL, local state and `localStorage` all "owning" the same filter).
- Writing to state during render, which causes loops and warnings.
- Using refs to hold values that should re-render the UI.
- Persisting derived values; persist the inputs and recompute.

### Checklist
- [ ] For each piece of state you can name its single owner.
- [ ] No prop is copied into state without a documented reason (e.g. "draft" of a prop).
- [ ] Shareable view state (filters, tabs, pagination) is in the URL.
- [ ] Mutations go through Server Actions or a typed API layer, followed by revalidation.
- [ ] Expected errors are returned as values and shown in the UI.
- [ ] No in-place mutation of state; arrays and objects are replaced.
- [ ] Contexts are split by change rate; providers wrap `{children}` as deep as possible.
- [ ] Each form field is clearly controlled or uncontrolled.
