## 17. Monorepo Structure

> Multiple apps and packages in one repository with smart, cached build orchestration. Atomic cross-package refactors in one PR. Turborepo or Nx rebuild only what changed.

### Definition
A monorepo is **one repository containing several projects** (apps and shared packages) with defined relationships between them. It is not the same as a monolith: the projects stay separately built and separately deployable. The value comes from two things: **shared code with atomic changes**, and a **task runner** that understands the dependency graph and skips work that has not changed.

### Key properties

**1. Atomic cross-package change**
- Changing a shared component and every app that uses it happens in **one PR, one review, one CI run**. No publish-then-bump-then-fix cycle across repositories.
- Versions drift less because everything is built from the same commit.

**2. Task graph and caching**
- A task runner (Turborepo, Nx) reads the package dependency graph, runs tasks in the right order and in parallel, and **caches outputs by input hash**. Unchanged packages are restored from cache instead of rebuilt.
- **Remote caching** shares the cache between developers and CI, so one person's build speeds up everyone else's.
- Only affected projects run on a PR (`--filter` / `affected`), which keeps CI time flat as the repo grows.

**3. Workspace layout**
```
repo/
  apps/
    web/              Next.js app (deployable)
    docs/             Next.js app (deployable)
  packages/
    ui/               design system (principle 15)
    config-eslint/    shared lint config
    config-ts/        shared tsconfig bases
    contracts/        shared types and API clients
  package.json        workspaces
  turbo.json          task graph
```
- **apps/** are deployable and are never imported by anything.
- **packages/** are libraries; dependencies point **downward** only (apps → packages; packages may depend on lower packages, never on apps; no cycles).

**4. Internal packages**
| Style | How | Trade-off |
|---|---|---|
| **Just-in-time (source)** | Package exports `.ts/.tsx` directly; the app compiles it (`transpilePackages` in Next.js, or bundler support) | Simplest, fastest iteration; the app owns the compile step |
| **Compiled** | Package builds to `dist/` with its own `build` task; apps consume the output | Faster consumer builds and cacheable; needs a build step and type declarations |
| **Published** | Released to npm | Only when consumers live outside the repo |

**5. Boundaries need enforcement**
- Without rules, a monorepo becomes a big ball of mud. Enforce boundaries with lint rules (Nx module boundaries, or `eslint-plugin-boundaries`, or `no-restricted-imports`), explicit `exports` in each package, and `CODEOWNERS` per directory.

### Turborepo vs Nx (short)
| | Turborepo | Nx |
|---|---|---|
| Focus | Fast task running and caching on top of npm/pnpm/yarn workspaces | Full toolkit: task runner, generators, boundaries, project graph UI, affected |
| Config | `turbo.json` | `nx.json` + per-project config |
| Remote cache | Vercel Remote Cache, or self-hosted | Nx Cloud, or self-hosted |
| Fit | Small and medium repos that want low ceremony | Large repos that want generators and strict boundaries |

Both work with Next.js. Pick one; do not combine.

### Practical patterns in Next.js (TypeScript)

**Workspace root**
```json
// package.json
{
  "name": "repo",
  "private": true,
  "packageManager": "pnpm@9.x",
  "workspaces": ["apps/*", "packages/*"],
  "devDependencies": { "turbo": "^2" }
}
```
(With pnpm, workspaces are declared in `pnpm-workspace.yaml` instead.)

**Task graph (`turbo.json`, Turborepo 2.x uses `tasks`)**
```json
{
  "$schema": "https://turborepo.dev/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": [".next/**", "!.next/cache/**", "dist/**"]
    },
    "lint": { "dependsOn": ["^build"] },
    "typecheck": { "dependsOn": ["^build"] },
    "test": { "dependsOn": ["^build"], "outputs": ["coverage/**"] },
    "dev": { "cache": false, "persistent": true }
  }
}
```
- `^build` means "build my dependencies first".
- `outputs` tells Turborepo what to cache; exclude `.next/cache`.
- `dev` is never cached and is long-running (`persistent`).
- Declare every environment variable that changes a build's output (`env` / `globalEnv`), or the cache can serve a stale result.

**Consuming a source-only internal package in Next.js**
```ts
// apps/web/next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  transpilePackages: ["@acme/ui", "@acme/contracts"],
};
export default nextConfig;
```
```css
/* apps/web/app/globals.css: Tailwind v4 must be told to scan the package */
@import "tailwindcss";
@source "../../../packages/ui/src";
```
Without `@source`, Tailwind v4 may not detect classes used inside the shared package, and those styles will be missing.

**Package `exports` as the public API**
```json
// packages/ui/package.json
{
  "name": "@acme/ui",
  "exports": {
    ".": "./src/index.ts",
    "./button": "./src/Button.tsx"
  }
}
```

**Running only what changed**
```bash
turbo run build lint test --filter=...[origin/main]   # affected since main, plus dependents
turbo run build --filter=web                          # one app and its dependencies
turbo prune web --docker                              # minimal subset for a Docker build
```
(Check flag names against the Turborepo docs for your installed version.)

**Remote caching in CI**
```bash
# one-time: turbo login && turbo link
# CI environment:
TURBO_TOKEN=...   # secret
TURBO_TEAM=...    # team slug
```

### When to use it
| Use when | Avoid when |
|---|---|
| More than one app shares UI, types or config | One app, one team, no shared code |
| You want atomic refactors across app and library | Teams need hard access isolation per codebase |
| CI time is growing with the repo | The repo is small enough that full builds take a minute |
| You are adopting a design system or Multi-Zones (principles 14, 15) | Nobody will own boundaries and tooling |

### Rules of thumb
1. **apps/ deploy; packages/ are libraries.** Dependencies only point down; no cycles.
2. **One package manager, one lockfile**, pinned versions of shared tooling.
3. **Configure caching correctly**: complete `outputs`, declared env variables, no cache for `dev`.
4. **Enable remote caching** for CI and developers.
5. **Run affected only on PRs**; run everything on the main branch.
6. **Explicit `exports`** in every package; no deep imports.
7. **Enforce boundaries by lint and `CODEOWNERS`**, not by convention.
8. **Share config as packages** (tsconfig, ESLint, Tailwind tokens).

### Anti-patterns
- A monorepo with one app and no shared package (all cost, no benefit).
- Apps importing from other apps.
- Circular dependencies between packages.
- Missing `outputs` or env declarations, causing stale cache hits (or no caching at all).
- Compiling every internal package on every change (no caching, no filtering).
- Deep imports into another package's `src/`.
- Per-package copies of ESLint and TypeScript config that drift.
- Everyone owns everything, so nobody owns the tooling.

### Industry best practices
- **Pick pnpm workspaces** (or npm/yarn workspaces) for strict, fast, disk-efficient installs; pnpm's non-flat `node_modules` also catches undeclared dependencies.
- **Use the `workspace:*` protocol** for internal dependencies so local packages always resolve to the repo version.
- **Share configuration as packages** (`@acme/tsconfig`, `@acme/eslint-config`, Prettier, Tailwind tokens) and extend them in each project.
- **Use TypeScript project references or path aliases consistently** so editors and builds agree on package boundaries.
- **Version shared packages with Changesets** when they are published; for private packages, a single repo version is fine.
- **Keep the root `package.json` thin**: orchestration scripts and shared dev tools only; each app owns its runtime dependencies.
- **Define `CODEOWNERS` and review rules per directory**, so shared packages need review from their owners.
- **Add dependency-boundary lint rules** (Nx `enforce-module-boundaries`, `eslint-plugin-boundaries`, or `import/no-restricted-paths`) and fail CI on cycles (`madge`, `dpdm`).
- **Make every task runnable from the root and per package**, with identical script names (`build`, `lint`, `typecheck`, `test`).
- **Use affected-only CI on PRs** and a scheduled full run on the main branch; track cache hit rate.
- **Deploy each app independently** with its own project, environment variables and root directory setting; prune the workspace for Docker builds.
- **Use `turbo prune` or equivalent** to keep container images small, and a single Node version file (`.nvmrc`, `engines`).
- **Document how to add a package or app** (template or generator) so structure stays consistent.
- **Keep large binary assets and generated code out of the repo** or use Git LFS and generated-file markers.

### Things to avoid
- Hoisting surprises: relying on a dependency that is installed only because another package needs it (phantom dependencies).
- Packages that import files from another package by relative path (`../../other/src`).
- A shared `utils` package that becomes a dumping ground with no owner.
- Mixing multiple package managers or multiple lockfiles.
- Running every task for every change on every PR.
- Caching tasks that read undeclared inputs (files, env variables, network), producing wrong cache hits.
- Giving every package its own tooling versions.
- Long-lived branches that touch many packages; the benefit of atomic change is lost.
- Treating a monorepo as a licence to skip versioning and release discipline for shared packages that external consumers use.
- Moving to a monorepo and a task runner at the same time as a framework migration.

### Checklist
- [ ] Layout is `apps/` (deployable) and `packages/` (libraries); no cycles.
- [ ] One lockfile and one package manager version for the whole repo.
- [ ] `turbo.json` (or Nx config) has `dependsOn`, `outputs` and env variables for each task.
- [ ] Remote cache enabled and verified (cache hits visible in CI logs).
- [ ] PR CI uses affected filtering; main runs the full graph.
- [ ] Each package has an explicit `exports` map; boundaries enforced by lint.
- [ ] Next.js apps set `transpilePackages` for source-only packages, and Tailwind `@source` covers shared packages.
- [ ] `CODEOWNERS` assigns owners for each package and for the build tooling.
