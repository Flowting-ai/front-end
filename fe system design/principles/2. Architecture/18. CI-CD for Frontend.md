## 18. CI/CD for Frontend

> Lint, type-check, test, build, preview and promote: automated on every PR. Preview deploys end "can you share your screen?". Feature flags decouple deploy from release.

### Definition
**Continuous Integration (CI)** runs automated checks on every change so that the main branch is always releasable. **Continuous Delivery/Deployment (CD)** ships verified builds to environments automatically. A frontend pipeline has extra duties compared with a back-end one: it must verify the **user-visible result** (a rendered page, accessibility, bundle size, Web Vitals), not only that code compiles.

Two ideas keep releases safe and fast:
- **Preview deployments**: every PR gets its own live URL.
- **Feature flags**: **deploying** code (it is on production) and **releasing** a feature (users see it) become separate decisions.

### Key properties

**1. A staged pipeline, cheapest and fastest first**
| Stage | Checks | Typical time | Fails the PR? |
|---|---|---|---|
| Install | Locked install (`npm ci`) with a cached package store | Seconds to minutes | Yes |
| Static | ESLint (including accessibility rules), `tsc --noEmit`, formatting | Under 1 min | Yes |
| Unit/component | Vitest or Jest with a Testing Library | 1 to 3 min | Yes |
| Build | `next build`; reads route table and First Load JS | 2 to 6 min | Yes |
| Preview | Deploy a unique URL per PR | 1 to 3 min | Informational |
| End-to-end and a11y | Playwright against the preview URL, axe checks | 3 to 10 min | Yes (smoke on PR; full on main) |
| Performance | Bundle-size budget, Lighthouse CI or lab CWV check | 2 to 5 min | Budget breach fails |
| Promote | Merge triggers production deploy, or manual promotion of a verified build | Minutes | n/a |

Run independent stages **in parallel** (lint, typecheck and unit tests do not depend on each other).

**2. Preview deploys for every PR**
- Reviewers, designers and QA look at the real thing, with real data in a safe environment, without a local checkout or a screen-share.
- Post the URL on the PR automatically (Vercel and most platforms do this). Run E2E and accessibility checks against that URL.
- Previews must use **non-production secrets and a non-production backend**.

**3. Build once, promote the same artifact**
- The artifact tested in preview should be the one promoted. Do not rebuild for production with different inputs.
- Config that differs per environment (API origin, keys) comes from the environment at deploy or run time, not from a different build. Note that `NEXT_PUBLIC_*` values are inlined at build time, so changing them means rebuilding.

**4. Feature flags decouple deploy from release**
- Merge unfinished or risky work behind a flag that is **off**; ship continuously; turn on for staff, then a percentage, then everyone; turn off instantly if something breaks, with no redeploy.
- Flags are **temporary**: each has an owner and a removal date. Old flags are debt.
- Evaluate flags on the **server** where possible (no flicker, no leaking hidden features); in Next.js use a library such as the Flags SDK or your flag provider's SDK, and keep evaluation compatible with static rendering (principles 3 to 5).

**5. Fast rollback beats perfect prevention**
- Keep previous deployments instantly promotable (instant rollback on most platforms).
- Combine with progressive rollout (canary or percentage) and error monitoring so regressions are caught in minutes.

**6. Cache to keep CI fast**
- Cache the package manager store and Next.js's `.next/cache` between runs, keyed on the lockfile and source hash. Without it you may see a "No Cache Detected" warning and slower builds.
- In a monorepo, use remote caching and affected-only runs (principle 17).

### Practical patterns

**GitHub Actions: parallel checks plus a cached build**
```yaml
# .github/workflows/ci.yml
name: ci
on:
  pull_request:
  push: { branches: [main] }

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true          # newer push cancels the older run

jobs:
  static:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version-file: .nvmrc, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npx tsc --noEmit
      - run: npm test

  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version-file: .nvmrc, cache: npm }
      - uses: actions/cache@v4
        with:
          path: .next/cache
          key: nextjs-${{ runner.os }}-${{ hashFiles('package-lock.json') }}-${{ hashFiles('src/**/*.[jt]s', 'src/**/*.[jt]sx') }}
          restore-keys: |
            nextjs-${{ runner.os }}-${{ hashFiles('package-lock.json') }}-
      - run: npm ci
      - run: npm run build
```
The `restore-keys` fallback restores the cache from the same lockfile even if source changed, which is the pattern the Next.js CI caching guide recommends.

**Server-evaluated feature flag (Flags SDK style)**
```ts
// flags.ts
import { flag } from "flags/next";

export const newBilling = flag<boolean>({
  key: "new-billing",
  decide: () => false,              // replace with your provider's lookup
});
```
```tsx
// app/(app)/billing/page.tsx   Server Component
import { newBilling } from "@/flags";

export default async function Page() {
  return (await newBilling()) ? <BillingV2 /> : <BillingV1 />;
}
```
Evaluating on the server avoids a flash of the wrong UI and keeps unreleased code paths out of the client bundle when the branch is server-only. Note that reading a request-based flag makes the route dynamic; if the page must stay static, use the Flags SDK's precompute pattern or a build-time flag.

**Bundle budget as a gate**
```json
// package.json (concept; use size-limit, bundlewatch or next build output checks)
"size-limit": [{ "path": ".next/static/chunks/*.js", "limit": "300 kB" }]
```
Fail the PR when First Load JS for a route crosses its budget (principle 8).

**Branch protection**
- Require the `static` and `build` jobs to pass and one review before merge; block direct pushes to `main`.

### Rules of thumb
1. **Every PR gets the full fast checks** (lint, types, tests, build) and a preview URL.
2. **Parallelise** independent jobs; **cache** dependencies and `.next/cache`.
3. **Build once, promote that artifact**; environment config is injected, not rebuilt (except `NEXT_PUBLIC_*`).
4. **Ship dark behind flags**; every flag has an owner and an expiry.
5. **Gate on budgets**: bundle size and accessibility are test failures.
6. **Make rollback a one-click action**, and rehearse it.
7. **Treat flaky tests as incidents**: quarantine and fix, never ignore.
8. **Never put production secrets in preview or CI logs.**

### Anti-patterns
- A single slow job that runs lint, tests, build and E2E in sequence.
- "Works on my machine" reviews: no preview URL, so reviewers read diffs only.
- Rebuilding for production with different settings than the tested build.
- Long-lived flags nobody removes; flag combinations nobody tests.
- Client-side flag evaluation that shows the old UI for a moment, then switches.
- CI without caching, then complaining builds take 15 minutes.
- Previews pointed at the production database.
- Manual deploy steps in a wiki that only one person knows.

### Industry best practices
- **Measure the DORA metrics**: deployment frequency, lead time for changes, change failure rate and time to restore. Optimise for small, frequent, reversible releases.
- **Use trunk-based development** with short-lived branches (ideally under a day or two) and small PRs.
- **Keep the pipeline fast**: aim for PR feedback in about ten minutes or less; use `concurrency` to cancel superseded runs; shard slow test suites.
- **Pin tool versions** (Node via `.nvmrc`, package manager, GitHub Action versions or SHAs) and use `npm ci` for reproducible installs.
- **Shift security left**: dependency audit and secret scanning on every PR, CodeQL or equivalent static analysis, least-privilege `permissions:` on workflows, and OIDC for cloud credentials rather than long-lived secrets.
- **Scope secrets**: separate environments (preview, staging, production) with separate secrets and required reviewers for production deploys.
- **Test the deployed preview**, not only the local build: smoke E2E, accessibility and visual-regression checks against the preview URL.
- **Track performance in CI**: bundle-size budget per route, Lighthouse CI or lab Web Vitals checks, and real-user monitoring after release.
- **Upload source maps to the error tracker in CI** and tag every event with the release (commit SHA).
- **Automate dependency updates** (Dependabot or Renovate) with CI as the gate, and auto-merge safe patch updates.
- **Release progressively**: canary or percentage rollout, watch error rate and Web Vitals, then promote; keep one-click rollback.
- **Keep database or API changes backward compatible** (expand, migrate, contract) so frontend and backend can deploy independently.
- **Surface failures well**: clear logs, annotations on the PR, and a named owner for the pipeline.
- **Retire flags promptly**: a flag cleanup ticket is created when the flag is.

### Things to avoid
- Long-running release branches and big-bang releases.
- Manual, undocumented deploy steps or "deploy from my laptop".
- `continue-on-error` and ignored lint or type failures to "unblock" a merge.
- Third-party actions referenced by a mutable tag (`@main`) without review.
- Broad workflow permissions (`write-all`) and secrets exposed to pull requests from forks.
- Printing environment variables or tokens in logs.
- Retrying flaky tests until they pass instead of fixing or quarantining them.
- Running production deploys without an approval or an automatic health check.
- Building different artifacts for staging and production.
- Treating a green pipeline as proof of quality while skipping accessibility, performance and security gates.
- Keeping flags forever, or flipping flags with no audit trail.

### Checklist
- [ ] PR pipeline: install, lint (incl. a11y rules), typecheck, unit tests, build, run in parallel where possible.
- [ ] Branch protection requires those checks and review before merge.
- [ ] A preview URL is created per PR and posted on it; previews use non-production data and secrets.
- [ ] E2E smoke and accessibility checks run against the preview.
- [ ] Bundle-size budget (First Load JS per route) enforced.
- [ ] `.next/cache` and package store are cached in CI.
- [ ] Production deploys promote a tested artifact; rollback is one action.
- [ ] Feature flags have owners and removal dates; evaluated on the server where possible.
- [ ] Errors from the new release are visible within minutes (principle 19).
