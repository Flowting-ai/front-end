## 20. Accessibility

> A system-level concern from day one; expensive to retrofit at launch. Semantic HTML gives keyboard support and ARIA for free. WCAG 2.1 AA is the legal baseline (WCAG 2.2 AA is the current standard to target).

### Definition
Accessibility (a11y) means people with visual, motor, hearing or cognitive differences, and people on keyboards, screen readers, zoomed screens or poor conditions, can use the product. It is a **quality attribute of the architecture**, like performance or security: decided in the design system, the component contracts and the review process, not painted on at the end.

### The standard and the law
- **WCAG** (Web Content Accessibility Guidelines) is organised around four principles, **POUR**: **P**erceivable, **O**perable, **U**nderstandable, **R**obust. Conformance levels are A, AA, AAA; **AA** is the target almost everywhere.
- WCAG 2.1 AA is what most laws and contracts name. **WCAG 2.2** (2023) is backwards compatible with 2.1 and adds criteria that matter for modern apps (for example visible focus not obscured, larger minimum target size of 24 by 24 CSS px, consistent help, accessible authentication, dragging alternatives). Target **2.2 AA** for new work.
- Legal drivers include the ADA and Section 508 (US) and the **European Accessibility Act** (EU Directive 2019/882; business obligations applied from 28 June 2025). This is a pointer, not legal advice; ask your legal team which applies.
- Automated tools find roughly a third to half of issues. **Manual keyboard and screen-reader testing is required.**

### Key properties

**1. Semantic HTML first**
- Use the element that has the meaning: `button`, `a`, `nav`, `main`, `header`, `footer`, `ul`/`li`, `label`, `h1`-`h6`, `table`, `dialog`, `details`.
- You then get keyboard handling, focus, roles and screen-reader behaviour **for free**. `<div onClick>` gives you none of it.
- First rule of ARIA: **do not use ARIA if a native element does the job.** Wrong ARIA is worse than none.

**2. Keyboard operable**
- Every interactive element is reachable with Tab and operable with Enter/Space (and arrows for composite widgets).
- **Visible focus** always: use `:focus-visible`; never `outline: none` without a replacement.
- Logical focus order follows the visual order. No keyboard traps, except in modals, which must trap focus **and** release it on close, returning focus to the trigger.
- Provide a **skip link** ("Skip to content") as the first focusable element.

**3. Names, roles, states**
- Every control has an accessible **name** (visible label, `aria-label` or `aria-labelledby`). Icon-only buttons need a name.
- State is exposed (`aria-expanded`, `aria-pressed`, `aria-selected`, `aria-current`, `aria-invalid`, `aria-busy`).
- Use `aria-live` / `role="status"` / `role="alert"` for dynamic updates (toasts, form errors, streamed chat output).

**4. Visual design**
- Contrast: **4.5:1** for body text, **3:1** for large text and UI components or focus indicators (AA).
- Do not use colour as the only signal. Text resizes to 200% without loss. Layout reflows at 320 CSS px wide (no horizontal scroll). Respect `prefers-reduced-motion` and `prefers-color-scheme`.
- Target size: at least 24 by 24 CSS px (WCAG 2.2), with 44 by 44 preferred on touch.

**5. Forms**
- A visible `<label>` for each input, connected by `htmlFor`/`id`. Placeholders are not labels.
- Errors are described in text, linked with `aria-describedby`, announced, and tied to the field. Use correct `type` and `autocomplete` values.

**6. Single-page app specifics**
- Client-side navigation does not reload, so assistive tech is not told the page changed. **Next.js includes a route announcer** that reads the new page name from `document.title`, then the `<h1>`, then the pathname. Give **every route a unique, descriptive title** (use the Metadata API).
- Move focus deliberately after route changes, modal open/close and content replacement.
- Streaming and Suspense (principle 7): a loading skeleton should be announced with `aria-busy` or a status message, not appear silently.

**7. Systemic ownership**
- Put accessibility **in the design system** (principle 15): focus styles, tokens that meet contrast, and components with behaviour tested once. Consumers inherit it.
- Use headless accessible primitives (Radix UI, Base UI, React Aria) for complex widgets (dialog, menu, tabs, combobox, tooltip) rather than writing ARIA patterns by hand.

### Practical patterns in Next.js (TypeScript)

**Root layout: language, landmarks, skip link**
```tsx
// app/layout.tsx
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <a href="#main" className="sr-only focus:not-sr-only focus:absolute focus:p-3">
          Skip to content
        </a>
        <header>{/* nav landmark inside */}</header>
        <main id="main" tabIndex={-1}>{children}</main>
      </body>
    </html>
  );
}
```
`lang` is required (WCAG 3.1.1). `sr-only` hides visually but keeps the link available to keyboards and screen readers; `focus:not-sr-only` reveals it on focus.

**Unique page titles with the Metadata API**
```tsx
// app/(app)/settings/billing/page.tsx
export const metadata = { title: "Billing | Settings" };
```
This drives the route announcer and WCAG 2.4.2 (Page Titled).

**Accessible form field with an error**
```tsx
function Field({ id, label, error }: { id: string; label: string; error?: string }) {
  const errId = `${id}-err`;
  return (
    <div>
      <label htmlFor={id}>{label}</label>
      <input id={id} aria-invalid={!!error} aria-describedby={error ? errId : undefined} />
      {error && <p id={errId} role="alert">{error}</p>}
    </div>
  );
}
```

**Icon-only button needs a name**
```tsx
<button type="button" aria-label="Delete chat"><TrashIcon aria-hidden="true" /></button>
```

**Use a native or headless primitive for a modal**
```tsx
import * as Dialog from "@radix-ui/react-dialog";

<Dialog.Root>
  <Dialog.Trigger asChild><button>Delete</button></Dialog.Trigger>
  <Dialog.Portal>
    <Dialog.Overlay className="fixed inset-0 bg-black/50" />
    <Dialog.Content>
      <Dialog.Title>Delete project?</Dialog.Title>
      <Dialog.Description>This cannot be undone.</Dialog.Description>
      <Dialog.Close asChild><button>Cancel</button></Dialog.Close>
    </Dialog.Content>
  </Dialog.Portal>
</Dialog.Root>
```
Radix manages focus trap, focus return, Escape, `aria-modal` and labelling. Hand-rolling these is the usual source of defects.

**Live region for streamed or async status**
```tsx
<div role="status" aria-live="polite">{pending ? "Saving…" : saved ? "Saved" : ""}</div>
```
Use `polite` for non-urgent updates and `role="alert"` (assertive) only for errors. Do not announce every streamed token; announce start and end.

**Respect motion and contrast preferences**
```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; }
}
```
Tailwind equivalents: `motion-reduce:transition-none`, `motion-safe:animate-pulse`.

**Automated checks in the pipeline (principle 18)**
```ts
// e2e/a11y.spec.ts (Playwright + axe)
import { test, expect } from "@playwright/test";
import AxeBuilder from "@axe-core/playwright";

test("billing page has no detectable a11y violations", async ({ page }) => {
  await page.goto("/settings/billing");
  const results = await new AxeBuilder({ page }).withTags(["wcag2a", "wcag2aa", "wcag22aa"]).analyze();
  expect(results.violations).toEqual([]);
});
```
- **Lint**: `eslint-plugin-jsx-a11y` rules ship in `eslint-config-next` (static, baseline only: it cannot see dynamic props).
- **Component tests**: Testing Library queries by role and name (`getByRole("button", { name: "Delete chat" })`) double as accessibility assertions.
- **Manual**: keyboard-only pass, a screen reader (NVDA, VoiceOver), 200% zoom, and high-contrast mode before each release.

### Rules of thumb
1. **Native element first**; ARIA only to fill gaps.
2. **Everything works with a keyboard**, and focus is always visible.
3. **Every control has a name; every state is exposed.**
4. **One `h1` per page, headings in order, landmarks on the layout, unique titles.**
5. **Contrast and target size live in the tokens and primitives**, not in each feature.
6. **Use headless accessible primitives** for dialogs, menus, tabs, comboboxes.
7. **Announce dynamic changes** sparingly and politely.
8. **Test automatically and manually**; automation is the floor.

### Anti-patterns
- `<div onClick>` or `<span role="button">` instead of `<button>`.
- `outline: none` with no replacement focus style.
- Placeholder text as the only label.
- Colour-only status (red/green dots with no text or icon).
- Positive `tabindex` values (it breaks natural order); use `0` or `-1` only.
- Custom modals without focus trap, Escape handling or focus return.
- Auto-playing, flashing or unstoppable animation; ignoring `prefers-reduced-motion`.
- `aria-hidden="true"` on focusable elements.
- Announcing every streamed token through a live region.
- Treating accessibility as a pre-launch audit instead of a continuous requirement.

### Industry best practices
- **Shift left**: include accessibility acceptance criteria in design specs and tickets, review designs for contrast, focus order and states before build.
- **Use the accessibility tree as your test surface**: query by role and accessible name in tests, and inspect the tree in browser devtools.
- **Layer your testing**: lint (static), component tests with `jest-axe`/`vitest-axe`, E2E with axe, manual keyboard pass, then screen-reader sessions (NVDA + Firefox/Chrome on Windows, VoiceOver + Safari on macOS and iOS, TalkBack on Android).
- **Include people with disabilities in user testing** where possible; it finds issues no tool does.
- **Write meaningful `alt` text** (describe purpose, not "image of"); use `alt=""` for decorative images; give charts a text summary or data table.
- **Provide captions and transcripts** for video and audio; no auto-play with sound.
- **Make errors recoverable**: describe the problem and the fix, keep user input, avoid clearing forms on error, and allow review before submit for important actions.
- **Do not rely on timeouts**; if a session must expire, warn and allow extension.
- **Support zoom and text-spacing overrides**; avoid fixed heights that clip text.
- **Manage focus on dynamic UI**: move focus into a newly opened dialog, restore it on close, and focus the heading or main region after a route change when appropriate.
- **Use `inert`** to disable background content behind a modal, and `<dialog>` where it fits.
- **Design for touch and pointer alternatives**: no drag-only interactions (provide buttons), adequate target size, no hover-only content.
- **Publish an accessibility statement** and a feedback channel; fix reported issues on a tracked schedule.
- **Make accessibility part of the definition of done** and of design-system component acceptance.

### Things to avoid
- Overlay or "accessibility widget" products sold as a one-line fix; they do not make a site compliant.
- Relying on automated scores alone (a 100 in Lighthouse does not mean accessible).
- Using `title` as the only accessible name or help text.
- Auto-advancing carousels, auto-playing video with sound, or content that moves without a pause control.
- Disabling zoom (`maximum-scale=1`, `user-scalable=no`).
- Fixed-position elements that cover focused content (WCAG 2.2 focus not obscured).
- Custom scrollbars, selects and checkboxes that remove native semantics without replacing them.
- Hiding content with `display: none` that should be available to screen readers, or with `aria-hidden` on content that should be visible.
- Reading order that differs from visual order (CSS `order`, absolute positioning) without checking.
- Error messages that only change colour, or disappear before they can be read.
- Hiding the focus indicator on mouse use by removing it for everyone.
- Treating accessibility as one person's job.

### Checklist
- [ ] `<html lang>` set; each page has one `h1`, a unique `<title>` and landmarks (`header`, `nav`, `main`, `footer`).
- [ ] A skip link is the first focusable element.
- [ ] All interactive elements are native or built from accessible primitives; none are click-handlers on `div`.
- [ ] Focus is always visible (`:focus-visible`); focus order is logical; modals trap and restore focus.
- [ ] Every input has a label and linked error text; every icon-only control has an accessible name.
- [ ] Colour tokens meet 4.5:1 text and 3:1 UI contrast in light and dark themes.
- [ ] Reduced-motion and 200% zoom / 320px reflow are respected.
- [ ] Dynamic updates use appropriate live regions.
- [ ] `jsx-a11y` lint, axe in E2E, and role-based component tests run in CI; a manual screen-reader pass precedes releases.
