## 4. Incremental Static Regeneration (ISR)

> Static pages that rebuild on their own schedule: the next visitor after the window gets the fresh copy.

### Definition
ISR keeps the speed of static pages but lets each page refresh itself after deploy. Pages are prerendered at build (or on first request) and cached. Once a page's revalidation window has passed, the next request triggers regeneration in the background. When the new version is ready it replaces the cached one.

**Precise timing (important):** the first request after the window expires is still served the *stale* copy and triggers the rebuild. Requests after the rebuild finishes get the fresh copy. So "the next visitor gets fresh" is true in practice only for the visitor after the one who triggered regeneration. On low-traffic pages, one visitor may always see content up to one window old plus the regen time.

### Key properties

**1. Stale-while-revalidate applied to whole HTML pages**
- Same idea as the HTTP `stale-while-revalidate` cache directive, but applied by the framework to a full rendered route (HTML + RSC payload).
- Visitors never wait on a rebuild: they always get a cached response immediately. Latency stays CDN-fast.
- If regeneration fails, the last good page keeps being served. A broken upstream does not take the page down.
- Tradeoff accepted: bounded staleness. Content may be up to one revalidate window old (plus regen time).

**2. Per-page revalidation, no full-site redeploy**
- Each route (or each fetch/cache entry) has its own freshness policy. A pricing page can refresh hourly while a changelog refreshes daily.
- Content updates do not need `next build` or a deploy. Editors publish; the page refreshes by timer or by an on-demand trigger.
- Pages not pre-built are generated on first request and then cached (`dynamicParams`), so build time stays small while the long tail still gets static performance.

### When to use
- Mostly shared content that changes on a known cadence: product catalogs, pricing, blog and docs with CMS edits, public leaderboards, status or stats pages.
- Large page sets where full rebuilds are too slow.
- Pages that should survive upstream outages by serving the last good copy.

### When not to
- Per-user or permissioned content: use [SSR](1.%20Server%20Side%20Rendering.md) or [CSR](2.%20Client%20Side%20Rendering.md).
- Data that must be correct on every request (balances, inventory at checkout, auth state).
- Real-time data: use client fetching, SSE or WebSocket.
- Content that never changes: plain [SSG](3.%20Static%20Site%20Generation.md) is enough.
- Deployments that cannot run the Next.js server or a platform with ISR support (`output: "export"` has no ISR).

### How in Next.js + TypeScript

**Time-based revalidation** (route segment config, simplest form):

```tsx
// app/blog/[slug]/page.tsx
type Params = { slug: string };

export const revalidate = 3600;          // seconds; must be a static literal

export async function generateStaticParams(): Promise<Params[]> {
  const posts = await getTopPosts();     // pre-build the popular subset
  return posts.map((p) => ({ slug: p.slug }));
}
// dynamicParams defaults to true: other slugs render on first request, then cache

export default async function Post({ params }: { params: Promise<Params> }) {
  const { slug } = await params;
  const post = await getPost(slug);      // if missing: call notFound()
  return <Article post={post} />;
}
```

**Per-fetch revalidation and tags** (finer than the page level):

```ts
const res = await fetch(`${API}/posts/${slug}`, {
  next: { revalidate: 600, tags: ["posts", `post:${slug}`] },
});
```
When a page mixes several fetches with different `revalidate` values, the page effectively refreshes at the shortest one.

**On-demand revalidation** (publish instantly, no timer wait). Trigger from a CMS webhook route handler or a server action:

```ts
// app/api/revalidate/route.ts
import { revalidatePath, revalidateTag } from "next/cache";
import { NextResponse } from "next/server";

type Body = { secret?: string; slug?: string };

export async function POST(req: Request) {
  const { secret, slug }: Body = await req.json();
  if (secret !== process.env.REVALIDATE_SECRET) {
    return NextResponse.json({ ok: false }, { status: 401 });
  }
  if (slug) revalidatePath(`/blog/${slug}`);   // one page
  else revalidateTag("posts", "max");           // everything tagged; SWR semantics
  return NextResponse.json({ ok: true });
}
```
- `revalidatePath` invalidates a whole route; the next request regenerates it.
- `revalidateTag` marks tagged data stale; the next request regenerates it while serving stale content. Prefer paths for simple cases and tags for granular control. Check the exact `revalidateTag` signature (profile argument) for Next 16.
- Always authenticate the endpoint (shared secret or signed webhook).

**With Cache Components** (`cacheComponents: true`): use `"use cache"` with `cacheLife()` profiles and `revalidateTag` instead of route-level `revalidate`. Static shell plus cached/streamed sections gives the same behavior with finer granularity. `generateStaticParams` must then return at least one param. See the ISR with Cache Components guide.

**Self-hosting notes:** ISR relies on a persistent cache. With one Node server the file-system cache works. With multiple instances or serverless, configure a shared cache handler so all instances see the same cache. On Vercel this is handled by the platform.

**TypeScript tips**
- Share a `Params` type and a `CACHE_TAGS` const (`as const`) so tag names are not typo-prone strings.
- Validate upstream payloads (zod) before rendering; a bad response should throw so the last good page keeps being served.
- Wrap data access in typed functions (`getPost(slug): Promise<Post>`), dedupe with React `cache()`.

### Tradeoffs
| Gain | Cost |
|---|---|
| Static speed with freshness; no full redeploy | Bounded staleness (up to window + regen time) |
| Resilient: last good copy served if regen fails | Needs a server/platform with cache support (no `output: "export"`) |
| Scales to large page sets, build stays small | Cache behavior in multi-instance hosting needs care |
| Per-page and per-tag control | Harder to reason about than pure SSG or SSR |

### Pitfalls
- **One visitor sees stale content** after expiry (stale served while regen runs). Fine for most content, not for correctness-critical data.
- Using `cookies()`/`headers()`/`searchParams` in the page makes it dynamic and disables ISR for that route.
- Choosing too short a window just recreates SSR cost; a window of a few seconds is usually a sign you want SSR or client fetching.
- `revalidate` must be a statically analyzable value (a literal, not computed).
- Mismatched `revalidate` values across layout, page and fetches (shortest wins).
- Forgetting to authenticate the revalidation endpoint, which lets anyone force regeneration.
- Multi-instance deploys with per-instance caches: different users see different versions until all revalidate.
- Publishing a change and not invalidating dependent pages (index/list pages, sitemaps, tag pages). Use tags to cover them.
- Missing `notFound()` for deleted content: a regenerated 404 should replace the old page.

### Checklist
- [ ] Content is shared across users and tolerates bounded staleness. State the acceptable window.
- [ ] Window chosen from content change rate, not guesswork (minutes to hours, not seconds).
- [ ] `generateStaticParams` pre-builds the hot set; `dynamicParams` set deliberately.
- [ ] Tags defined (typed constants) for data shared across pages; on-demand revalidation wired to the CMS or mutation path.
- [ ] Revalidation endpoint authenticated and rate-limited.
- [ ] No request-time APIs in the route; build output confirms ISR (shows a revalidate period).
- [ ] Failure path verified: upstream error keeps the last good page.
- [ ] Hosting verified to support ISR cache (shared cache for multiple instances).
- [ ] Related list, sitemap and tag pages invalidated alongside the item page.
