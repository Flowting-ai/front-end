## 56. Performance Budget and CI

> A threshold the pipeline enforces on every pull request: exceed it and the build fails. It is the only reliable way to stop bundle creep, because no single change looks harmful.

### Definition
A **performance budget** is a set of numeric limits on things that affect speed: JavaScript bytes, image weight, request counts, and metrics such as LCP, CLS, INP or Total Blocking Time. **Enforcing** the budget means a CI job measures the pull request's build against the limits and fails (or at least reports loudly) when it exceeds them.

Without enforcement, performance decays by accretion: each PR adds 5 KB, a dependency, an image, and nobody notices until the app is 40% heavier. Reviewers cannot see bytes in a diff. A budget turns "be careful" into a failing check with a name, a number and an owner.

### Key properties

**1. Budgets are specific, measurable and per scope**
- Set them per **route or route group** (marketing page, app shell, chat), not one global number; a dashboard and a landing page have different needs.
- Mix **quantity budgets** (bytes, requests) with **quality budgets** (LCP, CLS, TBT).

**2. Two kinds of check, with different jobs**
| Check | Measures | Strength | Weakness |
|---|---|---|---|
| **Static size** (bundle budget) | Bytes in build output | Deterministic, fast, runs on every PR, no flakiness | Does not capture runtime cost or network |
| **Lab metrics** (Lighthouse CI) | LCP, CLS, TBT, etc. in a controlled run | Catches regressions that bytes miss (render-blocking, slow server) | Noisy; needs repeated runs and tolerance; one device profile |
| **Field metrics** (RUM, principle 55) | Real users' p75 LCP, INP, CLS | The truth | Lagging: it tells you after release |
The pipeline enforces the first two; observability confirms the third. INP cannot be measured in the lab the same way; Total Blocking Time is the usual lab proxy.

**3. Budgets must start achievable and tighten over time**
- Measure the current state, set the budget slightly above it, then ratchet down with each optimisation. A budget that fails on day one is switched off on day two.

**4. Fail fast, explain clearly**
- The failure message must say which budget, by how much, and where to look (the analyzer diff). "Build failed" is not enough.

**5. Budgets need an exception process**
- Sometimes a feature legitimately needs more. Allow raising a budget in a reviewed PR with a stated reason, so the number stays honest and visible.

### Typical budget set
| Budget | Example ceiling | Enforced by |
|---|---|---|
| First-load JS per route (compressed) | 170 KB for content pages; a higher, explicit figure for heavy app screens | Bundle-size check |
| Shared JS (layout + providers) | Tracked; fail on growth above a small delta | Bundle-size check |
| Single chunk size | e.g. no chunk over 100 to 150 KB compressed | Bundle-size check |
| Image weight per page | e.g. under 500 KB above the fold | Lighthouse budgets |
| Third-party requests | A fixed count and an allowlist | Lighthouse budgets |
| LCP (lab, mobile profile) | Under 2.5 s | Lighthouse CI assertion |
| CLS | Under 0.1 | Lighthouse CI assertion |
| Total Blocking Time (INP proxy) | Under 200 to 300 ms | Lighthouse CI assertion |
| Lighthouse performance score | At least 0.9 on key public routes | Lighthouse CI assertion |
The figures are starting points drawn from common guidance (Core Web Vitals "good" thresholds: LCP 2.5 s, CLS 0.1, INP 200 ms). Tune them to your own measured baseline.

### Practical patterns in Next.js (TypeScript)

**Know that `next build` no longer prints First Load JS**
Next.js 16 removed the `size` and `First Load JS` columns from the build output because they were inaccurate with Server Components. Measure bundles another way:
- `npx next experimental-analyze` (Turbopack analyzer, v16.1+). Add `--output` to write the report to `.next/diagnostics/analyze`, which you can copy and compare between builds.
- `@next/bundle-analyzer` for webpack builds (this repo's build uses `--webpack`).
- A script that reads the built files in `.next/static/chunks` and checks their gzip or brotli size against a limit.

**A simple, dependency-free bundle budget script**
```js
// scripts/check-bundle-budget.mjs
import { readdirSync, readFileSync, statSync } from "node:fs";
import { join } from "node:path";
import { gzipSync } from "node:zlib";

const DIR = ".next/static/chunks";
const MAX_CHUNK_KB = 150;      // single chunk, gzip
const MAX_TOTAL_KB = 1800;     // all client JS, gzip (set from your measured baseline)

const files = readdirSync(DIR, { recursive: true })
  .filter((f) => String(f).endsWith(".js"))
  .map((f) => join(DIR, String(f)))
  .filter((f) => statSync(f).isFile());

let total = 0;
const failures = [];
for (const f of files) {
  const kb = gzipSync(readFileSync(f)).length / 1024;
  total += kb;
  if (kb > MAX_CHUNK_KB) failures.push(`${f}: ${kb.toFixed(1)} KB > ${MAX_CHUNK_KB} KB`);
}
if (total > MAX_TOTAL_KB) failures.push(`Total client JS ${total.toFixed(0)} KB > ${MAX_TOTAL_KB} KB`);

if (failures.length) {
  console.error("Performance budget exceeded:\n" + failures.join("\n"));
  console.error("Run `ANALYZE=true npm run build` (or `npx next experimental-analyze`) to find the cause.");
  process.exit(1);
}
console.log(`Bundle budget OK: ${total.toFixed(0)} KB total client JS (gzip).`);
```
Total size across all routes grows with every new route, so also budget **per route** (see Lighthouse or `size-limit` below), and keep the total as a coarse guard.

**`size-limit` for per-entry budgets and PR comments**
`size-limit` (with the `@size-limit/file` plugin) takes a list of files or globs with limits, measures brotli or gzip size, fails above the limit, and has a GitHub Action that posts the size change on each PR.
```json
// package.json (excerpt)
{
  "scripts": { "size": "size-limit" },
  "size-limit": [
    { "name": "shared framework + app chunks", "path": ".next/static/chunks/*.js", "limit": "1.8 MB", "gzip": true }
  ]
}
```

**Lighthouse CI: assert metrics and post scores**
```json
// lighthouserc.json
{
  "ci": {
    "collect": {
      "startServerCommand": "npm run start",
      "url": ["http://localhost:3000/", "http://localhost:3000/pricing"],
      "numberOfRuns": 3
    },
    "assert": {
      "assertions": {
        "categories:performance": ["error", { "minScore": 0.9 }],
        "largest-contentful-paint": ["error", { "maxNumericValue": 2500 }],
        "cumulative-layout-shift": ["error", { "maxNumericValue": 0.1 }],
        "total-blocking-time": ["warn", { "maxNumericValue": 300 }],
        "resource-summary:script:size": ["error", { "maxNumericValue": 350000 }],
        "resource-summary:image:size": ["warn", { "maxNumericValue": 500000 }]
      }
    },
    "upload": { "target": "temporary-public-storage" }
  }
}
```
`numberOfRuns: 3` takes the median and reduces noise. Use `error` for hard limits and `warn` for advisory ones. Lighthouse CI uploads the report and, with its GitHub App token (`LHCI_GITHUB_APP_TOKEN`), sets a status check with scores on the PR; some Actions also post the scores as a PR comment. Pages behind login need a `puppeteerScript` (or an authenticated cookie) so Lighthouse measures the real screen, not the login redirect.

**A GitHub Actions workflow**
```yaml
# .github/workflows/perf-budget.yml
name: Performance budget
on:
  pull_request:
    types: [opened, synchronize, reopened]
concurrency:
  group: perf-${{ github.event.pull_request.number }}
  cancel-in-progress: true
jobs:
  budget:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 22, cache: npm }
      - uses: actions/cache@v4            # persist the Next.js build cache between runs
        with:
          path: .next/cache
          key: nextjs-${{ runner.os }}-${{ hashFiles('package-lock.json') }}-${{ hashFiles('src/**') }}
          restore-keys: nextjs-${{ runner.os }}-${{ hashFiles('package-lock.json') }}-
      - run: npm ci
      - run: npm run build
      - run: node scripts/check-bundle-budget.mjs        # fails fast, no browser needed
      - run: npx @lhci/cli@latest autorun                # lab metrics against lighthouserc.json
        env:
          LHCI_GITHUB_APP_TOKEN: ${{ secrets.LHCI_GITHUB_APP_TOKEN }}
```
Pin tool versions rather than using `@latest` in a real pipeline, and fix the Node version to the one used in production. Build caching (`.next/cache`) follows the Next.js CI build-caching guide.

**Make results visible: the diff, not the absolute number**
Posting "this PR changes JS on `/chat` by +18 KB" is more actionable than "bundle is 1.1 MB". Compare the PR's analyzer output (`.next/diagnostics/analyze`) with the base branch's and comment the delta.

**Close the loop with production**
Compare lab thresholds with field p75 from RUM (principle 55). If lab says "good" but field says "poor", tighten the lab test (slower device and network profile, a logged-in scenario, more routes).

### Rules of thumb
1. **Measure first, then set the budget just above reality, then ratchet down.**
2. **Budget per route and per shared path**, not only globally.
3. **Prefer deterministic checks (bytes) as hard gates; make noisy checks (lab metrics) tolerant** (median of several runs, margins).
4. **Fail with a diagnosis**: which route, how much over, and how to investigate.
5. **Allow a documented exception path**: a budget change is a reviewed diff.
6. **Run on every PR**, plus on `main` for trend tracking.
7. **Budget what you can control**: bundle size, image weight, third parties; observe what you cannot (user networks).
8. **Review the budget quarterly** with field data.

### Anti-patterns
- A budget that fails on day one and gets disabled.
- A single global size number that hides a route regression.
- A flaky Lighthouse assertion (one run, no margin) that teaches the team to ignore red builds.
- Only measuring in CI on a fast runner with no throttling, then claiming mobile performance.
- Budgets that nobody owns and nobody can raise through a clear process.
- Counting only first-party bytes while third-party scripts quietly double the cost.
- Gating on the Lighthouse score alone; it hides which metric moved. Assert the individual metrics.
- Measuring a dev build or a cold server with no warm-up.
- Treating CI results as the truth and never checking field data.

### Industry best practices
- **Use both layers**: a fast deterministic bundle-size gate on every PR (seconds), and Lighthouse CI on key routes (minutes) with multiple runs and a tolerance band.
- **Throttle realistically**: Lighthouse's default mobile emulation (slow 4G, 4x CPU slowdown) is a reasonable baseline; keep the profile constant so trends are comparable.
- **Compare to the base branch**, not only to a fixed number: fail on regressions above a delta (for example more than 5 KB gzip on a route without justification).
- **Post results where people look**: PR status checks and a sticky comment with the table of changes; link to the full report and to the analyzer diff.
- **Separate gates by severity**: `error` for Core Web Vitals "poor" and hard size limits, `warn` for early-warning thresholds; graduate warnings to errors when the signal is trusted. (This repository's React Doctor workflow takes the same advisory-first approach.)
- **Track trends on `main`**: store metrics per commit (Lighthouse CI server, a dashboard, or a JSON artifact) so slow drifts are visible.
- **Budget dependencies**: require a bundle-size note when adding a package (bundlephobia-style data, analyzer diff) and review the largest dependencies regularly.
- **Test authenticated and data-heavy routes** with seeded data and a login step; public marketing pages are not the whole app.
- **Include third-party scripts** in the budget (count, size, allowlist); they are often the largest controllable cost.
- **Keep CI fast**: cache `node_modules` and `.next/cache`, run size checks before browser checks, cancel superseded runs.
- **Make the budget discoverable**: document it in the repo (`budgets.md` or in this principles folder), with owners and how to request an increase.
- **Tie into release management**: block releases on failed budgets, and compare each release's field vitals (principle 55) against the lab numbers.

### Things to avoid
- Relying on "First Load JS" from `next build` output in Next.js 16; it was removed and cannot be used as a gate.
- Copying budget numbers from another product without measuring your own baseline.
- Letting `main` fail the budget without a fix or an explicit, recorded exception.
- Using only Lighthouse performance score as the gate.
- Running Lighthouse once and trusting a single number.
- Hiding failures with `continue-on-error: true` forever.
- Adding a budget check without telling the team how to investigate a failure.
- Excluding the heaviest routes from checks because they "always fail".
- Using unpinned `@latest` tools that change thresholds and results between runs.
- Gating on metrics the team cannot influence (random network variance, third-party outages).

### Checklist
- [ ] Baselines were measured for the main routes; budgets sit just above them.
- [ ] A deterministic bundle-size check runs on every PR and fails with a clear message.
- [ ] Lighthouse CI (or equivalent) runs on key public and authenticated routes, with several runs and tolerances.
- [ ] LCP, CLS and TBT (or INP in the field) are asserted individually, not only the overall score.
- [ ] Results are posted on the PR (status check and comment) with the change versus the base branch.
- [ ] There is a documented way to raise a budget with justification.
- [ ] Field data (principle 55) is reviewed against lab results, and budgets are tightened over time.
- [ ] Tool versions, the Node version and the build cache are pinned and configured.

### In this codebase
- The only workflow in `.github/workflows/` is `react-doctor.yml` (advisory, posts a PR summary, includes bundle-size findings). There is no bundle-size gate, no Lighthouse CI, and no performance budget file yet.
- `npm run build` is `next build --webpack`, so `@next/bundle-analyzer` (`ANALYZE=true`, already wired in `next.config.ts`) is the matching analyzer; `npx next experimental-analyze` is also available on Next.js 16.2.
- Most screens are behind Auth0 login, so Lighthouse CI needs a login step (a `puppeteerScript` or a seeded session) to measure the app shell and chat; the public routes (landing, share pages) can be measured directly.
- A good first step: add `scripts/check-bundle-budget.mjs` with budgets set from today's measured numbers, run it after `npm run build` in a new workflow, and graduate to Lighthouse CI on two or three routes once it is stable.
- `vitest` tests run in CI-friendly mode (`npm test`); keep the performance workflow separate so test feedback stays fast.
