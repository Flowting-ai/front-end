## 52. Bundle Splitting Strategy

> Go past route splitting: separate stable vendor code from fast-changing app code, and isolate heavy components. Vendor chunks stay cached across deploys, so returning users skip the vendor download.

### Definition
Code splitting (principle 46) answers "which code does this route or interaction need?". A **bundle splitting strategy** answers a second question: "how should the code be grouped into files so that browsers cache as much as possible and download as little as possible?"

The idea rests on caching. Build output files carry a content hash in their name and are served with `Cache-Control: public, max-age=31536000, immutable`, so a file whose content has not changed keeps the same URL and stays in the browser and CDN cache. The strategy is to put **code that changes rarely** (React, framework, large libraries) in separate files from **code that changes on every deploy** (your features), so a typical deploy invalidates only a small part of the download.

### Key properties

**1. Group by change frequency**
| Group | Changes | Examples | Goal |
|---|---|---|---|
| Framework | Only on framework upgrades | React, React DOM, Next.js runtime | Cached for weeks |
| Vendor libraries | On dependency upgrades | Radix, TanStack Query, Zod, date libraries | Cached across most deploys |
| Shared app code | Often | Design-system components, utilities | Shared between routes |
| Route code | Every feature change | Page and feature components | Small, so re-download is cheap |
| Heavy, rare code | Rarely used | Maps, charts, editors, diagram renderers | Loaded on demand only |

**2. Next.js already does most of this**
- The bundler splits per route, extracts a framework chunk, shares common modules between routes, and may split very large third-party modules into their own chunks.
- Content hashing makes unchanged chunks cache-stable. You get most of the benefit with no configuration.

**3. Cache stability is fragile**
- A chunk's hash changes when **any** module inside it changes. A vendor chunk that also contains one frequently edited file loses its caching benefit.
- Adding or removing a dependency can reshuffle which modules land in which chunk and invalidate several files at once.

**4. More chunks is not always better**
- Each chunk is a request and carries overhead. HTTP/2 and HTTP/3 multiplex requests, so moderate chunk counts are fine, but hundreds of tiny files slow startup and compress worse. Aim for a small number of well-chosen groups.

**5. Heavy components are isolated by loading, not by configuration**
- A library used on one rare screen belongs in a lazily loaded chunk (`next/dynamic`, `import()`), so it is absent from the shared and vendor chunks every user downloads.

### Strategy decision table
| Goal | Approach | Notes |
|---|---|---|
| Keep React and framework cached | Rely on the default framework chunk | Do not bundle it into your app chunks |
| Cache big stable libraries across deploys | Let default shared chunks work; check with the analyzer; only customise `splitChunks` if a measured problem remains | Custom config is not covered by semver |
| Keep rare, heavy features out of the main path | `next/dynamic`, `import()` | The strongest lever (principle 46) |
| Avoid duplicated library copies across routes | Align dependency versions; use one library per job | Duplicates appear as two copies in the analyzer |
| Remove a heavy library entirely | Replace it with a lighter alternative or a native API | Often beats any splitting trick |
| Cut third-party script cost | `next/script` strategies; load after interaction | Not part of the bundle graph, but part of the page cost |
| Survive deploys without breaking tabs left open | `deploymentId` (version-skew protection) | Static assets get `?dpl=` so old and new builds do not mix |

### Practical patterns in Next.js (TypeScript)

**Step 1: look before you split**
```bash
# Next.js 16.1+ Turbopack analyzer
npx next experimental-analyze
# Webpack builds: @next/bundle-analyzer, enabled with an env variable (this repo uses ANALYZE=true)
ANALYZE=true npm run build
```
Questions to answer: Which chunks do all routes load? Is any library present twice? Which route has the largest first-load JS? Which libraries could be deferred?

**Step 2: remove and defer before customising**
```tsx
"use client";
import dynamic from "next/dynamic";

// Heavy renderer used on a few messages only: never part of the shared chunk
const MermaidDiagram = dynamic(() => import("./MermaidDiagram"), { ssr: false, loading: () => null });
```

**Step 3: stable chunks across deploys with a deployment ID**
```ts
// next.config.ts
const nextConfig: NextConfig = {
  deploymentId: process.env.DEPLOYMENT_VERSION,   // enables version-skew protection
};
```
With a deployment ID, static asset URLs carry `?dpl=<id>`, so a tab opened before a deploy keeps requesting the files of its own build instead of mixing old and new chunks. Hosts that support skew protection route those requests to the matching build.

**Step 4 (only if measured): tune webpack chunk groups**
```ts
// next.config.ts: advanced; changes are not covered by semver, so keep this small and tested
const nextConfig: NextConfig = {
  webpack(config, { isServer }) {
    if (!isServer && config.optimization?.splitChunks && typeof config.optimization.splitChunks === "object") {
      config.optimization.splitChunks.cacheGroups = {
        ...config.optimization.splitChunks.cacheGroups,
        radix: {
          test: /[\\/]node_modules[\\/]@radix-ui[\\/]/,
          name: "radix",
          chunks: "all",
          priority: 20,
        },
      };
    }
    return config;
  },
};
```
Only do this after the analyzer shows that a library family appears in many chunks and the default grouping defeats caching. Verify the result with the analyzer and a before/after cache test; the default Next.js heuristics are tuned for typical apps, and custom groups can easily make things worse (more requests, lost shared-chunk reuse, a `name`-fixed chunk that every route must load).

**Step 5: keep vendor chunks pure**
- Do not import frequently edited app files from inside a vendor-only module graph.
- Pin dependency upgrades into deliberate PRs (and watch bundle diffs), so vendor chunk hashes change only when you intend them to.

**Step 6: verify caching works**
```bash
# After two deploys, compare chunk file names: unchanged vendor/framework chunks keep the same hash
curl -sI https://app.example.com/_next/static/chunks/<file>.js | grep -i cache-control
# expect: public, max-age=31536000, immutable
```

### Rules of thumb
1. **Remove, then defer, then split.** Replacing a heavy library or deferring it beats tuning chunk groups.
2. **Trust the defaults first**; customise only with an analyzer finding and a measurable goal.
3. **Separate by change frequency**: stable code should never share a file with volatile code.
4. **Keep the shared path small**: what every route loads (layout, providers, design system) is the highest-cost code in the app.
5. **Watch duplicates**: one library, one version, one copy.
6. **Fewer, meaningful chunks** beat many tiny ones.
7. **Pair with `deploymentId`** so caching and rolling deploys do not fight.
8. **Re-measure after dependency upgrades**; chunk composition shifts.

### Anti-patterns
- One catch-all `vendor.js` containing every dependency: any upgrade invalidates the whole file, and every route loads libraries it does not use.
- Hand-written `cacheGroups` copied from a blog post written for another bundler or version.
- Hundreds of micro-chunks created by splitting every module.
- Putting rarely used heavy libraries (maps, charts, editors, diagram renderers) in layouts or providers, so they join the shared path.
- Importing a heavy library in a provider or root layout "just in case".
- Two versions of the same library pulled in by different dependencies.
- Assuming caching benefits without checking hashes between two deploys.
- Splitting by feature team or folder instead of by change frequency and load path.

### Industry best practices
- **Define the first-load JS budget per route** and a shared-path budget, and fail CI when they grow (principle 56).
- **Audit on every dependency change**: PR checks that show the bundle size diff (size-limit or the analyzer in CI).
- **Prefer smaller libraries** and native platform APIs (`Intl`, `fetch`, `URL`, `structuredClone`, `crypto.randomUUID`) to large utility libraries.
- **De-duplicate dependencies** (`npm ls <pkg>`, `npm dedupe`) and align versions across the repo; in monorepos hoist shared versions.
- **Keep third-party scripts off the critical path** with `next/script` and defer them until after interaction or idle.
- **Use `import()` for event-driven code** and `next/dynamic` for visible-on-demand components; prefetch on hover or focus for likely next steps.
- **Cache at the CDN**: immutable year-long caching for hashed assets, short caching for HTML (principle 9); do not purge hashed assets on deploy.
- **Handle old clients**: keep previous deploy assets available for a grace period, or use skew protection, so open tabs do not 404 on missing chunks; add an error boundary that offers a reload on chunk load errors (principle 19).
- **Prefer Server Components** for large data-rendering libraries (markdown, syntax highlighting, date formatting), so they never reach the client bundle at all (principle 6).
- **Compress at the edge** (Brotli) and confirm with response headers; compressed size, not raw size, is what the network pays.
- **Track real-world cache hit rate** of static assets in CDN logs, and the share of repeat-visit bytes served from cache.
- **Document the strategy** in the repo (what goes where, budgets, who approves custom `splitChunks`).

### Things to avoid
- Customising `splitChunks` before reading the analyzer report.
- Forcing every dependency into named vendor chunks that all routes must load.
- Using fixed chunk names that defeat content hashing or collide between builds.
- Disabling content hashing or overriding the immutable cache headers of `_next/static`.
- Importing both a lightweight and a heavyweight library for the same job (two date libraries, two animation libraries).
- Letting a design-system barrel import pull all components into every route (principle 47).
- Treating the bundler config as a substitute for removing unnecessary code.
- Deploying without a plan for clients holding old chunk references.

### Checklist
- [ ] The analyzer was run on the production build; the shared path and the largest routes are known.
- [ ] Heavy, rare code is loaded on demand and absent from layouts and providers.
- [ ] No library appears twice; versions are aligned.
- [ ] Any custom `splitChunks` has a documented reason and a measured improvement.
- [ ] Hashed assets are served `immutable` with long max-age; HTML is not cached that way.
- [ ] `deploymentId` or an equivalent skew strategy is in place, and chunk load errors show a reload prompt.
- [ ] Per-route and shared-path JS budgets are enforced in CI.

### In this codebase
- `npm run build` runs `next build --webpack`, so webpack's `splitChunks` applies (not Turbopack's). `@next/bundle-analyzer` is wired in `next.config.ts` and runs when `ANALYZE=true`.
- No custom `webpack` or `splitChunks` configuration exists, which is the right starting point; keep it that way unless the analyzer proves a need.
- Heavy client libraries to keep out of the shared path: `maplibre-gl` with `@vis.gl/react-maplibre`, `beautiful-mermaid`, `recharts` and `framer-motion`. The map and diagram code already use `next/dynamic` (principle 46); confirm the others are only imported on the routes that use them.
- No `deploymentId` is set. If deploys are rolling or tabs stay open for long sessions (chat), consider setting one to prevent chunk mismatch errors.
- The providers in `src/context/` and the root layout are on every route's path, so avoid adding heavy imports there.
