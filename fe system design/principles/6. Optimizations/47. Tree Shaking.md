## 47. Tree Shaking

> Bundlers drop exports that are never used, but only when they can prove it from static ES module imports. Import the function you need, not the whole library.

### Definition
Tree shaking (dead-code elimination across modules) removes exports that nothing imports. It works because ES module `import` and `export` are **static**: the bundler can read the import graph at build time without running code. CommonJS (`require`, `module.exports`) is dynamic, so a bundler generally cannot tell which parts are used and keeps the whole module.

Shaking happens in two steps: the bundler marks which exports are used, then the minifier removes the unused code. Both steps need to be sure that removing the code changes nothing, which is where **side effects** matter.

### Key properties

**1. Only static ES imports shake reliably**
- `import { format } from "date-fns"` is analysable. `const lib = require("lib")` and `import(variable)` are not.
- Libraries must ship ES module output (`"module"` or `"exports"` with an `import` condition) to be shakeable.

**2. Side effects block removal**
- A module with top-level side effects (registering something, patching a global, importing CSS) cannot be dropped even if nothing is used from it.
- Packages declare `"sideEffects": false` (or a list of files with effects) in `package.json` so the bundler may skip unused modules entirely.

**3. Barrel files hide the graph**
- `index.ts` files that re-export dozens of modules make the bundler load and analyse all of them. If any re-exported module has side effects, or the package lacks `sideEffects: false`, much of it can end up in the bundle.
- This also slows dev server and build, because every import resolves the entire barrel.

**4. Granular imports are the safe default**
- Import from the specific file or the package's documented subpath when a library is large and its barrel is not optimised.

**5. Modern bundlers shake namespace imports used by property access**
- `import * as utils from "./utils"; utils.a()` is usually shaken correctly by modern bundlers. The patterns that really defeat shaking are dynamic access (`utils[name]`), passing the namespace object around (`doSomething(utils)`), spreading it, or re-exporting it through CommonJS interop.
- Treat namespace imports of **large third-party libraries** as a risk anyway: they make the intent unclear and are easy to break by accident.

### What blocks tree shaking
| Cause | Example | Fix |
|---|---|---|
| CommonJS dependency | `lodash` (CJS) | Use `lodash-es` or per-method imports |
| Missing `sideEffects` flag | Library without `"sideEffects": false` | Pick a library that sets it; or import deep |
| Barrel re-exports with effects | `export * from "./everything"` | Import from the specific module; split the barrel |
| Dynamic or whole-object access | `icons[name]`, `import * as all` then `all[key]` | Import the used members explicitly; map names to imports |
| Classes with static initialisers or decorators | Large class-based SDKs | Prefer function-based APIs |
| Transpiling ES modules to CJS | `@babel/preset-env` with `modules: "commonjs"` | Keep ESM output (Next.js does by default) |
| Top-level work in your own module | `registerAll()` at file scope | Move work into functions called on demand |

### Practical patterns in Next.js (TypeScript)

**Import the function, not the library**
```tsx
// Good: named import from an ESM, side-effect-free package
import { format } from "date-fns";

// Bad: pulls a CJS build, whole library lands in the bundle
import _ from "lodash";
const first = _.head(items);

// Good alternatives
import head from "lodash-es/head";
// or write the one-liner yourself
const first = items[0];
```

**Let Next.js rewrite barrel imports: `optimizePackageImports`**
```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  experimental: {
    optimizePackageImports: ["@acme/ui", "react-icons/fi"],
  },
};
export default nextConfig;
```
Next.js rewrites `import { A } from "pkg"` so only the modules you use are loaded, which also speeds up dev and build. `lucide-react`, `date-fns`, `lodash-es`, `rxjs`, `@headlessui/react`, `@mui/material` and several others are optimised by default, so they need not be listed. The option is marked experimental in the docs, so check the current page when upgrading.

**Dynamic icons without shipping every icon**
```tsx
// Bad: bundles the whole icon set to look one up by name
import * as Icons from "lucide-react";
const Icon = Icons[name as keyof typeof Icons];

// Good: an explicit map; only listed icons are bundled
import { Bot, Plug, Share2 } from "lucide-react";
const ICONS = { agent: Bot, connector: Plug, share: Share2 } as const;
const Icon = ICONS[kind];
```

**A well-behaved library's `package.json`**
```json
{
  "name": "@acme/ui",
  "type": "module",
  "sideEffects": ["**/*.css"],
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" },
    "./button": { "types": "./dist/button.d.ts", "import": "./dist/button.js" }
  }
}
```
`sideEffects` lists the files that must stay (CSS); everything else may be removed if unused. Subpath `exports` give consumers a safe granular import.

**Keep your own barrels small and effect-free**
```ts
// components/ui/index.ts: re-exports only, no top-level work
export { Button } from "./Button";
export { Badge } from "./Badge";
// Do not: import "./register-globals"; (side effect in a barrel)
```
For large feature folders, import the specific file (`@/components/ChatInput`) rather than a catch-all barrel.

**Verify, do not assume**
- Run the bundle analyzer (`npx next experimental-analyze`, or `@next/bundle-analyzer`) and search for the library; if the whole package appears, shaking failed.
- Check the build output's first-load JS per route before and after a change.

### Rules of thumb
1. **Named imports from ESM packages**; avoid default-importing a whole library object (`_`, `moment`).
2. **Prefer ESM-first, side-effect-free libraries** (`sideEffects: false`, `exports`, small functions).
3. **Check bundle cost before adding a dependency**, and re-check after upgrades.
4. **Keep module top levels pure**: no work, no registration, no global writes at import time.
5. **Avoid dynamic access to module members** (`ns[key]`); use explicit maps.
6. **Use `optimizePackageImports`** for large barrel packages that are not in the default list.
7. **Verify with the analyzer** instead of trusting that "it should shake".

### Anti-patterns
- `import _ from "lodash"` or `import moment from "moment"` for one function.
- Importing an entire icon library and selecting by string at runtime.
- A single root `index.ts` that re-exports the whole app and is imported everywhere.
- Marking your own app code `"sideEffects": false` when it relies on import-time side effects (CSS imports, polyfills), which breaks the app silently.
- Putting setup code (analytics init, feature registration) at module scope in shared files.
- Assuming a library tree-shakes because it is "modern" without looking at its build output.

### Industry best practices
- **Ship and consume ESM**: libraries set `"type": "module"` or provide an ESM entry through `exports`; consumers avoid transpiling to CommonJS.
- **Set `"sideEffects"` correctly** in your own packages: `false` when pure, or an array listing CSS and files with effects. Wrong values either bloat bundles or delete needed code.
- **Use subpath exports** (`@acme/ui/button`) in design-system packages (principle 15) so consumers get granular imports with no barrel cost.
- **Prefer small, composable functions** over class-heavy SDKs when choosing libraries.
- **Use `import type`** (or `verbatimModuleSyntax`) so type-only imports are erased and never create runtime edges.
- **Compare alternatives by bundle size** (for example `date-fns` or `dayjs` instead of `moment`; per-method `lodash-es` instead of `lodash`).
- **Track bundle size in CI** with a per-route budget and a failing check on regressions.
- **Mark pure calls** when authoring libraries (`/*#__PURE__*/`) so the minifier can drop unused factory calls.
- **Do not rely on the minifier for heavy logic**: code in unused branches behind runtime flags is not removed; use build-time constants (`process.env.NODE_ENV`, `NEXT_PUBLIC_*` inlined at build) for dead branches.
- **Separate server and client code** (`server-only`, `"use client"` boundaries) so server libraries never enter the client graph at all.
- **Re-audit periodically**: a library upgrade can add side effects or change its entry, silently growing a route.

### Things to avoid
- Namespace imports (`import * as X`) of large third-party libraries; they are easy to break with a later dynamic access.
- Believing that namespace imports always disable shaking; with modern bundlers they usually do not, so verify rather than assume.
- Re-exporting everything with `export *` in app-level barrels.
- Side-effectful imports in shared modules (`import "./polyfill"` in a component library).
- CommonJS-only dependencies in client code when an ESM alternative exists.
- Compiling to CJS in custom Babel or TS settings (`module: "commonjs"`).
- Importing server-only libraries from files that a Client Component also imports.
- Claiming a size win without checking the analyzer.

### Checklist
- [ ] Imports from large libraries are named and come from ESM entries.
- [ ] The analyzer shows no whole-library inclusions (full icon set, `lodash`, `moment`).
- [ ] `optimizePackageImports` covers big barrel packages not optimised by default.
- [ ] Own barrels contain only re-exports and no top-level side effects.
- [ ] `sideEffects` in `package.json` matches reality (CSS and polyfills kept).
- [ ] Type-only imports use `import type`.
- [ ] A per-route first-load JS budget is enforced in CI.

### In this codebase
- `lucide-react` is imported with named imports in about 16 files; it is on Next.js's default optimised list, so no extra config is needed. Avoid `import * as Icons` lookups by name.
- Heavy dependencies to watch in the analyzer: `recharts`, `framer-motion`, `maplibre-gl` (with `@vis.gl/react-maplibre`) and `beautiful-mermaid`. Confirm that each is imported only where used, and that map and diagram code is loaded on demand (principle 46).
- `package.json` has no `sideEffects` field, which is fine for an app; the field matters mainly if the design system becomes a separate package (principle 15).
- Barrel files exist (for example `src/components/ui/index.ts`); keep them re-export only, and prefer folder imports (`@/components/Button`) in hot paths.
- No `optimizePackageImports` entry is set in `next.config.ts`; add one only if the analyzer shows a barrel package inflating a route.
