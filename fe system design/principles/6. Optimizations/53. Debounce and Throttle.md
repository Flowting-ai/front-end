## 53. Debounce and Throttle

> Rate-limit expensive work that is tied to fast, repeated events. Debounce waits for a pause (search fires when typing stops); throttle caps the rate (scroll work runs at most once per frame).

### Definition
Some events fire dozens or hundreds of times per second: `input` while typing, `scroll`, `resize`, `pointermove`, drag, window focus. Running an expensive handler on every one wastes CPU, floods the network and hurts INP.

- **Debounce**: delay the work until the events stop for `n` milliseconds. Each new event resets the timer. Only the **last** call runs. Use it when only the final value matters (search box, autosave, form validation).
- **Throttle**: run the work at most once per `n` milliseconds while events keep coming. The **first** (and optionally last) call in each window runs. Use it when you need regular updates during a continuous gesture (scroll position, resize, drag).
- **`requestAnimationFrame` (rAF)**: a frame-aligned throttle (about 16 ms at 60 Hz). Use it for visual updates tied to scroll, pointer or resize so work happens once per frame.

### Key properties

**1. Choose by what the user needs**
| Need | Pattern | Typical delay |
|---|---|---|
| Final value only (type-ahead search, autosave) | Debounce | 150 to 400 ms (search), 500 to 1,500 ms (autosave) |
| Steady updates during a gesture (scroll, resize, drag) | Throttle or rAF | One frame (16 ms), or 100 to 250 ms for non-visual work |
| First click only (submit button, "like") | Leading-edge debounce or throttle, plus a disabled state | 300 to 1,000 ms |
| Visual update tied to scroll or pointer | `requestAnimationFrame` | One frame |
| Render lag while typing (expensive list) | `useDeferredValue` or `useTransition`, not a timer | n/a (principle 54) |
| Detect visibility or size changes | `IntersectionObserver`, `ResizeObserver`, not scroll or resize listeners | n/a |

**2. Leading and trailing edges**
- **Trailing** (default for debounce): run after the pause. Feels slightly delayed but sends one request.
- **Leading**: run on the first event, ignore the rest. Feels instant for single actions.
- Throttle often runs both: leading for responsiveness, trailing so the final value is not lost.

**3. Debounce delays; it does not cancel in-flight work**
- A debounced search can still receive an older, slower response after a newer one. Pair debouncing with request cancellation (`AbortController`) or a query library that keys by input (principle 30).

**4. Timers must be cleaned up**
- In React, a pending timer outliving its component calls `setState` on unmounted state or fires stale work. Clear it in an effect cleanup.

**5. Prefer a better primitive when one exists**
- Many scroll and resize listeners can be replaced by `IntersectionObserver`, `ResizeObserver`, CSS (`position: sticky`, scroll snap, scroll-driven animations), or `content-visibility`, which cost no main-thread time per event.

### Practical patterns in Next.js (TypeScript)

**A `useDebouncedValue` hook for search inputs**
```tsx
"use client";
import { useEffect, useState } from "react";

export function useDebouncedValue<T>(value: T, delayMs = 250): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(id);                 // cleanup resets the timer on every change
  }, [value, delayMs]);
  return debounced;
}
```
```tsx
function ChatSearch() {
  const [raw, setRaw] = useState("");
  const query = useDebouncedValue(raw, 250);       // input stays instant; filtering/fetching uses `query`
  const { data } = useQuery({
    queryKey: ["chats", "search", query],
    queryFn: ({ signal }) => searchChats(query, { signal }),   // aborted when the key changes
    enabled: query.length > 1,
  });
  return (<><input value={raw} onChange={(e) => setRaw(e.target.value)} /><Results items={data ?? []} /></>);
}
```
The controlled input updates on every keystroke (so typing never lags), while the expensive part reads the debounced value. A query library with a key per input also dedupes and cancels stale requests.

**Debounced callback (autosave) that survives re-renders**
```tsx
"use client";
import { useEffect, useMemo, useRef } from "react";

export function useDebouncedCallback<A extends unknown[]>(fn: (...args: A) => void, delayMs: number) {
  const fnRef = useRef(fn);
  useEffect(() => { fnRef.current = fn; });         // always call the latest closure
  const timer = useRef<ReturnType<typeof setTimeout>>(undefined);

  const debounced = useMemo(() => {
    const call = (...args: A) => {
      clearTimeout(timer.current);
      timer.current = setTimeout(() => fnRef.current(...args), delayMs);
    };
    call.cancel = () => clearTimeout(timer.current);
    return call;
  }, [delayMs]);

  useEffect(() => () => debounced.cancel(), [debounced]);   // cancel on unmount
  return debounced;
}
```
For autosave, also flush or save on `visibilitychange`/`pagehide`, so the last edit is not lost when the user leaves.

**Throttle with `requestAnimationFrame` (scroll, pointer)**
```tsx
"use client";
import { useEffect, useRef } from "react";

export function useRafScroll(onFrame: (scrollTop: number) => void, el: React.RefObject<HTMLElement | null>) {
  const ticking = useRef(false);
  useEffect(() => {
    const node = el.current;
    if (!node) return;
    const onScroll = () => {
      if (ticking.current) return;
      ticking.current = true;
      requestAnimationFrame(() => {
        onFrame(node.scrollTop);                   // at most once per frame
        ticking.current = false;
      });
    };
    node.addEventListener("scroll", onScroll, { passive: true });   // passive: never blocks scrolling
    return () => node.removeEventListener("scroll", onScroll);
  }, [el, onFrame]);
}
```
At 60 Hz a frame is about 16.7 ms; on 120 Hz displays it is about 8.3 ms. rAF adapts to the display, which a fixed `16` ms timer does not. Use a time-based throttle (for example 100 to 250 ms) for non-visual work such as analytics or saving scroll position.

**Prefer observers to scroll and resize listeners**
```tsx
// Instead of listening to scroll to know when a sentinel is visible:
const io = new IntersectionObserver(([e]) => e.isIntersecting && loadMore(), { rootMargin: "200px" });
io.observe(sentinelRef.current!);

// Instead of window.resize to measure an element:
const ro = new ResizeObserver(([entry]) => setWidth(entry.contentRect.width));
ro.observe(containerRef.current!);
```

**Prevent double submits**
```tsx
const [pending, startTransition] = useTransition();
<button disabled={pending} onClick={() => startTransition(() => submit())}>Save</button>
```
A disabled state (and server-side idempotency keys for payments or creates) is more reliable than debouncing a click.

**Server side: rate limiting is the other half**
Client debouncing only protects the client. APIs still need server-side rate limits and idempotency (principle 21), because any client can ignore your timers.

**Libraries**
`lodash-es` (`debounce`, `throttle`) and `use-debounce` are common. Import the single function (principle 47), and wrap it in a ref or `useMemo` so the debounced function keeps its identity and timer across renders. A bare `debounce(fn, 300)` created in render is a new function with a new timer on every render, so it never debounces anything.

### Rules of thumb
1. **Debounce for "after the user stops"; throttle (or rAF) for "while the user is doing it".**
2. **Keep inputs instant**: update the controlled value immediately; debounce the expensive consumer.
3. **Cancel stale work**: abort in-flight requests, ignore out-of-order responses.
4. **Clean up timers and listeners** on unmount and dependency change.
5. **Use rAF for visual work**; use passive listeners for scroll and touch.
6. **Reach for observers and CSS first**; fall back to throttled listeners.
7. **For render lag, use `useDeferredValue` or `useTransition`**, not a timer (principle 54).
8. **Do not rely on the client for protection**: add server rate limits.

### Anti-patterns
- Creating a debounced function inside the component body without memoisation, so every render gets a fresh timer.
- Debouncing the state that feeds the input (`value` itself), making typing feel laggy or dropping characters.
- Firing a network request on every keystroke with no cancellation.
- A scroll handler that reads layout (`getBoundingClientRect`, `offsetHeight`) and writes styles on every event (layout thrash).
- A fixed `setTimeout(..., 16)` standing in for a frame.
- Non-passive `touchstart`, `touchmove` or `wheel` listeners that block scrolling.
- Debouncing a submit button to hide a double-click problem, with no idempotency on the server.
- Stacking multiple delays (debounce plus a transition plus a server delay) until the UI feels sluggish.

### Industry best practices
- **Pick delays from the interaction**: roughly 150 to 300 ms for type-ahead (fast enough to feel live), longer for autosave, and shorter for validation messages that should appear soon after typing pauses.
- **Give feedback during the wait**: a spinner, a "Saving..." status, or stale-result dimming, so a debounced action never looks broken.
- **Use leading-edge calls for one-off commands** (open, send, toggle) so the first action responds immediately.
- **Flush on exit**: for autosave and analytics, send pending work on `visibilitychange` and `pagehide` (use `navigator.sendBeacon` or `fetch` with `keepalive`).
- **Throttle analytics and telemetry events**, and batch them (one request per interval, not per event).
- **Make handlers cheap, then limit them**: first remove avoidable work (derived values, DOM reads), then add rate limiting.
- **Use `AbortController` and query keys** so out-of-order responses cannot overwrite newer results (principle 30).
- **Respect the display**: use rAF for animation-linked updates; test on high-refresh and low-power devices.
- **Mark scroll, wheel and touch listeners `{ passive: true }`**, so the browser can scroll without waiting for your handler.
- **Prefer CSS** for scroll-linked effects (`position: sticky`, scroll snap, scroll-driven animations where supported).
- **Test with fake timers** (Vitest `vi.useFakeTimers()`): assert one call after a burst, cancellation on unmount, and leading/trailing behaviour.
- **Keep shared hooks in one place** (`useDebouncedValue`, `useDebouncedCallback`) rather than hand-rolling timers in each component.

### Things to avoid
- Debouncing as a fix for a slow render; that is a rendering problem (principles 50 and 54).
- Very long debounce delays on interactive search (over about 500 ms feels broken).
- Missing cleanup, which leaks timers and causes updates after unmount.
- Using a stale closure inside a debounced callback (store the latest function in a ref).
- Throttling without a trailing call when the final state matters (the last scroll position, the last resize).
- Using scroll events to detect visibility (use `IntersectionObserver`).
- Treating client-side limiting as security.
- Adding a heavy library just to debounce one handler.

### Checklist
- [ ] Each rate-limited handler is deliberately debounce, throttle, rAF or an observer, and the reason is clear.
- [ ] Inputs remain instant; only the expensive consumer is delayed.
- [ ] Debounced functions are memoised and cleaned up on unmount.
- [ ] In-flight requests are cancelled or keyed; stale responses cannot overwrite fresh ones.
- [ ] Scroll, wheel and touch listeners are `passive`; visual work runs in rAF.
- [ ] Autosave and analytics flush on `visibilitychange` or `pagehide`.
- [ ] The server enforces rate limits and idempotency independently.
- [ ] Timer behaviour is covered by fake-timer tests.
