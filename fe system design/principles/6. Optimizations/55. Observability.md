## 55. Observability

> Production fails in ways staging never reveals. Get layered visibility: errors with stack traces, what the user did, how fast it felt, and readable code behind every stack.

### Definition
Observability is the ability to understand what is happening in a running system from the signals it emits, without shipping new code to investigate. For the front end that means answering, for any incident: **what broke, for whom, after what actions, how often, and in which release**.

Staging cannot reproduce production's diversity of devices, networks, browser extensions, data and user behaviour. At scale, small rates are large numbers: **0.1% of sessions failing at 1,000,000 sessions is 1,000 broken sessions**, and none of those users will write a bug report. Observability is how you find them.

### The layers
| Layer | Question it answers | Typical tools | Signal |
|---|---|---|---|
| **a. Error monitoring** | What threw, where, how often, since which release? | Sentry, Rollbar, Bugsnag, Datadog RUM, Highlight | Exceptions with stack traces, breadcrumbs, release, user and device context |
| **b. Session replay** | What did the user do before it broke? | Sentry Replay, LogRocket, PostHog, FullStory, Highlight | A reconstructed DOM recording, network and console events |
| **c. Real User Monitoring (RUM)** | How fast and stable did it feel for real users? | `useReportWebVitals`, Vercel Speed Insights, web-vitals library, Datadog, New Relic, Sentry Performance | LCP, INP, CLS, TTFB per route, device, network and release (p75) |
| **d. Source maps** | Which original line failed, not which minified line? | Uploaded to the monitoring tool at build time | Readable stack traces mapped to your TypeScript |
| **e. Logs and traces (server)** | What happened on the server for this request? | OpenTelemetry, `instrumentation.ts`, structured logs, `onRequestError` | Request traces, server errors, latency |
| **f. Product analytics** | What are users doing and where do they drop off? | Mixpanel, PostHog, Amplitude | Events, funnels, feature use |

Layers a to d are the front-end core; e connects front-end failures to backend causes; f is related but answers product questions, not reliability questions.

### Key properties

**1. Errors need context, not just messages**
- A stack trace without release, route, user or session, browser, and breadcrumbs (the last clicks, requests, console lines) is hard to act on.
- Group (deduplicate) errors by fingerprint so 10,000 occurrences are one issue with a count, not 10,000 alerts.

**2. Replay turns "cannot reproduce" into minutes**
- A recording of the session showing the clicks, DOM state and network calls often shows the root cause directly. Teams commonly report much shorter time-to-diagnosis; the value is in skipping the guess-and-reproduce loop.
- Replay has privacy and cost implications; see below.

**3. Lab data is not field data**
- Lighthouse runs one device on one network. RUM measures real devices. Core Web Vitals (LCP, INP, CLS) at the 75th percentile of real users are what matter (principle 8). INP in particular only exists in the field.

**4. Source maps make stacks readable, but are sensitive**
- Production bundles are minified; stack traces point at `main-4f3a.js:1:48213`. Source maps translate that back to `ChatInput.tsx:87`.
- Upload source maps to the monitoring service during the build, tagged with the release, and **do not serve them publicly** unless you accept exposing your source (Next.js disables browser source maps in production by default; `productionBrowserSourceMaps` turns them on).

**5. Everything is tagged with a release**
- Tag events with the git SHA or version. Then "is this new?" and "which deploy caused it?" have immediate answers, and releases can be compared in CI and canary checks.

**6. Signals need owners and alerts**
- Data nobody watches is not observability. Define alerts on error rate, new issue types, and Web Vitals regressions, and route them to the team that owns the code.

### Practical patterns in Next.js (TypeScript)

**Capture client errors: error boundaries report to the monitor**
```tsx
// app/error.tsx: segment-level boundary
"use client";
import { useEffect } from "react";
import { reportError } from "@/lib/observability";

export default function Error({ error, reset }: { error: Error & { digest?: string }; reset: () => void }) {
  useEffect(() => { reportError(error, { source: "error.tsx", digest: error.digest }); }, [error]);
  return (
    <div role="alert">
      <p>Something went wrong.</p>
      <button onClick={reset}>Try again</button>
    </div>
  );
}
```
```tsx
// app/global-error.tsx: catches errors in the root layout; must render <html> and <body>
"use client";
export default function GlobalError({ error }: { error: Error & { digest?: string } }) {
  useEffect(() => { reportError(error, { source: "global-error" }); }, [error]);
  return (<html><body><h1>Something went wrong</h1></body></html>);
}
```
Error boundaries do not catch errors in event handlers or async code; add global handlers too.

**Catch what boundaries miss**
```ts
// src/instrumentation-client.ts: runs on the client before hydration (a Next.js convention)
window.addEventListener("error", (e) => reportError(e.error ?? e.message, { source: "window.onerror" }));
window.addEventListener("unhandledrejection", (e) => reportError(e.reason, { source: "unhandledrejection" }));
```
`instrumentation-client.ts` is the place to initialise a client monitoring SDK early so it also captures errors during hydration.

**Server errors: `instrumentation.ts` and `onRequestError`**
```ts
// src/instrumentation.ts
import type { Instrumentation } from "next";

export async function register() {
  // initialise the server-side SDK or OpenTelemetry here (runs once per server instance)
}

export const onRequestError: Instrumentation.onRequestError = async (err, request, context) => {
  // called for server errors in routes, Server Components, Server Actions and route handlers
  await reportServerError(err, { path: request.path, method: request.method, routeType: context.routeType });
};
```

**RUM: send Web Vitals with context**
```tsx
// components/WebVitals.tsx: a small client component imported by the root layout
"use client";
import { useReportWebVitals } from "next/web-vitals";

export function WebVitals() {
  useReportWebVitals((metric) => {
    const body = JSON.stringify({
      name: metric.name, value: metric.value, rating: metric.rating, id: metric.id,
      path: location.pathname, release: process.env.NEXT_PUBLIC_RELEASE,
    });
    (navigator.sendBeacon && navigator.sendBeacon("/api/vitals", body)) ||
      fetch("/api/vitals", { method: "POST", body, keepalive: true });
  });
  return null;
}
```
Report per route and per release, and read p75, not averages. A managed service (Vercel Speed Insights, Sentry, Datadog) does collection, storage and dashboards for you.

**Source maps: upload at build, serve nothing public**
```ts
// next.config.ts
const nextConfig: NextConfig = {
  productionBrowserSourceMaps: false,    // default; keep maps off the public site
};
// CI step (conceptual): after `next build`, upload .next/static/**/*.map to the monitor,
// keyed by release = git SHA, then delete the maps from the deployed artefact.
```
Most monitoring SDKs ship a build plugin or CLI that does the upload and release tagging. If you do enable `productionBrowserSourceMaps`, you publish your source; do it only knowingly.

**Release and identity tags**
```ts
setContext({ release: process.env.NEXT_PUBLIC_RELEASE, route: location.pathname });
setUser({ id: user.id, orgId: user.orgId });   // IDs, never email, name or tokens
```

**Privacy and cost controls for replay**
- Mask all text and inputs by default; unmask only what is safe. Block elements such as payment fields, chat content, documents and secrets (`data-*` attributes or CSS classes the tool understands).
- Sample: record 100% of sessions with an error and a low percentage (for example 1 to 10%) of normal sessions.
- Respect consent: gate replay and analytics behind your consent banner where regulations (GDPR, CCPA) require it.

**Alerts that matter**
- New issue first seen in the latest release.
- Error rate above a threshold per release or route.
- Regression in p75 LCP or INP versus the previous release.
- A spike in failed API calls grouped by endpoint (front end sees it first).

### Rules of thumb
1. **Instrument before you need it**: add monitoring before launch; you cannot retroactively record yesterday's failure.
2. **Every event carries release, route and a user or session ID** (never personal data in the clear).
3. **Report from boundaries and global handlers**; hand-written `try/catch` that swallows errors is the enemy.
4. **Field data decides performance work**; lab data guides it.
5. **Upload source maps per release**, and keep them private.
6. **Mask by default** in replay; unmask by exception.
7. **Alert on change** (new issue, regression), not only on absolute thresholds.
8. **Close the loop**: each alert has an owner, a runbook and a link to the replay or trace.

### Anti-patterns
- `catch (e) { console.log(e) }`: the error never leaves the user's browser.
- Monitoring only the server while the client fails silently.
- Shipping minified stack traces with no source maps.
- Publicly serving source maps while believing the code is private.
- Recording unmasked sessions that contain personal data, chat messages, secrets or payment details.
- Capturing tokens, emails or full request bodies in error context or breadcrumbs.
- Alerting on every error occurrence (alert fatigue), so real incidents are ignored.
- Sampling away all error sessions, or tracking only averages for Web Vitals.
- Collecting data with no dashboards, alerts or owner.
- Adding a heavy monitoring SDK to the critical path without measuring its own cost.

### Industry best practices
- **Use an established platform** (Sentry, Datadog, New Relic, Highlight, PostHog) rather than building your own; they provide grouping, source map handling, release tracking, replay and alerting.
- **Initialise early but cheaply**: load the SDK from `instrumentation-client.ts`, keep it small, lazy-load replay, and check its effect on LCP and INP; use `tunnel` or a first-party proxy route to avoid ad-blocker loss where acceptable.
- **Use structured breadcrumbs**: navigation, key clicks, fetch status codes, state transitions of important flows (checkout, chat send, upload).
- **Distinguish error classes**: expected user errors (validation, 4xx) vs unexpected failures (5xx, exceptions); do not page on the first.
- **Group by fingerprint and release**; mark issues resolved in the release that fixes them so regressions reopen automatically.
- **Link front-end and back-end traces** with a request ID or W3C `traceparent` header (OpenTelemetry), so a failed fetch leads straight to the server span.
- **Treat observability data as production data**: apply retention limits, access control, and PII scrubbing (principle 21); scrub in the SDK (`beforeSend`) as well as at ingestion.
- **Track Core Web Vitals per route and release** at p75, with segments for device class and connection, and compare each release to the last; add alerts for regressions (principle 56 enforces budgets earlier, in CI).
- **Monitor the whole journey**: synthetic checks for the critical flows (login, send a message, checkout) complement real-user data when traffic is low or at night.
- **Define SLOs** (for example, 99.5% of sessions error-free, p75 INP under 200 ms) and review them regularly; use error budgets to decide between feature work and reliability work.
- **Run incident reviews**: for each incident, ask which signal could have caught it sooner, and add it.
- **Keep it testable**: wrap the reporting calls in a small module (`@/lib/observability`) so components do not depend on a vendor SDK, tests can mock it, and swapping vendors is one file.
- **Respect privacy law and consent**: document what is collected, where it is stored, and how users opt out.

### Things to avoid
- Logging secrets, tokens, passwords, health or payment data to any monitoring tool.
- Recording replay on pages that display sensitive content without masking.
- Using `console.error` as the only error reporting.
- Assuming error boundaries catch event-handler, async and server-side errors.
- Letting source maps leak publicly by accident (CDN uploads of `.map` files).
- Reporting performance only from your own fast machine or CI.
- Averages as the headline Web Vitals number (tail latency hides in them).
- Reporting every handled, expected error as an incident.
- Building a custom pipeline for events, replay or grouping before trying a hosted tool.
- Leaving old SDK versions: they miss framework changes (Next.js 16, React 19 error APIs) and drop events.

### Checklist
- [ ] Client errors are reported from `error.tsx`, `global-error.tsx`, `window.onerror` and `unhandledrejection`.
- [ ] Server errors are reported through `instrumentation.ts` (`onRequestError`) or the vendor SDK.
- [ ] Source maps are uploaded per release and are not publicly served.
- [ ] Every event carries release, route and a user or session identifier (no raw personal data).
- [ ] Session replay is masked by default, sampled, and consent-aware.
- [ ] Web Vitals are collected from real users, per route and release, read at p75.
- [ ] Alerts exist for new issues, error-rate spikes and vitals regressions, each with an owner.
- [ ] A request or trace ID links front-end failures to server traces.

### In this codebase
- No `error.tsx`, `global-error.tsx`, `instrumentation.ts` or monitoring SDK (Sentry or similar) was found in `src/`. Today a client-side exception in production is not reported anywhere. This is the biggest observability gap and the first thing to close (see principle 19).
- `src/instrumentation-client.ts` exists but only strips browser-extension attributes in development; it is the right place to initialise a client monitoring SDK.
- Product analytics exists through Mixpanel (`src/components/Analytics/MixpanelProvider.tsx`, `OrgStamps.tsx`, `auth-context.tsx`) and a `dispatch` proxy route; that answers usage questions, not reliability questions. Keep the two separate.
- No `useReportWebVitals` use was found; adding a small `WebVitals` client component to the root layout would give real-user LCP, INP and CLS.
- The Content Security Policy in `next.config.ts` builds `connect-src` from an allowlist (backend, Auth0, Mixpanel, Formspree, map tiles). Any monitoring endpoint (or a first-party tunnel route) must be added there, or reports will be blocked.
- `next build --webpack` is used; source maps are not published (default). Upload them to the chosen monitor in CI, tagged with the release.
- Replay candidates must treat chat content, uploaded documents and API keys as sensitive: mask or block them.
