## 54. useTransition

> Mark heavy updates as non-urgent so input stays responsive. React renders the transition in the background and abandons it if something more urgent arrives. INP improves on filter-heavy UIs.

### Definition
React splits state updates into two priorities:
- **Urgent**: direct feedback to the user's action (typing, clicking, pressing). These must paint immediately.
- **Transition**: updates that move the UI from one view to another (switch tab, apply a filter, navigate, render a big list). These may take longer and may show intermediate states.

`useTransition` returns `[isPending, startTransition]`. State updates scheduled inside `startTransition` are marked as transitions. React renders them at lower priority, **in a way that can be interrupted**, and keeps the current UI on screen (with `isPending` true) rather than blocking the main thread or replacing the screen with a Suspense fallback.

The standalone `startTransition` (imported from `react`) does the same without the `isPending` flag. `useDeferredValue` (a sibling API) defers a **value** instead of an update.

### Key properties

**1. Transitions are interruptible, not uninterruptible**
- A common misreading is that a transition blocks input. It is the opposite: urgent updates (a keystroke, a click) **interrupt** an in-progress transition render. React throws away the stale work and starts again with the new state, so input stays responsive.
- What a transition cannot do is make a single long synchronous task shorter. If one component's render takes 400 ms by itself, React cannot yield in the middle of it; transitions help when work can be split across components and renders, and they work best with `memo`/compiled components and Suspense boundaries.

**2. The old UI stays visible while the new one prepares**
- With a transition, if the new render suspends (waits for data or code), React keeps the previous UI instead of showing the fallback again. `isPending` lets you show a subtle indicator (dimming, a spinner).

**3. It is not a timer**
- Unlike debounce (principle 53), a transition does not delay work by a fixed time. It runs as soon as possible, but at lower priority, and finishes when the main thread is free.

**4. Transitions are for updates you can mark, not for updates you must not delay**
- Do **not** wrap the update of a controlled text input's value in a transition: the input would lag. Update the input state urgently, and put the expensive derived state in the transition (or use `useDeferredValue`).

**5. React 19: async transitions ("Actions")**
- `startTransition` accepts an async function. React tracks `isPending` for the whole duration, handles errors with error boundaries, and combines with `useOptimistic` and Server Actions.
- State updates after an `await` inside the async function are no longer inside the transition scope; wrap them in another `startTransition`.

### `useTransition` vs related tools
| Tool | What it controls | Use when |
|---|---|---|
| **`useTransition`** | A **state update** you trigger (you own the `setState`) | Tab switch, filter apply, route change, any update that triggers heavy rendering |
| **`useDeferredValue`** | A **value** you receive (props from a parent, a library hook) | You cannot wrap the setter; list should lag behind the input |
| **Debounce** (principle 53) | **When** work starts (after a pause) | Network requests, autosave: cost is outside React rendering |
| **`Suspense`** | Showing fallbacks while content loads | Data or code that is not ready |
| **`useOptimistic`** (principle 33) | A temporary value shown during an async action | Instant feedback for mutations |
| **Virtualisation** (principle 51) | How many rows exist in the DOM | A render is slow because there are too many nodes |
| **Server Components / pagination** | Where work happens | The work should not run in the browser at all |

### Practical patterns in Next.js (TypeScript)

**Filter a large list without lagging the input**
```tsx
"use client";
import { memo, useState, useTransition } from "react";

export function FilterableList({ items }: { items: Item[] }) {
  const [text, setText] = useState("");            // urgent: bound to the input
  const [query, setQuery] = useState("");          // transition: drives the heavy list
  const [isPending, startTransition] = useTransition();

  return (
    <>
      <input
        value={text}
        onChange={(e) => {
          setText(e.target.value);                 // never inside the transition
          startTransition(() => setQuery(e.target.value));
        }}
      />
      <div className={isPending ? "opacity-60 transition-opacity" : ""} aria-busy={isPending}>
        <Results items={items} query={query} />
      </div>
    </>
  );
}

const Results = memo(function Results({ items, query }: { items: Item[]; query: string }) {
  const visible = items.filter((i) => i.name.toLowerCase().includes(query.toLowerCase()));
  return <ul>{visible.map((i) => <li key={i.id}>{i.name}</li>)}</ul>;
});
```
Typing stays instant; the list re-renders in the background and is interrupted if the user keeps typing. `Results` should be memoised (or compiled by the React Compiler) so the urgent `text` update does not re-render it.

**Same goal with `useDeferredValue` (when you only receive the value)**
```tsx
const deferredQuery = useDeferredValue(query);
const stale = query !== deferredQuery;
<Results items={items} query={deferredQuery} />
```

**Tab switch with a pending indicator**
```tsx
const [tab, setTab] = useState<"overview" | "activity">("overview");
const [isPending, startTransition] = useTransition();

<nav>
  <button onClick={() => startTransition(() => setTab("activity"))}>Activity</button>
</nav>
<div className={isPending ? "opacity-70" : ""}>
  <Suspense fallback={<Skeleton />}>{tab === "overview" ? <Overview /> : <Activity />}</Suspense>
</div>
```
Because the switch is a transition, a tab whose content suspends does not replace the visible tab with a skeleton; the old tab stays until the new one is ready.

**Navigation and URL state: use the router in a transition**
```tsx
"use client";
import { useRouter, useSearchParams, usePathname } from "next/navigation";
import { useTransition } from "react";

export function SortSelect() {
  const router = useRouter();
  const pathname = usePathname();
  const params = useSearchParams();
  const [isPending, startTransition] = useTransition();

  function onChange(sort: string) {
    const next = new URLSearchParams(params);
    next.set("sort", sort);
    startTransition(() => router.replace(`${pathname}?${next}`, { scroll: false }));
  }
  return (
    <select defaultValue={params.get("sort") ?? "recent"} onChange={(e) => onChange(e.target.value)} aria-busy={isPending}>
      <option value="recent">Recent</option><option value="name">Name</option>
    </select>
  );
}
```
Server-rendered filtered pages (principle 34) re-fetch when search params change; `isPending` covers the time until the new server payload arrives. In the App Router, navigations are already transitions internally, so `isPending` here is a convenient way to show progress locally.

**Async transition with a Server Action (React 19)**
```tsx
"use client";
const [isPending, startTransition] = useTransition();

function onSave(formData: FormData) {
  startTransition(async () => {
    const result = await saveAction(formData);            // Server Action
    startTransition(() => setStatus(result.ok ? "saved" : "error"));   // updates after await need their own transition
  });
}
<button disabled={isPending}>Save</button>
```
For forms, `useActionState` and `<form action={...}>` handle pending state for you (principle 35).

**Measure the improvement**
- Record an interaction in the browser Performance panel before and after, on a CPU throttled 4x to 6x; look at the long task and the "Interaction" duration.
- Track INP in the field (`useReportWebVitals`, principle 8). INP measures the time from an interaction to the next paint, which is precisely what transitions protect.

### Rules of thumb
1. **Urgent state for the input, transition state for the heavy result.**
2. **Use it when the cost is React rendering**; use debounce when the cost is the network or an external side effect.
3. **Show `isPending`** (dim, spinner, `aria-busy`) so the UI never looks frozen.
4. **Combine with `memo` or the React Compiler** so the urgent update does not re-render the heavy tree.
5. **Keep Suspense boundaries tight** so a suspending transition keeps old content visible and only the changed region waits.
6. **Do not wrap controlled-input updates** or anything that must paint immediately.
7. **Profile first** (principle 50): transitions do not fix a single 500 ms synchronous render; split or virtualise that.

### Anti-patterns
- Wrapping `setText` of a controlled input in `startTransition`, so typing lags.
- Expecting a transition to make one slow component faster; it only lets React yield between units of work.
- Using transitions to hide a slow mutation without error handling; handle errors with error boundaries or return values.
- Using `isPending` as the only loading state for a first load (use Suspense fallbacks and `loading.tsx` for initial content).
- Doing `await` work, then calling `setState` outside any transition inside an async transition, so the late update is treated as urgent.
- Starting transitions for trivial updates (toggling a boolean), adding noise.
- Using a transition where a Server Component or pagination should avoid the client work entirely.
- Reading `isPending` from one `useTransition` to represent many independent actions.

### Industry best practices
- **Apply to interaction types that INP flags**: filtering, sorting, tab switching, expanding large trees, toggling views, search-as-you-type over client data.
- **Pair with state structure**: keep an urgent copy of the value (`text`) and a transition copy (`query`), or use `useDeferredValue` when the setter is not yours.
- **Keep transitions short and focused**: put only the heavy updates inside the callback, not the whole handler.
- **Add accessible feedback**: `aria-busy` on the updating region, and a visually hidden live-region message for significant changes; avoid layout shift from spinners (reserve space).
- **Use the stale UI intentionally**: dim or overlay old results rather than blanking them; this preserves context and reduces perceived latency.
- **Use `router` calls inside transitions** for programmatic navigation when you want local pending state; use `<Link>` for ordinary navigation (principle 34).
- **Combine with Suspense and streaming** (principle 7): transitions keep committed UI during suspension; Suspense defines where waiting UI appears.
- **Combine with `useOptimistic`** for mutations: show the optimistic value immediately, and let the transition track the action's pending state (principle 33).
- **Handle errors in async transitions** with error boundaries (errors thrown inside `startTransition` surface to the nearest boundary) or by returning results from the action.
- **Test with React Testing Library**: wrap updates in `act`, assert that urgent UI updates immediately and the heavy result appears after the transition settles.
- **Verify with the React DevTools Profiler**, which marks transition renders, and in the Performance panel for long tasks.
- **Keep the React Compiler on** and keep render pure; impure renders produce inconsistent results when React retries or discards transition renders.

### Things to avoid
- Treating transitions as a replacement for correct architecture (colocation, virtualisation, server work).
- Assuming `startTransition` delays by a fixed time; there is no timer.
- Relying on transitions to fix slow handlers that do synchronous work outside React rendering (heavy JSON parsing, sorting 100,000 items in the handler): move it to a worker or the server.
- Side effects in the transition callback beyond state updates (they run immediately, not at low priority).
- Wrapping network requests (non-state work) and expecting prioritisation; transitions schedule React renders only.
- Showing both a Suspense fallback and an `isPending` spinner for the same wait.
- Stacking `useDeferredValue`, a debounce and a transition on the same input without measuring.
- Forgetting that a discarded transition render may run component code more than once; render must be pure.

### Checklist
- [ ] The slow part was measured as React rendering, on an interaction users perform.
- [ ] Input state updates urgently; the derived, heavy state is in the transition (or deferred).
- [ ] The heavy subtree is memoised or compiled so urgent updates do not re-render it.
- [ ] `isPending` drives a visible, accessible indicator without layout shift.
- [ ] Suspense boundaries are placed so old content stays visible during a transition.
- [ ] Async transitions wrap post-`await` state updates in another transition and handle errors.
- [ ] INP or the Performance panel showed an improvement on a throttled device.

### In this codebase
- `useTransition` and `useDeferredValue` are not used in `src/`. Good first candidates are the filter and search UIs: chat history search in `src/app/(app)/chats/page.tsx`, the agents and templates pages, the model selector, and the right-sidebar search (which currently uses a 150 ms debounce in `src/components/layout/RightSidebar.tsx`).
- For search backed by the network, keep debouncing and query keys (principles 53 and 30); for filtering data that is already in memory, prefer a transition or deferred value.
- Lists that use `@tanstack/react-virtual` (chats, agents, pinboard) already limit DOM work (principle 51); a transition helps when the filtering or sorting of the data itself is the slow step.
- `reactCompiler` is on, which memoises heavy children automatically; keep components pure so transition renders can be safely retried.
