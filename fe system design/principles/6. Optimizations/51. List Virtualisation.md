## 51. List Virtualisation

> Render only the rows in the viewport (plus a small buffer) and reuse DOM nodes as the user scrolls. Cost depends on what is visible, not on how long the list is.

### Definition
A virtualised list (also called windowing) keeps the full dataset in memory but mounts only the items that intersect the scroll container, plus an **overscan** buffer. A tall spacer element (or total-size container) gives the scrollbar the correct length, and visible rows are absolutely positioned at their computed offsets. As the user scrolls, rows leaving the window unmount or are recycled, and new rows mount.

The effect: a list of 10,000 rows mounts a few dozen DOM nodes, so the initial render takes milliseconds and scrolling stays smooth. A common rule of thumb is to consider virtualisation for any list beyond roughly 200 rows, or sooner when rows are expensive (images, rich content, many child components). Measure; the threshold depends on row cost.

### Key properties

**1. Cost follows the window, not the dataset**
- DOM node count, style recalculation, layout and memory stay roughly constant as the list grows.
- React render work is limited to visible rows.

**2. Row size must be known or measured**
- **Fixed size** is the simplest and fastest: `estimateSize: () => 44`.
- **Variable size** needs measurement: give an estimate, then measure each rendered row (`measureElement`), which refines positions as rows appear. Dynamic heights are what make chat transcripts and feeds harder.

**3. Overscan trades memory for smoothness**
- Rendering a few extra rows above and below (`overscan: 5` to `10`) avoids blank flashes during fast scrolling.

**4. Scroll position and identity are your responsibility**
- Stable `key`s (ids, not indexes), scroll restoration, "scroll to item", and "stick to bottom" behaviour are not automatic.

**5. Virtualisation changes what the browser knows**
- Off-screen rows do not exist in the DOM, so find-in-page, text selection across rows, anchors, tab order and screen readers cannot reach them without extra work.

### Virtualise, paginate or stream?
| Approach | Good for | Cost |
|---|---|---|
| **Virtualisation** | Long scrollable lists, grids, logs, chat history, dropdown options (hundreds to millions of rows already in memory) | Complexity: sizing, a11y, find-in-page |
| **Pagination** (server-side) | Data too large to hold, SEO-visible pages, tables where users jump to a page | Extra clicks; page state in the URL (principle 34) |
| **Infinite scroll + virtualisation** | Feeds loaded in pages from an API, with a bounded DOM | Needs a "load more" trigger near the end |
| **`content-visibility: auto`** | Moderate lists of heavy sections where you want find-in-page to keep working | Less control; browser support and sizing caveats (principle 48) |
| **Plain rendering** | Under about 100 to 200 simple rows | None; do not add machinery |

### Practical patterns in Next.js (TypeScript)

**Fixed-height rows with `@tanstack/react-virtual`**
```tsx
"use client";
import { useRef } from "react";
import { useVirtualizer } from "@tanstack/react-virtual";

type Row = { id: string; title: string };

export function VirtualList({ rows }: { rows: Row[] }) {
  const parentRef = useRef<HTMLDivElement>(null);

  const virtualizer = useVirtualizer({
    count: rows.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 44,
    overscan: 8,
    getItemKey: (index) => rows[index].id,       // stable keys, not indexes
  });

  return (
    <div ref={parentRef} className="h-[600px] overflow-auto" role="list">
      <div style={{ height: virtualizer.getTotalSize(), position: "relative" }}>
        {virtualizer.getVirtualItems().map((item) => (
          <div
            key={item.key}
            role="listitem"
            className="absolute inset-x-0 top-0"
            style={{ height: item.size, transform: `translateY(${item.start}px)` }}
          >
            {rows[item.index].title}
          </div>
        ))}
      </div>
    </div>
  );
}
```
The scroll element needs a fixed height (or a flex/grid parent that constrains it); an unconstrained container renders every row.

**Variable-height rows: measure after render**
```tsx
const virtualizer = useVirtualizer({
  count: messages.length,
  getScrollElement: () => parentRef.current,
  estimateSize: () => 96,                       // a good guess limits scroll jumps
  overscan: 10,
});

{virtualizer.getVirtualItems().map((item) => (
  <div
    key={item.key}
    data-index={item.index}
    ref={virtualizer.measureElement}            // the measured height replaces the estimate
    className="absolute inset-x-0 top-0"
    style={{ transform: `translateY(${item.start}px)` }}
  >
    <Message message={messages[item.index]} />
  </div>
))}
```
Do not put `height` on the measured element; let content size it. Avoid margins on measured rows (use padding), because margins are not included in the measurement.

**Infinite loading near the end**
```tsx
const items = virtualizer.getVirtualItems();
const last = items[items.length - 1];

useEffect(() => {
  if (last && last.index >= rows.length - 5 && hasNextPage && !isFetchingNextPage) {
    fetchNextPage();                            // e.g. TanStack Query useInfiniteQuery (principle 30)
  }
}, [last?.index, rows.length, hasNextPage, isFetchingNextPage, fetchNextPage]);
```

**Grids: virtualise rows, lay out columns inside**
Compute `columns` from the container width, set `count = Math.ceil(items.length / columns)`, and render each virtual row as a CSS grid of `columns` cells. The agents grid in this app follows this idea.

**Keep rows cheap and stable**
```tsx
const RowView = memo(function RowView({ row }: { row: Row }) { /* pure render */ });
```
Rows remount as they scroll in, so keep mount work small: no per-row network calls, lazy images (`loading="lazy"`, fixed sizes), and no heavy effects in the row component. Keep row state outside the row (in the parent or a store keyed by id) if it must survive scrolling away.

**Search or find-in-page**
Provide an in-app search that filters the data (not the DOM) and jumps with `virtualizer.scrollToIndex(i)`; the browser's Ctrl+F cannot find text in unmounted rows.

### Rules of thumb
1. **Virtualise when rows are many or heavy**: start considering it around 200 rows, earlier for expensive rows; measure before and after.
2. **Fix the scroll container's height**, and use `overflow: auto` on it.
3. **Estimate close, measure for variable rows**, and use stable ids as keys.
4. **Overscan 5 to 10**; raise it for heavy rows or fast scrolling, lower it for memory.
5. **Keep row components pure and light**; lift state out of rows.
6. **Preserve accessibility** (roles, `aria-rowcount`, `aria-rowindex`/`aria-setsize`/`aria-posinset`) and keyboard navigation.
7. **Do not virtualise tiny lists**, and do not virtualise what you can paginate on the server.

### Anti-patterns
- Rendering 5,000 DOM rows and then optimising each with `memo`.
- Virtualising without a bounded scroll container (the virtualiser sees a huge viewport and renders everything).
- Using array index as `key` when rows can reorder, insert or delete.
- Variable-height rows with a fixed `estimateSize` and no measurement, causing overlap or scroll jumps.
- Margins on measured rows, causing clipped or overlapping content.
- Per-row fetching inside the row component, triggering a request storm while scrolling.
- Storing row-local state in the row, then losing it when it scrolls out and back.
- Virtualising a list whose content must be indexable by search engines or found with Ctrl+F, with no alternative.

### Industry best practices
- **Choose a maintained headless library** (`@tanstack/react-virtual`, `react-window`, `react-virtuoso`) instead of writing windowing math; headless means you keep your own markup and Tailwind styling.
- **Measure with real data**: profile scroll and initial render with 10,000 rows on a throttled CPU, and track INP (principle 8).
- **Prefer server-side filtering, sorting and pagination** for very large data sets; virtualise the page you have, do not download a million rows.
- **Use `transform: translateY` for positioning** (compositor-friendly) rather than changing `top` for each row.
- **Use `will-change` sparingly** and avoid heavy shadows, filters and blur per row.
- **Make scroll anchoring and restoration explicit**: save `scrollOffset` per list (or the index of the first visible row), restore it on return, and handle prepend (older chat messages) without jumping.
- **Support keyboard and assistive tech**: keep focus on a row that must stay mounted (`rangeExtractor` to always include the focused or pinned index), set `aria-rowcount` and per-row positions for tables and grids.
- **Handle "stick to bottom" deliberately** for chat: auto-scroll only if the user is already near the bottom.
- **Handle resize**: virtualisers observe container size; make sure ResizeObserver is available in tests (stub it) and re-measure on width changes (text wrapping changes row height).
- **Combine with lazy images and skeleton rows** so scrolling does not trigger layout shift.
- **Test the list**: unit-test the data logic, and use a browser test (Playwright) for scroll, selection and "scroll to item" behaviour, since jsdom has no layout.
- **Offer an alternative path** where discoverability matters: pagination or a "show all" mode for printing and accessibility.

### Things to avoid
- Adding virtualisation to a list of 30 items.
- Letting the DOM grow unbounded in an infinite-scroll feed without windowing.
- Using layout-triggering style changes on every scroll event.
- Rendering the whole data set to compute heights.
- Setting `overscan` to hundreds "to be safe", which defeats the purpose.
- Putting `position: sticky` headers inside a virtualised container without handling them in the range logic.
- Forgetting that unmounted rows do not receive events, focus or form state.
- Testing with a handful of rows only, then shipping against production-sized data.

### Checklist
- [ ] The list has more rows than the DOM comfortably handles, or rows are heavy; this was measured.
- [ ] The scroll container has a bounded height and `overflow: auto`.
- [ ] Row sizes are fixed, or measured with `measureElement` and a close estimate.
- [ ] Keys are stable ids; row components are light and pure.
- [ ] Overscan is tuned; no blank flashes during fast scroll.
- [ ] Keyboard navigation, focus and ARIA roles still work; in-app search or "scroll to" replaces Ctrl+F.
- [ ] Infinite loading triggers near the end and is guarded against duplicate fetches.
- [ ] Scroll position is restored or anchored where users expect it.
