## 46. Code Splitting

> Break one bundle into chunks that load on demand. The highest-leverage bundle optimisation: a user should download only the code for the route and interactions they actually use.

### Definition
Code splitting divides the JavaScript the browser must download into **chunks** that load when needed, instead of one file containing the whole app. The bundler (Turbopack by default in Next.js 16, or webpack) creates the chunk graph; you decide where the split points are.

Splitting has three levels:
1. **Route level** (automatic): every `page.tsx` and its client imports become their own chunk set.
2. **Component level** (manual): heavy or rarely shown Client Components are loaded through `next/dynamic` or `React.lazy`.
3. **Library level** (manual): large dependencies are loaded with `import()` at the moment of use.

A commonly cited rule of thumb is that route splitting alone cuts the initial bundle by half or more compared with a single bundle (figures of 50 to 70% are quoted for apps that start from one big bundle). Treat that as a typical range, not a guarantee; measure your own app.

### Key properties

**1. Route splitting is free in the App Router**
- Each route segment loads only its own client code plus shared chunks.
- Server Components are never part of the client bundle at all (principle 6), so the cheapest "split" is keeping code on the server.

**2. Split points are dynamic `import()`**
- A static `import` pulls code into the parent chunk. A dynamic `import()` creates a separate chunk fetched when the call runs.
- `next/dynamic` is a composite of `React.lazy()` and Suspense; it behaves the same in `app` and `pages`.

**3. Split what is heavy and not needed on first paint**
- Good candidates: modals and dialogs, rich-text editors, charts, maps, code highlighters, PDF or diagram renderers, admin-only panels.
- Poor candidates: small components, anything above the fold, anything needed for LCP.

**4. Shared chunks are extracted automatically**
- Code used by several routes becomes a shared chunk, so splitting does not duplicate libraries. Over-splitting can still create many small requests; check the chunk graph.

**5. Splitting trades bytes for latency**
- A deferred chunk is a network round trip when first needed. Preload on hover, focus or idle so the wait is hidden.

### Decision table
| What you want to defer | Technique | Notes |
|---|---|---|
| A route | Nothing to do (automatic) | Keep `page.tsx` thin; push client code to leaves |
| A Client Component shown on interaction (modal, popover) | `next/dynamic(() => import(...))` | Render it only when open so the chunk loads on demand |
| A browser-only Client Component (map, canvas, editor) | `next/dynamic(..., { ssr: false })` in a Client Component | `ssr: false` is not allowed in Server Components |
| A Server Component's heavy client children | Plain `next/dynamic` import from the server | Only the client children are lazy-loaded; the server part still renders |
| A library used after an event (fuzzy search, export to PDF) | `await import("lib")` inside the handler | No component wrapper needed |
| A component below the fold | `next/dynamic`, or Suspense with `React.lazy` | Also see [48. Lazy Loading](48.%20Lazy%20Loading.md) |
| Code that must never reach the client | Keep it in a Server Component, add `server-only` | Zero client bytes |

### Practical patterns in Next.js (TypeScript)

**Route splitting needs no code, only thin pages**
```tsx
// app/(app)/reports/page.tsx   Server Component: fetch + assemble
import { getReports } from "@/lib/data/reports";
import { ReportsTable } from "@/components/ReportsTable";   // server-safe
import { ExportButton } from "@/components/ExportButton";   // small client leaf

export default async function Page() {
  const reports = await getReports();
  return (
    <>
      <ExportButton />
      <ReportsTable reports={reports} />
    </>
  );
}
```

**Component splitting: load a dialog only when opened**
```tsx
"use client";
import dynamic from "next/dynamic";
import { useState } from "react";

const ShareDialog = dynamic(() => import("@/components/ShareDialog").then((m) => m.ShareDialog), {
  loading: () => null,
});

export function ShareButton() {
  const [open, setOpen] = useState(false);
  return (
    <>
      <button onClick={() => setOpen(true)}>Share</button>
      {open && <ShareDialog onClose={() => setOpen(false)} />}
    </>
  );
}
```
The dialog's chunk is requested the first time `open` becomes true. Named exports are returned from the promise with `.then((m) => m.ShareDialog)`.

**Browser-only widget: `ssr: false` lives in a Client Component**
```tsx
"use client";
import dynamic from "next/dynamic";

const Map = dynamic(() => import("./Map"), {
  ssr: false,
  loading: () => <div className="h-80 animate-pulse rounded-md bg-muted" aria-hidden />,
});
export function MapPanel() { return <Map />; }
```
Reserve the box height in `loading` so the layout does not shift (see principle 8).

**Library splitting inside an event handler**
```tsx
"use client";
export function ExportButton({ rows }: { rows: Row[] }) {
  async function onClick() {
    const { exportToXlsx } = await import("@/lib/export-xlsx"); // chunk fetched on first click
    await exportToXlsx(rows);
  }
  return <button onClick={onClick}>Export</button>;
}
```

**Hide the latency: preload on intent**
```tsx
const loadEditor = () => import("@/components/Editor");
const Editor = dynamic(loadEditor);

<button onPointerEnter={loadEditor} onFocus={loadEditor} onClick={() => setEditing(true)}>Edit</button>
```
Calling the same `import()` early warms the module cache, so the click shows the editor immediately.

**Find what to split: the bundle analyzer**
- Next.js 16.1 and later: `npx next experimental-analyze` (Turbopack bundle analyzer).
- Webpack: `@next/bundle-analyzer`, enabled by an environment variable.
Look for the largest client chunks, libraries that appear in many routes, and server-only code that leaked into the client.

### Rules of thumb
1. **Server first.** Moving code to a Server Component beats lazy-loading it.
2. **Split by interaction and visibility**, not by file size alone: if the user may never open it, do not ship it up front.
3. **Never split the LCP element or above-the-fold UI**; it only delays the metric.
4. **Reserve space** for deferred UI to avoid layout shift.
5. **Preload on intent** (hover, focus, idle) for splits the user is likely to trigger.
6. **Measure with the analyzer** before and after; keep a per-route JS budget in CI.
7. **Split once, at the boundary**: lazy-load the wrapper, not each of its small children.

### Anti-patterns
- Lazy-loading small components: the extra request costs more than the bytes saved.
- Wrapping the whole page in `dynamic` so nothing renders until JS arrives.
- Using `ssr: false` for content that matters for SEO or LCP.
- A `"use client"` file that statically imports a heavy library used on one rare path.
- Importing a barrel file (`index.ts`) that drags a whole feature into a route chunk.
- Waterfalls: a lazy component that itself lazy-loads its data, then another lazy component, one after another.
- Splitting every modal by habit without checking that the chunks are large.

### Industry best practices
- **Set JavaScript budgets per route** (for example, a first-load JS ceiling) and fail CI when a route exceeds it; track changes in each pull request.
- **Run the bundle analyzer regularly**, especially after adding a dependency; one library can outweigh the rest of the route.
- **Prefer lighter dependencies** (`date-fns` over `moment`, a small markdown parser over a full editor) and check bundle cost before installing (bundlephobia-style checks).
- **Keep Client Components as leaves** so most of a page ships zero JS (principles 6 and 12).
- **Use `import()` for event-driven libraries** (export, charts on tab switch, syntax highlighting after expand).
- **Provide a stable `loading` fallback** with fixed dimensions, or `null` for invisible UI such as dialogs.
- **Preload critical next steps** with `onPointerEnter`, `onFocus`, `requestIdleCallback` or `router.prefetch`; Next.js already prefetches linked routes in view.
- **Split third-party scripts too**: load analytics and widgets with `next/script` and a non-blocking strategy (principle 8).
- **Check chunk counts, not only size**: many tiny chunks on HTTP/1.1 or poor networks hurt; on HTTP/2 or HTTP/3 a moderate number is fine.
- **Test the deferred path**: throttle the network and click quickly to see the loading state, errors and focus handling.
- **Handle chunk load failures**: wrap lazy parts in an error boundary (principle 19) so a failed fetch (offline, new deploy) shows a retry, not a blank screen.
- **Keep deployments version-skew safe**: stale clients requesting removed chunks after a deploy need a reload path (Next.js supports deployment IDs for skew protection on supporting hosts).

### Things to avoid
- Treating the 50 to 70% figure as a promise instead of measuring.
- `ssr: false` inside a Server Component (it is an error); move it into a Client Component.
- Expecting a dynamically imported Server Component to defer its own server code; only its Client Component children are lazy-loaded.
- Dynamic import paths built from variables the bundler cannot analyse, which can include far more than intended.
- Lazy-loading anything that appears on every page load, such as the header or the main content.
- Leaving heavy libraries (charts, editors, maps) in the shared layout bundle.
- Adding magic-comment tweaks without a measured reason.
- Forgetting a loading state or an error boundary around lazy parts.

### Checklist
- [ ] Pages and layouts are Server Components that assemble small client leaves.
- [ ] The analyzer was run; the largest client chunks are justified.
- [ ] Heavy, rarely used Client Components are loaded with `next/dynamic` or `import()`.
- [ ] Above-the-fold and LCP content is not lazy-loaded.
- [ ] `ssr: false` is used only in Client Components, and only for browser-only code.
- [ ] Deferred UI has reserved space and a loading fallback; lazy parts sit inside an error boundary.
- [ ] A first-load JS budget per route is enforced in CI.
