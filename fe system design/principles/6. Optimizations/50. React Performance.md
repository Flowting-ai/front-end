## 50. React Performance

> `memo`, `useMemo` and `useCallback` skip work when inputs have not changed. Profile first, optimise second. With the React Compiler on, most of this is automatic.

### Definition
React performance work means doing **less rendering work** and making each render **cheaper**. A component re-renders when its state changes, its parent re-renders, or a context it reads changes. Re-rendering is normally cheap; it becomes a problem when a render is expensive (heavy computation, huge lists) or happens far too often (state too high in the tree, fast-changing context).

The manual tools are:
- **`React.memo(Component)`**: skip re-rendering when props are shallow-equal to the last render.
- **`useMemo(fn, deps)`**: cache a computed value between renders.
- **`useCallback(fn, deps)`**: cache a function identity between renders (useful so a `memo` child sees a stable prop).

Since React 19, the **React Compiler** (`babel-plugin-react-compiler`) applies this memoisation automatically at build time. Next.js supports it through `reactCompiler: true` and applies it only to relevant files (those with JSX or hooks) to keep builds fast.

### Key properties

**1. Measure before changing anything**
- Use the React DevTools Profiler ("why did this render?") and the browser Performance panel. Fix what is measured to be slow, in interactions that users actually feel (INP, principle 8).

**2. Fix structure before adding memoisation**
- The cheapest optimisations are architectural: move state down to where it is used (colocation), pass `children` so static parts are not re-created, and split fast-changing state from slow (principle 24).

**3. `memo`, `useMemo` and `useCallback` only help when inputs are stable**
- `memo` is defeated by a new object, array or function prop on every render. `useCallback` and `useMemo` exist mainly to keep such props stable, or to avoid truly expensive recomputation.

**4. The React Compiler changes the default**
- With the compiler enabled, components and hooks are memoised automatically when they follow the Rules of React (pure render, no mutation of props or state). Manual hooks are rarely needed and can stay where they already exist.
- Manual memoisation is still valid for **precise control**: a value used as an effect dependency, or a case the compiler cannot analyse.

**5. Rendering is not the only cost**
- Slow pages also come from large bundles (principle 46), long lists, layout thrash, big images (principle 49) and waterfalls. Profile to find which one.

### Where to look first
| Symptom | Likely cause | Fix |
|---|---|---|
| Typing in an input lags | Whole page re-renders on each keystroke | Colocate input state; `useDeferredValue` for the expensive consumer |
| Click feels slow (INP) | Long synchronous render or handler | `useTransition`; split work; virtualise; move to the server |
| Long list janks while scrolling | Thousands of DOM nodes | Virtualise (`@tanstack/react-virtual`); paginate |
| Many components re-render on one change | Context value changes too often | Split contexts, use selectors or a store (principle 24) |
| Child re-renders though its props look the same | New object, array or function props each render | Stable props via compiler, `useMemo`, `useCallback`; or restructure |
| Expensive calculation on every render | Derived data computed in render | `useMemo`, or compute on the server or in a worker |
| Slow initial load | Too much JavaScript | Code splitting, Server Components (principles 6, 46) |
| List items remount or lose state | Unstable or index `key`s | Use stable ids |

### Practical patterns in Next.js (TypeScript)

**Colocate state instead of memoising**
```tsx
// Bad: typing re-renders the expensive list
function Page() {
  const [query, setQuery] = useState("");
  return (<><input value={query} onChange={(e) => setQuery(e.target.value)} /><HeavyList /></>);
}

// Good: state lives in the component that needs it
function SearchBox() {
  const [query, setQuery] = useState("");
  return <input value={query} onChange={(e) => setQuery(e.target.value)} />;
}
function Page() { return (<><SearchBox /><HeavyList /></>); }
```

**`children` as a performance boundary**
```tsx
function Tracker({ children }: { children: React.ReactNode }) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  return <div onPointerMove={(e) => setPos({ x: e.clientX, y: e.clientY })}>{children}</div>;
}
// <Tracker><ExpensiveTree /></Tracker>: ExpensiveTree element is created by the parent,
// so it is not re-rendered when `pos` changes.
```

**Keep input responsive: `useDeferredValue`**
```tsx
"use client";
import { useDeferredValue, useState } from "react";

export function Search({ items }: { items: Item[] }) {
  const [query, setQuery] = useState("");
  const deferred = useDeferredValue(query);          // lags behind while React is busy
  const stale = query !== deferred;
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <div className={stale ? "opacity-60" : ""}><Results items={items} query={deferred} /></div>
    </>
  );
}
```
`Results` should be memoised (or compiled) so it skips re-rendering while `deferred` is unchanged.

**Non-urgent updates: `useTransition`**
```tsx
const [isPending, startTransition] = useTransition();
function onTab(next: string) {
  startTransition(() => setTab(next));   // urgent updates (typing, clicks) stay responsive
}
```

**Manual memoisation where it still earns its place**
```tsx
const Row = memo(function Row({ item, onSelect }: { item: Item; onSelect: (id: string) => void }) {
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

function List({ items }: { items: Item[] }) {
  const onSelect = useCallback((id: string) => select(id), []);          // stable identity for memo child
  const sorted = useMemo(() => [...items].sort(byName), [items]);        // only if profiling shows the sort is slow
  return <ul>{sorted.map((i) => <Row key={i.id} item={i} onSelect={onSelect} />)}</ul>;
}
```
With the React Compiler on, `memo`, `useCallback` and `useMemo` here are mostly redundant; keep them only for a measured, specific reason (and never remove existing ones in bulk without profiling; removing them can change compiler output).

**Virtualise long lists**
```tsx
"use client";
import { useVirtualizer } from "@tanstack/react-virtual";
import { useRef } from "react";

export function VirtualList({ rows }: { rows: Row[] }) {
  const parent = useRef<HTMLDivElement>(null);
  const v = useVirtualizer({ count: rows.length, getScrollElement: () => parent.current, estimateSize: () => 44 });
  return (
    <div ref={parent} className="h-[600px] overflow-auto">
      <div style={{ height: v.getTotalSize(), position: "relative" }}>
        {v.getVirtualItems().map((vi) => (
          <div key={rows[vi.index].id} className="absolute inset-x-0" style={{ transform: `translateY(${vi.start}px)`, height: vi.size }}>
            <RowView row={rows[vi.index]} />
          </div>
        ))}
      </div>
    </div>
  );
}
```

**Enable and tune the compiler**
```ts
// next.config.ts
const nextConfig: NextConfig = {
  reactCompiler: true,                                  // or { compilationMode: "annotation" } for opt-in "use memo"
};
```
Install `babel-plugin-react-compiler` and keep `eslint-plugin-react-hooks` current (its compiler-aware rules flag code the compiler must skip). Opt a component out with `"use no memo"` if it breaks and cannot be fixed immediately, and leave a comment with the reason.

### Rules of thumb
1. **Profile, then fix.** No optimisation without a measured problem in a real interaction.
2. **Structure first**: colocate state, pass `children`, split contexts, derive instead of syncing.
3. **Trust the compiler**: write pure, plain code; do not add `useMemo`/`useCallback` by habit.
4. **Stable identities matter only at boundaries**: `memo` children, effect dependencies, context values.
5. **Defer or transition expensive, non-urgent updates** (`useDeferredValue`, `useTransition`).
6. **Virtualise lists** beyond a few hundred rows; do not render what is off screen.
7. **Keep render pure**: no side effects, no mutation, no reading mutable globals; the compiler and Strict Mode depend on it.
8. **Use stable, unique keys.**

### Anti-patterns
- Wrapping every function in `useCallback` and every value in `useMemo`, with no measurement.
- `memo` on components whose props are new objects or inline functions each render, so it never skips.
- Memoising cheap calculations; the cost of comparing dependencies can exceed the cost of the work.
- Copying props into state and syncing with effects (extra renders and bugs).
- Using array index as `key` on reorderable lists.
- Putting a fast-changing value (pointer position, typing) in a wide context.
- Fixing slow renders with `useMemo` when the real problem is a 3,000-row DOM.
- Disabling the compiler (`"use no memo"`) broadly instead of fixing the rule violation.
- Passing inline `{}` or `[]` literals as props or context values and then wondering why `memo` fails (unless the compiler handles it).

### Industry best practices
- **Use the React DevTools Profiler** with "Record why each component rendered", and the browser Performance panel; test on a throttled CPU (4x to 6x) and a mid-range phone.
- **Track INP in the field** (principle 8) and tie React fixes to it; lab renders alone can mislead.
- **Adopt the React Compiler** on new and existing code, keep `eslint-plugin-react-hooks` on, and fix violations of the Rules of React rather than silencing them.
- **Prefer derived state over synchronised state**: compute during render, or with `useMemo` only when proven expensive.
- **Move work off the client**: Server Components for data-heavy display (principle 6), Web Workers for CPU-bound tasks, server-side pagination and filtering.
- **Keep Client Components small and leaf-level** so a state change re-renders little.
- **Use selectors with external stores** so components subscribe to slices (principle 24).
- **Avoid layout thrash**: batch DOM reads and writes; use CSS (`transform`, `opacity`) for animation instead of per-frame React state.
- **Debounce or throttle high-frequency events** (resize, scroll, input to search APIs); prefer `useDeferredValue` for render-bound lag and debounce for network-bound lag.
- **Use `Suspense` boundaries** to let fast parts appear while slow parts load, and `startTransition` to keep existing UI while new UI prepares.
- **Test performance regressions**: component render counts in tests for hot paths, and bundle and INP budgets in CI.
- **Name and document intentional memoisation** with a short comment ("stable for effect dependency", "profiled: 40 ms sort") so later readers know it is deliberate.

### Things to avoid
- Optimising without a profile, or from lab data you cannot reproduce.
- Removing existing memoisation in bulk after enabling the compiler without checking.
- Adding libraries (`why-did-you-render`, heavy state libs) to production builds; keep diagnostics dev-only.
- Mutating state or props (breaks `memo`, the compiler and concurrent rendering).
- Reading or writing `ref.current` during render for values that affect output.
- Creating components inside components (they remount every render).
- Relying on `React.memo` to stop context-driven renders (it cannot).
- Using `useEffect` to compute values from props or state.
- Rendering huge tables, chat histories or logs without virtualisation or pagination.

### Checklist
- [ ] A measured problem (Profiler trace, INP, long task) exists before any change.
- [ ] State is colocated; expensive subtrees receive stable `children` or props.
- [ ] `reactCompiler` is on, `eslint-plugin-react-hooks` is clean, and opt-outs have comments.
- [ ] Remaining manual `memo`/`useMemo`/`useCallback` have a stated reason.
- [ ] Expensive non-urgent updates use `useDeferredValue` or `useTransition`.
- [ ] Long lists are virtualised or paginated; keys are stable ids.
- [ ] Context values are split by change frequency; high-frequency state uses selectors.
- [ ] INP and bundle budgets are checked after the change.
