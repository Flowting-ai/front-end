## 49. Image Optimisation

> Send the right format, at the right size, at the right time. Images are the heaviest part of most pages and very often the LCP element, so a few settings decide a large share of load time.

### Definition
Image optimisation is the set of decisions that make an image cheap to deliver: **format** (AVIF, WebP, SVG), **dimensions** (no bigger than displayed, per device), **compression quality**, **loading priority** (eager for the hero, lazy elsewhere, principle 48), **layout stability** (reserved space) and **caching** (long-lived, immutable URLs).

In Next.js the `<Image>` component from `next/image` does most of this: it resizes on demand, serves modern formats chosen from the browser's `Accept` header, generates `srcset`, lazy-loads by default and prevents layout shift when dimensions are known.

### The four levers
Images are commonly quoted as roughly half or more of the bytes on image-heavy pages such as ecommerce catalogues (figures of 50 to 75% are common; the HTTP Archive Web Almanac publishes current medians, which are lower across all sites). Four levers cover almost all of the savings:

| Lever | What it does | Typical effect | In Next.js |
|---|---|---|---|
| **a. Format** | Serve WebP or AVIF instead of JPEG/PNG | WebP is often about 25 to 35% smaller than JPEG at similar quality, AVIF more (commonly 30 to 50%); a rule of thumb is 20 to 25% or better | `images.formats`, chosen per request from the `Accept` header |
| **b. Responsive `srcset`** | Give each device an image of the right width, not the largest one | Mobile downloads a fraction of the desktop bytes | `sizes` on `<Image>` generates the `srcset` |
| **c. Compression (quality)** | Lower quality until differences are invisible | Quality 75 to 85 is usually visually identical to the original at a much smaller size | `quality` prop, restricted by `images.qualities` (default `[75]`) |
| **d. Explicit dimensions** | Declare `width` and `height` (or an aspect ratio) so the browser reserves the box before the file arrives | No layout shift (CLS), no reflow | `width` + `height`, static imports, or `fill` in a sized parent |

Levers a to c shrink the download; lever d does not change the bytes but keeps the layout stable while they arrive, which is what protects CLS. Do all four: a small image that shifts the page is still a Core Web Vitals failure.

```tsx
<Image
  src="/products/shoe.jpg"
  alt="Red running shoe, side view"
  width={800}            // d. explicit dimensions: the browser reserves 800 x 600 before loading
  height={600}
  sizes="(max-width: 768px) 100vw, 400px"   // b. responsive srcset: right size per device
  quality={80}           // c. compression: 75 to 85 range (must be allowed in images.qualities)
  // a. format: AVIF or WebP is chosen automatically from images.formats and the Accept header
/>
```
These percentages are typical ranges, not guarantees: results depend on image content, so compare file sizes for your own assets before setting budgets.

### Key properties

**1. Format**
- **AVIF** is usually smallest, **WebP** is a widely supported good default, **JPEG/PNG** are fallbacks. **SVG** is best for icons, logos and simple illustrations (resolution independent, tiny).
- Next.js serves WebP by default (`images.formats: ['image/webp']`). Add AVIF with `formats: ['image/avif', 'image/webp']`; the order matters, and each format is cached separately, which increases storage and the first-request encode cost.

**2. Dimensions and `sizes`**
- Serve an image close to its displayed size times the device pixel ratio, not the original upload.
- `sizes` tells the browser how wide the image will be at each breakpoint. Without it the browser assumes `100vw` and may download a needlessly large file. With it, Next.js generates a full `srcset` (640w, 750w, ...); without it, a limited 1x/2x set for fixed-size images.

**3. Quality**
- A single quality around 75 is a good default. In Next.js 16 `images.qualities` defaults to `[75]` and acts as an allowlist; a `quality` prop that is not listed is rounded to the closest allowed value.

**4. Priority**
- The LCP image loads eagerly and early: `preload` on `<Image>` (Next.js 16; `priority` is deprecated), or `loading="eager"` with `fetchPriority="high"`. Everything else stays lazy.

**5. Layout stability**
- Provide `width` and `height` (static imports supply them automatically), or use `fill` inside a container that has a size or aspect ratio. This prevents CLS.

**6. Caching**
- Optimised images are cached; the lifetime is the larger of `minimumCacheTTL` and the upstream `Cache-Control`. There is no invalidation mechanism, so change the image URL when the content changes (hashed filename, version query) rather than raising the TTL.

### Decision table
| Situation | Use |
|---|---|
| Icon, logo, simple illustration | Inline SVG or an SVG file (served as a plain `<img>`/`unoptimized`) |
| Photo in the repo | Static import: `import hero from "./hero.jpg"` (auto width, height, blur data) |
| Remote or CMS image | `<Image src="https://...">` with `images.remotePatterns` |
| User-uploaded image | Resize and re-encode on upload (or via a loader/CDN); validate type and size server-side |
| Hero / LCP | `<Image preload sizes="100vw" />` and a correctly sized source |
| Image in a grid | `sizes="(max-width: 768px) 100vw, 33vw"`, lazy by default |
| Image that fills a container | `fill` + `sizes` + a positioned parent with a fixed size or aspect ratio |
| Different crops per breakpoint | Art direction with `getImageProps()` and `<picture>` |
| Authenticated image URL | `unoptimized` (the optimiser cannot send your credentials) |
| Animated GIF/WebP | `unoptimized` or convert to video (`<video muted loop playsInline>`) |
| Already-optimised CDN (Cloudinary, imgix, Vercel) | A custom `loader` or `loaderFile` |

### Practical patterns in Next.js (TypeScript)

**Static import: dimensions and blur placeholder for free**
```tsx
import Image from "next/image";
import hero from "@/../public/images/hero.jpg";

export function Hero() {
  return <Image src={hero} alt="Dashboard showing usage by team" preload sizes="100vw" placeholder="blur" />;
}
```
Static imports let Next.js read the intrinsic size at build time and create a `blurDataURL`.

**Remote images need an allowlist**
```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  images: {
    formats: ["image/avif", "image/webp"],
    remotePatterns: [
      { protocol: "https", hostname: "images.example-cdn.com", pathname: "/uploads/**" },
    ],
    qualities: [60, 75],
    minimumCacheTTL: 60 * 60 * 24 * 7, // 7 days; change URLs on content change
  },
};
export default nextConfig;
```
Be specific with `protocol`, `hostname` and `pathname`. `images.domains` is deprecated because it allows a whole host. Remote responses are also bounded by `maximumResponseBody`, and local or private IPs are blocked unless `dangerouslyAllowLocalIP` is set (do not set it in production).

**Responsive grid image**
```tsx
<Image
  src={card.cover}
  alt={card.title}
  width={640}
  height={360}
  sizes="(max-width: 768px) 100vw, (max-width: 1200px) 50vw, 33vw"
  className="h-auto w-full rounded-md object-cover"
/>
```

**`fill` inside a sized, positioned container**
```tsx
<div className="relative aspect-video w-full overflow-hidden rounded-md">
  <Image src={cover} alt="" fill sizes="(max-width: 768px) 100vw, 640px" className="object-cover" />
</div>
```
The parent needs `position: relative` and a size or aspect ratio; otherwise `fill` collapses. Use `alt=""` only for purely decorative images.

**Art direction with `<picture>`**
```tsx
import { getImageProps } from "next/image";

export function ResponsiveHero() {
  const common = { alt: "Team collaborating on a project", sizes: "100vw" };
  const { props: { srcSet: desktop } } = getImageProps({ ...common, src: "/hero-wide.jpg", width: 1600, height: 600 });
  const { props: { srcSet: mobile, ...rest } } = getImageProps({ ...common, src: "/hero-tall.jpg", width: 800, height: 1000 });
  return (
    <picture>
      <source media="(min-width: 768px)" srcSet={desktop} />
      <source media="(max-width: 767px)" srcSet={mobile} />
      <img {...rest} alt={common.alt} style={{ width: "100%", height: "auto" }} />
    </picture>
  );
}
```

**Open Graph and social images**
Generate them with the `opengraph-image` file convention or `ImageResponse` (`next/og`) rather than hand-uploading each size; keep them at the recommended 1200 by 630 pixels and cache them.

### Rules of thumb
1. **Use `next/image`** for content images; use SVG for icons and logos.
2. **Always give dimensions** (or `fill` with a sized parent) and a meaningful `sizes`.
3. **One eager image per page** (the LCP one): `preload`. The rest lazy.
4. **Do not upscale**: source resolution should be about 2x the largest displayed size, not 6000 pixels wide.
5. **Prefer AVIF then WebP**, with a fallback; accept the extra encode cost on first request.
6. **Change the URL when the image changes**; do not rely on cache invalidation.
7. **Treat alt text as required**: descriptive for content, empty for decorative.
8. **Allowlist remote hosts narrowly** and never optimise untrusted arbitrary URLs.

### Anti-patterns
- A plain `<img>` pointing at a 4 MB original upload.
- Missing `sizes` on a responsive image, so every device downloads the full-width variant.
- `fill` without a positioned, sized parent.
- Lazy-loading the hero image, or preloading ten images at once.
- Using `unoptimized` everywhere to "make it work", losing resizing and modern formats.
- Wildcard `remotePatterns` (`hostname: "**"`) that let anyone use your server as an image proxy and exhaust compute.
- Allowing SVG through the optimiser (`dangerouslyAllowSVG`) without a strict `contentSecurityPolicy` and `contentDispositionType`.
- Putting text in images when it could be real, translatable, accessible text.
- Large animated GIFs instead of a muted looping `<video>`.

### Industry best practices
- **Budget image weight per route** (for example, a total image transfer ceiling and a hero under about 100 to 200 KB) and review it with Lighthouse and the network panel.
- **Make the LCP image discoverable** in the HTML (not set by JavaScript or CSS `background-image`), with `fetchPriority="high"`.
- **Strip metadata** (EXIF, GPS) from user uploads for privacy and size, and re-encode them; never serve user uploads as-is.
- **Validate uploads server-side**: content type by magic bytes, size limits, dimension limits, and malware scanning where relevant.
- **Use a CDN in front of the optimiser** (principle 9) so each variant is generated once and cached at the edge; consider an external image service if volume is high.
- **Keep variant count low**: limit `deviceSizes`, `imageSizes` and `qualities` to what you use, since each combination is cached and encoded separately.
- **Use blur or dominant-colour placeholders** for large images (`placeholder="blur"`), and a fixed-aspect box for others, so perceived load is smooth.
- **Prefer vector SVG for UI graphics**, optimise it (SVGO), and inline only when it must be styled with CSS; avoid huge inline SVG paths in many components.
- **Consider `decoding="async"`** on non-critical images and keep image requests on a first-party or preconnected origin.
- **Respect user preferences**: dark-mode variants through `<picture>` or CSS, and reduced-data hints where supported.
- **Write useful alt text**: describe the information or function, not "image of"; leave `alt=""` for decoration; keep text in images to a minimum (principle 20).
- **Monitor in the field**: track LCP element type and image failures with `useReportWebVitals` and RUM.

### Things to avoid
- Serving originals to every device.
- Using the deprecated `priority` prop in new code; use `preload`.
- Overriding `qualities` with many values; every value multiplies cache entries.
- Setting a very high `minimumCacheTTL` and then needing to change the image at the same URL.
- Trusting `Content-Type` or file extension from user uploads.
- `dangerouslyAllowLocalIP: true` in production (server-side request forgery risk).
- Using `<Image>` with `unoptimized` for large photos just to silence a warning.
- Using CSS `background-image` for content images (no `srcset`, not discoverable by the preload scanner, no alt text).
- Blur placeholders on tiny images (the data URL costs more than the image).

### Checklist
- [ ] Content images use `next/image` or an equivalent responsive pipeline; icons are SVG.
- [ ] Every image has dimensions (or a sized `fill` parent), `sizes`, and appropriate `alt`.
- [ ] The LCP image is `preload` (or eager with `fetchPriority="high"`); others are lazy.
- [ ] `formats`, `qualities` and `remotePatterns` are configured deliberately and narrowly.
- [ ] Uploads are validated, re-encoded, size-limited and stripped of metadata.
- [ ] Image URLs change when content changes; caching is long-lived.
- [ ] Image weight and LCP are tracked per route.

### In this codebase
- About 21 files use `next/image`, and about 48 places use plain `<img>`. Audit the plain `<img>` usages for large or content images and move them to `next/image` or give them dimensions and `loading="lazy"`.
- `next.config.ts` has no `images` block, so defaults apply (WebP only, `qualities: [75]`, no remote hosts allowed). Remote user or avatar images that go through `<Image>` need `remotePatterns`, or they are rendered with `unoptimized`, which is what `ProfileTab.tsx`, `agent/configure/layout.tsx` and `instructions/page.tsx` currently do for agent avatars.
- Decide per case: small avatars (36 to 65 px) are cheap, but user-uploaded images should be resized on upload so even `unoptimized` serves a small file.
- If AVIF is wanted, add `formats: ["image/avif", "image/webp"]` and watch encode time and cache size.
- The app is mostly behind login, so LCP-driven SEO gains apply mainly to public pages (landing, docs); for in-app screens the priority is layout stability and total weight.
