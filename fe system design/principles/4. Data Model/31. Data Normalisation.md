## 31. Data Normalisation

> Store each entity once, keyed by id, and reference it everywhere else. One update then reaches every view, and duplicated copies cannot go stale.

### Definition
**Normalisation** means holding data the way a database does: one record per entity, stored in a lookup table by id, with relations expressed as ids rather than nested copies. A nested API response such as `post -> author -> company` becomes three tables (`posts`, `users`, `companies`) where a post holds `authorId`.

The opposite, a **document cache**, stores each response as the server returned it. The same user can then exist inside the feed, the profile, a comment list and a search result as four independent copies, and nothing keeps them in sync.

### Key properties

**1. Single source of truth per entity**
- A change to user 7 is written in exactly one place. Every view that reads user 7 sees it on the next render.
- This is principle 13 (one-way data flow) applied to data shape: fewer places to write means fewer inconsistencies.

**2. Relations by id, not by nesting**
- Store `authorId`, not an embedded `author` object. Join at read time with a selector.
- Deep updates stop being deep: no more rebuilding `state.posts[3].comments[2].author.name` immutably.

**3. Lookup by id is O(1), order is separate**
- Keep `byId: Record<Id, Entity>` plus `ids: Id[]` (or per-list id arrays). Sorting, filtering and pagination operate on id lists, not on copies of entities.

**4. Normalise at the boundary**
- Convert API shapes to the normalised shape once, where data enters the client store. Components never see the raw nested payload.

**5. Normalisation is a client-cache concern**
- Server Components fetch and render per request; there is no long-lived client store to go stale (principle 6). The problem appears once data lives in the browser across many views.

### When to use what
| Situation | Use |
|---|---|
| Few lists, little overlap between views, server is the source of truth | Document cache (TanStack Query per-resource keys) plus invalidation |
| Same entity shown in many lists and detail views, edited often (likes, status, rename) | Normalised store, or `setQueryData` fan-out to the affected keys |
| Client-side store with many entities and relations | `createEntityAdapter` (Redux Toolkit) or a hand-rolled `byId` map |
| Deeply nested payload you must flatten once | `normalizr` (maintained but low activity; a small hand-written normaliser is often enough) |
| Offline-first, local edits, real-time merges | Normalised store (or a local database) with sync |
| Read-only data shown once | Do not normalise |
| Many cross-entity relations resolved on the server | GraphQL client with a normalised cache (Apollo, urql Graphcache, Relay) |

### Practical patterns in Next.js (TypeScript)

**Map-by-id with a normaliser (no library)**
```ts
// lib/normalise.ts
export type Id = string;

export type User = { id: Id; name: string };
export type Post = { id: Id; title: string; authorId: Id };

export type ApiPost = { id: Id; title: string; author: User };

export type Entities = {
  users: Record<Id, User>;
  posts: Record<Id, Post>;
};

export function normalisePosts(api: ApiPost[]): { ids: Id[]; entities: Entities } {
  const entities: Entities = { users: {}, posts: {} };
  const ids: Id[] = [];
  for (const p of api) {
    entities.users[p.author.id] = p.author;
    entities.posts[p.id] = { id: p.id, title: p.title, authorId: p.author.id };
    ids.push(p.id);
  }
  return { ids, entities };
}
```

**Denormalise with a selector (join at read time)**
```ts
export function selectPostView(e: Entities, id: Id) {
  const post = e.posts[id];
  return post ? { ...post, author: e.users[post.authorId] } : undefined;
}
```

**`createEntityAdapter` (Redux Toolkit), if Redux is ever adopted**
```ts
import { createEntityAdapter, createSlice, type PayloadAction } from "@reduxjs/toolkit";

type User = { id: string; name: string };
const usersAdapter = createEntityAdapter<User>(); // selectId defaults to entity.id

const usersSlice = createSlice({
  name: "users",
  initialState: usersAdapter.getInitialState(), // { ids: [], entities: {} }
  reducers: {
    usersReceived: usersAdapter.upsertMany,
    userRenamed(state, a: PayloadAction<{ id: string; name: string }>) {
      usersAdapter.updateOne(state, { id: a.payload.id, changes: { name: a.payload.name } });
    },
  },
});

export const usersSelectors = usersAdapter.getSelectors();
```
The adapter generates `addOne`, `upsertMany`, `updateOne`, `removeOne` and selectors such as `selectById` and `selectAll`. Redux is not installed in this project; this is for reference.

**`normalizr` for a nested payload**
```ts
import { normalize, schema } from "normalizr";

const user = new schema.Entity("users");
const post = new schema.Entity("posts", { author: user });

const { entities, result } = normalize(apiPosts, [post]);
// entities.users[id], entities.posts[id].author === user id, result === post ids
```

**React Query reality: a document cache, not a normalised one**

TanStack Query caches the result of each query key as a whole document. It does not split a response into entities. The same user inside `["posts"]` and `["user", 7]` is two copies. Two honest options:

1. **Invalidate** every key that may contain the entity and refetch. Simple and correct; costs requests.
2. **Fan out with `setQueryData` / `setQueriesData`** to patch each cached copy at once.

```tsx
"use client";
import { useMutation, useQueryClient } from "@tanstack/react-query";

type User = { id: string; name: string };
type Post = { id: string; title: string; author: User };

export function useRenameUser() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: async (v: { id: string; name: string }): Promise<User> => {
      const res = await fetch(`/api/users/${v.id}`, {
        method: "PATCH",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ name: v.name }),
      });
      if (!res.ok) throw new Error("Rename failed");
      return res.json();
    },
    onSuccess: (user) => {
      // 1. the detail query
      qc.setQueryData<User>(["user", user.id], user);
      // 2. every cached list that embeds this user (matches any ["posts", ...] key)
      qc.setQueriesData<Post[]>({ queryKey: ["posts"] }, (old) =>
        old?.map((p) => (p.author.id === user.id ? { ...p, author: user } : p)),
      );
    },
    onSettled: (_d, _e, v) => qc.invalidateQueries({ queryKey: ["user", v.id] }),
  });
}
```
Fan-out is manual normalisation: you must remember every key shape that embeds the entity. When that list grows, either invalidate by key prefix or normalise on the client.

**Normalise inside React Query with `select` (the middle path)**

Keep the cache as documents, but have list queries return ids and read each entity from its own query:
```tsx
// list returns ids, each row reads ["user", id]; one setQueryData updates every row
const userQuery = (id: string) => ({ queryKey: ["user", id], queryFn: () => fetchUser(id) });
```
Seed the per-entity caches when a list arrives with `qc.setQueryData(["user", u.id], u)` inside the list `queryFn` or `onSuccess` equivalent. Mind the `staleTime`, or each row will refetch.

### Rules of thumb
1. **Normalise only when the same entity appears in several places and is edited.** Otherwise a document cache is fine.
2. **Server-rendered data needs no normalisation**; it is fresh per request.
3. **Ids are the contract**: stable, unique per entity type, never array indexes.
4. **Store relations as ids; join in selectors** and keep selectors cheap or memoised.
5. **Keep order and filters as id arrays**, not as reordered copies of entities.
6. **With React Query, prefer invalidation** first; add `setQueryData` fan-out only for hot paths such as likes or renames.
7. **Centralise the normaliser** in one module; do not hand-roll shapes per component.
8. **Treat normalised state as a cache of the server**, not as an independent source of truth.

### Anti-patterns
- The same entity copied into several `useState` or context values.
- Embedding full child objects in every list item and then updating each by hand.
- Normalising everything by default, including data shown once and never edited.
- A `setQueryData` fan-out that misses one key, so one screen shows the old name.
- Using array indexes as ids or storing `items.find(...)` results in state.
- Putting server data into a client store only to mirror a query that already caches it.
- Cyclic nested copies (`user.posts[].author`) that cannot be serialised or merged.
- Partial entities from a list overwriting complete entities from a detail view without a merge strategy.

### Industry best practices
- **Follow the Redux style guide**: normalise relational data with `{ ids, entities }`; RTK's `createEntityAdapter` provides the CRUD reducers and selectors.
- **Use a ready-made normalised cache** (Apollo, urql Graphcache, Relay) when on GraphQL; normalisation by `__typename:id` is built in.
- **Accept TanStack Query's document-cache model** and keep query keys hierarchical (`["users", id]`, `["posts", { filter }]`) so one prefix can invalidate or patch a family.
- **Use `setQueriesData` with a key filter** to patch many cached lists in one call; use `setQueryData` for one exact key.
- **Return updated entities from mutations** so `onSuccess` can write the server's truth instead of guessing.
- **Merge, do not replace**, when a list payload carries fewer fields than the detail payload (`{ ...existing, ...incoming }`).
- **Keep entity types at the boundary**: parse API data with a Zod schema (principle 35) before normalising.
- **Memoise joined views** (`useMemo`, reselect, or the React Compiler) so denormalised objects keep stable references.
- **Pair with optimistic updates** (principle 33): a normalised write makes the optimistic patch and the rollback one change each.
- **Garbage-collect orphans** deliberately; removing a post does not remove its author if other posts reference it.
- **Measure before adding a library**: a `Map` or `Record` by id covers most apps.
- **Document which entities are normalised** and which query keys embed them.

### Things to avoid
- Adding Redux, normalizr or an ORM-like layer to a small app that a few query keys already serves.
- Normalising server-owned data and then editing it locally without a sync path back.
- Mutating entities in place; produce new objects so subscribers re-render.
- Storing derived or joined objects in the store; derive them in selectors.
- Duplicating data between a normalised store and the React Query cache.
- Relying on `invalidateQueries` alone for real-time lists when many keys are affected and the network cost is high.
- Treating ids from different entity types as interchangeable (`user 1` versus `post 1`); key by type.
- Normalising ephemeral UI state such as form drafts or open panels.

### Checklist
- [ ] Each entity type has one canonical home (a store table or one query key).
- [ ] Relations are ids; joins happen in selectors.
- [ ] Order and filters are id lists, not entity copies.
- [ ] Every mutation updates or invalidates every cache location that holds the entity.
- [ ] List and detail payloads merge rather than overwrite.
- [ ] Normalisation is justified by real overlap between views, not applied by default.
- [ ] API data is validated before it is normalised.

### In this codebase
- Neither `normalizr` nor `@reduxjs/toolkit` is installed, and there is no `setQueryData` or `setQueriesData` call in `src/`. Server data lives in React Context providers (`src/context/`) and `useState`, which are document-style copies.
- `@tanstack/react-query` is used sparingly: `src/lib/queries/personas.ts` uses one query key (`PERSONAS_QUERY_KEY`) with `invalidateQueries`, which is the right default for a single-resource cache.
- Check whether the same entity (a project, a team, an agent, a persona) is held in more than one provider; if so, a `Record<id, Entity>` in one provider, or per-entity query keys, would remove the duplicate. Only do it where an edit already leaves one screen stale.
- `zustand`, `redux`, `mobx` and `react-hook-form` are not dependencies.
