## 28. Global State (Zustand)

> A tiny store shared across distant components, read through a simple hook. Components re-render only when the slice they subscribe to changes.

### Definition
**Zustand** is a small state library (roughly 1 kB gzipped for the core) built on a plain store object and a hook. You create a store with `create`, and any component calls the returned hook with a **selector** to read a slice. State lives outside React, so it is shared by distant components without prop drilling.

"No provider" is true for the client-only case: a module-level store from `create` can be imported anywhere in client code. In the Next.js App Router it is only safe for **client-only UI state**. On the server, a module is shared between requests, so a module-level store that is written during render can leak one user's state to another. Zustand's own Next.js guide recommends a per-request store created with `createStore` and handed down through context (principle 24). So the honest rule is: no provider for pure client UI state that the server never reads or writes; a provider-scoped store as soon as the server renders from it or initialises it.

### Key properties

**1. Hook-based, selector-driven API**
- `const open = useUiStore((s) => s.sidebarOpen)` re-renders only when `sidebarOpen` changes (compared with `Object.is`).
- Selecting a whole object, or a new object or array on every call, re-renders on every change. Use one selector per primitive, or `useShallow` for several fields.

**2. State outside React**
- Actions can be called from event handlers, timers and non-React modules (`useUiStore.getState().close()`).
- `subscribe` and `getState` allow reading without rendering.

**3. Client Components only**
- Hooks need `"use client"`. Server Components cannot read the store.
- Never mutate a module-level store from a Server Component.

**4. Small surface, optional middleware**
- `persist` (storage), `devtools` (Redux DevTools), `immer` and `subscribeWithSelector` are opt-in.
- `persist` rehydrates after mount on the client; render-time differences cause hydration mismatches unless handled (`skipHydration` and a manual `rehydrate()`).

**5. Not a server-cache**
- Fetched data, caching, retries and invalidation belong to a query library (principle 30), not a store.

### When to use what
| Situation | Use |
|---|---|
| State used by one component or a small subtree | `useState` / `useReducer` (principle 27) |
| Low-frequency, wide-reach values (theme, locale, session) | Context (principle 24) |
| Client UI state read by many distant components, changes often | Zustand |
| Same, but the server initialises it or renders from it | Zustand per-request store via context |
| Data from the API | TanStack Query (principle 30) |
| Filters, sort, pagination, tabs | URL (principle 34) |
| Strict actions, time travel, large team conventions | Redux Toolkit (principle 29) |
| One tiny shared value, no library wanted | `useSyncExternalStore` over a module variable |

### Practical patterns in Next.js (TypeScript)

**Client-only UI store (no provider)**
```tsx
// stores/ui-store.ts
"use client";
import { create } from "zustand";

type UiState = {
  sidebarOpen: boolean;
  commandPaletteOpen: boolean;
  toggleSidebar: () => void;
  setCommandPalette: (open: boolean) => void;
};

export const useUiStore = create<UiState>()((set) => ({
  sidebarOpen: true,
  commandPaletteOpen: false,
  toggleSidebar: () => set((s) => ({ sidebarOpen: !s.sidebarOpen })),
  setCommandPalette: (open) => set({ commandPaletteOpen: open }),
}));
```
This is safe because the state is UI-only, starts the same for every user and is never rendered into the server HTML in a way that depends on a changed value. If the first paint depends on it, use the per-request pattern below.

**Subscribe to a slice**
```tsx
"use client";
import { useShallow } from "zustand/react/shallow";
import { useUiStore } from "@/stores/ui-store";

export function SidebarToggle() {
  const toggle = useUiStore((s) => s.toggleSidebar); // stable action, never re-renders on state
  return <button onClick={toggle} className="rounded-md px-3 py-1.5 hover:bg-muted">Menu</button>;
}

export function Flags() {
  const { sidebarOpen, commandPaletteOpen } = useUiStore(
    useShallow((s) => ({ sidebarOpen: s.sidebarOpen, commandPaletteOpen: s.commandPaletteOpen })),
  );
  return <span>{String(sidebarOpen)} {String(commandPaletteOpen)}</span>;
}
```

**Per-request store (server-initialised, App Router safe)**
```tsx
// stores/cart-store.ts
import { createStore } from "zustand/vanilla";

export type CartState = { items: string[]; add: (id: string) => void };
export const createCartStore = (init: Partial<CartState> = {}) =>
  createStore<CartState>()((set) => ({
    items: [],
    add: (id) => set((s) => ({ items: [...s.items, id] })),
    ...init,
  }));
export type CartStore = ReturnType<typeof createCartStore>;

// stores/cart-provider.tsx
"use client";
import { createContext, use, useState, type ReactNode } from "react";
import { useStore } from "zustand";
import { createCartStore, type CartState, type CartStore } from "./cart-store";

const CartContext = createContext<CartStore | null>(null);

export function CartProvider({ initial, children }: { initial?: Partial<CartState>; children: ReactNode }) {
  const [store] = useState(() => createCartStore(initial));
  return <CartContext value={store}>{children}</CartContext>;
}

export function useCart<T>(selector: (s: CartState) => T): T {
  const store = use(CartContext);
  if (!store) throw new Error("useCart must be used inside <CartProvider>");
  return useStore(store, selector);
}
```
Mount `CartProvider` in a Server Component layout and pass server-fetched values as `initial`. The same selector rules apply.

**Persisting safely**
```tsx
import { create } from "zustand";
import { persist } from "zustand/middleware";

export const usePrefs = create<{ density: "compact" | "roomy"; setDensity: (d: "compact" | "roomy") => void }>()(
  persist((set) => ({ density: "roomy", setDensity: (density) => set({ density }) }), {
    name: "prefs",
    skipHydration: true, // rehydrate in an effect to avoid a server/client mismatch
  }),
);

// in a client component: useEffect(() => { void usePrefs.persist.rehydrate(); }, []);
```
Never persist auth tokens (principle 32); store only preferences.

### Rules of thumb
1. **Local first, then lift, then context, then a store.** Zustand is the last step, not the first (principle 27).
2. **Always pass a selector.** `useStore()` with no selector subscribes to everything.
3. **Select primitives or stable references.** Use `useShallow` for multi-field picks; never build a new object inside a plain selector.
4. **Expose intent-named actions** (`toggleSidebar`), not a generic `set`.
5. **Slice by domain.** Several small stores beat one global one.
6. **Module-level store only for client-only UI state.** If the server reads it or seeds it, use a per-request store.
7. **Keep server data out.** Fetched entities go in the query cache; the store holds ids and UI flags.
8. **Derive, do not store.** Compute totals and filtered lists in selectors or components.

### Anti-patterns
- Fetching API data into a store with `useEffect`, then hand-rolling loading and error flags.
- A module-level store written from Server Components, Route Handlers or during server render.
- `const state = useStore()` in a large component, which re-renders on every change.
- `useStore((s) => ({ a: s.a, b: s.b }))` without `useShallow`, causing render loops or constant re-renders.
- One `useAppStore` holding auth, cart, modals, form drafts and cached lists.
- Persisting auth tokens or sensitive data to `localStorage` through `persist`.
- Using a store for state one component owns.
- Storing URL-worthy state (filters, current page) in a store, so it cannot be shared or bookmarked.

### Industry best practices
- **Pick the right tool for the kind of state:** server state in a query library, URL state in the URL, form state in a form library, and a store only for the remaining shared client state.
- **Use selectors everywhere** and keep them cheap and pure.
- **Use `useShallow`** for multi-field selections instead of returning fresh objects.
- **Create stores per request** in the App Router when the server seeds them; use a module store only for client-only UI.
- **Split stores by domain** or use the slices pattern, rather than growing one global object.
- **Keep actions inside the store** next to the state they change, named by intent.
- **Use `devtools` in development** to inspect updates with Redux DevTools; strip or guard it in production.
- **Handle `persist` hydration deliberately** with `skipHydration` or a client-only rehydrate, and version the persisted shape (`version`, `migrate`).
- **Use `subscribeWithSelector`** when non-React code needs to react to one field.
- **Reset stores between tests** and in per-request creation; avoid hidden state shared across test cases.
- **Type the store with the curried `create<T>()(...)` form** so middleware types infer correctly.
- **Measure before adopting:** check React DevTools "Highlight updates" to confirm a real re-render problem exists before adding a dependency.

### Things to avoid
- Adding Zustand for state that `useState` plus composition handles.
- Mutating state directly instead of returning updates through `set` (or using `immer`).
- Reading `window` or `localStorage` while creating initial state on the server.
- Storing non-serialisable or server-only objects (secrets, class instances) in a store that may be hydrated.
- Calling `getState()` inside render to read values; it will not re-render. Use the hook.
- Duplicating server data in a store, which creates stale copies (principle 31).
- Putting everything behind one store "so it is easy to find".
- Treating "under 2 kB" as the whole cost: the real cost is another global that any file can write to.
- Selecting an entire array or object when one field is needed.

### Checklist
- [ ] The state is genuinely shared by distant components; local state and composition were ruled out.
- [ ] It is client UI state, not server data, URL state or form state.
- [ ] Every read uses a selector; multi-field reads use `useShallow`.
- [ ] A per-request store is used if the server seeds or renders from the state; a module store only if client-only.
- [ ] Actions are intent-named and live in the store.
- [ ] `persist` uses `skipHydration` or a client-only rehydrate, stores no secrets, and has a `version`.
- [ ] The store is small, domain-scoped and reset in tests.

### In this codebase
- `zustand` is **not installed** (also no Redux, MobX or react-hook-form). Shared client state today is `src/context/` (16 providers) plus TanStack Query for server data.
- `src/lib/active-chat-agent-store.ts` is a hand-rolled module-level store: a variable, a listener `Set`, and `useSyncExternalStore` with a `() => null` server snapshot. It exists because the Agents panel sits in the app shell, outside the chat page's tree, which is exactly the "distant components, no provider" case. It is a client-only value that the server never seeds, so the module-store approach is safe here. Other `useSyncExternalStore` users include `src/lib/notifications/read-state.ts` and `src/hooks/use-is-client.ts`.
- Candidates for a store with selectors are the fast-changing contexts (`notifications-context`, `search-context`, `chat-history-context`). Check with React DevTools whether they cause wasteful re-renders first; splitting state from actions (principle 24) may be enough.
- Adding Zustand is a decision for the first genuinely high-frequency shared state. For small values like the one above, the existing `useSyncExternalStore` pattern needs no new dependency.
