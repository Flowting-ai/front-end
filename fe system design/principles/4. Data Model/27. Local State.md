## 27. Local State

> `useState` and `useReducer` for UI state that no other component needs. Use `useReducer` when sub-values update together, and lift state up only when two components truly share it.

### Definition
**Local state** is state owned by one component (and passed down by props to its children). It describes transient UI: whether a menu is open, the text in an input, the active tab, a draft being edited. It is created with `useState` or `useReducer`, lives and dies with the component, and is invisible to the rest of the app.

The default home for any piece of state is the component that uses it. State moves outward only when a second component needs it.

### Key properties

**1. Start local, move out on evidence**
- Begin with `useState` in the component that renders the value.
- Promote to a parent only when a sibling must read or write it (lifting state up), to context or a store only when distant components need it (principles 24, 28).

**2. `useState` for independent values**
- One value, simple updates: a boolean, a string, a selected id.
- Use the functional form (`setCount((c) => c + 1)`) when the next value depends on the previous one.

**3. `useReducer` for values that change together**
- When several fields update in one event, or the next state depends on a named transition, a reducer keeps the rules in one pure function.
- Actions describe what happened (`{ type: "submitted" }`), the reducer decides the new state. Impossible combinations become unrepresentable.

**4. Lifting state up**
- Move state to the closest common parent of the components that need it, then pass the value and a setter (or callbacks) down. Data flows down, events flow up (principle 13).

**5. Local state is a Client Component concern**
- Hooks need `"use client"`. Keep the stateful part a small leaf so the surrounding page stays a Server Component (principle 6).

**6. Derive, do not store**
- Anything computable from props or other state (filtered lists, totals, `isValid`) is calculated during render, not kept in state.

### When to use what
| Situation | Use |
|---|---|
| One independent value (open/closed, input text) | `useState` |
| Several fields updated together, or named transitions | `useReducer` |
| Two siblings need the same value | Lift to the nearest common parent |
| Many distant components, rare changes | Context (principle 24) |
| Many distant components, frequent changes | Store with selectors (principle 28) |
| Data from the API | TanStack Query (principle 30) |
| Filters, sort, page that should survive refresh and be shared | URL (principle 34) |
| Form fields with validation | Form library and schema (principle 35) |
| Reset a component's state when an identity changes | `key` prop |

### Practical patterns in Next.js (TypeScript)

**Independent state with `useState`**
```tsx
"use client";
import { useState } from "react";

export function Disclosure({ title, children }: { title: string; children: React.ReactNode }) {
  const [open, setOpen] = useState(false);
  return (
    <section>
      <button type="button" aria-expanded={open} onClick={() => setOpen((o) => !o)}>
        {title}
      </button>
      {open && <div className="mt-2">{children}</div>}
    </section>
  );
}
```

**Related values with `useReducer` and a discriminated union**
```tsx
"use client";
import { useReducer } from "react";

type State =
  | { status: "idle" }
  | { status: "saving" }
  | { status: "error"; message: string }
  | { status: "saved"; savedAt: number };

type Action =
  | { type: "submit" }
  | { type: "failed"; message: string }
  | { type: "succeeded"; savedAt: number }
  | { type: "reset" };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "submit":
      return { status: "saving" };
    case "failed":
      return { status: "error", message: action.message };
    case "succeeded":
      return { status: "saved", savedAt: action.savedAt };
    case "reset":
      return { status: "idle" };
  }
}

export function SaveButton({ save }: { save: () => Promise<void> }) {
  const [state, dispatch] = useReducer(reducer, { status: "idle" });

  async function onClick() {
    dispatch({ type: "submit" });
    try {
      await save();
      dispatch({ type: "succeeded", savedAt: Date.now() });
    } catch (e) {
      dispatch({ type: "failed", message: e instanceof Error ? e.message : "Failed" });
    }
  }

  return (
    <button type="button" disabled={state.status === "saving"} onClick={onClick}>
      {state.status === "saving" ? "Saving..." : "Save"}
      {state.status === "error" && <span className="ml-2 text-red-600">{state.message}</span>}
    </button>
  );
}
```
One union replaces `isSaving`, `isError`, `error` and `isSaved` flags that could otherwise disagree.

**Lifting state up**
```tsx
"use client";
import { useState } from "react";

export function Picker({ options }: { options: { id: string; label: string }[] }) {
  const [selectedId, setSelectedId] = useState<string | null>(null);
  return (
    <div className="grid grid-cols-2 gap-4">
      <OptionList options={options} selectedId={selectedId} onSelect={setSelectedId} />
      <OptionDetail option={options.find((o) => o.id === selectedId) ?? null} />
    </div>
  );
}
```
Store the id, not a copy of the object, and derive the selected option during render.

**Reset state with `key`, not an effect**
```tsx
<ProfileEditor key={userId} user={user} />
```
Changing `key` remounts the component with fresh state, which avoids a `useEffect` that copies props into state.

**Updating objects and arrays immutably**
```tsx
setForm((f) => ({ ...f, name: value }));
setItems((xs) => xs.filter((x) => x.id !== id));
```

**Lazy initial state for expensive setup**
```tsx
const [index] = useState(() => buildIndex(items)); // runs once
```

### Rules of thumb
1. **Keep state as close as possible to where it is used.**
2. **Lift only when two components truly share** the value; do not lift "just in case".
3. **Reach for `useReducer` when updates are coupled** or the next state depends on a named transition.
4. **Do not store what you can compute** from props or other state.
5. **Store ids, not objects**, when the object also lives in a list or in server data.
6. **Model status as one union**, not several booleans.
7. **Use the functional updater** when the next value depends on the previous one.
8. **Use `key` to reset**, not an effect that syncs props into state.
9. **Keep reducers pure**: no fetches, timers or `Date.now()` inside; do effects in handlers.

### Anti-patterns
- Copying a prop into state (`useState(props.value)`) and then expecting it to follow later prop changes.
- Redundant state: `items`, `filteredItems` and `count` all stored, then drifting apart.
- Several booleans (`isLoading`, `isError`, `isSuccess`) that allow impossible combinations.
- Mutating state in place (`items.push(x); setItems(items)`), which skips re-rendering.
- A `useEffect` that sets state from other state, where a render-time calculation would do.
- Lifting state to the page or to context at the start, so every keystroke re-renders a large tree.
- Storing server data in `useState` and refetching by hand instead of using a query library.
- Defining a component inside another component, which resets its state on every render.

### Industry best practices
- **Follow the official guidance**: choose the structure of state to avoid duplication and contradiction, and keep it minimal.
- **Colocate state** with the component that renders it; the render path should be easy to trace.
- **Prefer reducers for state machines**: loading flows, wizards and multi-step dialogs read better as explicit transitions.
- **Use discriminated unions** so TypeScript rejects impossible states at compile time.
- **Split a component rather than a state object** when two pieces of state change on different events; each leaf owns its own state.
- **Pass children as props** (composition) so a stateful wrapper does not re-render its static content.
- **Keep Server Components stateless** and push `"use client"` to the smallest interactive leaf.
- **Use `useTransition` or `useDeferredValue`** to keep inputs responsive when state drives expensive rendering.
- **Do not store derived data**; compute in render and memoise only when measured to be slow (or let the React Compiler do it).
- **Use a lazy initialiser** for costly starting values, and read browser-only APIs after mount to avoid hydration mismatches.
- **Move to the right tool when the state's nature changes**: shared client state to a store, remote data to a query cache, shareable state to the URL.
- **Test reducers as plain functions**, and test components through user events rather than internal state.

### Things to avoid
- Putting all UI state in a global store "for consistency".
- Using `useReducer` for a single boolean; it adds ceremony without value.
- Dispatching actions named after setters (`setName`) instead of events (`nameChanged`).
- Side effects (fetch, `localStorage`, timers) inside a reducer.
- Reading `window` or `localStorage` in the initial `useState` value during server render.
- Storing refs-like values (timer ids, previous values) in state when they do not affect rendering; use `useRef`.
- Passing a setter through many layers; this signals that state should be lifted, or moved to context or composition.
- Nesting deep objects in state, which makes immutable updates error-prone; flatten or normalise (principle 31).

### Checklist
- [ ] Each piece of state lives in the lowest component that needs it.
- [ ] Nothing computable is stored in state.
- [ ] Coupled values use `useReducer` or one union, not several flags.
- [ ] State is lifted only where two components actually share it.
- [ ] Updates are immutable and use functional updaters where needed.
- [ ] Props are not copied into state; `key` is used to reset.
- [ ] Reducers are pure and typed with an action union.
- [ ] Shared, remote and URL-worthy state has been moved to the right tool.
