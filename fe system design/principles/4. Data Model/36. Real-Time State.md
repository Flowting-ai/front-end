## 36. Real-Time State

> Some state arrives continuously. Pick the transport by direction and latency needs: WebSockets for two-way, SSE for server-to-client, polling for the rest. The wrong choice wastes bandwidth or infrastructure.

### Definition
**Real-time state** is client state that changes because the server (or another user) changed something, not because this user acted: chat tokens, notifications, presence, job progress, live prices, collaborative edits.

The first decision is the **transport**, chosen by two questions: who talks (one way or both), and how stale may the data be (milliseconds, seconds, minutes). The second decision is where the arriving events **land**: in the same cache that holds fetched data (principle 30), so one update reaches every view (principle 31).

### Key properties

**1. Direction decides the transport**
- Server to client only (feeds, progress, token streams): SSE or polling.
- Client and server both send frequently (collaboration, games, live cursors): WebSocket.
- Client to server only: an ordinary `POST` or Server Action; no persistent connection.

**2. Latency decides push versus pull**
- Needs sub-second delivery: push (SSE or WebSocket).
- Seconds to minutes is acceptable: polling is the simplest and most robust option.
- Do not open a socket for data that changes once a minute.

**3. Serverless changes the options**
- A function instance on Vercel is short-lived and cannot hold an inbound WebSocket. Route Handlers can stream a response (SSE), bounded by `maxDuration`.
- Persistent two-way connections belong to a separate service (a managed realtime provider or your own long-running server).

**4. Connections fail; design for it**
- Every long-lived connection drops (deploys, timeouts, proxies, sleeping laptops). Reconnect with backoff and jitter, and re-sync state after reconnect so missed events are not lost.

**5. Events are patches to the cache, not a second store**
- Merge each event into the React Query cache by key (`setQueryData`) or invalidate the affected query. Do not copy the same data into `useState` or a parallel store.

### Decision table
| Need | Transport | Direction | Notes |
|---|---|---|---|
| Dashboard refreshed every 30 s | Polling (`refetchInterval`) | Pull | Simplest; cacheable; works everywhere |
| Job finishes in minutes, no push infra | Polling with backoff, stop on terminal state | Pull | Stop polling once status is `done` or `failed` |
| Near-instant updates, no sockets available | Long polling | Pull, held open | Fewer empty responses than short polling; one request in flight |
| LLM token stream, progress, notifications | SSE | Server to client | Plain HTTP, auto-reconnect in `EventSource`, works through most proxies |
| Chat with typing, presence, cursors, games | WebSocket | Both | Needs a stateful server or a managed provider |
| One-time result after a user action | `POST` or Server Action, then refetch | Request/response | No real-time transport needed |
| Cross-tab sync in one browser | `BroadcastChannel` or `storage` event | Local | No server involved |

| Concern | Polling | SSE | WebSocket |
|---|---|---|---|
| Protocol | HTTP | HTTP, `text/event-stream` | `ws://` upgrade |
| Browser auto-reconnect | You write it (or React Query does) | Yes, `EventSource` | No, you write it |
| Binary data | Yes | No (text only) | Yes |
| Custom auth headers | Yes | `EventSource` no; `fetch` streaming yes | Not in browser handshake |
| Works on Vercel Route Handlers | Yes | Yes (streamed response) | No inbound sockets |
| Server cost | Many short requests | One long request per client | One persistent socket per client |

### Practical patterns in Next.js (TypeScript)

**Polling with React Query, stopping at a terminal state**
```tsx
"use client";
import { useQuery } from "@tanstack/react-query";

type Job = { id: string; status: "queued" | "running" | "done" | "failed"; progress: number };

export function useJob(id: string) {
  return useQuery({
    queryKey: ["jobs", id],
    queryFn: async ({ signal }): Promise<Job> => {
      const res = await fetch(`/api/jobs/${id}`, { signal });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      return res.json();
    },
    // Return false to stop. Back off as the job runs longer.
    refetchInterval: (query) => {
      const job = query.state.data;
      if (job && (job.status === "done" || job.status === "failed")) return false;
      return query.state.dataUpdateCount < 10 ? 2_000 : 10_000;
    },
    refetchIntervalInBackground: false, // pause while the tab is hidden
  });
}
```

**SSE endpoint in a Route Handler (server)**
```ts
// app/api/events/route.ts
export const dynamic = "force-dynamic";
export const maxDuration = 300; // the platform will end the stream; the client must reconnect

export async function GET(request: Request) {
  const encoder = new TextEncoder();
  const lastEventId = request.headers.get("last-event-id"); // use it to replay missed events

  const stream = new ReadableStream<Uint8Array>({
    start(controller) {
      let id = Number(lastEventId ?? 0);
      const send = (event: string, data: unknown) => {
        id += 1;
        controller.enqueue(
          encoder.encode(`id: ${id}\nevent: ${event}\ndata: ${JSON.stringify(data)}\n\n`),
        );
      };
      // Heartbeat comment keeps proxies from closing an idle connection.
      const heartbeat = setInterval(() => controller.enqueue(encoder.encode(": ping\n\n")), 15_000);
      const tick = setInterval(() => send("notification", { at: Date.now() }), 5_000);

      request.signal.addEventListener("abort", () => {
        clearInterval(heartbeat);
        clearInterval(tick);
        try { controller.close(); } catch { /* already closed */ }
      });
    },
  });

  return new Response(stream, {
    headers: {
      "Content-Type": "text/event-stream",
      "Cache-Control": "no-cache, no-transform",
      Connection: "keep-alive",
    },
  });
}
```
In production the `setInterval` producer is replaced by a subscription to a real source (a pub/sub channel, or a proxied backend stream as in `/api/chat`).

**Client hook: reconnect with exponential backoff and jitter**
```tsx
"use client";
import { useEffect, useRef } from "react";

export function useEventStream<T>(url: string, onEvent: (type: string, data: T) => void) {
  const handler = useRef(onEvent);
  useEffect(() => { handler.current = onEvent; });

  useEffect(() => {
    let source: EventSource | null = null;
    let attempt = 0;
    let timer: ReturnType<typeof setTimeout> | undefined;
    let closed = false;

    const connect = () => {
      source = new EventSource(url);
      source.onopen = () => { attempt = 0; };
      source.addEventListener("notification", (e) => handler.current("notification", JSON.parse((e as MessageEvent).data)));
      source.onerror = () => {
        source?.close(); // take over from the browser so backoff is under our control
        if (closed) return;
        const base = Math.min(30_000, 1_000 * 2 ** attempt++);
        timer = setTimeout(connect, base / 2 + Math.random() * (base / 2)); // jitter
      };
    };

    connect();
    return () => { closed = true; clearTimeout(timer); source?.close(); };
  }, [url]);
}
```
`EventSource` sends the `Last-Event-ID` header only on its own automatic reconnects. When you close and reopen manually, pass the last seen id yourself (query string) or re-sync with a refetch on reconnect.

**Merge live events into the React Query cache**
```tsx
"use client";
import { useQueryClient } from "@tanstack/react-query";

type Notification = { id: string; text: string; read: boolean };
type NotificationEvent = { kind: "created" | "updated"; item: Notification };

export function useLiveNotifications() {
  const qc = useQueryClient();
  useEventStream<NotificationEvent>("/api/events", (_type, ev) => {
    qc.setQueryData<Notification[]>(["notifications"], (old = []) => {
      const without = old.filter((n) => n.id !== ev.item.id); // idempotent: safe if delivered twice
      return ev.kind === "created" ? [ev.item, ...without] : old.map((n) => (n.id === ev.item.id ? ev.item : n));
    });
  });
}
```
Handlers must be **idempotent** and tolerate out-of-order delivery (compare a version or timestamp), because reconnects can replay events. For events that are only a hint ("something changed"), call `qc.invalidateQueries({ queryKey: ["notifications"] })` instead of patching. After a reconnect, invalidate once to close the gap.

**Consuming a streamed POST with `fetch` (auth headers, request body)**
```ts
export async function streamChat(body: FormData, onChunk: (text: string) => void, signal: AbortSignal) {
  const res = await fetch("/api/chat", { method: "POST", body, signal });
  if (!res.ok || !res.body) throw new Error(`HTTP ${res.status}`);
  const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
  let buffer = "";
  for (;;) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += value;
    const frames = buffer.split("\n\n");
    buffer = frames.pop() ?? ""; // keep the incomplete tail for the next chunk
    for (const frame of frames) {
      const data = frame.split("\n").find((l) => l.startsWith("data: "))?.slice(6);
      if (data) onChunk(data);
    }
  }
}
```
`EventSource` can only `GET` without custom headers. For `POST` bodies or bearer tokens, stream with `fetch` as above and buffer partial frames across chunks.

**WebSocket on Vercel: use a managed service**
```tsx
"use client";
// Vercel Functions cannot accept inbound WebSocket connections.
// Connect the browser directly to a realtime provider (Ably, Pusher, PartyKit, Supabase Realtime, etc.)
// using a short-lived token minted by your own Route Handler.
const res = await fetch("/api/realtime/token", { method: "POST" });
const { url } = (await res.json()) as { url: string };
const socket = new WebSocket(url);
```
Your Route Handler authenticates the user and returns a scoped, expiring token or URL; the long-lived connection then goes to the provider, not to Next.js.

### Rules of thumb
1. **Start with polling.** Move to SSE when polling latency or request volume hurts, and to WebSockets only when the client must also send a continuous stream.
2. **Use SSE for server-to-client** on Next.js; it is plain HTTP and fits Route Handlers.
3. **Do not plan on WebSockets inside Vercel functions**; use a managed provider or a separate stateful server.
4. **Always reconnect with exponential backoff plus jitter** and cap the delay.
5. **Re-sync after every reconnect** (replay by `Last-Event-ID`, or invalidate the query).
6. **Land events in the React Query cache**; do not keep a second copy in component state.
7. **Make event handlers idempotent** and order-tolerant.
8. **Send heartbeats** on idle streams and **stop polling** when work is finished or the tab is hidden.
9. **Authenticate on the server** and mint short-lived tokens for third-party sockets.

### Anti-patterns
- Opening a WebSocket for data that changes once a minute.
- Polling every second from every client with no stop condition.
- Handling a dropped stream by showing nothing, or reconnecting in a tight loop with no backoff.
- Appending every event to `useState` arrays that grow forever.
- A second store that mirrors query data and drifts from it.
- Assuming a Route Handler can hold a stream forever; `maxDuration` ends it.
- Putting a long-lived token in a query string that is logged by proxies.
- Parsing SSE chunks by splitting on newline without buffering partial frames.

### Industry best practices
- **Choose the simplest transport that meets the latency need**; every step up (polling, SSE, WebSocket) adds infrastructure and failure modes.
- **Use SSE for token streams and notifications**; its auto-reconnect and `Last-Event-ID` replay are built into the standard.
- **Delegate WebSockets to a managed realtime service** on serverless platforms, with tokens issued by a Route Handler.
- **Exponential backoff with full or partial jitter**, a ceiling (about 30 s), and a reset after a successful open.
- **Heartbeat every 15 to 30 seconds** so intermediaries do not close idle connections.
- **Give events ids** and support replay so a reconnect fills the gap.
- **Merge into the query cache** with `setQueryData` for full payloads and `invalidateQueries` for hints.
- **Pause in the background**: stop polling and close streams when the tab is hidden, resume with a refetch on focus.
- **Abort on unmount and on navigation** with `AbortController` or `EventSource.close()`.
- **Set `Cache-Control: no-cache, no-transform`** and disable proxy buffering so chunks reach the client.
- **Show connection state** (live, reconnecting, offline) so users know whether data is current.
- **Cap concurrent connections per user** (browsers limit HTTP/1.1 connections per origin; HTTP/2 raises this).

### Things to avoid
- WebSockets for one-way feeds that SSE handles.
- Polling intervals below what the data actually changes at.
- Relying on `EventSource` when you need custom headers or a `POST` body.
- Reconnect logic without jitter, which makes all clients retry at the same instant after an outage.
- Unbounded in-memory event buffers on the server or client.
- Trusting event payloads without validating them (parse with Zod, principle 35).
- Streaming secrets or other users' data on a shared channel without per-user authorisation.
- Treating the stream as the source of truth; the server's query endpoint is, and the stream is a hint or delta.
- Skipping `maxDuration` and runtime settings and being surprised when streams end early.

### Checklist
- [ ] Transport chosen from direction and latency, recorded in the decision table.
- [ ] No inbound WebSocket planned inside a Vercel function.
- [ ] Reconnect uses exponential backoff with jitter and a cap.
- [ ] State is re-synced after reconnect (replay or invalidate).
- [ ] Events merge into the React Query cache; handlers are idempotent.
- [ ] Polling stops at terminal states and pauses in hidden tabs.
- [ ] Streams are cancelled on unmount and client disconnect.
- [ ] Event payloads are validated and the user is authorised server-side.
- [ ] Connection status is visible in the UI where staleness matters.

### In this codebase
- SSE is already the live transport. `src/app/api/chat/route.ts` and `src/app/api/persona-chat/route.ts` proxy the backend `text/event-stream` through a `ReadableStream` with `Cache-Control: no-cache, no-transform` and cancel the backend reader when the client disconnects. Both set `maxDuration = 800` and `dynamic = "force-dynamic"`; `src/app/api/backend/[...path]/route.ts` detects `text/event-stream` responses and streams them too.
- Clients consume these streams with `fetch` and `response.body.getReader()` (`src/lib/api-client.ts`, `src/lib/api/personas.ts`, `src/components/compare/CompareModels.tsx`) rather than `EventSource`, which is correct because the requests are `POST` with a body. Check that each reader buffers partial frames and aborts on unmount.
- No `EventSource`, `WebSocket` or `refetchInterval` usage was found under `src/`. If notifications or job status need to be live, start with `refetchInterval` on the existing React Query hooks (stopping at terminal states), then consider an SSE route using the pattern above.
- No WebSocket server exists and none can run in the Vercel functions; any future two-way need should use a managed realtime provider with tokens minted by a Route Handler.
