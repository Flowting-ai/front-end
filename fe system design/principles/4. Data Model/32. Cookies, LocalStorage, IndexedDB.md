## 32. Cookies, LocalStorage, IndexedDB

> Three storage primitives with different sizes, sync or async access, data models and security. The wrong choice is a security or UX bug. Auth tokens belong in httpOnly cookies.

### Definition
Browsers offer several places to keep data on the client. Each answers a different question:

- **Cookies** are small key/value strings the browser attaches to every matching HTTP request. They are the only primitive the server can read and set, so they carry identity and anything the server needs on first render.
- **`localStorage`** is a synchronous string key/value store, per origin, that survives restarts. It is for small client-only preferences.
- **`sessionStorage`** is the same API, scoped to one tab and cleared when the tab closes.
- **IndexedDB** is an asynchronous, transactional, indexed object database for structured data, blobs and large volumes, available on the main thread and in workers.

Storage is a cache or a convenience, never the source of truth. The server (or the URL) owns durable truth; the browser keeps what makes the next visit faster or nicer.

### Key properties

**1. Cookies are the server-visible channel**
- Sent automatically with each request to the matching host and path, which costs bandwidth on every call. Keep them tiny (about 4 KB per cookie).
- `HttpOnly` hides the cookie from JavaScript, so an XSS bug cannot read it. `Secure` limits it to HTTPS. `SameSite=Lax` or `Strict` limits cross-site sending (CSRF defence). `Path`, `Domain`, `Max-Age` and `Expires` scope and expire it.
- Readable on the server in Next.js through `cookies()` from `next/headers`. In Server Components it is read-only; writes happen in Server Actions and Route Handlers.

**2. Web Storage is synchronous and client-only**
- `localStorage` and `sessionStorage` hold strings only (about 5 MB per origin, browser dependent). Calls block the main thread, so large reads and writes cause jank.
- Every script on the page can read it. Any XSS or compromised third-party script can exfiltrate it, so it is the wrong place for tokens or personal data.
- Unavailable during SSR. Reading it in render causes hydration mismatches.

**3. IndexedDB is for volume and structure**
- Asynchronous, transactional, indexable, stores structured-clonable objects, `Blob` and `File`. Quotas are far larger (a fraction of free disk, browser dependent).
- Verbose raw API; wrap it with a small library such as `idb` or Dexie. Use it for offline queues, drafts with attachments, cached search indexes.
- Also readable by any script on the origin, so the XSS caveat is the same as `localStorage`.

**4. Storage is per origin, per browser, and not guaranteed**
- Private windows, "clear site data", quota pressure and Safari's eviction can empty it at any time. Reads and writes can throw. Code must work with it missing.
- Several tabs share `localStorage` and IndexedDB; use the `storage` event or `BroadcastChannel` to sync them.

**5. Other primitives exist**
- **Cache API** (service worker or window) stores `Request`/`Response` pairs for offline assets.
- **OPFS** (Origin Private File System, `navigator.storage.getDirectory()`) gives fast private file access, including synchronous handles in workers, for large binary data such as SQLite-in-WASM.
- `navigator.storage.persist()` and `estimate()` request durable storage and report quota.

### Comparison table
| | Cookies | `localStorage` | `sessionStorage` | IndexedDB |
|---|---|---|---|---|
| Typical size | about 4 KB each | about 5 MB | about 5 MB | hundreds of MB or more (quota) |
| API | Sync (`document.cookie`), or headers | Sync | Sync | Async (promises or events) |
| Data model | Strings | Strings | Strings | Structured objects, blobs, indexes |
| Lifetime | Session or until `Max-Age` | Until cleared | Until tab closes | Until cleared |
| Sent to server | Yes, every matching request | No | No | No |
| XSS exposure | None if `HttpOnly`; readable otherwise | Fully readable | Fully readable | Fully readable |
| CSRF exposure | Yes, mitigate with `SameSite` and tokens | No | No | No |
| SSR access | Yes: `cookies()` from `next/headers` | No | No | No |
| Shared across tabs | Yes | Yes | No | Yes |
| Works in workers | No (header based) | No | No | Yes |

### When to use what
| Data | Use |
|---|---|
| Session or auth token, refresh token | `HttpOnly; Secure; SameSite` cookie, set by the server |
| UI preference needed on first server render (theme, sidebar collapsed, locale) | Cookie (readable in the layout), optionally mirrored to `localStorage` |
| Client-only preference (last used model, dismissed banner) | `localStorage` behind a safe wrapper |
| Wizard progress, per-tab scratch state | `sessionStorage` |
| Filters, sort, tab, page | URL (principle 34) |
| Server data cache | TanStack Query (principle 30), optionally persisted to IndexedDB |
| Offline queue, large drafts, files, local search index | IndexedDB (via `idb` or Dexie) |
| Offline assets and app shell | Cache API through a service worker |
| Large binary or database files | OPFS |

### Practical patterns in Next.js (TypeScript)

**Set an auth cookie on the server (Server Action)**
```ts
// app/actions/session.ts
"use server";
import { cookies } from "next/headers";

export async function createSession(token: string) {
  const jar = await cookies();
  jar.set("session", token, {
    httpOnly: true,
    secure: true,
    sameSite: "lax",
    path: "/",
    maxAge: 60 * 60 * 24 * 7,
  });
}

export async function destroySession() {
  (await cookies()).delete("session");
}
```
`cookies()` is async in Next.js 15 and later, so it must be awaited. Setting and deleting is allowed only in Server Actions and Route Handlers, not while rendering a Server Component.

**Read a preference cookie in a Server Component**
```tsx
// app/(app)/layout.tsx (Server Component)
import { cookies } from "next/headers";

export default async function AppLayout({ children }: { children: React.ReactNode }) {
  const collapsed = (await cookies()).get("sidebar_collapsed")?.value === "true";
  return <Shell initialCollapsed={collapsed}>{children}</Shell>;
}
```
The server renders the correct state on the first paint, so the client has nothing to correct. Reading `cookies()` opts the route into dynamic rendering, so use it where that is acceptable.

**A safe `localStorage` wrapper**
```ts
// lib/safe-storage.ts
export function readJson<T>(key: string, fallback: T, validate: (v: unknown) => v is T): T {
  try {
    const raw = window.localStorage.getItem(key);
    if (raw === null) return fallback;
    const parsed: unknown = JSON.parse(raw);
    return validate(parsed) ? parsed : fallback;
  } catch {
    return fallback; // storage blocked, corrupt JSON, or quota
  }
}

export function writeJson(key: string, value: unknown): void {
  try {
    window.localStorage.setItem(key, JSON.stringify(value));
  } catch {
    /* quota exceeded or storage unavailable: degrade silently */
  }
}
```
Always wrap in `try/catch`, and validate what you read (a Zod schema works well here) because the data may be stale, corrupt or edited by the user.

**Hydration-safe persisted state with `useSyncExternalStore`**
```tsx
// hooks/use-local-storage.ts
"use client";
import { useCallback, useSyncExternalStore } from "react";

function subscribe(cb: () => void) {
  window.addEventListener("storage", cb);
  return () => window.removeEventListener("storage", cb);
}

export function useLocalStorageString(key: string, serverValue: string) {
  const value = useSyncExternalStore(
    subscribe,
    () => {
      try { return window.localStorage.getItem(key) ?? serverValue; } catch { return serverValue; }
    },
    () => serverValue, // server and hydration snapshot
  );
  const set = useCallback((next: string) => {
    try { window.localStorage.setItem(key, next); } catch { /* ignore */ }
    window.dispatchEvent(new StorageEvent("storage", { key })); // same-tab notify
  }, [key]);
  return [value, set] as const;
}
```
The server snapshot makes hydration match the HTML, then React re-renders with the real value. The `storage` event fires only in other tabs, so same-tab writes dispatch one manually.

**Gate browser-only reads instead of reading in render**
```tsx
"use client";
import { useEffect, useState } from "react";

export function DraftBanner({ id }: { id: string }) {
  const [draft, setDraft] = useState<string | null>(null);
  useEffect(() => {
    try { setDraft(window.sessionStorage.getItem(`draft_${id}`)); } catch { /* ignore */ }
  }, [id]);
  if (!draft) return null;
  return <p className="rounded-md bg-amber-50 p-3 text-sm">Resume your draft?</p>;
}
```
Reading in an effect keeps the first client render identical to the server's.

**Mirror a preference to a cookie so SSR can match**
```ts
// client-side write, paired with the server read above
export function persistSidebar(collapsed: boolean) {
  try { localStorage.setItem("sidebar_collapsed", String(collapsed)); } catch {}
  document.cookie = `sidebar_collapsed=${collapsed}; path=/; max-age=31536000; samesite=lax`;
}
```
Use this only for non-sensitive UI preferences. Never write tokens with `document.cookie`, because such a cookie cannot be `HttpOnly`.

**IndexedDB through `idb`**
```ts
// lib/outbox.ts
import { openDB, type DBSchema } from "idb";

interface OutboxDB extends DBSchema {
  messages: { key: string; value: { id: string; body: string; createdAt: number }; indexes: { "by-created": number } };
}

const dbPromise = typeof window === "undefined"
  ? null
  : openDB<OutboxDB>("outbox", 1, {
      upgrade(db) {
        const store = db.createObjectStore("messages", { keyPath: "id" });
        store.createIndex("by-created", "createdAt");
      },
    });

export async function queueMessage(m: { id: string; body: string }) {
  const db = await dbPromise;
  await db?.put("messages", { ...m, createdAt: Date.now() });
}
```
`idb` is not installed in this project; adding it is a decision for a real offline or large-data need. Guard on `window` so the module can be imported from shared code without touching IndexedDB during SSR.

### Rules of thumb
1. **Tokens go in `HttpOnly; Secure; SameSite` cookies, set by the server.** Never in `localStorage`, `sessionStorage`, IndexedDB or a JS-written cookie.
2. **If the server must know it, use a cookie. If only the client needs it, use Web Storage.**
3. **If it fits in a URL and should be shareable, put it in the URL** (principle 34).
4. **Large, structured or binary data goes to IndexedDB**, not `localStorage`.
5. **Treat all storage as optional.** Wrap in `try/catch`, provide a fallback, validate what you read.
6. **Never read storage during render.** Use an effect, `useSyncExternalStore` with a server snapshot, or a cookie read on the server.
7. **Version and namespace keys** (`app:v2:sidebar`) so schema changes do not crash on old data.
8. **Store no secrets or PII in client-readable storage.**
9. **Centralise key names** in one module instead of repeating string literals.

### Anti-patterns
- Saving a JWT or refresh token in `localStorage` "because it is easy". One XSS bug steals every user's session.
- `const theme = localStorage.getItem("theme")` in a component body: throws on the server, or mismatches on hydration.
- `JSON.parse(localStorage.getItem(k)!)` with no try/catch or validation.
- Putting API responses or large lists in `localStorage` (blocks the main thread, hits the 5 MB cap).
- Using cookies for large client-only state, so every request carries the extra bytes.
- Setting a cookie from a Server Component render (not allowed; use a Server Action or Route Handler).
- Duplicating server data into storage and treating it as truth, so it goes stale.
- Cookies without `SameSite` on state-changing endpoints, leaving CSRF open.

### Industry best practices
- **Keep session credentials in `HttpOnly`, `Secure`, `SameSite` cookies** and manage them on the server; the OWASP guidance and Next.js authentication guide both follow this.
- **Prefer the `__Host-` cookie prefix** for session cookies (forces `Secure`, `Path=/`, no `Domain`).
- **Make cookie lifetimes explicit** with `Max-Age` and rotate session tokens on login and privilege change.
- **Defend against CSRF** with `SameSite`, Origin checks, and tokens for sensitive actions; Server Actions compare `Origin` to `Host` by default.
- **Mirror UI preferences to a cookie** when the first server render depends on them, to avoid flashes and hydration errors.
- **Use `useSyncExternalStore` with a server snapshot** for subscribing to storage, rather than ad-hoc effects in each component.
- **Validate every stored value with a schema** (Zod) and fall back to defaults on failure.
- **Wrap IndexedDB** with `idb` or Dexie, version the schema through `upgrade`, and keep transactions short.
- **Request persistence for important offline data** with `navigator.storage.persist()` and check `estimate()` before writing large payloads.
- **Sync across tabs** with the `storage` event or `BroadcastChannel`; do not assume a single tab.
- **Clear client storage on logout** (preferences that are user-specific, caches, drafts) so the next user on a shared device sees none of it.
- **Persist TanStack Query selectively** (an IndexedDB persister) and exclude sensitive queries.

### Things to avoid
- Storing tokens, passwords, card data or personal data in any client-readable storage.
- Writing auth cookies with `document.cookie`.
- Accessing `window`, `localStorage` or `indexedDB` at module scope in files imported by Server Components.
- Reading storage in `useState` initialisers that also run on the server.
- Unbounded growth: logs, histories and caches with no eviction or size cap.
- Relying on storage surviving; Safari and private modes evict or block it.
- Storing non-serialisable values and expecting `JSON.stringify` to round trip (`Date`, `Map`, `undefined`).
- Hard-coding the same key literal in several files.
- Sharing one cookie across subdomains (`Domain=`) without a reason; it widens the attack surface.

### Checklist
- [ ] Auth and session tokens live only in `HttpOnly; Secure; SameSite` cookies set server-side.
- [ ] Every storage access is in `try/catch` and validated, with a default.
- [ ] No storage is read during render; hydration-sensitive values use a cookie or a server snapshot.
- [ ] Shareable view state is in the URL, not storage.
- [ ] Large or structured data uses IndexedDB through a wrapper, with versioned schema.
- [ ] Keys are namespaced, versioned and defined in one module.
- [ ] Nothing sensitive is in `localStorage`, `sessionStorage` or IndexedDB.
- [ ] Logout clears user-specific client storage.
- [ ] Cross-tab behaviour is considered for shared keys.
