## 33. Optimistic Updates

> Apply the change at click speed; roll back only if the server errors. Likes, follows and reorders feel instant.

### Definition
An **optimistic update** shows the expected result of a mutation in the UI immediately, before the server confirms it. If the request succeeds, the server's truth replaces the guess. If it fails, the UI returns to the previous state and tells the user.

It is a bet that the server will almost always say yes. The cost of losing the bet (a visible flip back) must be lower than the benefit of removing the wait on every other click.

### Key properties

**1. Three steps: apply, confirm, reconcile**
- Apply the expected state at once. Send the request. On success or failure, reconcile with the server (refetch, or replace with the response).
- Always reconcile at the end, even on success. The server may have changed other fields (counts, timestamps, ids).

**2. Rollback must be possible**
- Either keep a snapshot of the previous state and restore it, or never touch the real state at all (a temporary overlay that disappears by itself).
- The overlay approach cannot leave stale data behind, which is why it is the simpler default.

**3. Concurrent requests need care**
- A background refetch that lands mid-mutation can overwrite the optimistic value. Cancel in-flight queries for the same key before writing.
- Two quick clicks mean two mutations. Rollback of the first must not erase the second.

**4. Failure must be visible**
- A silent flip back is confusing. Pair rollback with a toast or inline error, and keep the user's input if it was a form.

**5. Entities are the unit (principle 31)**
- With normalised data, one write to the entity updates every view that shows it. With duplicated copies, you must patch each copy or the UI disagrees with itself.

### When to use what
| Approach | How it works | Best for | Watch out for |
|---|---|---|---|
| TanStack Query, UI-only (`useMutation` `variables`) | Render the pending `variables` next to the cached data; no cache writes | One or two places show the result (a list plus a pending row) | Other components on the page do not see it |
| TanStack Query, cache-based (`onMutate` / `onError` / `onSettled`) | Snapshot, write to cache with `setQueryData`, restore on error, invalidate on settle | Many components read the same query key (a like count in a card and a header) | More code; you own the rollback |
| React 19 `useOptimistic` | Temporary state layered on a value, reset automatically when the action ends | Forms and Server Actions inside a transition | Local to the component tree; not a shared cache |
| No optimism, show a pending state | Spinner or disabled button until the server answers | Payments, deletes of shared data, anything with side effects | Feels slower |

| Situation | Choice |
|---|---|
| Like, follow, bookmark, toggle | Optimistic |
| Reorder, drag and drop, check off a task | Optimistic |
| Add a comment or chat message | Optimistic with a "sending" state and a retry |
| Payment, order placement, permissions change | Not optimistic; wait for confirmation |
| Server decides the outcome (validation, uniqueness, stock) | Not optimistic, or only the pending indicator |
| Slow or flaky network, high failure rate | Prefer honest pending state |

### Practical patterns in Next.js (TypeScript)

**1. TanStack Query v5, variables-based (simplest)**

`useMutation` returns `isPending` and `variables`. Render the pending item from `variables`; nothing is written to the cache, so there is nothing to roll back.
```tsx
"use client";
import { useMutation, useQuery, useQueryClient } from "@tanstack/react-query";

type Todo = { id: string; title: string };

async function fetchTodos(): Promise<Todo[]> {
  const res = await fetch("/api/todos");
  if (!res.ok) throw new Error("Failed to load todos");
  return res.json();
}

async function postTodo(title: string): Promise<Todo> {
  const res = await fetch("/api/todos", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ title }),
  });
  if (!res.ok) throw new Error("Failed to add todo");
  return res.json();
}

export function TodoList() {
  const queryClient = useQueryClient();
  const { data: todos = [] } = useQuery({ queryKey: ["todos"], queryFn: fetchTodos });

  const add = useMutation({
    mutationFn: postTodo,
    onSettled: () => queryClient.invalidateQueries({ queryKey: ["todos"] }),
  });

  return (
    <ul className="space-y-2">
      {todos.map((t) => (
        <li key={t.id}>{t.title}</li>
      ))}
      {add.isPending && <li className="opacity-50">{add.variables}</li>}
      {add.isError && (
        <li className="text-red-600">
          {add.variables} failed.{" "}
          <button className="underline" onClick={() => add.mutate(add.variables)}>
            Retry
          </button>
        </li>
      )}
    </ul>
  );
}
```
The pending row disappears by itself when the mutation settles and the invalidation refetch lands. If several components need to show it, `useMutationState` can read the pending variables of a mutation from elsewhere (give the mutation a `mutationKey`).

**2. TanStack Query v5, cache-based with rollback**

Use this when other components subscribe to the same query key.
```tsx
"use client";
import { useMutation, useQueryClient } from "@tanstack/react-query";

type Post = { id: string; liked: boolean; likes: number };

async function toggleLike(vars: { id: string; liked: boolean }): Promise<Post> {
  const res = await fetch(`/api/posts/${vars.id}/like`, {
    method: vars.liked ? "PUT" : "DELETE",
  });
  if (!res.ok) throw new Error("Like failed");
  return res.json();
}

export function useToggleLike() {
  const queryClient = useQueryClient();
  const key = ["posts"] as const;

  return useMutation({
    mutationFn: toggleLike,
    onMutate: async (vars, context) => {
      // Stop in-flight refetches from overwriting the optimistic value.
      await context.client.cancelQueries({ queryKey: key });
      const previous = context.client.getQueryData<Post[]>(key);
      context.client.setQueryData<Post[]>(key, (old = []) =>
        old.map((p) =>
          p.id === vars.id
            ? { ...p, liked: vars.liked, likes: p.likes + (vars.liked ? 1 : -1) }
            : p,
        ),
      );
      return { previous };
    },
    onError: (_err, _vars, onMutateResult, context) => {
      if (onMutateResult?.previous) {
        context.client.setQueryData(key, onMutateResult.previous);
      }
    },
    onSettled: (_data, _err, _vars, _onMutateResult, context) =>
      context.client.invalidateQueries({ queryKey: key }),
  });
}
```
Notes for v5:
- `onMutate` runs before `mutationFn`. Whatever it returns arrives in `onError` and `onSettled` as the mutate result, which is where the snapshot travels.
- Callback signatures gained a trailing `context` argument (with `context.client`) in recent v5 releases; older v5 code closes over `useQueryClient()` instead, as the `queryClient` variable above allows. Check the signature in the installed version before copying.
- Always `cancelQueries` first, snapshot second, write third. Always `invalidateQueries` in `onSettled`, so success and failure both end in server truth.
- Write immutably. Mutating the cached object in place breaks structural sharing and change detection.

**3. React 19 `useOptimistic` with a Server Action**

`useOptimistic` layers temporary state on top of a real value. When the surrounding transition or action finishes, the layer is dropped and the real (revalidated) value shows, so a failure rolls back with no extra code.
```ts
// app/posts/actions.ts
"use server";
import { revalidatePath } from "next/cache";

export async function addComment(postId: string, text: string): Promise<void> {
  // await db.comment.create(...)  // throws on failure
  revalidatePath(`/posts/${postId}`);
}
```
```tsx
// app/posts/[id]/comments.tsx
"use client";
import { useOptimistic, useRef, useTransition } from "react";
import { addComment } from "../actions";

type Comment = { id: string; text: string; pending?: boolean };

export function Comments({ postId, comments }: { postId: string; comments: Comment[] }) {
  const [optimistic, addOptimistic] = useOptimistic(
    comments,
    (current: Comment[], text: string) => [
      ...current,
      { id: `tmp-${crypto.randomUUID()}`, text, pending: true },
    ],
  );
  const [, startTransition] = useTransition();
  const formRef = useRef<HTMLFormElement>(null);

  function onSubmit(formData: FormData) {
    const text = String(formData.get("text") ?? "").trim();
    if (!text) return;
    formRef.current?.reset();
    startTransition(async () => {
      addOptimistic(text);
      await addComment(postId, text);
    });
  }

  return (
    <div>
      <ul className="space-y-1">
        {optimistic.map((c) => (
          <li key={c.id} className={c.pending ? "opacity-50" : undefined}>
            {c.text}
          </li>
        ))}
      </ul>
      <form ref={formRef} action={onSubmit} className="mt-3 flex gap-2">
        <input name="text" className="flex-1 rounded border px-2 py-1" />
        <button className="rounded bg-black px-3 py-1 text-white">Send</button>
      </form>
    </div>
  );
}
```
Rules: call `addOptimistic` inside a transition or a form `action`; the first argument is the source of truth passed from the server component (`comments`), so the refreshed props after `revalidatePath` replace the optimistic list. A rejected action rolls the optimistic layer back; surface the error with an error boundary or by returning a result object from the action and checking it.

**4. Reorder with rollback**

The same shape works for drag and drop: snapshot the order, write the new order to the cache, send one request with the final order, and restore the snapshot on error. Debounce or send only the final position so rapid drags do not queue many requests.

### Rules of thumb
1. **Optimistic only when failure is rare and cheap to undo.**
2. **Prefer the simplest mechanism**: `variables` overlay, then `useOptimistic`, then cache writes with rollback.
3. **Cancel, snapshot, write; then invalidate on settle.** Always end in server truth.
4. **Never rely on the optimistic value as saved.** Do not navigate, close dialogs permanently, or chain dependent actions until the server confirms, unless the flow tolerates rollback.
5. **Use stable client ids** for new items (temporary id, replaced by the real one on settle) so keys do not flicker.
6. **Show pending and error states**: dim the pending item, offer retry on failure.
7. **Keep the update pure and small**: a function from (current, input) to next.
8. **Make the server idempotent** for toggles and retries (PUT/DELETE with explicit target state rather than "flip").

### Anti-patterns
- Optimistic payments, order placement or permission changes.
- Writing to the cache without `cancelQueries`; a background refetch undoes the change and the UI flickers.
- No rollback on error, leaving a "liked" heart that the server rejected.
- Skipping the final `invalidateQueries`, so counts and ids stay as guessed.
- Mutating cached objects in place.
- Toggle endpoints that "flip" server-side; a retry or double click flips it back.
- Optimistic updates on data the server validates (unique name, stock levels) with no failure UI.
- Hand-rolled optimistic state in context copies of server data, when the query cache could own it (principle 30).
- Using `useOptimistic` outside a transition or action, so the value reverts immediately.

### Industry best practices
- **Prefer the `variables` approach** for single-place feedback; it has no rollback logic to get wrong.
- **Use cache-based updates only for shared data**, and keep query keys centralised (a key factory) so `onMutate` and `onSettled` target the same keys.
- **Cancel, snapshot, set, invalidate**: follow this order every time.
- **Roll back on error and say so** with a toast naming what failed and offering retry.
- **Use `useOptimistic` for Server Actions and forms**; pass the server value as its first argument so refreshed props replace the optimistic layer.
- **Normalise entities** (principle 31) so one cache write updates every view.
- **Make mutations idempotent** and send the desired end state, not a delta, where possible.
- **Handle races**: use a `mutationKey` and, for rapid toggles, send only the latest state or invalidate only when no related mutation is still in flight (`queryClient.isMutating`).
- **Mark pending items** visually and keep them non-interactive until confirmed (no delete on a row that has no real id yet).
- **Pause on offline**: mutations queue under `networkMode`; decide whether an optimistic change should persist across reload, and if not, do not persist the paused mutation.
- **Test the failure path**: force a 500 and assert the rollback and error message, not only the happy path.
- **Measure**: track rollback rate; a high rate means the bet is wrong and a pending state is better.

### Things to avoid
- Optimism for irreversible or money-related actions.
- Optimistic updates with no visible error handling.
- Storing the snapshot in component state that may unmount before the error arrives; keep it in the mutation context.
- Updating several unrelated caches by hand instead of invalidating them.
- Relying on optimistic ids as real ids in later requests.
- Calling `addOptimistic` outside a transition or form action.
- Mixing `useOptimistic` and cache writes for the same data; pick one owner.
- Hiding the loading state completely on slow endpoints; users still need to know a save is in flight.
- Reconciling by trusting the client's guessed counts after success; take the server response.
- Retrying automatically on non-idempotent mutations.

### Checklist
- [ ] Failure is rare and the rollback is acceptable to the user.
- [ ] The simplest mechanism is used (`variables`, `useOptimistic`, then cache writes).
- [ ] Cache-based updates cancel queries, snapshot, write immutably, and restore on error.
- [ ] `onSettled` invalidates or the response replaces the guess.
- [ ] Errors are shown and retry is possible.
- [ ] Server endpoints are idempotent for toggles and retries.
- [ ] Pending items are visibly distinct and not actionable.
- [ ] Failure path is tested.
