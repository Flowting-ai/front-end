## 29. Redux vs MobX

> Redux gives strict, traceable actions and a single predictable store. MobX gives implicit, automatic observable tracking with less code. Pick by how much you value an audit trail versus brevity, and check the choice against SSR.

### Definition
**Redux** (today, Redux Toolkit, "RTK") keeps client state in one store that changes only when an **action** is dispatched to a **reducer**. State is plain, serialisable data, updates are explicit events, and every change can be logged, replayed and inspected.

**MobX** keeps state in **observable** objects (classes or plain objects). Components wrapped with `observer` automatically track which observables they read and re-render only when those change. You mutate state directly inside **actions**; the library derives the rest (`computed`, reactions).

Both solve "shared client state with fine-grained updates". They differ in philosophy: Redux makes change **explicit and recorded**, MobX makes change **implicit and automatic**.

### Key properties

**1. Redux: predictability through ceremony**
- One-way flow: UI dispatches an action, a reducer returns the next state, subscribers re-render (principle 13).
- State is serialisable and immutable (RTK uses Immer so reducers may be written in "mutating" style).
- Redux DevTools gives an action log, state diffs and time travel.
- Middleware (listeners, thunks) is the place for side effects.
- RTK Query adds data fetching and caching on top of the store.

**2. MobX: less code, surgical re-renders**
- Mutate observables directly; no action types, reducers or selectors to write.
- `observer` components re-render only for the exact properties they dereferenced during render.
- `computed` values are cached and recalculated only when their inputs change.
- Mutable class-based stores with methods feel familiar to object-oriented teams.

**3. Both need extra care under SSR**
- A module-level store on the server is shared between requests and users. Create the store **per request** and provide it through context (principle 24).
- Redux state is serialisable, so it is simple to seed on the server and hydrate on the client. MobX stores are class instances; you must hand-write a hydrate step or pass plain snapshots.
- Both are client-side libraries: they need `"use client"` and cannot be read in Server Components (principle 6).

**4. Neither owns server data well by default**
- Fetched API data belongs in a server-state tool (principle 30). RTK Query is Redux's answer; MobX has no built-in equivalent, so it usually pairs with TanStack Query or SWR.

### Decision table
| Need | Best fit | Why |
|---|---|---|
| UI state in one component or a small subtree | `useState` / `useReducer` ([27](27.%20Local%20State.md)) | No library needed |
| Rarely changing, wide-reach values (theme, locale, session) | Context ([24](../3.%20Component%20Patterns/24.%20Provider%20Pattern.md)) | Built in, low update rate |
| Small shared client store, simple hook API | Zustand ([28](28.%20Global%20State%20-%20Zustand.md)) | Tiny, selectors, no provider boilerplate |
| API data, caching, dedup, background sync | TanStack Query ([30](30.%20Server%20State%20-%20React%20Query.md)) or RTK Query | Built for server state |
| Large team, many events, audit trail, undo/redo, time travel debugging | Redux Toolkit | Explicit actions and DevTools |
| Rich, deeply derived, frequently mutated client graph (editors, canvases, spreadsheets) | MobX | Automatic fine-grained tracking, `computed` |
| Shareable or bookmarkable state | URL (`searchParams`) ([34](34.%20URL%20as%20State.md)) | Link, refresh and Back/Forward free |
| Team strongly prefers immutable, functional style | Redux Toolkit or Zustand | Plain data, pure updates |
| Team strongly prefers OOP, mutable models | MobX | Class stores, direct mutation |

Rule of thumb: most Next.js App Router apps need **server components + TanStack Query + local state + a little Context, and Zustand if a store is needed**. Redux or MobX earn their weight only for large, event-heavy or graph-heavy client state.

### Comparison
| Aspect | Redux Toolkit | MobX |
|---|---|---|
| Model | Single store, actions and reducers | Observable objects, actions mutate |
| Update style | Immutable (Immer-assisted) | Mutable |
| Boilerplate | Moderate (slices, store, hooks) | Low |
| Re-render control | Selectors (`useSelector`), memoised | Automatic via `observer` |
| Traceability | Excellent: every action logged | Weaker: mutations are implicit; devtools exist but no time travel as a core feature |
| Serialisable state | Yes, by design | Not by default |
| SSR hydration | Straightforward (plain state) | Manual |
| Data fetching | RTK Query built in | Bring your own |
| Learning curve | Concepts (actions, reducers, middleware) | "Magic" tracking, harder to debug when it misses |
| Typical risk | Over-engineering, store as dumping ground | Hidden dependencies, forgetting `observer` or dereferencing too early |

### Practical patterns in Next.js (TypeScript)

**Redux Toolkit: per-request store (App Router safe)**
```ts
// lib/store.ts
import { configureStore, createSlice, type PayloadAction } from "@reduxjs/toolkit";

type CartState = { ids: string[] };

const cartSlice = createSlice({
  name: "cart",
  initialState: { ids: [] } as CartState,
  reducers: {
    added(state, action: PayloadAction<string>) {
      state.ids.push(action.payload); // Immer makes this immutable
    },
    removed(state, action: PayloadAction<string>) {
      state.ids = state.ids.filter((id) => id !== action.payload);
    },
  },
});

export const { added, removed } = cartSlice.actions;

// A function, not a singleton: each request / client gets its own store.
export const makeStore = () => configureStore({ reducer: { cart: cartSlice.reducer } });

export type AppStore = ReturnType<typeof makeStore>;
export type RootState = ReturnType<AppStore["getState"]>;
export type AppDispatch = AppStore["dispatch"];
```

```tsx
// lib/hooks.ts
import { useDispatch, useSelector, useStore } from "react-redux";
import type { AppDispatch, AppStore, RootState } from "./store";

export const useAppDispatch = useDispatch.withTypes<AppDispatch>();
export const useAppSelector = useSelector.withTypes<RootState>();
export const useAppStore = useStore.withTypes<AppStore>();
```

```tsx
// app/store-provider.tsx
"use client";
import { useRef, type ReactNode } from "react";
import { Provider } from "react-redux";
import { makeStore, type AppStore } from "@/lib/store";

export function StoreProvider({ children }: { children: ReactNode }) {
  const ref = useRef<AppStore>(null);
  if (!ref.current) ref.current = makeStore();
  return <Provider store={ref.current}>{children}</Provider>;
}
```
Mount `StoreProvider` in the smallest subtree that needs it, not necessarily the root layout. To seed server data, pass it as a prop and dispatch it once when the store is created.

**Redux Toolkit: component usage**
```tsx
"use client";
import { useAppDispatch, useAppSelector } from "@/lib/hooks";
import { added } from "@/lib/store";

export function AddToCart({ id }: { id: string }) {
  const dispatch = useAppDispatch();
  const count = useAppSelector((s) => s.cart.ids.length); // re-renders only when this value changes
  return (
    <button className="rounded-md bg-primary px-3 py-1.5 text-white" onClick={() => dispatch(added(id))}>
      Add ({count})
    </button>
  );
}
```

**RTK Query (server data inside the Redux store)**
```ts
import { createApi, fetchBaseQuery } from "@reduxjs/toolkit/query/react";

type Project = { id: string; name: string };

export const api = createApi({
  reducerPath: "api",
  baseQuery: fetchBaseQuery({ baseUrl: "/api" }),
  tagTypes: ["Project"],
  endpoints: (build) => ({
    getProjects: build.query<Project[], void>({
      query: () => "projects",
      providesTags: ["Project"],
    }),
    addProject: build.mutation<Project, { name: string }>({
      query: (body) => ({ url: "projects", method: "POST", body }),
      invalidatesTags: ["Project"],
    }),
  }),
});

export const { useGetProjectsQuery, useAddProjectMutation } = api;
```
Add `api.reducer` and `api.middleware` to `configureStore`. If the app already uses TanStack Query, do not add RTK Query as a second cache.

**MobX: observable store with `observer`**
```tsx
// stores/cart-store.ts
import { makeAutoObservable } from "mobx";

export class CartStore {
  ids: string[] = [];

  constructor() {
    makeAutoObservable(this);
  }

  get count() {
    return this.ids.length; // computed, cached
  }

  add(id: string) {
    this.ids.push(id); // action, mutation is allowed here
  }
}
```

```tsx
// stores/cart-provider.tsx
"use client";
import { createContext, use, useState, type ReactNode } from "react";
import { observer } from "mobx-react-lite";
import { CartStore } from "./cart-store";

const CartContext = createContext<CartStore | null>(null);

export function CartProvider({ children }: { children: ReactNode }) {
  const [store] = useState(() => new CartStore()); // one instance per provider mount, not per module
  return <CartContext value={store}>{children}</CartContext>;
}

function useCartStore() {
  const store = use(CartContext);
  if (!store) throw new Error("useCartStore must be used inside <CartProvider>");
  return store;
}

export const CartBadge = observer(function CartBadge() {
  const cart = useCartStore();
  return <span>{cart.count}</span>; // re-renders only when count changes
});
```
Dereference observables **inside** the `observer` component, not in a parent that passes the plain value down; otherwise the tracking happens in the wrong place and the child will not update on its own.

**Choosing by the shape of the problem (sketch)**
```
Need an action log, undo, or strict team conventions?   -> Redux Toolkit
Big mutable object graph with many derived values?       -> MobX
Just a few shared fields with selectors?                 -> Zustand (28)
Data that lives on the server?                           -> TanStack Query (30)
```

### Rules of thumb
1. **Reach for the simplest tool first**: server components, TanStack Query, local state, URL, Context, then a store.
2. **Choose Redux for traceability and conventions**, MobX for productivity on rich derived state, Zustand for a small shared store.
3. **Never use a module-level store on the server**; create one per request and provide it through context.
4. **Keep state serialisable** in Redux: no class instances, functions or Dates in state.
5. **Subscribe to slices**: `useAppSelector` with a narrow selector, or MobX `observer` with late dereferencing.
6. **Do not store server data in Redux or MobX** when TanStack Query is available; one cache per concern.
7. **Do not mix two global state libraries** for the same kind of state.
8. **Wrap every MobX component that reads observables** in `observer`, and mutate only inside actions (`enforceActions` on).

### Anti-patterns
- Adding Redux or MobX for state that `useState` plus Context would handle.
- A singleton `export const store = configureStore(...)` imported by Server Components or shared across requests.
- Copying API responses into a Redux slice and manually keeping them fresh, next to a working Query cache.
- Putting form input state, modal open flags and hover state in the global store.
- Storing non-serialisable values in Redux state, then silencing the serializability check.
- MobX: mutating observables outside actions, or reading an observable in a parent and passing the raw value to a non-observer child.
- Selecting the whole slice (`useSelector((s) => s.cart)`) or returning a new object from a selector on every call.
- Hydrating a persisted store during render and causing server/client mismatches.

### Industry best practices
- **Prefer Redux Toolkit over hand-written Redux**; it is the officially recommended way and removes most boilerplate.
- **Create the store per request in Next.js** with a `makeStore` factory and a client provider, as the RTK docs for Next.js describe.
- **Use typed hooks** (`useAppSelector`, `useAppDispatch`, `.withTypes`) once, instead of annotating every call site.
- **Model actions as events** ("cartItemAdded"), not setters ("setCart"); slices stay small and feature-owned.
- **Use `createSelector` or narrow selectors** for derived data so memoisation and re-render control stay intact.
- **Turn on Redux DevTools in development** and use the action log as a debugging and review tool; keep it off or sanitised in production.
- **Use RTK Query or TanStack Query, not both**; pick the one that matches the rest of the stack.
- **With MobX, use `makeAutoObservable` and `observer` from `mobx-react-lite`**, keep `enforceActions` enabled, and keep stores per feature.
- **Seed the client from the server with plain snapshots**: pass server data in as props, and initialise the store once.
- **Persist deliberately**: restore client-only state after mount (or with skipped hydration) to avoid hydration mismatches.
- **Write store tests without React**: reducers are pure functions, MobX stores are plain classes.
- **Revisit the choice when the app grows or shrinks**; a store that holds only two flags may no longer justify a library.

### Things to avoid
- Choosing a library by popularity instead of the decision table above.
- Putting every piece of state in a global store "for consistency".
- Dispatching from Server Components or reading a store there; they cannot subscribe.
- Mutating Redux state outside reducers or Immer drafts.
- Side effects inside reducers; use listener middleware, thunks or event handlers.
- Relying on MobX "magic" without understanding what is tracked; use the devtools or `trace` when a component fails to update.
- Large, deeply nested normalised state without selectors or entity adapters (principle 31).
- Sharing one store instance across users through a global in a server module.
- Wrapping the whole app in several state providers at the root when only one route needs them.

### Checklist
- [ ] The state genuinely needs a global client store (not server, URL, local or Context state).
- [ ] The choice (Redux Toolkit, MobX, Zustand or none) is justified against the decision table.
- [ ] Store is created per request/mount and provided through a client component.
- [ ] State is serialisable (Redux) or hydrated through plain snapshots (MobX).
- [ ] Components subscribe to narrow slices; selectors do not return fresh objects.
- [ ] Server data is owned by one cache (TanStack Query or RTK Query).
- [ ] MobX: `observer` on readers, mutations only in actions.
- [ ] DevTools and tests cover the store.

- Neither `redux` / `@reduxjs/toolkit` nor `mobx` is installed, and no source file imports them. `zustand` and `react-hook-form` are also absent.
