## 35. Form State - RHF and Zod

> Uncontrolled inputs read at submit time, validated by a schema. One Zod schema serves the client and the server.

### Definition
**Form state** is the in-progress values, validation errors, touched/dirty flags and submission status of a form. **React Hook Form (RHF)** keeps field values in refs on uncontrolled DOM inputs and reads them when needed (on submit, blur or change), rather than storing every keystroke in React state. **Zod** is a TypeScript-first schema library: the schema is the single source of truth for the shape, the validation rules and (through `z.infer`) the TypeScript type.

The pairing works because they split responsibilities: RHF owns **interaction state**, Zod owns **what is valid**. `@hookform/resolvers` connects them.

### Key properties

**1. Uncontrolled by default, so fewer re-renders**
- A controlled form re-renders the component on every keystroke. RHF registers inputs and reads the DOM at submit, so typing does not re-render the form.
- Subscribe narrowly (`useWatch`, `formState` fields you actually read) because `formState` is a proxy and only tracked properties trigger renders.

**2. The schema is the contract**
- Define the schema once, derive the type with `z.infer<typeof schema>` (or `z.input` / `z.output` when transforms or defaults make them differ).
- Share the same schema file between the client form and the Server Action or route handler.

**3. Never trust the client**
- Client validation is UX. The server must run the same schema again with `safeParse`, because requests can bypass the browser.

**4. Errors are part of the UI contract**
- Field errors are tied to inputs with `aria-invalid` and `aria-describedby`, announced through `role="alert"` or a live region, and focus moves to the first invalid field.

**5. Progressive enhancement is available**
- A plain `<form action={serverAction}>` with `useActionState` works without client JavaScript and needs no form library. RHF is added when you need rich client-side behaviour (field arrays, dependent fields, per-field async validation).

### When to use what
| Situation | Use |
|---|---|
| One or two fields, submit only | Native `<form>` plus `FormData`, or `useActionState` |
| Simple form, server validation only | Server Action + `useActionState` + Zod `safeParse` |
| Large form, many fields, live validation, field arrays | RHF + `zodResolver` |
| Same rules needed in browser and server | One shared Zod schema |
| Filters, sort, pagination | URL state (principle 34), not a form library |
| Server data prefilled into a form | Fetch in a Server Component, pass as `defaultValues` |
| Post-submit list update | Mutation + invalidate or optimistic update (principles 30, 33) |

### Practical patterns in Next.js (TypeScript)

**Shared schema (Zod 4)**
```ts
// lib/schemas/contact.ts
import { z } from "zod";

export const contactSchema = z.object({
  name: z.string().min(1, "Name is required"),
  email: z.email("Enter a valid email"),
  message: z.string().min(10, "At least 10 characters").max(2000),
  subscribe: z.boolean(),
});

export type ContactInput = z.infer<typeof contactSchema>;
```
In Zod 4, string formats are top-level (`z.email()`, `z.uuid()`, `z.url()`); the `z.string().email()` form still works but is deprecated. A second argument or `{ error: "..." }` sets the message (the older `message` and `errorMap` options are replaced by the unified `error` parameter).

**Server Action that revalidates with the same schema**
```ts
// app/contact/actions.ts
"use server";
import { z } from "zod";
import { contactSchema } from "@/lib/schemas/contact";

export type ContactState = {
  ok: boolean;
  errors?: Record<string, string[] | undefined>;
  values?: Record<string, string>;
};

export async function submitContact(_prev: ContactState, formData: FormData): Promise<ContactState> {
  const raw = {
    name: formData.get("name"),
    email: formData.get("email"),
    message: formData.get("message"),
    subscribe: formData.get("subscribe") === "on",
  };
  const parsed = contactSchema.safeParse(raw);
  if (!parsed.success) {
    return {
      ok: false,
      errors: z.flattenError(parsed.error).fieldErrors,
      values: { name: String(raw.name ?? ""), email: String(raw.email ?? ""), message: String(raw.message ?? "") },
    };
  }
  // authenticate + authorise here, then persist
  return { ok: true };
}
```
`z.flattenError(error)` is the Zod 4 function form (`error.flatten()` is deprecated). Treat a Server Action as a public endpoint: check the session and permissions inside it.

**Progressive form with `useActionState` (no library)**
```tsx
// app/contact/contact-form.tsx
"use client";
import { useActionState } from "react";
import { submitContact, type ContactState } from "./actions";

const initial: ContactState = { ok: false };

export function ContactForm() {
  const [state, action, pending] = useActionState(submitContact, initial);
  const err = state.errors;
  return (
    <form action={action} noValidate className="grid gap-4">
      <label className="grid gap-1 text-sm">
        Email
        <input
          name="email"
          type="email"
          defaultValue={state.values?.email}
          aria-invalid={!!err?.email}
          aria-describedby={err?.email ? "email-err" : undefined}
          className="rounded border px-3 py-2 aria-invalid:border-red-600"
        />
        {err?.email && <span id="email-err" role="alert" className="text-red-600">{err.email[0]}</span>}
      </label>
      <button disabled={pending} className="rounded bg-black px-4 py-2 text-white disabled:opacity-50">
        {pending ? "Sending..." : "Send"}
      </button>
    </form>
  );
}
```
React 19 resets uncontrolled fields after a successful action, so echo submitted values back through `defaultValue` when you return errors.

**RHF + `zodResolver` for a rich client form**
```tsx
"use client";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { contactSchema, type ContactInput } from "@/lib/schemas/contact";

export function ContactFormRhf({ onSubmit }: { onSubmit: (v: ContactInput) => Promise<void> }) {
  const {
    register,
    handleSubmit,
    setFocus,
    formState: { errors, isSubmitting },
  } = useForm<ContactInput>({
    resolver: zodResolver(contactSchema),
    defaultValues: { name: "", email: "", message: "", subscribe: false },
    mode: "onTouched",
  });

  return (
    <form onSubmit={handleSubmit(onSubmit, (errs) => setFocus(Object.keys(errs)[0] as keyof ContactInput))} noValidate>
      <input {...register("email")} aria-invalid={!!errors.email} aria-describedby="email-err" />
      {errors.email && <p id="email-err" role="alert">{errors.email.message}</p>}
      <button disabled={isSubmitting}>Send</button>
    </form>
  );
}
```
Use a recent `@hookform/resolvers` (v5+) for Zod 4 support. If the schema uses transforms or defaults, type the form with the **input** type and the submit handler with the **output** type (`useForm<z.input<S>, unknown, z.output<S>>`); verify against the resolvers README for your installed versions.

**Server errors back into RHF**
```tsx
const res = await submitContactAction(values);
if (!res.ok) {
  for (const [field, msgs] of Object.entries(res.errors ?? {})) {
    if (msgs?.[0]) setError(field as keyof ContactInput, { type: "server", message: msgs[0] });
  }
}
```

### Rules of thumb
1. **Schema first**: write the Zod schema, then derive types and the form from it.
2. **Validate on the server always**; the client pass is a convenience.
3. **Prefer `<form action>` + `useActionState`** until you genuinely need RHF features.
4. **Use RHF for large or dynamic forms** (field arrays, dependent fields, many inputs).
5. **Keep a form's state in the form**, not in context or a global store; reset it on unmount.
6. **Show errors next to fields**, link them with `aria-describedby`, and focus the first invalid one.
7. **Return values with errors** from actions so the user does not retype.
8. **Pick `mode` deliberately**: `onSubmit` default, `onTouched` for friendlier feedback, `onChange` only when needed.

### Anti-patterns
- A controlled input per field with `useState` in a 30-field form, re-rendering everything on each keystroke.
- Duplicating validation rules in the client and the server by hand, so they drift.
- Trusting client validation and skipping `safeParse` in the Server Action.
- Using `watch()` at the root of a large form and re-rendering it on every change.
- Storing form values in Redux, Zustand or context for a single-page form.
- Showing only a red border, with no text or ARIA link.
- Placeholder text used as the only label.
- Using `z.infer` on a schema with transforms and expecting it to match the raw input type.
- Disabling the submit button forever until valid, hiding why it is disabled.

### Industry best practices
- **One schema module** per form or entity under `lib/schemas/`, imported by both the form and the action; export the inferred type.
- **Use `z.input` / `z.output`** when schemas coerce or transform (for example `z.coerce.number()` for text inputs).
- **Return structured errors** (`z.flattenError` or `z.treeifyError`) from actions, not thrown exceptions, for validation failures.
- **Authenticate and authorise inside every Server Action**; the endpoint is reachable directly.
- **Pass `defaultValues` from the server** for edit forms, and use `reset(values)` when fresh server data arrives.
- **Use `Controller` or `useController` only** for non-native components (Radix Select, custom date pickers); `register` for native inputs.
- **Narrow subscriptions** with `useWatch({ name })` or `getValues()` at event time instead of root `watch()`.
- **Label every input**, mark required fields, and announce errors with `role="alert"` or `aria-live`.
- **Prevent double submit** with `isSubmitting` or the `pending` flag from `useActionState`/`useFormStatus`.
- **Combine with mutations**: on success invalidate the relevant TanStack Query keys (principle 30) or apply an optimistic update (principle 33).
- **Warn on unsaved changes** with `formState.isDirty` for long forms.
- **Test the schema in isolation** with valid and invalid fixtures; it is pure and cheap to test.

### Things to avoid
- Client-only validation for anything that matters (permissions, limits, uniqueness).
- Hand-written TypeScript types that duplicate the Zod schema.
- Passing the Zod error object to the client wholesale; map it to plain messages.
- Mixing `register` and controlled `value` props on the same input.
- Calling `reset()` or `setValue()` during render.
- Using RHF for filter bars and pagination; those belong in the URL.
- Exposing internal error messages or stack traces from server validation.
- Reading `process.env` or server-only modules in a shared schema file that the client imports.
- Mixing old Zod 3 APIs (`.flatten()`, `errorMap`, `z.string().email()`) into new Zod 4 code.

### Checklist
- [ ] One Zod schema per form, shared by client and server; type from `z.infer`.
- [ ] The Server Action or route handler re-validates with `safeParse` and checks auth.
- [ ] Simple forms use `useActionState`; RHF is used only where its features are needed.
- [ ] Errors are linked to fields with `aria-invalid` / `aria-describedby`, and focus goes to the first error.
- [ ] Submitted values are preserved on validation failure.
- [ ] Submit is guarded against double submission.
- [ ] Successful submit invalidates or updates the affected server state.
- [ ] Zod 4 APIs used (`z.email()`, `z.flattenError`, `error` option).
