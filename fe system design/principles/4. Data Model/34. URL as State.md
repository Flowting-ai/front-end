## 34. URL as State

> Filters, sort and pagination belong in the URL, not component state. The URL is shareable, bookmarkable and refresh-proof, and Back/Forward works with no extra code.

### Definition
**URL as state** means that any state describing *what the user is looking at* (search text, filters, sort order, page, selected tab, open item id) lives in the URL (path segments and the query string) and is the single source of truth. Components read it, and change it by navigating.

The test: "If the user copies the link and opens it in another browser, should they see the same view?" If yes, that state belongs in the URL. Ephemeral UI state (a tooltip open, a half-typed draft, a hover) does not.

### Key properties

**1. Shareable, bookmarkable, refresh-proof**
- A link reproduces the exact view. Refresh, deep links, and sharing in chat all work with no persistence code.

**2. Back/Forward for free**
- Each `router.push` adds a history entry, so the browser buttons step through view changes. No custom history logic.

**3. Server-readable**
- Server Components receive `searchParams` and can fetch the right data on the first render, with no client waterfall and no loading flash.

**4. Strings only, so validate**
- The URL is untrusted user input and every value is a string. Parse and validate it (zod) and fall back to defaults. Never cast.

**5. One source of truth**
- Do not mirror the URL into `useState`. Derive from it. Mirroring creates two truths that drift.

### When to use what
| State | Where it lives |
|---|---|
| Search text, filters, sort, page, tab, selected id | URL (`searchParams` or path segment) |
| Which entity is shown (`/projects/42`) | Path segment (dynamic route) |
| Draft text, hover, open popover, form in progress | Local state ([27](27.%20Local%20State.md)) |
| Data fetched for the current URL | Server Component or React Query keyed by URL params ([30](30.%20Server%20State%20-%20React%20Query.md)) |
| Per-user preference (theme, column widths) | Cookie or localStorage ([32](32.%20Cookies%2C%20LocalStorage%2C%20IndexedDB.md)) |
| Secrets, tokens, PII | Never in the URL (logged, cached, leaked via Referer) |

### Practical patterns in Next.js (TypeScript)

**Server page: `searchParams` is a Promise in Next.js 15+**
```tsx
// app/projects/page.tsx (Server Component)
import { z } from "zod";

const Query = z.object({
  q: z.string().trim().max(100).catch(""),
  sort: z.enum(["name", "updated"]).catch("updated"),
  page: z.coerce.number().int().min(1).catch(1),
});

type Props = { searchParams: Promise<Record<string, string | string[] | undefined>> };

export default async function Page({ searchParams }: Props) {
  const { q, sort, page } = Query.parse(await searchParams);
  const data = await getProjects({ q, sort, page });
  return <ProjectList data={data} />;
}
```
Awaiting `searchParams` opts the page into dynamic rendering (it is request-time data). `.catch()` gives a safe default for any malformed value, so `Query.parse` never throws on a hand-edited URL. A repeated key (`?tag=a&tag=b`) arrives as `string[]`; model it with `z.array(z.string())` plus a normaliser.

**Client: `useSearchParams` needs a Suspense boundary**
```tsx
// app/projects/page.tsx
import { Suspense } from "react";
export default function Page() {
  return (
    <Suspense fallback={<FiltersSkeleton />}>
      <Filters />
    </Suspense>
  );
}
```
In a statically rendered route, a component calling `useSearchParams()` opts the nearest boundary into client-side rendering. Without a `<Suspense>` boundary, the whole page up to the root falls back to client rendering, and `next build` can fail with a "Missing Suspense boundary with useSearchParams" error. Wrap the smallest subtree that reads it.

**Update helper: build from the current params, preserve the rest**
```tsx
"use client";
import { usePathname, useRouter, useSearchParams } from "next/navigation";
import { useCallback } from "react";

export function useQueryUpdater() {
  const router = useRouter();
  const pathname = usePathname();
  const params = useSearchParams();

  return useCallback(
    (patch: Record<string, string | null>, mode: "push" | "replace" = "replace") => {
      const next = new URLSearchParams(params.toString());
      for (const [k, v] of Object.entries(patch)) {
        if (v === null || v === "") next.delete(k);
        else next.set(k, v);
      }
      if (!("page" in patch)) next.delete("page"); // a filter change resets pagination
      const qs = next.toString();
      const url = qs ? `${pathname}?${qs}` : pathname;
      router[mode](url, { scroll: false });
    },
    [params, pathname, router],
  );
}
```
`useSearchParams()` returns a read-only `ReadonlyURLSearchParams`, so copy it into a new `URLSearchParams` before editing. `scroll: false` stops the page jumping to the top on each filter change.

**`push` vs `replace`**
| Change | Use | Why |
|---|---|---|
| Typing in a search box | `replace` | Each keystroke should not add a history entry |
| Toggle a filter, change sort | `replace` (or `push` if the user would expect Back to undo) | Usually a refinement of one view |
| Next page, open a detail tab | `push` | A distinct place the user may want to return to |
| Normalising or defaulting a bad URL | `replace` | Do not trap Back on the bad URL |

**Debounced text search**
```tsx
"use client";
import { useEffect, useState } from "react";

export function SearchBox() {
  const params = useSearchParams();
  const update = useQueryUpdater();
  const urlQ = params.get("q") ?? "";
  const [draft, setDraft] = useState(urlQ);

  // Back/Forward or external navigation changes the URL: resync the draft.
  useEffect(() => setDraft(urlQ), [urlQ]);

  useEffect(() => {
    if (draft === urlQ) return;
    const id = setTimeout(() => update({ q: draft }), 300);
    return () => clearTimeout(id);
  }, [draft, urlQ, update]);

  return (
    <input
      value={draft}
      onChange={(e) => setDraft(e.target.value)}
      className="h-9 rounded-md border px-3 text-sm"
      aria-label="Search"
    />
  );
}
```
The input stays responsive through a local draft, and the URL updates once the user pauses. This is the one legitimate mirror: a short-lived draft that is reconciled to the URL.

**Transition for pending UI**
```tsx
const [isPending, startTransition] = useTransition();
startTransition(() => update({ sort: "name" }));
// show a subtle opacity or spinner while isPending
```
Navigation is a transition, so the current UI stays interactive while the server renders the new `searchParams`.

**Type-safe parsing in clients: nuqs**
```tsx
"use client";
import { parseAsInteger, parseAsString, useQueryStates } from "nuqs";

const [{ q, page }, setQuery] = useQueryStates({
  q: parseAsString.withDefault(""),
  page: parseAsInteger.withDefault(1),
});
setQuery({ q: "shoes", page: 1 });
```
[nuqs](https://nuqs.dev) is a type-safe `useState`-like hook that stores state in the query string, with parsers, defaults, `history: "replace" | "push"` and `limitUrlUpdates: debounce(...)` options, plus server-side cache helpers (`createSearchParamsCache`) for Server Components. It needs a `NuqsAdapter` mounted in the root layout for the App Router (`nuqs/adapters/next/app`). It is not installed here; adopt it when several screens repeat the helper above, not before.

**Path segments for identity, query for view**
```
/projects/42?tab=files&sort=updated   // identity in the path, view state in the query
```
Use dynamic routes for "which thing", and query params for "how I am looking at it".

### Rules of thumb
1. **If it should survive refresh or be shareable, it goes in the URL.**
2. **The URL is the source of truth**; derive, do not mirror (except a debounced input draft).
3. **Validate every param** with zod and `.catch()` defaults; never trust or cast.
4. **`replace` for refinement, `push` for navigation.**
5. **Reset `page` when a filter or sort changes.**
6. **Omit defaults** from the URL to keep links short and canonical.
7. **Wrap `useSearchParams` readers in `<Suspense>`.**
8. **Read `searchParams` on the server** when the data depends on it; pass results down.
9. **Keep it small and non-sensitive**; no tokens, no large JSON blobs.
10. **Use stable, readable keys** (`?sort=updated`, not `?s=2`) and treat them as a public API.

### Anti-patterns
- `useState` for filters and page, losing them on refresh and making links useless.
- Syncing URL to state and state to URL in two effects (infinite loops, drift).
- `router.push` on every keystroke, filling the history with one entry per letter.
- `Number(params.get("page"))` with no validation (`NaN`, negative, `1e9`).
- Reading `searchParams` synchronously in a Next.js 16 server page (it is a Promise; sync access is removed).
- `useSearchParams` in a client component with no Suspense boundary in a static route.
- Putting auth tokens, emails or PII in query strings.
- Storing whole objects as JSON in a single param.

### Industry best practices
- **Treat the URL as an API**: document param names, types and defaults per route, and keep them backward compatible once shared.
- **Parse once at the edge** with a zod schema shared by the server page and client components, so both agree on defaults.
- **Use `.catch()` or `safeParse`** so a bad URL degrades to defaults instead of a 500.
- **Prefer server-side reading** of `searchParams` for first render and SEO; use `useSearchParams` only for client interactivity.
- **Debounce text input 250 to 400 ms**, and update immediately for discrete controls (select, checkbox).
- **Use `replace` for refinements and `push` for navigations**; test the Back button as a feature.
- **Pass `scroll: false`** on same-page param changes.
- **Reset dependent params** (page on filter change; selected id when the list changes).
- **Key client caches by the validated params** (`queryKey: ["projects", { q, sort, page }]`) so React Query and the URL agree ([30](30.%20Server%20State%20-%20React%20Query.md)).
- **Use `useTransition` or `useDeferredValue`** to keep the UI responsive while a param change renders.
- **Keep the URL canonical**: sort keys, drop defaults and empties, so one view has one URL (better caching and analytics).
- **Consider nuqs** for type-safe parsers, throttling and shared server and client definitions once the pattern repeats.

### Things to avoid
- Treating `searchParams` as typed or trusted data.
- Using the URL for high-frequency state (scroll position, drag coordinates, per-keystroke text without debounce); browsers also rate-limit `history` updates.
- Putting secrets or PII in the URL; it lands in logs, history, analytics and Referer headers.
- Very long URLs (keep well under roughly 2,000 characters); store large selections server-side and reference an id.
- Encoding client-only UI details (open accordion, hover) in the query string.
- Mutating `useSearchParams()` results; they are read-only.
- Building query strings by string concatenation instead of `URLSearchParams` (escaping bugs).
- Mixing path and query for the same concept (`/p/42` and `?id=42`).
- Forgetting to preserve unrelated params (UTM, `ref`) when updating one key.

### Checklist
- [ ] Every shareable view state (filter, sort, page, tab) is in the URL.
- [ ] A zod schema parses params with defaults; no raw `Number()` or casts.
- [ ] Server pages `await searchParams`; no sync access.
- [ ] Every `useSearchParams` consumer sits under `<Suspense>`.
- [ ] Text inputs are debounced and use `replace`; navigations use `push`.
- [ ] Changing a filter resets `page`.
- [ ] Defaults are omitted from the URL; no secrets or PII in it.
- [ ] Back and Forward restore the expected view (manually tested).
