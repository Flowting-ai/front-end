## 30. Server State (React Query)

> Server state is a cached, shared, possibly stale copy of data you do not own. Let a library built for it handle fetching, caching, background sync and deduplication instead of `useEffect` and `useState`.

### Definition
**Server state** is data that lives on a server and is only borrowed by the client: lists, profiles, search results. It is asynchronous, shared with other users, and can become out of date without the UI knowing. **Client state** (a modal open flag, a draft input) is the opposite: owned by the browser and synchronous.

**TanStack Query** (`@tanstack/react-query`, v5) is a cache keyed by **query key**. Components subscribe to a key with `useQuery`; the library fetches, caches, dedupes concurrent requests, refetches in the background when data is stale, retries, and garbage-collects unused entries. Writes go through `useMutation`, which then invalidates or updates the affected keys.

### Key properties

**1. Same query key, one request**
- Every component that calls `useQuery` with the same key shares one cache entry and one in-flight request. Ten consumers cause one network call.
- Keys are hashed deterministically, so `["todos", { status: "open" }]` and `["todos", { status: "open" }]` match even with different object identity.
- Everything the `queryFn` depends on (ids, filters, page) must be in the key, so a change in input is a new entry rather than a stale one.

**2. Freshness is `staleTime`, retention is `gcTime`**
- `staleTime` (default `0`) is how long data counts as fresh. While fresh, mounting a component reads the cache with no request.
- `gcTime` (default 5 minutes; renamed from `cacheTime` in v5) is how long an entry with no observers stays in memory.
- A `staleTime` of `0` is why people see "too many refetches"; set a deliberate default for the app (this repo uses 30 seconds).

**3. Background sync**
- Stale data is shown immediately and refetched on window focus, reconnect and mount (stale-while-revalidate). The UI never blocks on a refresh it already has data for.
- `isPending` means no data yet; `isFetching` means a request is in flight (including background); `isError` means it failed. In v5 `isLoading` is `isFetching && isPending`.

**4. Mutations invalidate; they do not edit state by hand**
- After a write, call `queryClient.invalidateQueries({ queryKey })` so every subscriber refetches. For instant feedback use an optimistic update (principle 33).

**5. The cache must be per request on the server**
- A module-level `QueryClient` on the server would be shared by every user and leak data between requests. Create one per request on the server and one singleton in the browser.

**6. The server can prefetch, the client can hydrate**
- A Server Component prefetches into a fresh `QueryClient`, serialises it with `dehydrate`, and a `<HydrationBoundary>` seeds the client cache. The client component calling `useQuery` with the same key renders data on first paint with no waterfall and no loading state.

### When to use what
| Need | Use |
|---|---|
| Data read once on the server, never refreshed on the client | `await fetch` in a Server Component (principle 6) |
| Data that is interactive on the client: refetch, polling, pagination, mutations, shared by many components | TanStack Query |
| Same data first rendered on the server, then kept fresh on the client | Server prefetch plus `HydrationBoundary` |
| A value derived from URL filters, sort, page | Put them in the URL (principle 34) and in the query key |
| UI-only state (open, selected tab, draft) | `useState` / `useReducer` (principle 27) or a store (principle 28) |
| Same fetch deduped inside one server render | `React.cache` |
| Real-time stream | WebSocket / SSE (principle 36); push events into the cache with `setQueryData` or `invalidateQueries` |
| Mutation with a form and redirect | Server Action, then `revalidatePath` / `revalidateTag` for server-rendered data |

### Practical patterns in Next.js (TypeScript)

**Per-request QueryClient (server) and singleton (browser)**
```ts
// lib/query/get-query-client.ts
import {
  QueryClient,
  defaultShouldDehydrateQuery,
  isServer,
} from "@tanstack/react-query";

function makeQueryClient() {
  return new QueryClient({
    defaultOptions: {
      queries: {
        // Above 0 so the client does not refetch immediately after hydration.
        staleTime: 30_000,
      },
      dehydrate: {
        // Also dehydrate in-flight queries so they can stream to the client.
        shouldDehydrateQuery: (query) =>
          defaultShouldDehydrateQuery(query) || query.state.status === "pending",
      },
    },
  });
}

let browserQueryClient: QueryClient | undefined;

export function getQueryClient(): QueryClient {
  if (isServer) {
    // Always a new client on the server: never share between requests.
    return makeQueryClient();
  }
  // Reuse in the browser, so React suspending during the initial render
  // does not throw the cache away.
  browserQueryClient ??= makeQueryClient();
  return browserQueryClient;
}
```
Use `getQueryClient()` on the server for prefetching (it is a new instance per call, so wrap it in `React.cache` if several Server Components in one request must share it).

**Provider in a small client file**
```tsx
// components/QueryProvider/index.tsx
"use client";
import { QueryClientProvider } from "@tanstack/react-query";
import type { ReactNode } from "react";
import { getQueryClient } from "@/lib/query/get-query-client";

export function QueryProvider({ children }: { children: ReactNode }) {
  // Do not use useState for the client if the line above might suspend;
  // getQueryClient() already returns a stable browser singleton.
  const queryClient = getQueryClient();
  return <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>;
}
```
`useState(() => new QueryClient())` is also valid and is what the TanStack docs show for a client-only setup. The singleton form is needed when the provider can suspend, because React discards state of a component that suspends before it first commits.

**Query key factory plus `queryOptions`**
```ts
// lib/queries/todos.ts
import { queryOptions } from "@tanstack/react-query";

export type Todo = { id: string; title: string; done: boolean };
export type TodoFilters = { status: "open" | "done" | "all"; page: number };

export const todoKeys = {
  all: ["todos"] as const,
  lists: () => [...todoKeys.all, "list"] as const,
  list: (filters: TodoFilters) => [...todoKeys.lists(), filters] as const,
  details: () => [...todoKeys.all, "detail"] as const,
  detail: (id: string) => [...todoKeys.details(), id] as const,
};

async function fetchTodos(filters: TodoFilters, signal: AbortSignal): Promise<Todo[]> {
  const params = new URLSearchParams({ status: filters.status, page: String(filters.page) });
  const res = await fetch(`/api/todos?${params}`, { signal });
  if (!res.ok) throw new Error(`Failed to load todos (${res.status})`);
  return res.json();
}

export const todosQuery = (filters: TodoFilters) =>
  queryOptions({
    queryKey: todoKeys.list(filters),
    queryFn: ({ signal }) => fetchTodos(filters, signal),
    staleTime: 60_000,
  });
```
`queryOptions` bundles key and function so the same definition is shared by `useQuery`, `prefetchQuery`, `ensureQueryData` and `getQueryData`, and keeps types inferred end to end. Hierarchical keys let `invalidateQueries({ queryKey: todoKeys.lists() })` refresh every list in one call without touching details.

**Prefetch in a Server Component, hydrate on the client**
```tsx
// app/todos/page.tsx (Server Component)
import { HydrationBoundary, dehydrate } from "@tanstack/react-query";
import { getQueryClient } from "@/lib/query/get-query-client";
import { todosQuery } from "@/lib/queries/todos";
import { TodoList } from "./todo-list";

export default async function Page() {
  const queryClient = getQueryClient();
  const filters = { status: "open", page: 1 } as const;

  // Do not await to stream; await to block render until data is ready.
  void queryClient.prefetchQuery(todosQuery(filters));

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <TodoList filters={filters} />
    </HydrationBoundary>
  );
}
```
```tsx
// app/todos/todo-list.tsx
"use client";
import { useQuery } from "@tanstack/react-query";
import { todosQuery, type TodoFilters } from "@/lib/queries/todos";

export function TodoList({ filters }: { filters: TodoFilters }) {
  const { data, isPending, isError, error } = useQuery(todosQuery(filters));
  if (isPending) return <p className="text-sm text-muted-foreground">Loading...</p>;
  if (isError) return <p role="alert" className="text-sm text-red-600">{error.message}</p>;
  return (
    <ul className="space-y-1">
      {data.map((t) => (
        <li key={t.id}>{t.title}</li>
      ))}
    </ul>
  );
}
```
Because `shouldDehydrateQuery` includes pending queries (see the client factory), the un-awaited prefetch streams to the browser and the client picks up the in-flight promise. If you `await` the prefetch instead, the page waits for the data and renders it in the initial HTML. Only prefetch what the first paint needs. Fetch calls inside a server `queryFn` must forward auth (cookies or headers) explicitly; the server has no browser session.

**Mutation with invalidation**
```tsx
"use client";
import { useMutation, useQueryClient } from "@tanstack/react-query";
import { todoKeys, type Todo } from "@/lib/queries/todos";

export function useToggleTodo() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (todo: Todo) => {
      const res = await fetch(`/api/todos/${todo.id}`, {
        method: "PATCH",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ done: !todo.done }),
      });
      if (!res.ok) throw new Error("Update failed");
      return (await res.json()) as Todo;
    },
    onSuccess: (updated) => {
      queryClient.setQueryData(todoKeys.detail(updated.id), updated);
      return queryClient.invalidateQueries({ queryKey: todoKeys.lists() });
    },
  });
}
```
Returning the `invalidateQueries` promise from `onSuccess` keeps the mutation in the pending state until the refetch completes. For optimistic rollback see principle 33.

**Suspense variant and infinite lists (v5)**
```tsx
const { data } = useSuspenseQuery(todosQuery(filters)); // data is never undefined

const list = useInfiniteQuery({
  queryKey: ["feed"],
  queryFn: ({ pageParam, signal }) => fetchFeed(pageParam, signal),
  initialPageParam: 0, // required in v5
  getNextPageParam: (last) => last.nextCursor ?? undefined,
});
```
`useSuspenseQuery` needs a `<Suspense>` boundary above it and an error boundary (principle 19) for failures. In v5 `useQuery` takes a single options object only; the old positional overloads are gone, and `onSuccess`, `onError` and `onSettled` callbacks on `useQuery` were removed (use the result, an effect, or the mutation callbacks).

### Rules of thumb
1. **Server state goes in React Query, not in `useState` + `useEffect`**, and not copied into a client store.
2. **Put every input of the `queryFn` in the key.** If the function reads it, the key contains it.
3. **Build keys and options with a factory and `queryOptions`**, never retype key arrays inline.
4. **Set a default `staleTime` above 0**, then tune per query: seconds for volatile data, minutes for reference data.
5. **Create the `QueryClient` per request on the server**, once per browser.
6. **Prefetch on the server only what the first paint needs**; leave the rest to client fetching.
7. **Invalidate by key prefix after mutations**; do not hand-edit lists unless you are doing an optimistic update.
8. **Pass `signal` to `fetch`** so unmounted or superseded queries cancel their requests.
9. **Throw on non-2xx** in the `queryFn`; React Query only treats a thrown error or rejected promise as failure.
10. **Keep the query layer in `lib/queries/`**, with components consuming small hooks, not raw keys.

### Anti-patterns
- `useEffect(() => { fetch(...).then(setData) }, [])`: no cache, no dedupe, no cancellation, race conditions on fast navigation.
- A module-level `const queryClient = new QueryClient()` imported by server code, shared between users.
- Query keys missing a dependency (`["todos"]` while the function reads a `status` filter), so changing the filter shows the wrong cached data.
- Copying query data into `useState` to "edit" it; the copy never updates when the cache does.
- `staleTime: 0` with prefetch, so the client refetches immediately after hydration and wastes the server work.
- Fetching the same data in a Server Component and again with an unrelated key in a client component.
- Awaiting many `prefetchQuery` calls in sequence, creating a server waterfall; start them together or use `Promise.all`.
- Passing a `QueryClient` instance or class instances across the server/client boundary as props; only the dehydrated plain-JSON state is serialisable.
- Calling `queryClient.invalidateQueries()` with no key after every mutation, refetching the whole app.
- Putting tokens in query keys, since keys are visible in devtools and hashed into the cache.

### Industry best practices
- **Use `queryOptions` as the single definition** of a query and share it between server prefetch and client hooks for type safety and key consistency.
- **Use hierarchical key factories** (`all`, `lists`, `list(filters)`, `details`, `detail(id)`) so invalidation granularity is a prefix choice.
- **Choose `staleTime` by data volatility** and set the app default in the `QueryClient`; the library default of `0` is conservative, not a recommendation.
- **Keep the browser client a singleton and the server client per request**, using `isServer` from `@tanstack/react-query`.
- **Dehydrate pending queries** with `shouldDehydrateQuery` to stream prefetches without blocking the shell.
- **Prefer `select`** to derive or narrow data per component; it re-renders only when the selected result changes (structural sharing keeps references stable).
- **Cancel with `signal`** and use `enabled` for dependent queries instead of conditional hooks.
- **Handle errors with boundaries**: `throwOnError` or `useSuspenseQuery` plus an error boundary for page-level failures, inline state for local ones. Set `retry` deliberately; never retry 4xx.
- **Use `placeholderData: keepPreviousData`** for paginated and filtered lists so the UI does not flash empty between keys.
- **Drive keys from the URL** for filters, sort and page (principle 34), so links, refresh and back/forward work.
- **Use Server Actions with `revalidatePath` / `revalidateTag`** for server-rendered data, and React Query invalidation for client-cached data; know which cache each write must clear.
- **Install `@tanstack/eslint-plugin-query`** to catch missing key dependencies and unstable client creation, and use the devtools in development only.

### Things to avoid
- Treating React Query as a global client-state store; use it for server data only.
- Relying on `cacheTime`, `isLoading` semantics, `keepPreviousData` option or callbacks on `useQuery` from v4; they changed or were removed in v5.
- Prefetching on the server and rendering data through props to the same client component at the same time, which creates two sources of truth.
- Setting `gcTime: 0` or `staleTime: Infinity` everywhere without a reason.
- Hydrating user-specific data into a cache that is shared across users (for example a global `unstable_cache` result keyed without the user).
- Mutating cached objects in place; always return new objects from `setQueryData` updaters.
- Inline `queryFn` closures that capture values not present in the key.
- Skipping an error state; `data` is `undefined` while `isPending` or `isError`.
- Polling with `setInterval` when `refetchInterval` (or a push channel, principle 36) exists.

### Checklist
- [ ] Every server-derived value is read through a query hook, not `useEffect` + `useState`.
- [ ] Keys come from a factory and include every input of the `queryFn`.
- [ ] Queries are defined with `queryOptions` and reused for prefetch and hooks.
- [ ] The app has a default `staleTime`; per-query overrides are justified.
- [ ] Server code creates a fresh `QueryClient` per request; the browser uses one.
- [ ] Prefetched pages wrap the client tree in `HydrationBoundary` with the same keys.
- [ ] Mutations invalidate by key prefix (or update the cache optimistically with rollback).
- [ ] `fetch` receives `signal`, and non-2xx responses throw.
- [ ] Loading, error and empty states are all rendered.
- [ ] Auth data is not placed in query keys; server prefetches forward credentials explicitly.

### In this codebase
- `@tanstack/react-query` ^5.101 is installed. `src/components/QueryProvider/index.tsx` creates the client with `useState`, a 30 second default `staleTime` and `retry: 1`, and is mounted from `src/app/layout.tsx`. This is the client-only setup; there is no server prefetch or `HydrationBoundary` yet, so no per-request server client is needed today.
- Adoption is early: only `src/lib/queries/personas.ts` (`usePersonas`) uses `useQuery`. It uses a constant key (`PERSONAS_QUERY_KEY = ["personas"]`) rather than a key factory, and bridges the legacy `PERSONAS_LIST_UPDATED_EVENT` window event into `invalidateQueries`. Other data (teams, AI models, most lists) still comes from module-level caches in `src/lib/api/*.ts` with their own 30 second TTLs and in-flight dedupe, which React Query would replace.
- No `useMutation`, `useInfiniteQuery`, `useSuspenseQuery` or `queryOptions` usage exists yet. Next steps when migrating a list: add a key factory beside the hook, switch to `queryOptions`, and replace the `useEffect` fetch in the consumer. Introduce the `get-query-client` pattern only when the first Server Component prefetch is added.
- The `retry: false` override in `usePersonas` preserves old no-retry behaviour; revisit it once the migration settles so the app-wide default applies.
