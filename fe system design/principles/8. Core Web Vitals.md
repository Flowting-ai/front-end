## 8. Core Web Vitals

> LCP, CLS and INP are the frontend's response time, stability and latency. Targets: LCP < 2.5 s, CLS < 0.1, INP < 200 ms. Google uses them in search ranking.

### Definition
Core Web Vitals (CWV) are Google's three user-centred metrics for page experience. Each maps to one question the user is silently asking:

| Metric | Question | Measures | "Good" | "Needs improvement" | "Poor" |
|---|---|---|---|---|---|
| **LCP** Largest Contentful Paint | Did it load? (response time) | Time until the largest visible element (hero image, heading, text block) is rendered | ≤ 2.5 s | 2.5 to 4 s | > 4 s |
| **CLS** Cumulative Layout Shift | Is it stable? | Sum of unexpected layout shifts during the page's life | ≤ 0.1 | 0.1 to 0.25 | > 0.25 |
| **INP** Interaction to Next Paint | Does it respond? (latency) | Latency from a user interaction (click, tap, key) to the next frame painted; reports about the worst interaction in the visit | ≤ 200 ms | 200 to 500 ms | > 500 ms |

Notes on the targets:
- **CLS is unitless.** It is a score (impact fraction × distance fraction), not seconds. The target is `< 0.1`, not `0.1 s`.
- A page "passes" a metric when the **75th percentile** of real page loads is in the "good" range, evaluated separately for mobile and desktop.
- **INP replaced FID** (First Input Delay) as a Core Web Vital in March 2024. FID only measured the delay of the first interaction; INP measures every interaction across the visit. Next.js still lists FID in its `useReportWebVitals` docs; treat INP as the target.
- Related, non-core diagnostics: **TTFB** (server response), **FCP** (first paint), **TBT** (lab proxy for INP). They explain CWV failures but are not themselves the targets.

### Ranking: what is and is not true
- CWV are part of Google's page experience signals and are used in search ranking, based on **real-user field data** (the Chrome UX Report, a rolling 28-day window), not on a lab run.
- It is one signal among many. Relevance and content quality dominate; a fast irrelevant page will not outrank a relevant slow one. Treat CWV as a tie-breaker and, more importantly, as a conversion and retention driver.
- Ranking only matters for pages Google can crawl. **Authenticated product screens (chat, agents, settings) are not indexed**, so for them CWV is a user-experience target, not an SEO one. Public pages (landing, pricing, docs, share links, invite pages) are where the ranking angle applies.

### Key properties

**1. Measured on real users, at the 75th percentile**
- Lab tools (Lighthouse, DevTools) are for diagnosis and regression checks. Field data (RUM, CrUX, PageSpeed Insights "field" section) is the truth.
- Slow devices and networks drive the p75. Test with CPU and network throttling, not on a developer machine.

**2. Each metric has a small set of root causes**
Most failures come from a handful of patterns, listed below per metric.

**3. The rendering principles directly set the budget**
SSG/ISR and streaming improve LCP. Server Components shrink JS, which improves INP. Reserved space and fonts fix CLS.

### LCP: Largest Contentful Paint (loading)
The time is the sum of four parts: **TTFB**, **resource load delay** (time before the browser starts fetching the LCP resource), **resource load duration**, and **element render delay**. Find which part dominates before optimising.

What to do in Next.js:
- **Get a fast TTFB.** Prefer static or cached rendering (SSG, ISR, `"use cache"`) for public pages; stream the shell instead of blocking on data ([principle 7](7.%20Streaming%20SSR%20and%20Suspense.md)); keep data close to the server.
- **Keep the LCP element in the static shell**, outside any Suspense boundary that waits on slow data.
- **Make the LCP image discoverable immediately** and prioritised:
```tsx
import Image from "next/image";

export function Hero() {
  return (
    <Image
      src="/hero.jpg"
      alt="Product overview"
      width={1200}
      height={630}
      preload              // <link rel="preload"> in the first chunk
      sizes="(min-width: 1024px) 1200px, 100vw"
    />
  );
}
```
  Do not lazy-load the LCP image. Use `loading="lazy"` (the default) only below the fold.
- **Right-size and compress images**: `next/image` serves modern formats (AVIF/WebP) at responsive sizes; always set `sizes`.
- **Fonts**: use `next/font` (self-hosted, preloaded, `display: swap` with a size-adjusted fallback) so text LCP does not wait on a third-party font request.
- **Remove render-blocking work**: minimise CSS and JS before first paint, defer non-critical scripts with `next/script` (`strategy="lazyOnload"` or `afterInteractive`).
- **Do not hide the LCP behind client-only rendering.** Content that appears only after hydration and a `useEffect` fetch pushes LCP out ([principle 6](6.%20React%20Server%20Components.md)).

### CLS: Cumulative Layout Shift (visual stability)
Things moving after the user has started to read or aim at them.

What to do:
- **Always reserve space for media.** `next/image` requires `width`/`height` or `fill` in a sized container, which sets the aspect ratio. For plain `<img>`/`<video>`/iframes, set `width`/`height` or `aspect-ratio`.
- **Skeletons must match the final size** of what replaces them (Suspense fallbacks, loading states, `loading.tsx`). Use min-height containers around async regions.
- **Fonts**: `next/font` generates a metric-adjusted fallback so the swap does not reflow text. Fonts without adjusted fallbacks should be checked manually.
- **Never inject content above existing content** after load (banners, cookie bars, toasts that push the page). Overlay them (fixed/absolute position) or reserve the slot.
- **Animate with `transform` and `opacity`**, not `top`/`left`/`width`/`height`/`margin`, so animations do not cause layout shifts.
- Avoid late-arriving ad/embed/widget slots without reserved dimensions.
- Shifts within 500 ms of a user input (expanding an accordion on click) are excluded; shifts the user did not trigger are counted.

### INP: Interaction to Next Paint (responsiveness)
An interaction has three phases: **input delay** (main thread busy), **processing time** (your handlers), **presentation delay** (rendering and painting the result). Long tasks (> 50 ms) on the main thread are the usual cause.

What to do:
- **Ship less JavaScript**: Server Components ([principle 6](6.%20React%20Server%20Components.md)), `"use client"` only on leaves, no heavy libraries in client bundles.
- **Code-split non-critical UI** so it does not compete during load or interaction:
```tsx
import dynamic from "next/dynamic";

const MarkdownEditor = dynamic(() => import("./MarkdownEditor"), {
  loading: () => <EditorSkeleton />,   // fixed size, avoids CLS
});
```
- **Split hydration with Suspense boundaries** ([principle 7](7.%20Streaming%20SSR%20and%20Suspense.md)) so hydration is many small tasks, not one blocking pass.
- **Keep handlers fast.** Do the minimum synchronously; update the UI first, then do the rest:
```tsx
"use client";
import { useTransition } from "react";

export function Filters({ onFilter }: { onFilter: (q: string) => void }) {
  const [isPending, startTransition] = useTransition();
  return (
    <input
      onChange={(e) => {
        const q = e.target.value;
        startTransition(() => onFilter(q));   // heavy re-render is interruptible
      }}
      aria-busy={isPending}
    />
  );
}
```
- **Use `useDeferredValue` / `useTransition`** for expensive renders (large lists, search-as-you-type), and virtualise long lists.
- **Avoid unnecessary re-renders**: stable props, colocated state, memoisation where profiling shows it matters. The React Compiler (`reactCompiler`) automates much of this.
- **Break up long tasks**: chunk heavy loops, move CPU work to a Web Worker, yield to the main thread (`scheduler.yield()` where available, else `setTimeout`).
- **Defer third-party scripts** (analytics, chat widgets, tag managers) with `next/script`; they are a frequent source of main-thread contention.
- **Give immediate visual feedback** on click (pressed state, spinner) so the next paint is not blocked by the work that follows.

### Measuring
**In the field (Next.js):**
```tsx
// components/WebVitals.tsx
"use client";

import { useReportWebVitals } from "next/web-vitals";

type ReportWebVitalsCallback = Parameters<typeof useReportWebVitals>[0];

const report: ReportWebVitalsCallback = (metric) => {
  // metric: { id, name, value, delta, rating, navigationType, entries }
  navigator.sendBeacon("/api/vitals", JSON.stringify({
    name: metric.name,          // "LCP" | "CLS" | "INP" | "FCP" | "TTFB"
    value: metric.value,
    rating: metric.rating,      // "good" | "needs-improvement" | "poor"
    id: metric.id,
    path: location.pathname,
  }));
};

export function WebVitals() {
  useReportWebVitals(report);   // keep the callback reference stable
  return null;
}
```
Mount `<WebVitals />` once in the root layout. This confines the client boundary to this one tiny component. Send results to the analytics backend, segmented by route, device and connection.

**In the lab:** Lighthouse and Chrome DevTools Performance panel (with 4x CPU and slow-4G throttling), `next build` First Load JS, `@next/bundle-analyzer`.
**Public data:** PageSpeed Insights and Search Console's Core Web Vitals report (CrUX field data for crawlable pages).
**Debug attribution:** the `web-vitals` library's attribution build (which element was the LCP, which element shifted, which handler was slow) turns a number into a fix.

### Performance budgets
Set per route and enforce in CI so regressions fail the build, not production:
- LCP p75 ≤ 2.5 s, CLS p75 ≤ 0.1, INP p75 ≤ 200 ms.
- First Load JS per route under an agreed ceiling.
- No new third-party script without review.

### Rules of thumb
1. **Optimise the metric that is failing**, found from field data, not the one that is easiest.
2. **LCP: shell + preload + right-sized image + fast TTFB.**
3. **CLS: reserve space for everything that arrives later.**
4. **INP: less JS, shorter tasks, instant feedback.**
5. **Test on slow devices.** The p75 user is not on your laptop.
6. **Measure after every change** and watch for regressions per route.
7. **Treat third-party scripts as a cost** that must be justified.

### Anti-patterns
- Lazy-loading (or client-rendering) the hero image or main heading.
- `<img>` without dimensions, or skeletons that differ in height from the content.
- Late-injected banners and toasts that push content down.
- Animating layout properties.
- Whole-page `"use client"` with a large hydration cost.
- Heavy work inside click handlers (parse, sort, filter thousands of rows synchronously).
- Running only Lighthouse on a fast machine and calling it done.
- Loading third-party tags `beforeInteractive` without need.
- Optimising for the lab score while the field p75 stays poor.
- Reading `0.1 s` for CLS: it is a unitless score.

### Checklist
- [ ] Public routes have an explicit target: LCP ≤ 2.5 s, CLS ≤ 0.1, INP ≤ 200 ms at p75 (mobile and desktop).
- [ ] The LCP element is identified per key route, sits in the static shell, and (if an image) uses `preload` and correct `sizes`.
- [ ] Every image, video, embed and async region has reserved dimensions; skeletons match content size.
- [ ] Fonts load through `next/font`; no layout jump on swap.
- [ ] No content is inserted above existing content after load; animations use `transform`/`opacity`.
- [ ] Client JS is minimised (RSC, `"use client"` on leaves, `next/dynamic` for heavy widgets); no long tasks on key interactions.
- [ ] Expensive updates use `useTransition`/`useDeferredValue`; long lists are virtualised.
- [ ] Third-party scripts use `next/script` with a deferred strategy.
- [ ] `useReportWebVitals` reports to the analytics backend; dashboards segment by route and device.
- [ ] CI checks First Load JS / Lighthouse budgets; field p75 reviewed after each release.

- No `useReportWebVitals` or `web-vitals` usage, so there is **no CWV field data today**. First step: add a `WebVitals` component to the root layout and send results to the existing analytics (Mixpanel is already wired in `src/components/Analytics/`) or a vitals endpoint.

- `reactCompiler` is enabled, which helps re-render cost for INP.
