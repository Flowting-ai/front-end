## 3. Static Site Generation (SSG)

> Pre-build every page to HTML at deploy time and serve the files straight from a CDN edge.

### Definition
At build time (`next build`) Next.js renders each route once, runs its data fetching, and writes the resulting HTML (plus RSC payload and JS) to disk. At request time nothing is rendered: the CDN returns a ready file. In the App Router, a route is static by default as long as it does not use request-time APIs (`cookies()`, `headers()`, `searchParams`, `connection()`) or uncached dynamic data.

### Key properties

**1. No server compute and no client fetch on first render**
- The HTML already contains the content, so there is no per-request rendering cost and no client-side data fetch to wait for. TTFB is CDN latency; LCP is usually the best of all strategies.
- Output is the same for every visitor, so it is cacheable everywhere (CDN, browser, shared proxies), scales without extra servers and survives traffic spikes.
- Hydration still runs for Client Components in the page; ship little JS to keep INP and TTI good.
- Build-time data fetching happens once. A slow or failing upstream breaks the build, not the visitor.

**2. Best for low-update content: docs, marketing, blogs**
- Content that changes on a deploy or editorial cadence (landing pages, pricing, docs, changelog, blog posts, legal pages, public templates).
- Public, indexable pages where SEO and link previews matter.
- Not for per-user data, frequently changing data, or anything that must reflect changes immediately.

### When to use
- Every visitor sees the same content.
- Content changes rarely, or only when you redeploy or explicitly revalidate.
- The set of pages is known (or enumerable) at build time.
- You want the cheapest hosting and the best first-load performance and SEO.

### When not to
- Personalized or permission-gated pages: use [SSR](1.%20Server%20Side%20Rendering.md) or [CSR](2.%20Client%20Side%20Rendering.md).
- Data changes every few seconds, or stale content is unacceptable.
- Millions of pages where build time becomes impractical (generate the popular ones, render the rest on demand, see below).
- Content only editable through a UI that must publish instantly, without a redeploy (use ISR or on-demand revalidation).

### How in Next.js + TypeScript

**Default static route:** a Server Component with no request-time API is prerendered at build.

```tsx
// app/(marketing)/pricing/page.tsx
import type { Metadata } from "next";

export const metadata: Metadata = {
  title: "Pricing",
  description: "Plans and pricing",
};

export default async function PricingPage() {
  const plans = await getPlans();          // runs at build time, typed
  return <PlanTable plans={plans} />;
}
```

**Dynamic segments with `generateStaticParams`:** enumerate the pages to build.

```tsx
// app/blog/[slug]/page.tsx
type Params = { slug: string };

export async function generateStaticParams(): Promise<Params[]> {
  const posts = await getAllPosts();
  return posts.map((p) => ({ slug: p.slug }));
}

export const dynamicParams = false;   // unknown slugs -> 404 (default true: render on demand)

export default async function Post({ params }: { params: Promise<Params> }) {
  const { slug } = await params;       // params is a Promise in Next 15+
  const post = await getPost(slug);
  return <Article post={post} />;
}

export async function generateMetadata({ params }: { params: Promise<Params> }) {
  const { slug } = await params;
  const post = await getPost(slug);
  return { title: post.title, description: post.summary };
}
```

- Dedupe the same fetch between `generateMetadata` and the page with React `cache()` or the shared `fetch` memoization.
- `dynamicParams = true` (default) renders paths not returned by `generateStaticParams` on first request, then caches them. `false` returns 404 for those.

**Keep static pages fresh without a redeploy (ISR):**

```ts
export const revalidate = 3600;          // regenerate at most once per hour, on request
```

```ts
// After a CMS publish, in a route handler or server action
import { revalidatePath, revalidateTag } from "next/cache";
revalidateTag("posts");                   // or revalidatePath("/blog/my-post")
```

**Force or verify static behavior**
- `export const dynamic = "force-static"` forces static rendering and makes `cookies()`/`headers()` return empty values. Use it deliberately, since it hides personalization bugs.
- Check the `next build` route table: `○` static, `●` SSG with params, `ƒ` dynamic. Treat an unexpected `ƒ` on a marketing page as a bug.

**Full static export (no Node server):** `output: "export"` in `next.config.ts` writes plain files to `out/` for any static host or CDN. It disables features that need a server (route handlers that read requests, middleware/proxy, default image optimization, ISR, `dynamicParams` on demand). Use only when you truly have no server.

```ts
// next.config.ts
import type { NextConfig } from "next";
const config: NextConfig = { output: "export", images: { unoptimized: true } };
export default config;
```

**Mixing static and dynamic:** serve a static shell and stream the personal parts (Suspense, partial prerendering with Cache Components), or hydrate user data on the client after load. This keeps the CDN-served first paint while still personalizing.

**TypeScript tips**
- Type the `Params` once and reuse it in `generateStaticParams`, the page and `generateMetadata`.
- Validate CMS or API data at the build boundary (e.g. zod) so a bad payload fails the build rather than shipping broken pages.
- With Cache Components enabled, `generateStaticParams` must return at least one param.

### Tradeoffs
| Gain | Cost |
|---|---|
| Fastest TTFB and LCP; CDN-served | Content is only as fresh as the last build or revalidation |
| No per-request server cost; scales and survives spikes | Build time grows with page count |
| Best SEO and link previews; very reliable | Cannot personalize at build time |
| Simple, cheap hosting | Needs a rebuild or revalidation to publish changes |

### Pitfalls
- Accidentally making a route dynamic by reading `cookies()`/`headers()`/`searchParams`, which silently turns SSG into SSR. Check the build output.
- Calling your own `/api` route handlers from `generateStaticParams`/pages at build time (the server is not running). Call the data layer directly.
- Build-time secrets and environment: values are baked into the output. Never embed secrets in static HTML or client bundles.
- Stale data surprises: set `revalidate` or on-demand revalidation for content that does change.
- Generating huge page sets at build: pre-render the popular subset and let `dynamicParams` handle the long tail.
- Forgetting 404 behavior for unknown params (`dynamicParams`, `notFound()`).
- Time-dependent output (`new Date()`) gets frozen at build time.

### Industry best practices
- **Give hashed static assets immutable caching** (`Cache-Control: public, max-age=31536000, immutable`); Next.js does this for `/_next/static/*` automatically, so do not override it.
- **Purge the CDN on deploy and on revalidation.** Next.js emits `s-maxage=31536000` for static HTML, so a self-managed CDN keeps serving the old copy until it is purged (both the HTML and RSC variants); managed platforms do this for you.
- **Generate `sitemap.ts`, `robots.ts` and canonical URLs** from the same content source as the pages, so SEO files never drift from what is built.
- **Use `opengraph-image` and `twitter-image` file conventions** to generate share previews at build time instead of hand-made images.
- **Emit structured data** (JSON-LD `Article`, `Product`, `BreadcrumbList`) as a typed object in the page, escaping `<` when serialising.
- **Use `next/image` with explicit `width`/`height` or `fill` plus `sizes`**, and `priority` only on the single LCP image.
- **Use `next/font`** so fonts are self-hosted, preloaded and size-adjusted, which removes font-driven layout shift on static pages.
- **Prebuild the high-traffic subset and keep `dynamicParams` on for the long tail**, so build time stays flat as content grows.
- **Cache expensive build-time fetches across pages** (for example, one CMS call shared by many pages through `cache()` or `use cache`) to avoid hammering the upstream and slowing the build.
- **Wire the CMS webhook to `revalidateTag`** (and `updateTag` or `revalidateTag(tag, "max")` as appropriate) so editors can publish without a redeploy.
- **Run `next build` in CI and fail on unexpected `ƒ` routes** for pages that are meant to be static, plus link and metadata checks.
- **Keep per-user features as small client islands** (cart count, sign-in state) that hydrate after the static HTML, rather than making the page dynamic.

### Things to avoid
- Fetching private or rate-limited APIs at build time with credentials that differ from production.
- Reading `new Date()`, `Math.random()` or environment-specific data in a static page and expecting runtime values.
- Setting `output: "export"` and then adding features it does not support (Server Actions, route handlers that read the request, default image optimization, ISR).
- Using `force-static` to silence a dynamic-API error instead of moving the dynamic part into a Suspense-wrapped component.
- Rebuilding the entire site for a one-word content fix when on-demand revalidation is available.
- Shipping a large client bundle on a page that is static and mostly text; the static HTML advantage is lost to hydration cost.
- Using `dynamicParams = false` without a full, up-to-date `generateStaticParams` list, which turns new content into 404s until the next deploy.
- Hard-coding absolute production URLs in static output; read the base URL from configuration so preview deployments work.
- Letting build-time fetch failures be swallowed with a fallback of empty data, which publishes a blank page.

### Checklist
- [ ] Is the content identical for all users and low-churn? If not, reconsider.
- [ ] Route has no request-time APIs; build output shows static (`○`/`●`).
- [ ] `generateStaticParams` typed; `dynamicParams` chosen deliberately.
- [ ] Freshness plan: redeploy, `revalidate`, or on-demand `revalidateTag`/`revalidatePath` from the CMS webhook.
- [ ] Metadata (`generateMetadata`), canonical URLs, sitemap, and OG images set for SEO.
- [ ] Data fetched via the data layer, not own API routes; payload validated.
- [ ] No secrets or per-user data in static output.
- [ ] Client JS on the page kept small; images optimized (`next/image`) and fonts preloaded (`next/font`).
- [ ] Build time acceptable; long-tail pages handled on demand.
