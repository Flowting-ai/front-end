## 2. Client Side Rendering (CSR)

> Ship an HTML shell plus a JS bundle; the browser mounts React and builds the page.

### Definition
The server returns a minimal HTML document (a shell with little or no content). The browser downloads JavaScript, React mounts, data is fetched from the client, and the UI is built in the browser. After that, navigation happens without full page loads.

In the App Router, CSR is not a route-level mode. You get it by marking a component (and its imports) with `"use client"` and fetching data in the browser. Note that Client Components are still prerendered to HTML on the server by default and then hydrated. True client-only rendering requires opting out (see below).

### Key properties

**1. Slow first paint, instant navigation after**
- First load pays for: HTML shell, then JS download, parse and execute, then data fetch, then render. Users see a blank page or skeleton until all of that finishes. LCP and TTI suffer on slow devices and networks.
- After the first load, route changes and interactions are fast: no full document reload, state stays in memory, only data (JSON) crosses the network.
- Mitigate first paint: ship less JS (code splitting, `next/dynamic`, tree shaking), show skeletons from a server-rendered shell, prefetch data and routes.

**2. Great for long-session apps, weak for SEO**
- Fits apps where users stay for a long time and interact heavily: chat, editors, dashboards, canvases, admin consoles behind a login. The one-time load cost is amortized.
- Weak for SEO and link previews: crawlers that do not run JS see only the empty shell or loading state. Content that must be indexed or previewed should be rendered on the server (SSR or static).
- Fine for authenticated pages that are not indexed anyway.

### When to use
- Behind login, no SEO need.
- Highly interactive, stateful UI: live streaming responses, drag and drop, rich editors, realtime updates.
- Browser-only dependencies: `window`, `localStorage`, WebGL, canvas, maps, charting libraries.
- Data that changes constantly on the client and is refetched or subscribed to (polling, SSE, WebSocket).

### When not to
- Public, indexable, or shareable pages (landing, docs, shared chat previews).
- Pages where fast first content on poor networks matters more than later interactivity.
- Content that is the same for everyone: static or cached server rendering is cheaper and faster.

### How in Next.js + TypeScript

**Client Component with a data-fetching library** (Next.js recommends SWR or TanStack Query over hand-written `useEffect` fetching):

```tsx
"use client";

import useSWR from "swr";

type Credits = { remaining: number; resetsAt: string };

const fetcher = async (url: string): Promise<Credits> => {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`Request failed: ${res.status}`);
  return res.json();
};

export function CreditsBadge() {
  const { data, error, isLoading } = useSWR<Credits>("/api/backend/credits", fetcher);
  if (isLoading) return <BadgeSkeleton />;
  if (error || !data) return <BadgeError />;
  return <span>{data.remaining} credits</span>;
}
```

**Skip server rendering for browser-only components**

```tsx
"use client";
import dynamic from "next/dynamic";

const Chart = dynamic(() => import("./Chart"), {
  ssr: false,                       // only allowed inside Client Components
  loading: () => <ChartSkeleton />,
});
```

**Hybrid (recommended default):** Server Component renders the shell and initial data, then a Client Component takes over for interactivity and refreshes.

```tsx
// app/(app)/dashboard/page.tsx  (Server Component)
export default async function Page() {
  const initial = await getDashboard();          // server fetch, typed
  return <DashboardClient initial={initial} />;  // hydrates, then SWR revalidates
}
```

**Guidelines**
- Push `"use client"` to the leaves. Every module imported by a Client Component joins the client bundle.
- Type props and fetchers explicitly (`useSWR<T>`, typed `fetch` wrappers); validate untrusted payloads.
- Avoid hydration mismatches: do not render `Date.now()`, `Math.random()`, or `window`-dependent values during the first render. Read them in `useEffect` or behind `dynamic(..., { ssr: false })`.
- Always render loading, empty and error states; there is no server HTML to fall back on.
- Code split heavy, below-the-fold or rarely used components with `next/dynamic` or `React.lazy` plus `Suspense`.
- Prefetch: `<Link>` prefetches routes in production; preload data on hover or intent where useful.
- Keep secrets out of the client. Call the API through our proxy route handlers (e.g. `/api/backend/...`) rather than embedding tokens.

### Tradeoffs
| Gain | Cost |
|---|---|
| Instant in-app navigation and rich interactivity | Slow first paint; blank or skeleton until JS and data load |
| Low server compute per page view | Larger JS bundle; heavier on low-end devices |
| Natural fit for browser APIs and realtime | Weak SEO and link previews |
| Simple mental model for long sessions | Request waterfalls (JS, then data, then render) and layout shift risk |

### Pitfalls
- Fetch waterfalls: parent fetches, then child fetches. Hoist or parallelize.
- Fetching in `useEffect` without cancellation, caching or dedupe (races, duplicate requests). Use SWR or TanStack Query.
- Bundle bloat from importing server-heavy or large libraries into client modules.
- Hydration errors from non-deterministic render output.
- Treating the whole app as client-only when most pages could be server-rendered.
- Putting `"use client"` at the top of a page just to use one hook; extract that piece instead.
- Layout shift (CLS) when content pops in without reserved space.

### Industry best practices
- **Set a JS budget per route** (a common target is under about 170 KB compressed for the critical path) and enforce it in CI with `@next/bundle-analyzer` or `next experimental-analyze` output review.
- **Use stale-while-revalidate caching on the client** (SWR or TanStack Query) with sensible `staleTime`, request dedupe and background refetch instead of per-component `useEffect` calls.
- **Use optimistic updates with rollback** (`useOptimistic` in React 19, or the query library's `onMutate`) so interactions feel instant on slow networks.
- **Use `useTransition` and `useDeferredValue`** to keep typing and clicks responsive while expensive client renders run in the background.
- **Virtualise long lists** (`@tanstack/react-virtual`) and paginate or infinite-scroll large datasets instead of mounting thousands of nodes.
- **Move heavy computation off the main thread** with Web Workers (parsing, diffing, search indexing) to protect INP.
- **Reserve layout space** with skeletons that match final dimensions, `aspect-ratio` and fixed-height containers to protect CLS.
- **Wrap client subtrees in error boundaries** (`error.tsx` per segment) and report errors with a client monitoring tool, since client failures are invisible to server logs.
- **Handle offline and flaky networks**: retry with backoff, show stale data with an indicator, and surface failed mutations for retry.
- **Persist only non-sensitive UI state** (filters, drafts, layout) in `localStorage` or IndexedDB, and read it after mount to avoid hydration mismatches.
- **Prefetch on intent** (hover, focus, viewport) with `<Link>` and `router.prefetch`, and preload the next likely chunk for heavy routes.
- **Measure on real devices** with field RUM (`useReportWebVitals`) and a throttled mid-range Android profile, not only on a developer laptop.

### Things to avoid
- Storing auth tokens in `localStorage`, where any XSS can read them; prefer `HttpOnly` cookies set by the server.
- Putting server state (API data) into global client stores such as Redux or Zustand and hand-syncing it; use a query cache.
- Fetching in `useEffect` without an abort signal or ignore flag, which causes race conditions on fast navigation.
- Importing a whole library for one function (`lodash`, full icon packs, `moment`); use per-method imports or lighter alternatives.
- Rendering unbounded lists, or re-rendering large trees on every keystroke without transitions or memoised children.
- Using `dynamic(..., { ssr: false })` for content that needs SEO or is above the fold; it delays LCP.
- Long tasks over 50 ms on the main thread during load, such as large JSON parsing or synchronous layout loops.
- Polling at short intervals when SSE or WebSocket would do, or polling in background tabs without pausing.
- Showing a full-page spinner for the whole app instead of progressive skeletons per region.
- Relying on client-only validation; always re-validate on the server.

### Checklist
- [ ] Is CSR justified (behind login, interactive, browser-only)? If it needs SEO, use SSR or static.
- [ ] `"use client"` limited to leaf components; page and layout stay Server Components where possible.
- [ ] Data fetched via SWR or TanStack Query with typed responses.
- [ ] Loading, empty and error states implemented; space reserved to avoid CLS.
- [ ] Heavy components code-split; bundle size checked.
- [ ] No hydration mismatches; browser-only values read after mount.
- [ ] No secrets in client code; API calls go through the proxy routes.
- [ ] First-load LCP and INP measured on a throttled device and network.
