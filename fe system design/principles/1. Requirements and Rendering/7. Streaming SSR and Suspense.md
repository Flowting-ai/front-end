## 7. Streaming SSR & Suspense

> Flush the HTML shell immediately and stream sections in as their data resolves. Each `<Suspense>` boundary is a streamable chunk. Slow data never blocks fast content.

### Definition
In classic SSR the server builds the whole HTML document before sending a byte, so one slow query makes the entire page slow (TTFB equals the slowest dependency). **Streaming SSR** uses chunked transfer encoding to send the page in pieces. The server first sends the **static shell** (layouts, navigation, headings and the `<Suspense>` fallbacks). As each async Server Component resolves, React streams its finished HTML, and the browser swaps it in place of the fallback.

React cuts the output along `<Suspense>` boundaries, and Next.js App Router wires this up with no extra configuration.

### How the page is delivered
Two streams work together on the initial load:

1. **The HTML stream.** The shell goes out first. When a suspended component resolves, React sends its HTML plus a small inline `<script>` that swaps the fallback node for the real content. The swap runs without waiting for the page's JS bundle or for hydration. This is what the user sees: the page painting section by section.
2. **The component payload.** The serialised RSC tree (see [principle 6](6.%20React%20Server%20Components.md)) arrives embedded in the same stream so React can hydrate. On client-side navigation only the payload is fetched (`rsc: 1` header) and no HTML is sent.

**The static shell** is everything that renders before any async work resolves. With Cache Components it can be prerendered at build time and served from the edge. Everything inside a boundary that suspends is the **dynamic hole** that streams.

### Key properties

**1. Each `<Suspense>` boundary is an independent streaming point**
- Sibling boundaries resolve and stream in whatever order their data arrives. They do not block each other.
- If revenue resolves in 200 ms, orders in 1 s and recommendations in 3 s, the user sees each section appear as soon as it is ready.

**2. Slow data never blocks fast content**
- Anything outside a boundary (headings, nav, hero, the LCP element) paints immediately.
- Slow work is isolated behind its own boundary, so it delays only its own section.

**3. Selective hydration**
- Each boundary is also a hydration unit. React hydrates streamed sections independently and prioritises the one the user is interacting with.
- Without boundaries, hydration is one blocking pass. With them, it splits into small tasks that yield to the browser, which helps INP.

**4. Early resource discovery**
- The first chunk already contains `<link>` and `<script>` tags, so the browser fetches CSS, JS and fonts while the server is still working on data.

### The two tools

| | `loading.tsx` | `<Suspense>` |
|---|---|---|
| Scope | Whole route segment (wraps `page` and below) | Any component |
| Setup | Drop in a file next to `page.tsx` | Wrap explicitly |
| Navigation | Fallback is prefetched, so it shows instantly | Not prefetched by default |
| Best for | Pages where nothing meaningful renders without data | Most pages: granular control |

Prefer explicit `<Suspense>` close to the slow data access. A high `loading.tsx` is a valid boundary, but it turns the whole page into one skeleton instead of streaming it in parts. If dynamic work is found and no boundary exists above it, the build fails with a blocking route error.

### Practical patterns in Next.js (TypeScript)

**Sibling boundaries (parallel streaming)**
```tsx
// app/(app)/dashboard/page.tsx   Server Component
import { Suspense } from "react";
import { Revenue } from "./revenue";
import { RecentOrders } from "./recent-orders";
import { Recommendations } from "./recommendations";
import { RevenueSkeleton, OrdersSkeleton, RecsSkeleton } from "./skeletons";

export default function DashboardPage() {
  return (
    <div>
      <h1>Dashboard</h1>                                  {/* shell: paints at once, good for LCP */}
      <div className="grid grid-cols-2 gap-4">
        <Suspense fallback={<RevenueSkeleton />}><Revenue /></Suspense>
        <Suspense fallback={<OrdersSkeleton />}><RecentOrders /></Suspense>
      </div>
      <Suspense fallback={<RecsSkeleton />}><Recommendations /></Suspense>
    </div>
  );
}
```
```tsx
// app/(app)/dashboard/revenue.tsx   async Server Component: the data fetch lives here
export async function Revenue() {
  const revenue = await getRevenue();     // slow? only this section waits
  return <RevenueCard data={revenue} />;
}
```
Put the `await` in the component that needs the data. Awaiting at the top of `page.tsx` moves the whole page behind that await and defeats streaming.

**Nested boundaries (progressive detail)**
```tsx
<Suspense fallback={<DetailsSkeleton />}>
  <ProductDetails id={id} />
  <Suspense fallback={<ReviewsSkeleton />}>
    <Reviews productId={id} />            {/* streams after the details */}
  </Suspense>
</Suspense>
```

**Push dynamic access down**
`params`, `searchParams`, `cookies()`, `headers()` and fetches are all dynamic. If a page or layout `await`s one at the top, everything below becomes dynamic and cannot be part of the static shell. Pass the promise down instead and resolve it inside a boundary:
```tsx
type Props = { params: Promise<{ category: string }> };

export default function ShopPage({ params }: Props) {   // note: not async
  return (
    <>
      <Hero />                                            {/* static shell */}
      <Suspense fallback={<GridSkeleton />}>
        {params.then(({ category }) => <ProductGrid category={category} />)}
      </Suspense>
    </>
  );
}
```

**Start early, await late; parallelise independent work**
```tsx
export default async function Page() {
  const statsPromise = getStats();        // starts now
  const feedPromise = getFeed();          // starts now, in parallel
  const stats = await statsPromise;       // only what the shell needs
  return (
    <>
      <Stats data={stats} />
      <Suspense fallback={<FeedSkeleton />}>
        <Feed dataPromise={feedPromise} /> {/* passes the unresolved promise */}
      </Suspense>
    </>
  );
}
```

**Stream data into a Client Component with `use()`**
```tsx
// Server: start the fetch, do not await
<Suspense fallback={<ChartSkeleton />}>
  <StatsChart dataPromise={getStats()} />
</Suspense>
```
```tsx
// components/StatsChart.tsx
"use client";
import { use } from "react";

type Stats = { revenue: number; orders: number };

export function StatsChart({ dataPromise }: { dataPromise: Promise<Stats> }) {
  const stats = use(dataPromise);         // suspends until resolved
  return <div>{/* chart */}</div>;
}
```
The fetch stays on the server, the fallback is sent with the shell, and the chart streams in when the promise resolves. A promise created in a Client Component on every render is not stable; create it in a Server Component or a cache.

**Dedupe shared data**
When several components in different boundaries need the same data, wrap the fetch in `React.cache` (or share the promise through context) so it runs once per request.

**Streaming outside React: Route Handlers**
For SSE, chat tokens or large exports, return a `ReadableStream` from `route.ts`:
```ts
export async function GET() {
  const encoder = new TextEncoder();
  const stream = new ReadableStream<Uint8Array>({
    async start(controller) {
      for (const chunk of await produce()) controller.enqueue(encoder.encode(chunk));
      controller.close();
    },
  });
  return new Response(stream, { headers: { "Content-Type": "text/plain; charset=utf-8" } });
}
```
This is a different layer (a raw HTTP stream, not Suspense) but the same idea: send what is ready now.

### Where to put boundaries
- **Around data-dependent sections that are slower or less important than the rest**: feeds, analytics, recommendations, comments, activity.
- **Around independent sections separately.** One shared boundary makes them wait for the slowest.
- **Not around the LCP element** or critical above-the-fold content. Keep it outside, or in the shell.
- **Not at too fine a grain.** A boundary per list row creates popcorn loading and many tiny swaps. Boundary per meaningful region (card, panel, list).
- **Close to the dynamic access**, not at the root.

### Streaming and Web Vitals

| Metric | Effect and rule |
|---|---|
| TTFB / FCP | Drop to the time to render layouts and fallbacks; decoupled from data time |
| LCP | Keep the LCP element outside slow boundaries; use `preload` on `next/image` for LCP images |
| CLS | Skeletons must match the final dimensions; reserve space with fixed or min-height containers |
| INP | Boundaries split hydration into smaller tasks, keeping the main thread responsive |

### Design the fallback
- Match the final layout: same height, width and grid, so the swap does not shift anything.
- Use skeletons that reflect structure, not a lone spinner, for content areas.
- Keep fallbacks light and server-renderable. They are part of the shell.
- Use the design system's skeleton primitives so loading states look the same everywhere.

### The HTTP contract (important limits)
Once streaming starts, the status code and headers have already been sent.
- Status is `200`. A `notFound()` that fires mid-stream cannot become a 404; Next.js adds `<meta name="robots" content="noindex">` instead. A mid-stream `redirect()` becomes a client-side redirect.
- To get a real `404` or HTTP redirect, call `notFound()` / `redirect()` **before** any slow `await` or `<Suspense>` boundary (for example after a fast existence check).
- Headers and cookies cannot be set after the shell is flushed.
- **Errors mid-stream:** the nearest `error.tsx` boundary replaces only the failed section; the rest of the page stays. Add `error.tsx` where you add boundaries so a failing section degrades gracefully.
- **Infrastructure:** proxies, CDNs and compression can buffer responses and hide streaming. Check that the deploy path (reverse proxy, API gateway) passes chunks through, and do not assume it works from `next dev` alone.

### Instant client navigation
Suspense alone does not guarantee instant client-side navigations. `loading.tsx` fallbacks are prefetched, but for routes that must feel instant, follow the Next.js instant navigation guide (`unstable_instant` export, an experimental API in this version; read `node_modules/next/dist/docs/01-app/02-guides/instant-navigation.mdx` first).

### Rules of thumb
1. **Ship the shell first.** Anything not needing data renders outside any boundary.
2. **One boundary per independent slow region.** Siblings, not a shared wrapper.
3. **Await in the leaf.** Fetch inside the component that needs the data, or pass the promise down.
4. **Start fetches early and in parallel.** Create promises up front; await late.
5. **Keep LCP out of boundaries.**
6. **Skeletons match the content's size.**
7. **Pair every boundary with an error path** (`error.tsx`).
8. **Decide status codes before streaming starts.**
9. **Verify the stream** in the browser Network tab (a single document response that keeps receiving data) and with `curl -N`, not just visually.

### Anti-patterns
- Awaiting everything at the top of `page.tsx` or `layout.tsx` and wrapping nothing in Suspense. No streaming happens.
- One page-wide `loading.tsx` where several independent sections could stream separately.
- A single boundary around unrelated sections, so a fast one waits for a slow one.
- Sequential `await`s of independent data inside one component (a waterfall). Use `Promise.all` or separate boundaries.
- Putting the hero, title or other LCP content inside a Suspense boundary that depends on slow data.
- Skeletons of a different size than the content, causing layout shift.
- A boundary per list item, producing flicker.
- Using `Suspense` with `useEffect` data fetching. Suspense only works with Suspense-compatible sources (RSC async components, `use()`, libraries that support it), not effects.
- Calling `notFound()` or `redirect()` after a boundary and expecting a 404 status or a header redirect.
- Creating a new promise during every Client Component render and passing it to `use()`.
- Assuming streaming works behind any proxy without testing.

### Industry best practices
- **Stream by importance**: render above-the-fold, LCP and navigation content in the shell; stream secondary and personalised sections.
- **Size boundaries by user-visible regions**, usually one per independent widget or card, not one per component and not one for the page.
- **Design skeletons that match the final layout** (same dimensions) so streaming content does not shift the page (CLS, principle 8).
- **Start slow fetches early and consume them late**: create the promise at the top, pass it down, `await` or `use()` it inside the boundary.
- **Decide status codes before streaming starts**: run `notFound()`, `redirect()` and auth checks before the first suspending `await`.
- **Use `loading.tsx` for route transitions** and `<Suspense>` for in-page sections; use both deliberately.
- **Provide `error.tsx` beside `loading.tsx`** so a failed streamed section falls back locally.
- **Give skeletons accessible semantics**: `aria-busy="true"` on the region, and a status message for long waits.
- **Check infrastructure**: reverse proxies, CDNs and compression layers must not buffer the response; test with `curl -N` and a real deployment, not only locally.
- **Prefer streaming plus Partial Prerendering / `use cache`** where the platform supports it, so the static shell comes from the CDN and only dynamic holes stream.
- **Measure** TTFB, FCP, LCP and INP in the field, and compare a streamed route with its blocking version before and after.
- **Mind hydration order**: selective hydration lets the part the user interacts with hydrate first, so keep interactive leaves small and independent.

### Things to avoid
- One `<Suspense>` around the entire page, which behaves like no streaming and shows one big skeleton.
- Wrapping the LCP element in a slow boundary.
- Nesting many boundaries that all resolve at once, producing "popcorn" loading with layout jumps.
- Showing spinners for fast content (flash of loading): keep boundaries around data that is actually slow.
- Skeletons whose size differs from the final content.
- Awaiting everything above the boundary, so the boundary has nothing left to stream.
- Throwing or calling `redirect()` inside a boundary and expecting the HTTP status to change.
- Streaming per-user data through a shared cache or CDN rule.
- Ignoring crawlers: confirm important content for SEO is in the initial HTML or reliably rendered.

### Checklist
- [ ] The static shell (layout, headings, nav, hero, LCP element) renders without waiting on data.
- [ ] Each slow or independent data region has its own `<Suspense>` boundary placed close to the data access.
- [ ] `await` happens in the leaf component, or promises are passed down; `params`/`searchParams`/`cookies()` are not awaited at the top without need.
- [ ] Independent fetches start together; no sequential waterfalls.
- [ ] Shared data is deduplicated with `React.cache` or a shared promise.
- [ ] Fallbacks are structure-matching skeletons with reserved dimensions (no CLS).
- [ ] LCP element is outside any slow boundary; LCP images use `preload`.
- [ ] `notFound()` / `redirect()` decisions happen before streaming starts where a real status matters.
- [ ] `error.tsx` exists where sections can fail; a failed section does not take down the page.
- [ ] Streaming verified in the Network tab and with `curl -N` on the deployed path, including any proxy.
- [ ] Web Vitals (TTFB, FCP, LCP, CLS, INP) checked after adding boundaries.

- No `loading.tsx` files exist under `src/app`, and about 36 files reference `<Suspense>`.
- Most pages are Client Components today (see [principle 6](6.%20React%20Server%20Components.md)), so server-side streaming cannot apply to them until the data fetching moves into Server Components. Streaming and RSC need to be adopted together.
