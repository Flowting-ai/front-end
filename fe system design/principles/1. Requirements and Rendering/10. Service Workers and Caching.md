## 10. Service Workers & Caching

> A background proxy that intercepts every request and decides cache versus network. Repeat visits load instantly from cache. Cache invalidation is the hard part: version it.

### Definition
A **service worker** (SW) is a JavaScript file the browser runs on a separate thread, with no DOM access, between your page and the network. Once registered for a scope (for example `/`), it receives a `fetch` event for requests made by pages it controls, and can answer from the **Cache Storage API**, from the network, or a mix. It keeps running (and can be woken) when no page is open, which also enables push notifications, background sync and offline support.

There are four caches in the path of a repeat visit, and they are easy to confuse:

| Layer | Where | Controlled by |
|---|---|---|
| Browser HTTP cache | Browser | `Cache-Control` headers |
| **Service worker cache (Cache Storage)** | Browser | **Your SW code** |
| CDN / edge cache | Network ([principle 9](9.%20CDN%20and%20Edge%20Delivery.md)) | `s-maxage`, purge APIs |
| Next.js server cache | Origin | `"use cache"`, `revalidate*` ([principle 4](4.%20Incremental%20Static%20Regeneration.md)) |

A service worker adds a programmable layer between the page and the HTTP cache. It is powerful because it can serve a response with **no network at all**, and dangerous for the same reason.

On "repeat visits load instantly": that is true for what is cached. A SW that precaches the app's static assets makes the second visit skip those network requests, but the HTML/RSC data for dynamic, personalised pages still has to come from the server unless you deliberately cache it. Note that Next.js already serves `/_next/static/*` with `immutable` one-year headers, so the browser HTTP cache already gives repeat visits most of that benefit. A SW's real additional value is **offline support, custom strategies, and push/background features**, not a general speed-up.

### Key properties

**1. Lifecycle (the source of most bugs)**
1. **Register** from a page (`navigator.serviceWorker.register("/sw.js")`).
2. **Install**: the new SW downloads and its `install` event runs (usually precaching).
3. **Waiting**: if an older SW still controls open tabs, the new one **waits** until all those tabs close (unless it calls `skipWaiting()`).
4. **Activate**: the `activate` event runs; this is where old caches are deleted. `clients.claim()` lets it take control of open pages immediately.
5. **Update check**: the browser re-fetches the SW script on navigation (at most every 24 h by default HTTP-cache rules, bypassing the HTTP cache for the script) and installs a new version if the bytes differ.

Because of step 3, users can run an old version of your app for a long time. This is why versioning and an update strategy are not optional.

**2. Scope and security**
- Works only on **HTTPS** (and `localhost`).
- The SW file's path sets the maximum scope; `/sw.js` at the root can control the whole origin.
- It sees and can rewrite **every same-origin request** in scope, so it must be treated as high-privilege code. Serve it with a strict CSP and `Cache-Control: no-cache, no-store, must-revalidate`, as the Next.js PWA guide recommends.

**3. Caching strategies**
Pick per request type:

| Strategy | Behaviour | Use for |
|---|---|---|
| **Cache first** | Cache, else network (and store) | Hashed static assets (`/_next/static/*`), fonts, versioned images |
| **Network first** | Network, fall back to cache when offline/slow | HTML/navigation, mostly-fresh data |
| **Stale-while-revalidate** | Serve cache now, refresh in the background | Avatars, public lists, content where "slightly old" is fine |
| **Network only** | Never cached | Auth, mutations, payments, streams, anything per-user |
| **Cache only** | Cache or fail | Precached offline fallback page |

**4. Invalidation is the hard part: version everything**
- **Cache names carry a version**: `app-static-v12`, `app-pages-v12`. On `activate`, delete every cache whose name is not in the current list.
- **Hashed filenames are the best invalidation there is.** `/_next/static/` assets are content-addressed, so a new deploy simply requests new URLs; old ones can be cached forever without ever being stale. Never apply cache-first to a URL whose content can change under the same name (HTML, `public/` files without hashes, API JSON).
- **Tie the SW version to the build.** Inject the Next.js build ID (or a hash of the precache manifest) into the SW so every deploy produces a changed SW file and therefore an update. An unchanged SW file never updates.
- **Have an expiry policy**: max entries and max age per cache; otherwise caches grow without bound and quota eviction picks for you.
- **Have a kill switch.** Keep a way to ship a SW that unregisters itself and clears all caches, because a broken SW can serve a broken app to users who cannot reload their way out of it.

### Practical patterns in Next.js (TypeScript)

**Where the file lives**
Put the SW at `public/sw.js` (served at `/sw.js`), or generate it at build time. The Next.js docs show the plain `public/sw.js` approach for push notifications and name **Serwist** as one option for offline support. That plugin currently requires webpack configuration, whereas Next.js 16 builds with Turbopack by default, so check compatibility before adopting it. A small hand-written SW is often enough.

**Registering safely (client leaf, after load)**
```tsx
// components/ServiceWorkerRegistration.tsx
"use client";

import { useEffect } from "react";

export function ServiceWorkerRegistration() {
  useEffect(() => {
    if (!("serviceWorker" in navigator)) return;
    if (process.env.NODE_ENV !== "production") return;      // avoid stale caches in dev

    navigator.serviceWorker
      .register("/sw.js", { scope: "/", updateViaCache: "none" })
      .then((reg) => {
        reg.addEventListener("updatefound", () => {
          const next = reg.installing;
          next?.addEventListener("statechange", () => {
            if (next.state === "installed" && navigator.serviceWorker.controller) {
              // a new version is waiting: show a "Reload to update" prompt
              window.dispatchEvent(new CustomEvent("sw-update-ready", { detail: reg }));
            }
          });
        });
      })
      .catch(() => { /* registration is an enhancement; the app must work without it */ });
  }, []);

  return null;
}
```
Mount it once in the root layout (a tiny client boundary, as in [principle 6](6.%20React%20Server%20Components.md)).

**A versioned, minimal service worker**
```js
// public/sw.js  (plain JS; or build from TypeScript with the "webworker" lib)
const VERSION = "v12";                       // inject the build ID at build time
const STATIC_CACHE = `static-${VERSION}`;
const PAGES_CACHE = `pages-${VERSION}`;
const CURRENT = [STATIC_CACHE, PAGES_CACHE];
const OFFLINE_URL = "/offline";

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(PAGES_CACHE).then((c) => c.add(OFFLINE_URL)) // precache the offline page only
  );
  // do NOT call skipWaiting() blindly; see "Updating" below
});

self.addEventListener("activate", (event) => {
  event.waitUntil(
    (async () => {
      const names = await caches.keys();
      await Promise.all(names.filter((n) => !CURRENT.includes(n)).map((n) => caches.delete(n)));
      await self.clients.claim();
    })()
  );
});

self.addEventListener("fetch", (event) => {
  const req = event.request;
  const url = new URL(req.url);

  if (req.method !== "GET") return;                              // never touch mutations
  if (url.origin !== self.location.origin) return;               // third parties: browser default
  if (url.pathname.startsWith("/api/")) return;                  // auth, chat streams, backend proxy
  if (url.pathname.startsWith("/auth/")) return;

  // Hashed build assets: cache first, safe forever
  if (url.pathname.startsWith("/_next/static/")) {
    event.respondWith(cacheFirst(req, STATIC_CACHE));
    return;
  }

  // Navigations: network first, offline fallback
  if (req.mode === "navigate") {
    event.respondWith(
      fetch(req).catch(async () => (await caches.match(OFFLINE_URL)) ?? Response.error())
    );
  }
});

async function cacheFirst(req, cacheName) {
  const cache = await caches.open(cacheName);
  const hit = await cache.match(req);
  if (hit) return hit;
  const res = await fetch(req);
  if (res.ok) cache.put(req, res.clone());
  return res;
}
```
The important choices are what it **refuses** to touch: non-GET requests, other origins, `/api/*` and `/auth/*`.

**Serve the SW with the right headers**
```ts
// next.config.ts
async headers() {
  return [
    {
      source: "/sw.js",
      headers: [
        { key: "Content-Type", value: "application/javascript; charset=utf-8" },
        { key: "Cache-Control", value: "no-cache, no-store, must-revalidate" },
        { key: "Content-Security-Policy", value: "default-src 'self'; script-src 'self'" },
      ],
    },
  ];
},
```
If the SW file itself is cached long by the HTTP cache or CDN, clients never see updates. This header is the single most important line for updates.

**Updating: tell the user, do not yank the app**
- `skipWaiting()` + `clients.claim()` activates the new SW instantly, but then an open page (old JS) may talk to a new SW (new cache contents), or lazily load chunks that no longer exist.
- Safer: let the new SW wait, show a "New version available, reload" prompt, and on accept `postMessage({ type: "SKIP_WAITING" })` to the waiting worker, then `location.reload()` on `controllerchange`.

**Chunk-load failures after a deploy**
Old HTML referencing deleted chunks fails with a chunk-load error. Handle it with an error boundary that reloads once, independent of the SW; a SW with stale precaches makes this worse if it serves old HTML with new asset URLs (or the reverse).

### What not to cache
- Authenticated pages and API responses, unless you key and clear them per user and per session.
- Responses with `Set-Cookie`, `Cache-Control: private`/`no-store`, or opaque cross-origin responses (they hide errors and burn quota).
- **Streaming and SSE responses** (`text/event-stream`, chunked chat output): caching them breaks streaming ([principle 7](7.%20Streaming%20SSR%20and%20Suspense.md)).
- Next.js RSC requests (`rsc` header / `_rsc` param) unless you understand the variants ([principle 9](9.%20CDN%20and%20Edge%20Delivery.md)); caching the HTML and the RSC payload under the same key breaks navigation.
- Non-GET requests: the Cache API cannot store them.
- Anything containing secrets or personal data on a shared device: the cache survives logout unless you clear it.

### Storage and privacy
- Quota is per origin and browser-dependent; the browser may **evict** caches under pressure (use `navigator.storage.persist()` only when you really need to keep data).
- On **logout**, clear user-specific caches (`caches.delete(...)`) and unregister if needed. A cached page from user A must never render for user B on the same device.
- Cache Storage is origin-scoped, readable by any script on the origin (including XSS). Do not store anything there you would not put in `localStorage`.

### Testing and debugging
- Chrome DevTools, **Application → Service Workers**: see state, "Update on reload", "Bypass for network", "Unregister", and offline mode. **Cache Storage** lists entries.
- Test the **upgrade path**, not just a clean install: load version N, deploy N+1, reload with an old tab open, and confirm what the user sees.
- Test offline, slow-3G and "network flaky" states; test logout then login as another user.
- Run Lighthouse's installability/PWA checks, and verify CWV does not regress ([principle 8](8.%20Core%20Web%20Vitals.md)): a SW adds startup cost to the first navigation (the SW boot, unless navigation preload is enabled).
- In `next dev`, do not register the SW; stale caches during development are a time sink.

### Rules of thumb
1. **Do you need one?** Offline, push or background sync, yes. "Faster repeat visits" alone: Next.js hashed assets plus HTTP caching and the CDN already cover most of it.
2. **Cache-first only for content-addressed URLs.**
3. **Never cache auth, mutations, streams or per-user data** by default; allow-list instead of block-list.
4. **Version every cache and delete old ones on `activate`.**
5. **The SW file must never be long-cached**; its bytes must change on every deploy.
6. **Prompt for updates; do not silently swap code under an open tab.**
7. **Ship a kill switch** and a way to clear caches on logout.
8. **Treat it as an enhancement**: the app must work when registration fails.

### Anti-patterns
- Cache-first on HTML or API JSON, so users see old data until the cache is cleared manually.
- Caching everything with a wildcard `fetch` handler instead of an allow-list.
- A SW script cached for a year by the CDN or HTTP cache; clients never update.
- A fixed cache name (`"cache"`) that is never versioned or cleaned.
- Calling `skipWaiting()` unconditionally and mixing old page code with new caches.
- Caching authenticated responses and leaving them after logout.
- Intercepting `/api/chat` or other streaming endpoints.
- Precaching the whole site (large installs, wasted bandwidth, quota evictions).
- Registering the SW in development.
- No plan for removing a bad SW.
- Assuming a hard refresh fixes it for users; they do not know to do that.

### Industry best practices
- **Choose a strategy per request type**: cache-first for fingerprinted assets, network-first (with timeout) for navigations and fresh data, stale-while-revalidate for tolerant content, network-only for auth and mutations.
- **Use Workbox (or Serwist for Next.js)** rather than hand-writing routing and expiry; it provides tested strategies, precaching and cache expiry.
- **Precache the minimum**: the offline fallback page and a few critical assets, not the whole site.
- **Version caches and clean old ones** in the `activate` event, and give each build a revision so updates are detected.
- **Serve `sw.js` with `Cache-Control: no-cache`** (and the correct scope) so updates are picked up, and register it at the root for full scope.
- **Control the update flow**: detect a waiting worker, show an "Update available" prompt, and call `skipWaiting()` only after the user agrees or the page is idle, to avoid mixing old pages with new code.
- **Limit cache size and age** (`maxEntries`, `maxAgeSeconds`) and handle storage quota errors.
- **Do not cache opaque or error responses** by accident: check `response.ok` and status before `cache.put`.
- **Exclude sensitive and personalised requests** (auth, `/api`, streams, `POST`) and clear caches on logout.
- **Provide an offline UX** that explains what works offline and queues writes with Background Sync where supported.
- **Add a kill switch**: a way to ship a service worker that unregisters itself and clears caches if a bad version escapes.
- **Test with DevTools Application panel**, offline mode, throttling, Lighthouse PWA checks, and an update scenario between two builds.
- **Register after load** (`window.addEventListener("load", …)`) so it does not compete with first render.

### Things to avoid
- Caching HTML navigations with cache-first (users get stuck on old versions).
- Long-caching `sw.js` itself, or serving it from a CDN rule that caches it.
- Using `skipWaiting()` and `clients.claim()` blindly, causing old pages to talk to a new worker.
- Caching authenticated, personalised or `no-store` responses.
- Unbounded caches that grow until the browser evicts everything.
- Caching error responses (`404`, `500`) and serving them offline.
- Writing service worker logic that depends on globals or modules not available in the worker scope.
- Forgetting to test the very first load (the worker is not yet in control) and the update path.
- Using a service worker only as a "performance trick" when HTTP caching and a CDN would suffice.
- Shipping with no way to remove a broken worker.

### Checklist
- [ ] A written reason exists for having a SW (offline, push, background sync), beyond "speed".
- [ ] Strategy per request type is documented; an allow-list defines what the SW handles.
- [ ] `/api/*`, `/auth/*`, non-GET requests, streams and third-party origins are excluded.
- [ ] Cache names include a version tied to the build; `activate` deletes old caches.
- [ ] `/sw.js` is served with `no-cache, no-store, must-revalidate` and a strict CSP; the CDN does not cache it.
- [ ] The update flow is user-visible (prompt to reload); `skipWaiting` is gated on that.
- [ ] Logout clears user-specific caches; no cross-user leakage on shared devices.
- [ ] Cache size/age limits exist; quota errors are handled.
- [ ] Registration is production-only and failure-tolerant.
- [ ] The upgrade path, offline mode and logout/login-as-another-user are tested.
- [ ] A kill-switch SW and a procedure to roll back are ready before launch.

### In this codebase
Measured with a quick search of `src/`, `public/` and `next.config.ts` (not a full audit):
- **No service worker exists today.** No `sw.js`, manifest, Workbox/Serwist dependency or `serviceWorker.register` call. Repeat-visit performance currently relies on the browser HTTP cache for `/_next/static/*` and any CDN in front ([principle 9](9.%20CDN%20and%20Edge%20Delivery.md)).
- The CSP in `next.config.ts` already contains `worker-src 'self' blob:`, so a same-origin SW would not be blocked by it (a new `/sw.js` header block, as shown above, would still be needed).
- The app is authenticated (Auth0) with a Next.js proxy gate, a backend proxy at `/api/backend/*`, and streaming chat routes. These are exactly the request types a SW must **not** cache. Any SW here should use an allow-list limited to hashed static assets, fonts and persona/icon images, plus an offline fallback page.
- Given that, the main reason to add a SW would be offline fallback or push notifications, not load speed. Decide that need first; if there is none, skip it and invest in [principles 8](8.%20Core%20Web%20Vitals.md) and [9](9.%20CDN%20and%20Edge%20Delivery.md) instead.
- If one is added: ensure logout clears its caches, and note that the Serwist plugin currently needs webpack while this project builds with Turbopack.
