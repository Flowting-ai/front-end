## 5. Hybrid Rendering

> Mix rendering strategies at the route level, and per component with Server Components.

### Definition
No single rendering mode fits a whole app, or even a whole page. Hybrid rendering picks the strategy that fits each **route** (static, ISR, dynamic) and each **component** (server, cached, streamed, client). In the App Router this is the model, not an add-on: every layout and page is a Server Component by default, and you opt individual pieces into the client, into caching, or into request-time rendering.

### Key properties

**1. Speed, freshness and interactivity, each where needed**
Match each piece of UI to the property it actually needs:

| Need | Strategy | Tool in Next.js |
|---|---|---|
| Speed for shared content | Static / cached | default static route, `generateStaticParams`, `"use cache"` |
| Bounded freshness, shared | ISR / cache lifetimes | `revalidate`, `cacheLife`, `revalidateTag` |
| Exact freshness or personalization | Request-time server render | `cookies()`, `headers()`, `searchParams`, `connection()` |
| Interactivity and browser APIs | Client rendering | `"use client"`, SWR or TanStack Query, `next/dynamic` |
| Slow data without blocking the page | Streaming | `<Suspense>`, `loading.tsx` |

**2. The Next.js App Router default**
- Layouts and pages are Server Components unless marked `"use client"`. Server code stays on the server (data access, secrets, heavy libraries) and ships no JS for those parts.
- Server Components can render Client Components; Client Components can receive Server Components as `children` or other props. This lets you nest server-rendered UI inside interactive wrappers.
- Next.js splits work for you: the RSC payload contains rendered server output, placeholders for client components, and references to their JS.

### Route-level mixing
Decide per route, not per app:

| Route | Typical choice |
|---|---|
| Landing, pricing, docs | Static ([SSG](3.%20Static%20Site%20Generation.md)) |
| Public catalog, templates, blog | [ISR](4.%20Incremental%20Static%20Regeneration.md) |
| Account, settings, dashboards | [SSR](1.%20Server%20Side%20Rendering.md) (request-time) |
| Chat, editors, canvases | Server shell + [CSR](2.%20Client%20Side%20Rendering.md) interior |

Verify what you got in the `next build` route table (`○` static, `●` SSG with params, `ƒ` dynamic).

### Component-level mixing

**Server by default, client at the leaves**
```tsx
// app/(app)/projects/[id]/page.tsx   Server Component
import { Suspense } from "react";

type Props = { params: Promise<{ id: string }> };

export default async function ProjectPage({ params }: Props) {
  const { id } = await params;
  const project = await getProject(id);        // server fetch, typed, no client JS

  return (
    <>
      <ProjectHeader project={project} />      {/* server, static-ish */}
      <Suspense fallback={<ActivitySkeleton />}>
        <ActivityFeed projectId={id} />        {/* server, slow, streamed */}
      </Suspense>
      <ChatComposer projectId={id} />          {/* "use client", interactive */}
    </>
  );
}
```

**Server content inside a client wrapper (children pattern)**
```tsx
// components/Collapsible.tsx
"use client";
import { useState, type ReactNode } from "react";

export function Collapsible({ title, children }: { title: string; children: ReactNode }) {
  const [open, setOpen] = useState(false);
  return (
    <section>
      <button onClick={() => setOpen((o) => !o)} aria-expanded={open}>{title}</button>
      {open && children}   {/* children can be Server Components, rendered ahead of time */}
    </section>
  );
}
```

**Static shell + dynamic holes (Partial Prerendering via Cache Components)**
With `cacheComponents: true`, Next prerenders a static HTML shell (all statically renderable content plus Suspense fallbacks) and streams the dynamic parts at request time. The shell is served immediately from the edge; holes stream in parallel.

```tsx
// next.config.ts
import type { NextConfig } from "next";
const config: NextConfig = { cacheComponents: true };
export default config;
```

```tsx
export default function Page() {
  return (
    <>
      <StaticHero />                              {/* in the static shell */}
      <CachedCatalog />                           {/* "use cache" + cacheLife */}
      <Suspense fallback={<CreditsSkeleton />}>
        <UserCredits />                           {/* request-time, per user */}
      </Suspense>
    </>
  );
}
```
- Data is dynamic by default under Cache Components; you choose what to cache at page, component or function level.
- Put `<Suspense>` as close as possible to the dynamic component so the static shell stays as large as possible.

**Client hydration of live data**
Server renders initial data, a Client Component takes over for live updates:
```tsx
<DashboardClient initial={await getDashboard()} />   // SWR revalidates after hydration
```

### Decision flow (per piece of UI)
1. Is it the same for everyone and slow-changing? **Static or cached** (`use cache`, ISR).
2. Does it depend on the user or request? **Dynamic server render**, wrapped in `<Suspense>`.
3. Does it need state, effects, event handlers or browser APIs? **Client Component**, as small as possible.
4. Does it need to update live after load? **Client data layer** (SWR, TanStack Query, SSE, WebSocket) seeded with server data.
5. Is anything slow? **Stream it**; never let one slow query block the shell.

### TypeScript guidance
- Keep the server/client boundary typed: props crossing it must be serializable (no functions, class instances or secrets). Define shared DTO types in a neutral module.
- Mark server-only modules with `import "server-only"` so an accidental client import fails the build; mark client-only helpers with `"client-only"` where useful.
- Type `params` and `searchParams` as `Promise<...>` (Next 15+) and `await` them.
- Share one `Session`/`User` type, resolved on the server and passed down as a minimal prop.

### Tradeoffs
| Gain | Cost |
|---|---|
| Each part gets the cheapest correct strategy | More decisions; mental model is larger than single-mode apps |
| Small client bundles (server code ships no JS) | Strict server/client boundary rules to learn and enforce |
| Fast shell plus fresh personal data | Caching mistakes can leak or stale personal data |
| Streaming avoids blocking on slow data | Needs good skeletons and error boundaries; layout shift risk |

### Pitfalls
- Putting `"use client"` on a page or layout "to make it work", which pulls its whole import tree into the bundle. Extract the interactive leaf instead.
- One request-time API in a high-level component making the whole route dynamic. Isolate it behind a Suspense boundary.
- Caching a component that reads per-user data, or sharing cache entries across users. Pass user or segment values as arguments so they become part of the cache key.
- Passing non-serializable props or secrets from server to client components.
- Unstable values during prerender or hydration (`Date.now()`, `Math.random()`, `crypto.randomUUID()` in Client Components) causing errors or mismatches.
- Wide Suspense boundaries that put most of the page in the fallback.
- Waterfalls: awaiting sequentially in a server component instead of parallelizing or streaming.
- Assuming a mode from memory instead of reading the build output.

### Industry best practices
- **Decide the rendering mode per route from a table**, not ad hoc: for each route record audience (public or per-user), freshness need, SEO need and interactivity, then pick static, cached, streamed or client. Keep the table in the repo and review it when a route changes.
- **Start static and add dynamism only where required.** Treat "this route became dynamic" as a decision, not a side effect.
- **Make the static shell as large as possible** and push request-time reads (`cookies()`, `headers()`, `searchParams`) into small `<Suspense>` islands.
- **Cache shared data with explicit lifetimes** (`use cache` with `cacheLife` and `cacheTag`, or `revalidate`), and never cache anything that reads per-user data without the user as a cache key.
- **Verify the outcome in `next build`.** Read the route table (`○` static, `●` SSG, `ƒ` dynamic) in CI and fail or flag when a route that should be static becomes dynamic.
- **Keep client leaves small** and let Server Components compose them (principle 6).
- **Use `generateStaticParams` for known high-traffic paths** and on-demand rendering for the long tail.
- **Tag data for targeted invalidation** (`revalidateTag`) so a content change refreshes only the affected pages.
- **Measure per mode.** Track Web Vitals (principle 8) and TTFB separately for static, cached and dynamic routes; they have different baselines.
- **Document the rendering contract of shared layouts**: which request APIs they read, because one `cookies()` call there changes every child route.

### Things to avoid
- One global mode for the whole app (everything dynamic, or everything client).
- Reading request-time APIs in a root or shared layout without a deliberate reason.
- Mixing personalised and shared data in one cached function.
- Choosing a mode by habit or by what the last project used.
- Relying on `force-static` to "fix" a route that reads request data; it hides the data instead of resolving the design.
- Letting each team pick its own caching rules with no shared convention.
- Hydrating large static-looking sections because a parent has `"use client"`.
- Forgetting that preview and development behave differently from production caching.

### Checklist
- [ ] Each route has a stated strategy (static, ISR, dynamic, or shell + dynamic holes) and the build output matches.
- [ ] Pages and layouts are Server Components; `"use client"` only on interactive leaves.
- [ ] Server-only modules import `server-only`; props across the boundary are serializable and minimal.
- [ ] Shared data cached or ISR'd; per-user data dynamic and wrapped in `<Suspense>` with a meaningful skeleton.
- [ ] Cache keys include segment or user values passed as arguments; no personal data in shared caches.
- [ ] Slow data streamed; independent fetches parallelized.
- [ ] Error boundaries (`error.tsx`) and `not-found.tsx` in place for dynamic holes.
- [ ] Bundle size and LCP/INP verified after composing.
