## 6. React Server Components

> Components that render on the server and send a serialised tree: zero JavaScript to the client. `"use client"` marks the interactive leaf. Big bundle savings on data-heavy pages.

### Definition
A React Server Component (RSC) is a component that runs **only on the server** (at build time or per request). Its code, its imports and its dependencies are never shipped to the browser. What the browser receives is its **output**: a serialised description of the rendered tree (the RSC Payload), plus references to the Client Components that must be hydrated.

This is different from SSR. SSR renders components to HTML on the server *and then ships all their JavaScript so they can hydrate*. A Server Component ships **no JavaScript and never hydrates**. In the App Router, SSR and RSC work together: Client Components are still prerendered to HTML, but Server Components add a layer on top that never reaches the client bundle.

In Next.js App Router, every `layout.tsx`, `page.tsx` and any component they import is a Server Component **unless** the module graph crosses a `"use client"` boundary.

### Key properties

**1. Zero client JavaScript for server-only UI**
- A Server Component's own code and its imports (markdown parsers, date libraries, syntax highlighters, schema validators) stay on the server.
- Heavy dependencies used only to produce markup cost the user nothing.
- The saving is largest on data-heavy pages (tables, lists, docs, dashboards, settings) where most of the tree is display, not interaction.

**2. `"use client"` marks the interactive leaf**
- The directive declares a **boundary** between the server module graph and the client module graph.
- Everything the marked file imports, and every component it renders directly, is part of the client bundle. You do not repeat the directive in each child.
- So the boundary should sit as **low in the tree as possible**: on the button, input, chart or editor that needs state or events, not on the page.

**3. Direct, secure data access**
- Server Components can be `async` and can `await` a database, an internal service or `fetch` directly. No client fetch, no loading state, no API route just to read data.
- Secrets (tokens, API keys, connection strings) are usable in server code and never exposed.
- Data is fetched close to the source, which also removes the client-to-server round trip.

**4. Serialised output, serialisable props**
- The RSC Payload is a compact binary representation of the rendered server tree. It contains the rendered output, placeholders where Client Components go with references to their JS, and the props passed across the boundary.
- Props that cross from a Server Component to a Client Component must be **serialisable** by React.

**5. Streaming and progressive delivery**
- Server output can be streamed. Wrap slow parts in `<Suspense>` and the rest of the page is delivered immediately, with the slow part filling in when ready.
- Improves First Contentful Paint and perceived speed without client-side data libraries.

**6. Composition: server inside client**
- A Client Component cannot import a Server Component, but it can **receive one as `children` or another prop** and render it. The server part is rendered ahead of time; the client component only provides the interactive wrapper (modal, tabs, accordion, drawer).

### When to use Server vs Client Components

| Need | Component type |
|---|---|
| Fetch data from a DB or API near the source | Server |
| Use secrets, tokens, API keys | Server |
| Render large static or data-driven markup | Server |
| Keep heavy libraries out of the bundle | Server |
| `useState`, `useReducer`, `useEffect`, `useRef` for UI state | Client |
| Event handlers (`onClick`, `onChange`, `onSubmit`) | Client |
| Browser APIs (`window`, `localStorage`, `IntersectionObserver`, `navigator`) | Client |
| Context providers and context consumers | Client |
| Custom hooks that use state or effects | Client |
| Client data libraries (TanStack Query, SWR) | Client |

### What Server Components cannot do
- No `useState`, `useReducer`, `useEffect`, `useLayoutEffect`, `useContext` or other stateful hooks.
- No event handlers passed to DOM elements.
- No browser-only APIs.
- No React context consumption (providers must be Client Components).
- Cannot be imported inside a Client Component. Pass them as `children` instead.

### Practical patterns in Next.js (TypeScript)

**Server page, client leaf**
```tsx
// app/(app)/projects/[id]/page.tsx   Server Component (no directive)
import { LikeButton } from "@/components/LikeButton";
import { getProject } from "@/lib/data/projects";

type Props = { params: Promise<{ id: string }> };

export default async function ProjectPage({ params }: Props) {
  const { id } = await params;
  const project = await getProject(id);      // runs on the server, typed, no client JS

  return (
    <main>
      <h1>{project.title}</h1>
      <p>{project.description}</p>            {/* ships as output, not as code */}
      <LikeButton initialLikes={project.likes} />   {/* the only client JS */}
    </main>
  );
}
```

```tsx
// components/LikeButton.tsx   Client Component (interactive leaf)
"use client";

import { useState } from "react";

type Props = { initialLikes: number };       // serialisable prop

export function LikeButton({ initialLikes }: Props) {
  const [likes, setLikes] = useState(initialLikes);
  return <button onClick={() => setLikes((n) => n + 1)}>{likes} likes</button>;
}
```

**Server content inside a client wrapper (the `children` slot)**
```tsx
// components/Modal.tsx
"use client";

import type { ReactNode } from "react";

export function Modal({ children }: { children: ReactNode }) {
  // client state for open/close lives here
  return <div role="dialog">{children}</div>;
}
```
```tsx
// app/page.tsx   Server Component
import { Modal } from "@/components/Modal";
import { Cart } from "@/components/Cart";    // Server Component that fetches on the server

export default function Page() {
  return (
    <Modal>
      <Cart />                                {/* rendered on the server, passed as children */}
    </Modal>
  );
}
```

**Context providers: client, but as deep as possible**
```tsx
// context/theme-provider.tsx
"use client";

import { createContext, type ReactNode } from "react";

export const ThemeContext = createContext<"light" | "dark">("light");

export function ThemeProvider({ children }: { children: ReactNode }) {
  return <ThemeContext.Provider value="dark">{children}</ThemeContext.Provider>;
}
```
Wrap `{children}`, not the whole `<html>`. A provider is a Client Component but `children` passed through it stay Server Components, so the static parts remain optimisable.

**Third-party components that need the client**
If a library uses hooks but has no `"use client"`, wrap it once and reuse the wrapper from Server Components:
```tsx
// components/Carousel.tsx
"use client";
export { Carousel as default } from "acme-carousel";
```

**Parallel fetching and streaming**
```tsx
export default async function Dashboard() {
  const statsPromise = getStats();           // start both before awaiting
  const activityPromise = getActivity();
  const stats = await statsPromise;          // fast part blocks the shell

  return (
    <>
      <Stats data={stats} />
      <Suspense fallback={<ActivitySkeleton />}>
        <Activity promise={activityPromise} /> {/* slow part streams in */}
      </Suspense>
    </>
  );
}
```
A Client Component can read a promise passed from the server with React's `use()` API, which keeps the fetch on the server while the UI streams.

**Keep server-only code on the server**
```ts
// lib/data/projects.ts
import "server-only";                         // build error if imported from a Client Component

export async function getProject(id: string) {
  const res = await fetch(`${process.env.API_URL}/projects/${id}`, {
    headers: { authorization: `Bearer ${process.env.API_KEY}` },
  });
  return (await res.json()) as Project;
}
```
Only `NEXT_PUBLIC_*` variables reach the client; unprefixed ones become empty strings there. `server-only` turns a silent bug into a build-time error. Use `client-only` for modules that touch `window`.

### Serialisation rules at the boundary
Props passed from a Server to a Client Component must be serialisable.

| Allowed | Not allowed |
|---|---|
| string, number, boolean, null, undefined, bigint | Functions (except Server Actions) |
| Plain objects and arrays of the above | Class instances with methods |
| `Date`, `Map`, `Set`, typed arrays | Symbols, DOM nodes |
| Promises (consumed with `use()`) | Anything holding secrets or an open connection |
| JSX / Server Components as `children` | Event handlers defined on the server |

- Pass the **smallest** data a client leaf needs (`{ id, title }`), not the whole database row. Every prop is serialised into the payload and sent to the browser.
- Type the props explicitly in TypeScript, and define DTO types so server-only fields (internal ids, tokens, other users' data) never get passed by accident.

### Bundle savings: where they come from
- Server-only imports (markdown, syntax highlighting, date formatting, sanitisers, ORMs) are not in any client chunk.
- Display-only components send output, not code.
- Shrinking a boundary from page level to leaf level moves everything above and beside the leaf out of the bundle.
- Measure instead of guessing: run `next build` and compare "First Load JS" per route, or use `@next/bundle-analyzer`. Move a boundary, re-measure.

### Rules of thumb
1. **Default to Server.** Add `"use client"` only when a component needs state, effects, event handlers or browser APIs.
2. **Push the boundary down.** Split a big interactive component into a server shell and small client leaves.
3. **Lift data fetching up.** Fetch in the server parent and pass minimal serialisable props down. Avoid `useEffect` fetching for initial data.
4. **Use `children` slots** to keep server content inside interactive wrappers.
5. **Providers go deep and wrap `{children}`.**
6. **Mark server-only modules with `import "server-only"`.** Never read secrets from a shared module.
7. **Parallelise and stream.** Start independent fetches together; put slow ones behind `<Suspense>`.
8. **Verify** with the build output and a bundle analysis, not by assumption.

### Anti-patterns
- Putting `"use client"` at the top of `page.tsx` or `layout.tsx` "to make it work". This moves the whole subtree into the bundle.
- Adding `"use client"` to every file by habit.
- Fetching initial page data in a Client Component with `useEffect`, adding a round trip, a spinner and an API route that did not need to exist.
- Importing a heavy server-friendly library (markdown, charts' data prep, formatters) in a Client Component.
- Passing a whole ORM entity, or objects containing secrets, as props to a client leaf.
- Trying to import a Server Component into a Client Component instead of passing it as `children`.
- Wrapping the entire `<html>` in a provider, which pushes more of the tree toward the client.
- Sequential `await`s in a Server Component that could run in parallel (a server waterfall).
- Using non-deterministic values (`Date.now()`, `Math.random()`) in Client Components rendered on the server, causing hydration mismatches.
- Assuming a component is a Server Component without checking: a Server Component imported from a `"use client"` file becomes a Client Component.

### Industry best practices
- **Keep a data access layer** (`import "server-only"`) that authorises, queries and returns minimal DTOs; components call it instead of the database or `fetch` directly (see principle 21).
- **Dedupe with `React.cache()`** for non-`fetch` data sources (ORM, SDK calls) so layout, page and metadata share one result per request.
- **Preload to avoid waterfalls**: start independent promises early and `await` them together (`Promise.all`), or pass promises to client leaves and read them with `use()`.
- **Pass promises, not awaited data, when a client leaf can show a fallback**, so the shell is not blocked.
- **Treat every Server Action as a public endpoint**: authenticate, validate with a schema (Zod), authorise by ownership, return minimal data.
- **Colocate server and client code by feature**, with the client leaf file named for what it does (`LikeButton.tsx`) and the boundary stated in its first line.
- **Use `server-only` and `client-only`** to make boundary mistakes build errors.
- **Wrap third-party client libraries once** in a `"use client"` module and reuse that wrapper.
- **Use the React Taint APIs** (experimental) as an extra guard for objects that must never reach the client, but do not rely on them as the main control.
- **Track the client boundary size** with `next build` First Load JS and `@next/bundle-analyzer` per route, and review it in PRs that move a `"use client"` line.
- **Prefer URL state and Server Actions** over client stores for data the server owns.
- **Test Server Components** through integration or E2E tests (they are async and server-only), and unit-test the pure functions and client leaves.

### Things to avoid
- Importing a large client-side library into a Server Component "because it works" without checking what it does at runtime.
- Passing functions, class instances or non-serialisable values across the boundary.
- Reading `process.env` secrets outside the data access layer.
- `"use client"` at the top of every file by habit, or on `layout.tsx` and `page.tsx`.
- Using Context to share server data; fetch where needed with `cache()` instead.
- Mutating shared module-level state in a Server Component (it persists across requests).
- Fetching from your own route handlers inside Server Components.
- Treating RSC as a security boundary for authorisation by itself: re-check access at the data layer and in each action.
- Relying on experimental or `unstable_` APIs without pinning the Next.js version.

### Checklist
- [ ] `page.tsx` and `layout.tsx` are Server Components (no `"use client"`), except where there is a documented reason.
- [ ] Each `"use client"` file has a stated reason (state, effect, event, browser API, context).
- [ ] Client boundaries sit on the smallest interactive leaf, not on a whole section or page.
- [ ] Data is fetched on the server and passed as minimal, typed, serialisable props.
- [ ] Server-only modules import `server-only`; no secrets reach client code.
- [ ] Server content nested in client wrappers is passed as `children`.
- [ ] Providers are Client Components that wrap `{children}` as deep as possible.
- [ ] Independent fetches run in parallel; slow data is behind `<Suspense>` with a meaningful skeleton.
- [ ] Third-party client-only components are wrapped once in a `"use client"` module.
- [ ] `next build` First Load JS and a bundle analysis checked before and after moving boundaries.
