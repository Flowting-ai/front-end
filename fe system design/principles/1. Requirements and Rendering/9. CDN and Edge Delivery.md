## 9. CDN & Edge Delivery

> Serve assets from the PoP nearest the user; run light logic at the edge itself. Latency drops from hundreds of ms to single digits. The edge runtime is limited: no full Node.

### Definition
A **CDN** (content delivery network) is a fleet of servers called **PoPs** (points of presence) spread across the world. A request is routed to a nearby PoP. If the PoP holds a fresh copy of the response (a **cache hit**), it answers from there; if not (a **miss**), it fetches from the **origin** (your Next.js server), usually stores the result, and answers. **Edge compute** goes one step further: small functions run in the PoP itself, so some decisions never reach the origin.

Why it matters: distance is latency. A request to a far-away origin pays a long network round trip, plus TLS and connection setup; a nearby PoP pays a short one and often reuses warm connections.

On the numbers: "hundreds of ms down to single digits" is the best case. A cache hit at a PoP in the user's metro area can respond in single-digit to low tens of milliseconds. A cache **miss** still costs the trip to the origin, and dynamic, uncached, per-user responses get little or no benefit from the cache. Treat the figure as the goal for cacheable content, not a guarantee for every request.

### Key properties

**1. Static assets: cache at the edge, forever**
- Files under `/_next/static/` (JS, CSS, fonts, images imported by the build) have content hashes in their names and are served with `Cache-Control: public, max-age=31536000, immutable`. A CDN and the browser can keep them for a year with no revalidation, because a change produces a new filename.
- Files in `public/` are **not** hashed. They get a short default cache lifetime; set explicit headers if you want them cached long, and version their filenames if they change.
- Use [`assetPrefix`](https://nextjs.org/docs/app/api-reference/config/next-config-js/assetPrefix) to serve static assets from a CDN origin or domain.

**2. Pages: cache by rendering strategy**
Next.js sets `Cache-Control` per route type, and a CDN that respects it can cache at the edge:

| Route type | Header Next.js sets | Edge behaviour |
|---|---|---|
| Static ([SSG](3.%20Static%20Site%20Generation.md)) | `s-maxage=31536000` | Cached "forever", served from the PoP |
| ISR ([principle 4](4.%20Incremental%20Static%20Regeneration.md)) | `s-maxage=<revalidate>, stale-while-revalidate=<expire - revalidate>` | Served instantly, refreshed in the background |
| Dynamic ([SSR](1.%20Server%20Side%20Rendering.md)) | `private, no-cache, no-store, max-age=0, must-revalidate` | Never cached; goes to the origin every time |

- `s-maxage` applies to shared caches (CDNs); `max-age` applies to the browser; `stale-while-revalidate` lets the edge serve the old copy while it refreshes.
- `revalidateTag()` / `revalidatePath()` invalidate the **Next.js server cache**, not the CDN's copy. The CDN keeps serving its copy until `s-maxage` expires, so call the CDN's purge API alongside them, for both the HTML and the RSC variants.

**3. Personalised responses must not be shared**
- Anything that depends on the user (cookies, auth, per-user data) must not be cached publicly. Use `private`/`no-store`, or keep it out of the cached shell and stream it in ([principle 7](7.%20Streaming%20SSR%20and%20Suspense.md)): a static, edge-cached shell with a dynamic hole is the best of both.
- A cached response that leaks one user's data to another is a security incident, not a performance bug. Be deliberate with `Vary` and cache keys.

**4. App Router responses vary by headers**
Responses can differ by `rsc`, `next-router-state-tree`, `next-router-prefetch`, `next-router-segment-prefetch` and `next-url` (set via `Vary`). Many CDNs ignore `Vary`, so Next.js adds an `_rsc` query parameter that acts as a hash of those headers. When configuring a CDN:
- **Forward the `rsc` request header.** If it is stripped, the server returns HTML where the client router expects an RSC payload, and client-side navigation breaks.
- **Keep the `_rsc` search parameter in the cache key.** CDNs that drop query strings from cache keys will serve the wrong variant (HTML for RSC or the reverse).
- For prefetch requests keep both the prefetch header and `_rsc`.
- Static prefetches on PPR/Cache Components routes can be cached under those rules.
- Next.js is moving toward pathname-based cache keys (`/page.rsc`, `/page.segments/...`), which will remove the need for `Vary` and `_rsc`. This is still in design, so do not rely on it yet.

**5. Images and fonts**
- `next/image` optimises to AVIF/WebP at responsive sizes. Optimised images carry cache headers, so a CDN in front can cache them; in self-hosted setups `sharp` must be installed.
- `next/font` self-hosts fonts from your own origin: one fewer third-party connection, and the files are static and CDN-cacheable.

**6. Edge compute: light logic near the user**
Good fits:
- Redirects and rewrites, locale or region routing.
- Auth presence checks (is a session cookie there?), bot filtering, geo-based decisions.
- A/B bucketing and feature-flag reads from an edge key-value store.
- Adding or normalising headers; simple request validation.
- Serving a cached or prerendered shell and stitching dynamic parts.

Poor fits:
- Anything that needs a database connection, heavy CPU, large dependencies or long execution.
- Logic that must call a far-away origin API on every request anyway: the edge saves nothing and adds a hop.

### The Edge runtime limits
The Edge runtime is a V8-isolate environment built on Web APIs, not full Node.js. Expect:
- **No Node.js built-ins** (`fs`, `net`, `child_process`, `crypto` beyond Web Crypto, most `stream`/`buffer` use) and **no native addons**.
- **Many npm packages will not run.** Anything that imports Node APIs, uses `eval`/`new Function`, or relies on a persistent TCP connection (most database drivers, some SDKs) fails or needs an HTTP-based alternative.
- **Small code-size limits** and **tight CPU/memory/time limits**, set by the platform. Large dependencies do not fit.
- **No persistent in-process state.** Isolates are short-lived and many; a module-level `Map` is per isolate and not shared.
- Platform-specific edge APIs and quotas: Vercel Edge, Cloudflare Workers, CloudFront Lambda@Edge/Functions and Akamai EdgeWorkers each differ. Check the target platform's documentation.
- `Cache Components` is not supported with `runtime: 'edge'`.

Rule: keep edge code small, dependency-light and Web-API-only. Heavy work stays on the Node.js runtime near your data.

### Edge in Next.js 16 specifically
- **`middleware.ts` is now `proxy.ts`.** In Next.js 16 the Proxy file **runs on the Node.js runtime** and the `runtime` option is **not available** in it (setting it throws). It is described as a network boundary in front of the app, but you should not assume it runs at the edge.
- If you do need the edge runtime, it is still selectable per route with `export const runtime = 'edge'` on a page, layout or route handler (`'nodejs'` is the default), subject to the limits above.
- Whether a Proxy or route actually runs at a PoP depends on the **hosting platform**, not on Next.js alone. A single `next start` process on one server is valid and every feature works; CDN caching and edge compute are performance improvements on top ("edge stitching" is an optimisation, not a correctness requirement).
- Place Proxy logic **before** the CDN cache when it decides auth, redirects or rewrites. If it sits behind the CDN, bypass caching for routes whose output depends on Proxy decisions.

```ts
// proxy.ts  (Next.js 16, Node.js runtime): keep it light regardless
import { NextRequest, NextResponse } from "next/server";

export function proxy(request: NextRequest) {
  const hasSession = request.cookies.has("appSession");
  if (!hasSession && request.nextUrl.pathname.startsWith("/app")) {
    return NextResponse.redirect(new URL("/auth/login", request.url));
  }
  return NextResponse.next();               // no network calls, no heavy work
}

export const config = {
  // never run on static assets: they must come straight from the CDN
  matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\..*).*)"],
};
```

### Practical patterns

**Set explicit cache headers for non-hashed public files and API responses**
```ts
// next.config.ts
const nextConfig: NextConfig = {
  async headers() {
    return [
      {
        source: "/icons/:path*",
        headers: [{ key: "Cache-Control", value: "public, max-age=31536000, immutable" }],
        // only if filenames are versioned; otherwise use a shorter max-age
      },
    ];
  },
};
```

**Cacheable API route with CDN-friendly headers**
```ts
// app/api/public/templates/route.ts
export async function GET() {
  const data = await getTemplates();
  return Response.json(data, {
    headers: {
      "Cache-Control": "public, s-maxage=300, stale-while-revalidate=3600",
    },
  });
}
```

**Purge the CDN together with Next.js revalidation**
```ts
"use server";
import { revalidateTag } from "next/cache";

export async function publishTemplate(id: string) {
  await savePublished(id);
  revalidateTag(`template-${id}`);       // Next.js server cache
  await purgeCdn([`/templates/${id}`]);  // CDN cache (HTML and RSC variants)
}
```

**Edge-friendly code is Web-API only**
```ts
export const runtime = "edge";           // only where the limits are acceptable

export async function GET(request: Request) {
  const country = request.headers.get("x-vercel-ip-country") ?? "US"; // platform header
  return Response.redirect(new URL(`/${country.toLowerCase()}`, request.url), 307);
}
```

### Placement and topology
- **Edge compute is only half the story: the data must be near it.** A function in 30 PoPs that calls one database in one region is slower than a function next to the database. For data-heavy rendering, pin the server to the data's region (`preferredRegion`, or the platform's region setting) and use the CDN for caching, not for compute.
- **Multiple origin instances** need a shared cache and tag coordination so ISR and `revalidateTag` stay consistent across them.
- **Keep the API and the frontend close.** The backend here is a separate service; the round trip from the Next.js server to it is often the largest cost on dynamic pages.

### Rules of thumb
1. **Cache everything that is not personal**, and make that explicit with headers.
2. **Hashed assets: immutable, one year.** Unhashed files: short TTL or versioned names.
3. **Shell cached, holes dynamic.** Serve a static shell from the edge and stream personalised parts.
4. **Edge logic must be tiny and Web-API-only.** If it needs Node or a database, it belongs at the origin.
5. **Put compute near the data**, not just near the user.
6. **Purge the CDN on on-demand revalidation.**
7. **Forward `rsc` and keep `_rsc` in the cache key.**
8. **Measure hit ratio and TTFB per region**, not just overall averages.

### Anti-patterns
- Caching authenticated or personalised responses publicly (`public`/`s-maxage` on user data).
- Stripping query strings or the `rsc` header at the CDN and breaking App Router navigation.
- Assuming `revalidateTag` clears the CDN.
- Running a Proxy/middleware on every request, including static assets, because the matcher is too wide (it adds latency to files that should come straight from cache).
- Making network calls to the origin API from Proxy on every request. If unavoidable, cache the result, remembering that any in-memory cache is per instance or isolate.
- Importing Node-only packages into edge code, or choosing `runtime = 'edge'` for a route that talks to a database.
- Serving user-uploaded or third-party files without cache headers, or with `no-store` by default.
- Adding edge compute before measuring: it adds complexity and a new failure mode.
- Cache busting by query-string only on assets behind CDNs that ignore query strings; use content hashes in filenames.
- Judging success from one lab run in one city.

### Industry best practices
- **Fingerprint static assets** (hashed filenames) and serve them with `Cache-Control: public, max-age=31536000, immutable`; Next.js does this for `/_next/static`.
- **Use `s-maxage` and `stale-while-revalidate`** for shared HTML you are happy to serve slightly stale, and keep `max-age` low so browsers revalidate.
- **Cache by explicit key**: define which headers, cookies and query parameters vary the response, and strip the rest (tracking parameters, unneeded cookies) so hit rate stays high.
- **Add `Vary` correctly** and never cache responses that set cookies or depend on `Authorization` in a shared cache.
- **Keep the origin shielded**: use an origin shield or tiered cache and request coalescing so a purge or a cold PoP does not stampede the origin.
- **Purge precisely**: tag-based or path-based invalidation tied to `revalidateTag`/`revalidatePath`, instead of purging everything.
- **Enable modern transport**: HTTP/2 or HTTP/3, TLS 1.3, Brotli compression for text, and HSTS.
- **Optimise images at the edge** with `next/image` or the CDN's image service, with a bounded set of sizes and formats to protect cache efficiency.
- **Keep edge logic small and stateless**: redirects, rewrites, geo and A/B routing, header rules, bot checks. Put database-bound logic near the database.
- **Watch the cache hit ratio and origin load** per route class; alert on drops after deploys.
- **Protect the edge**: WAF rules, rate limiting, DDoS protection and bot management in front of the origin.
- **Test caching behaviour** with `curl -I` (look at `Cache-Control`, `Age`, `X-Cache`/`CF-Cache-Status`) in each environment, and in a production build.
- **Plan for CDN failure** (multi-CDN or documented fallback) for critical properties.

### Things to avoid
- Caching responses that contain personal data, set cookies or vary by `Authorization`.
- Putting session cookies in the cache key by default, which destroys hit rate.
- Long TTLs on non-fingerprinted files (HTML, `sw.js`, `manifest`).
- Purging the entire cache as a deploy step.
- Treating `revalidateTag` as a CDN purge; it only clears the Next.js cache.
- Running Node-only or connection-heavy database code at the edge runtime.
- Large edge functions with many dependencies (slow cold starts, size limits).
- Cache keys that include unneeded query parameters (`utm_*`, `fbclid`).
- Assuming "it's on a CDN" means fast: a dynamic origin with a cold cache can be slower than before.
- Skipping a test of cache headers because development mode does not cache.

### Checklist
- [ ] Each route's cache behaviour is known (static, ISR, dynamic) and matches its `Cache-Control` header; verified with `curl -I` against production.
- [ ] `/_next/static/*` is served with `immutable`; non-hashed `public/` files have deliberate headers.
- [ ] No personalised or authenticated response is publicly cacheable; shared caches never hold user data.
- [ ] The CDN forwards the `rsc` header, keeps `_rsc` in the cache key and honours `Cache-Control`/`Vary`.
- [ ] On-demand revalidation also purges the CDN (HTML and RSC variants).
- [ ] Proxy matcher excludes static assets; Proxy logic is light and makes no per-request origin calls without caching.
- [ ] Any `runtime = 'edge'` code uses only Web APIs and fits the platform's size/CPU limits; heavy and database work stays on Node.js.
- [ ] Servers are placed near the data store; multi-instance deployments share a cache.
- [ ] Streaming still works through the CDN/proxy (not buffered).
- [ ] Cache hit ratio, TTFB and LCP are tracked per region after rollout.

### In this codebase
Measured by reading `next.config.ts` and `src/proxy.ts` (not a full audit):
- **The hosting platform and CDN are not stated in the repo.** There is no `vercel.json`, and `next.config.ts` has no `assetPrefix` or `images` config. Which CDN sits in front, and where the origin runs, needs to be confirmed before applying the CDN rules above.
- `src/proxy.ts` already follows the Next.js 16 name and its matcher excludes `_next` internals and any path with a file extension, so static files from `public/` bypass the auth/onboarding gate. Good for edge caching.
- That Proxy calls the backend (`/users/me`) to check onboarding, and keeps a **per-instance in-memory `Map`** to cache the positive result for 60 s. This is a Node.js-runtime Proxy; it would not work as-is under the Edge runtime (and an in-memory map is not shared across instances or isolates). Moving that check to the edge would need a shared store or a signed cookie claim.
- `next.config.ts` sets security headers (HSTS, CSP, frame options) on every path with `/(.*)`. These are fine for a CDN to cache with the response, but nothing sets `Cache-Control` for `public/` assets (`icons/`, `persona-avatars/`, `onboarding/`, `pdf.worker.min.mjs`), so they use the default short lifetime. Hashing their filenames or setting explicit headers is a cheap win.
- Almost every screen is authenticated and dynamic, so the CDN's biggest wins are static assets, public pages (landing, share, invite) and fonts, not the app shell data. Chat streams from the backend and must not be buffered or cached by the CDN.
