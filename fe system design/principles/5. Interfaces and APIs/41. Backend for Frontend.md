## 41. Backend for Frontend

> A thin layer fans out to services and returns one UI-shaped response. The browser shouldn't orchestrate microservices. Keep internal service contracts private.

### Definition
A **Backend for Frontend (BFF)** is a server-side layer **owned by the front-end team** that sits between one client experience (the web app) and the back-end services. It:
- **Aggregates**: calls several services in parallel and merges the results into one response shaped for a screen.
- **Adapts**: translates internal contracts into the shapes and names the UI wants.
- **Protects**: holds secrets and tokens, applies authentication and authorisation, and hides internal topology.

The BFF is **not** a place for domain logic. Business rules stay in the services; the BFF only composes, translates and secures.

```
Browser ──one request──▶ BFF (Next.js) ──┬─▶ Users service
                                         ├─▶ Billing service
                                         └─▶ Projects service
        ◀──one UI-shaped response────────┘
```

### Key properties

**1. One request per screen, not N requests per screen**
- Without a BFF, the browser calls several services itself: multiple round trips on a slow network, waterfalls when calls depend on each other, and the browser must know every service URL, auth scheme and error format.
- With a BFF, the server makes those calls over a fast internal network, in parallel, and returns one payload.

**2. The browser does not orchestrate microservices**
- Orchestration (ordering, retries, partial failure handling, merging) belongs on the server. The client gets a single contract per view.
- Partial failure is decided in one place: return the page with a degraded section, rather than every component handling each service's failure.

**3. Internal contracts stay private**
- Services can rename fields, split or merge, or change protocol without breaking the web app, as long as the BFF contract holds. The BFF is the anti-corruption layer.
- Never leak internal IDs, topology, stack traces or fields the UI does not need (principle 21).

**4. Tokens and secrets live on the server**
- The BFF holds service credentials and exchanges the user's session for downstream tokens. The browser holds only an opaque session cookie (principle 42). This is also the pattern recommended for browser-based OAuth clients.

**5. One BFF per experience**
- A web BFF, a mobile BFF and a partner API can have different shapes. A single shared "general API" for all clients drifts back to over- and under-fetching.
- Team ownership matters: the team that builds the UI owns its BFF, so UI changes do not wait on a back-end team's roadmap.

### Ways to build a BFF with Next.js
| Mechanism | Use for | Notes |
|---|---|---|
| **Server Components + a data access layer** | Reading data for a page | The Server Component *is* the BFF for that view: fan out with `Promise.all`, return JSX. No extra HTTP hop (principle 6) |
| **Server Actions** | Mutations from your own UI | Public POST endpoints: authenticate, validate and authorise each |
| **Route Handlers** (`app/api/**/route.ts`) | Endpoints for client-side calls (React Query, uploads, streaming, webhooks, non-UI clients) | Public HTTP endpoints; Node runtime for long-lived streams |
| **Proxy / rewrites** | Pass-through to a service, header injection | A thin proxy is not a BFF; it adds no composition. Fine for auth header and streaming |
| **Separate BFF service** | Several clients, non-Next consumers | More infrastructure; justified when one BFF serves mobile and web |

### Practical patterns in Next.js (TypeScript)

**Fan-out in a Server Component (no extra endpoint needed)**
```ts
// data/dashboard.ts
import "server-only";

export async function getDashboardDTO(userId: string) {
  const [user, usage, projects] = await Promise.all([      // parallel, internal network
    users.get(userId),
    billing.usage(userId),
    projects.recent(userId, { limit: 5 }),
  ]);
  return {                                                  // UI-shaped, minimal
    name: user.displayName,
    creditsLeft: usage.limit - usage.used,
    recent: projects.map((p) => ({ id: p.id, title: p.title })),
  };
}
```
```tsx
// app/(app)/dashboard/page.tsx
export default async function Page() {
  const user = await getSessionUser();
  const dto = await getDashboardDTO(user.id);
  return <Dashboard {...dto} />;
}
```

**Partial failure handled once**
```ts
const results = await Promise.allSettled([users.get(id), billing.usage(id), projects.recent(id)]);
const [u, b, p] = results;
return {
  name: u.status === "fulfilled" ? u.value.displayName : "there",
  usage: b.status === "fulfilled" ? b.value : null,         // UI renders a degraded card, not a crash
  recent: p.status === "fulfilled" ? p.value : [],
};
```
Use `Promise.all` when every part is required; `allSettled` when sections can degrade independently.

**Route Handler as a BFF endpoint (for client-side data hooks)**
```ts
// app/api/dashboard/route.ts
import { NextResponse } from "next/server";

export async function GET() {
  const user = await getSessionUser();
  if (!user) return NextResponse.json({ error: "unauthorised" }, { status: 401 });
  return NextResponse.json(await getDashboardDTO(user.id));  // same DTO function, different entry point
}
```
Keep the logic in the data function; both the Server Component and the route handler call it.

**Streaming pass-through proxy (when you only need auth and transport)**
```ts
export const runtime = "nodejs";
export const dynamic = "force-dynamic";

export async function POST(req: Request) {
  const token = await getServerAccessToken();
  const upstream = await fetch(`${process.env.SERVER_URL}/chat`, {
    method: "POST",
    headers: { authorization: `Bearer ${token}`, "content-type": "application/json" },
    body: req.body,
    // @ts-expect-error duplex is required for streaming request bodies in Node
    duplex: "half",
  });
  return new Response(upstream.body, { status: upstream.status, headers: upstream.headers });
}
```
Strip hop-by-hop headers and the session cookie before forwarding, and pass the response body through unchanged so Server-Sent Events are not buffered.

**Anti-corruption mapping**
```ts
// Map internal names to UI names in one function; services can change without UI churn.
const toProjectCard = (p: InternalProject): ProjectCard => ({
  id: p.project_uuid,
  title: p.display_title ?? "Untitled",
  updatedAt: p.modified_ts,
});
```

### Rules of thumb
1. **No domain logic in the BFF**; compose, translate, secure.
2. **One contract per screen/experience**, typed and validated.
3. **Fan out in parallel**; decide per section whether failure is fatal or degradable.
4. **Prefer Server Components for reads**; add Route Handlers only for client-initiated calls.
5. **Keep secrets and downstream tokens server-side.**
6. **Return minimal DTOs**; never forward raw service responses.
7. **Set timeouts and budgets** per downstream call; one slow service must not hold the page.
8. **The front-end team owns it**, with tests and observability like any service.

### Industry best practices
- **Timeouts, retries (idempotent calls only), circuit breakers and fallbacks** on every downstream call; bound the total request time.
- **Propagate request IDs and trace context** (`traceparent`, OpenTelemetry) from the browser through the BFF to services so a slow page can be traced end to end.
- **Cache at the BFF** what is shared (`use cache`, `React.cache()`), never per-user data in a shared cache.
- **Authorise at the BFF and again in services**; the BFF is not a trust boundary replacement.
- **Validate inputs and outputs** with schemas; reject unknown fields.
- **Rate limit** and add abuse protection on public Route Handlers.
- **Version the BFF contract** with the front end in the same repo and release (they deploy together).
- **Generate clients** for downstream services from their OpenAPI documents so the BFF is typed.
- **Log aggregated latency per downstream call** to find the slowest dependency.
- **Keep the BFF stateless** so it scales horizontally; session state lives in a store or signed cookie.
- **Limit to one BFF per client type**, and resist adding a second general-purpose API in the same layer.

### Things to avoid
- Putting business rules, pricing or authorisation decisions only in the BFF.
- A "thin proxy" that forwards everything and is called a BFF (no composition, no benefit, new attack surface).
- Letting the browser call internal services directly with long-lived tokens.
- Sequential `await`s for independent downstream calls (server waterfall).
- Returning entire downstream payloads and trimming on the client.
- One giant "get everything" endpoint that every screen shares.
- A BFF owned by the back-end team's backlog, so UI changes queue behind unrelated work.
- Swallowing downstream errors and returning `200` with empty data and no signal.
- Server Components fetching their own `/api` route handlers (an extra hop for no benefit).
- Exposing Route Handlers without authentication because "only our front end calls it".
- Shared mutable module state in the BFF (leaks between requests).

### Checklist
- [ ] Each major screen is served by one data function returning a UI-shaped DTO.
- [ ] Independent downstream calls run in parallel with explicit timeouts.
- [ ] Failure policy per section is explicit (required vs degradable).
- [ ] Tokens and service credentials never reach the browser; cookies are not forwarded downstream.
- [ ] Route Handlers and Server Actions authenticate, validate and authorise.
- [ ] Internal field names and IDs are mapped, not leaked.
- [ ] Trace and request IDs propagate to downstream calls; per-dependency latency is logged.
- [ ] Domain rules stay in services; the BFF has none.
- [ ] Streaming endpoints run on the Node runtime and are not buffered by proxies.

### In this codebase
Measured with a quick scan of `src/` (not a full audit):
- `src/app/api/backend/[...path]/route.ts` is a **same-origin streaming proxy** to the back-end (Node runtime, `maxDuration` 800, drops hop-by-hop headers and the session `cookie`, forwards a Bearer token, passes the upstream body straight through so SSE is not buffered). It replaced a `next.config.ts` rewrite that buffered chunked responses. This is a pass-through proxy, not yet a composing BFF.
- `src/app/api/chat/route.ts` and `src/app/api/persona-chat/route.ts` are named routes for the streaming chat paths.
- `src/proxy.ts` (Next.js 16 proxy, formerly middleware) calls the back-end `/users/me` to gate onboarding, with a per-user positive cache so each prefetched link no longer costs a backend call.
- Screens that currently make several client calls on mount (dashboards, settings, billing and plan pages) are candidates for a server data function that fans out with `Promise.all` and returns a DTO; the proxy can stay for streaming and generic calls.
