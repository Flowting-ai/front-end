## 37. REST vs GraphQL

> Resource endpoints versus one endpoint that returns exactly what you ask for. GraphQL ends over- and under-fetching. REST caches better and debugs easier.

### Definition
- **REST** models the API as **resources** addressed by URL (`/projects/42`), manipulated with HTTP verbs (`GET`, `POST`, `PUT`/`PATCH`, `DELETE`). The server decides the response shape per endpoint. It leans on HTTP itself: status codes, caching headers, content negotiation.
- **GraphQL** exposes a **typed schema** behind (usually) one endpoint. The client sends a query naming the exact fields it wants, across related objects, and gets back a response with exactly that shape. Writes are **mutations**; live updates are **subscriptions**.

Neither is "better". They move complexity to different places: REST puts it in **many endpoints and many round trips**; GraphQL puts it in **a query engine, resolvers and a more demanding caching story**.

### Key properties

**1. Over-fetching and under-fetching**
- *Over-fetching*: an endpoint returns 40 fields, the screen needs 3. *Under-fetching*: one screen needs data from four endpoints, so four round trips (and a waterfall if they depend on each other).
- GraphQL removes both by letting the client select fields and traverse relations in **one request**.
- REST mitigations: sparse fieldsets (`?fields=id,title`), expansion (`?include=owner`), purpose-built endpoints, or a Backend for Frontend (principle 41) that returns one UI-shaped response.

**2. Caching**
- REST: **HTTP caching works out of the box.** `GET /projects/42` is a cacheable URL for the browser, the CDN and Next.js's own data cache (`use cache`, `revalidate`, tags). `ETag` and `Cache-Control` give conditional requests and stale-while-revalidate.
- GraphQL: queries are usually **`POST` to one URL**, which browsers and most CDNs do not cache. Options: **normalised client caches** (Apollo Client, urql graphcache, Relay), **persisted queries** with `GET` (send a hash, so a CDN can cache), and server-side response caching. This works, but needs deliberate setup.

**3. Debugging and tooling**
- REST: `curl`, browser address bar, network panel and logs show URL, status and body at a glance. Per-endpoint metrics and rate limits are natural.
- GraphQL: every request is `POST /graphql` with `200 OK` even when it contains errors (`errors[]` next to `data`). You need operation names in logs and traces, schema-aware tooling (GraphiQL, Apollo Studio) and per-field performance tracing.

**4. Types and contracts**
- REST: contract is an **OpenAPI** document. Generate TypeScript types or a client from it (`openapi-typescript`, `openapi-fetch`, `orval`) so the front end is typed without hand-copying.
- GraphQL: the **schema is the contract** and is introspectable. Generate typed operations with GraphQL Code Generator (client preset). Changes are additive by convention (deprecate fields, do not version the endpoint).

**5. Evolution**
- REST: versioning (`/v2`, headers) or additive changes. Many clients mean many versions to support.
- GraphQL: continuous schema evolution with `@deprecated`, field usage analytics tell you when something is safe to remove.

**6. Server cost and safety**
- REST cost per endpoint is predictable. GraphQL clients can write expensive queries: deeply nested selections, huge lists, N+1 resolvers. You need **depth and complexity limits, pagination everywhere, DataLoader-style batching, timeouts, persisted-query allow-lists and rate limiting by query cost**, plus authorisation **per field/resolver**.
- File upload, streaming and binary responses are natural in REST; in GraphQL they need extra specs or a side channel.

### Decision table
| Situation | Lean towards |
|---|---|
| Public API, third-party consumers, CDN-cacheable content | **REST** |
| Many different clients (web, iOS, Android, partners) each needing different shapes | **GraphQL** |
| One web app, one team, one backend | **REST** (plus typed client); add a BFF if screens need aggregation |
| Deeply relational UI that fetches many entities per screen | **GraphQL**, or REST with includes / BFF |
| Heavy HTTP caching, simple CRUD, file transfer | **REST** |
| Federation across many services behind one graph | **GraphQL** (federated gateway) |
| Small team, little GraphQL experience, tight deadline | **REST** |
| Real-time collaboration with partial updates | Either, with SSE/WebSocket (principle 44) |

### Practical patterns in Next.js (TypeScript)

**REST in a Server Component (cached, typed)**
```ts
// lib/data/projects.ts
import "server-only";

export async function getProject(id: string) {
  const res = await fetch(`${process.env.API_URL}/projects/${id}`, {
    headers: { authorization: `Bearer ${process.env.API_TOKEN}` },
    next: { revalidate: 60, tags: [`project:${id}`] },   // HTTP-style caching, tag-based invalidation
  });
  if (!res.ok) throw new Error(`Project ${id}: ${res.status}`);
  return (await res.json()) as Project;
}
```
`fetch` in Next.js composes with the framework's caching and request deduplication; a `POST`-based GraphQL call does not get the same automatic treatment.

**Typed REST from an OpenAPI document**
```ts
// npx openapi-typescript ./openapi.yaml -o src/lib/api/schema.d.ts
import createClient from "openapi-fetch";
import type { paths } from "./schema";

export const api = createClient<paths>({ baseUrl: "/api/backend" });

const { data, error } = await api.GET("/projects/{id}", { params: { path: { id: "42" } } });
```

**GraphQL with persisted queries and `GET` (CDN-friendly reads)**
```ts
// Apollo Client link chain: persisted query hash, GET for hashed queries
import { createPersistedQueryLink } from "@apollo/client/link/persisted-queries";
import { sha256 } from "crypto-hash";

const persisted = createPersistedQueryLink({ sha256, useGETForHashedQueries: true });
// link = persisted.concat(httpLink)   // mutations still use POST
```
Better still for production: **registered (allow-listed) persisted queries**, where the server only accepts known operations. That removes arbitrary-query abuse and keeps requests small.

**GraphQL in a Server Component (no client library)**
```ts
// lib/data/graphql.ts
import "server-only";

export async function gql<T>(query: string, variables?: Record<string, unknown>): Promise<T> {
  const res = await fetch(process.env.GRAPHQL_URL!, {
    method: "POST",
    headers: { "content-type": "application/json", authorization: `Bearer ${process.env.API_TOKEN}` },
    body: JSON.stringify({ query, variables }),
    cache: "no-store",                                   // POST is not cached by default; be explicit
  });
  const json = await res.json();
  if (json.errors?.length) throw new Error(json.errors[0].message);   // 200 can still mean failure
  return json.data as T;
}
```

**Gateway option: GraphQL for clients, REST behind it**
- A GraphQL layer (or a BFF, principle 41) can aggregate several REST services for the front end while the services stay simple and cacheable.

### Rules of thumb
1. **Default to REST with a typed client**; adopt GraphQL for a clear, named problem (many client shapes, graph-shaped UI, federation).
2. **Fix under-fetching first with a BFF or includes**; it solves most of the same pain.
3. **Generate types from the contract** (OpenAPI or GraphQL schema); never hand-write response types.
4. **Make reads cacheable**: stable URLs and `Cache-Control` for REST; persisted queries over `GET` for GraphQL.
5. **Always check `errors[]`** on GraphQL responses; a `200` is not success.
6. **Bound everything on the server**: pagination, depth, complexity, timeouts.
7. **Name every GraphQL operation** so logs, traces and metrics are readable.
8. **Pick one primary style per application**, and wrap the other behind it if both exist.

### Industry best practices
- **REST**: nouns for resources, plural collections, consistent verbs; correct status codes; idempotent `PUT`/`DELETE`; `Idempotency-Key` for retryable `POST`; pagination, filtering and sorting through query parameters; `ETag`/`If-None-Match`; standard error body (RFC 9457 problem details); an OpenAPI document as the source of truth; additive changes and clear deprecation (`Deprecation` / `Sunset` headers).
- **GraphQL**: design the schema around the domain, not the database; use Relay-style cursor connections for lists (principle 39); nullable by default for fields that can fail; return typed errors (union result types) for expected failures; use `@deprecated`; disable introspection and the playground in production where the API is not public; enforce depth and cost limits; batch with DataLoader; trace per resolver.
- **Both**: authenticate and authorise on the server for every operation and field; rate limit; log with request IDs and operation names; contract tests in CI; publish changelogs.
- **Client**: central API module (principle 40), runtime validation of responses at the boundary (Zod) where the backend is not fully trusted, and one error model (principle 45).

### Things to avoid
- Choosing GraphQL "because it is modern" for a CRUD app with one client.
- Exposing a public GraphQL API without depth, cost and rate limits (a single query can take the server down).
- Letting clients send arbitrary query strings in production when persisted-query allow-listing is possible.
- N+1 resolver patterns with no batching.
- Returning `200` for everything in REST, or hiding errors in the body.
- Verbs in URLs (`/getUser`, `/createOrder`) and inconsistent naming.
- Breaking REST response shapes without versioning or deprecation.
- Hand-written `any`-typed fetch calls and copied response types that drift from the contract.
- Using GraphQL for file uploads, large binaries or streaming without a plan.
- Treating introspection and a dev playground as safe on the public internet.
- Building a "REST-shaped" GraphQL schema (one query per table) that gains none of the benefits.
- Mixing two data-fetching styles inside one component tree with no boundary.

### Checklist
- [ ] A written reason exists for the chosen style and who the consumers are.
- [ ] Types are generated from OpenAPI or the GraphQL schema, not hand-written.
- [ ] Reads that can be cached are cacheable (URL + headers, or persisted queries over `GET`).
- [ ] GraphQL: depth/complexity limits, pagination on lists, batching, field-level authorisation, introspection policy.
- [ ] REST: correct status codes, standard error format, idempotency keys on retried writes, pagination.
- [ ] Every GraphQL operation is named; logs and traces include operation name and request ID.
- [ ] One error model on the client for both transport-level and GraphQL `errors[]`.
- [ ] Contract tests run in CI; breaking changes are blocked or versioned.

### In this codebase
Measured with a quick scan of `src/` (not a full audit):
- The front end talks **REST** to a separate back-end project (Python, with an `openapi.yaml`). Calls go through a same-origin proxy at `src/app/api/backend/[...path]/route.ts` and a central `apiFetch` in `src/lib/api/client.ts`. No GraphQL library is installed.
- The back-end's error bodies use a `detail` array with `loc`/`msg`, consistent with a validation-oriented REST API; `scripts/split-openapi.mjs` splits the OpenAPI document by tag, so a contract file exists.
- Response types appear to be hand-maintained alongside Zod schemas (`src/lib/api/*-schemas.ts`). Generating types from the OpenAPI document (for example with `openapi-typescript`) would remove drift risk.
- Under-fetching is best handled with a BFF endpoint (principle 41) for screens that currently chain several calls; GraphQL is not justified for one web client and one back-end.
