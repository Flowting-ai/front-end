## 43. tRPC: End-to-End Types

> Call server procedures from the client with full TypeScript inference. No codegen, no schema files to keep in sync. A private contract, not for public APIs.

### Definition
tRPC lets a TypeScript client call server **procedures** as if they were local functions, with input and output types **inferred directly from the server code**. There is no OpenAPI file, no GraphQL schema and no generated client: the type of the server's `AppRouter` is imported into the client **as a type only**, and the compiler does the rest.

```
server:  const appRouter = router({ post: router({ byId: query(...) }) })
                              │  export type AppRouter = typeof appRouter
client:  trpc.post.byId.query({ id })   ◀── fully typed, autocompleted, refactor-safe
```

Under the hood it is plain HTTP + JSON (queries via `GET`, mutations via `POST`), so it works with fetch, caching headers and standard infrastructure.

### Key properties

**1. Types flow from server to client with no build step**
- Rename a field on the server and the client **fails to compile** until it is updated. Refactors are safe across the boundary.
- Input validation (Zod, Valibot, ArkType) doubles as the **input type**; the return type is inferred from the resolver.

**2. A private contract between two parts of one codebase**
- tRPC shines when **the same team owns client and server** and both are TypeScript, ideally in one repo or monorepo (principle 17).
- It is **not** a public API format: no stable URL contract, no language-neutral schema, no versioning story for external consumers. For public or multi-language APIs use REST + OpenAPI or GraphQL (principle 37).

**3. No schema to maintain, but a tighter coupling**
- Client and server share a type, so they must be **deployed together** or be compatible. A skewed deploy (old client, new server) can break at runtime even though types were fine at build time. Keep procedures backward compatible across a rollout window.
- The client imports **types only** (`import type { AppRouter }`); never import server runtime code into the client bundle.

**4. Procedures: queries, mutations, subscriptions**
- `query` for reads, `mutation` for writes, `subscription` for streams (SSE via `httpSubscriptionLink`, or WebSockets).
- **Middleware** and **context** give you authentication, logging and rate limiting on groups of procedures; **`protectedProcedure`** is the common pattern.

**5. Pairs naturally with TanStack Query**
- In v11 the recommended client is `@trpc/tanstack-react-query`: `trpc.post.byId.queryOptions({ id })` returns standard `queryOptions`, so everything in principle 38 (keys, invalidation, optimistic updates, SSR hydration) applies unchanged. Query keys are generated from the procedure path and input, giving hierarchical keys for free.

**6. Works with the App Router**
- The HTTP endpoint is a Route Handler using the fetch adapter. A **server-side caller** invokes procedures directly from Server Components with no HTTP hop, and can prefetch into a hydrated cache.

### When to use it
| Use when | Avoid when |
|---|---|
| One team owns web client and API; both TypeScript | Public API or third-party integrators |
| Next.js full-stack app or TypeScript monorepo | Back-end is in another language (Python, Go, Java) |
| You want refactor-safe, schema-free types | Mobile or other native clients must share the API |
| Rapid iteration on internal product features | You need a stable, versioned contract and independent deploys |
| You are already using TanStack Query | A separate back-end team owns an OpenAPI contract |

### Practical patterns in Next.js (TypeScript)

**Initialise tRPC with context and a protected procedure**
```ts
// trpc/init.ts
import "server-only";
import { initTRPC, TRPCError } from "@trpc/server";
import { cache } from "react";
import { z } from "zod";

export const createTRPCContext = cache(async () => ({ user: await getSessionUser() }));
type Context = Awaited<ReturnType<typeof createTRPCContext>>;

const t = initTRPC.context<Context>().create();
export const createTRPCRouter = t.router;
export const baseProcedure = t.procedure;

export const protectedProcedure = t.procedure.use(({ ctx, next }) => {
  if (!ctx.user) throw new TRPCError({ code: "UNAUTHORIZED" });     // authenticate once, in middleware
  return next({ ctx: { user: ctx.user } });                         // narrows ctx.user to non-null
});
```

**Router with validated input**
```ts
// trpc/routers/post.ts
export const postRouter = createTRPCRouter({
  byId: protectedProcedure
    .input(z.object({ id: z.string().uuid() }))
    .query(async ({ ctx, input }) => {
      const post = await db.post.findFirst({ where: { id: input.id, ownerId: ctx.user.id } });  // ownership check
      if (!post) throw new TRPCError({ code: "NOT_FOUND" });
      return { id: post.id, title: post.title };                                              // DTO, not the row
    }),
  rename: protectedProcedure
    .input(z.object({ id: z.string().uuid(), title: z.string().trim().min(1).max(80) }))
    .mutation(({ ctx, input }) => renameOwnedPost(ctx.user.id, input.id, input.title)),
});

// trpc/routers/_app.ts
export const appRouter = createTRPCRouter({ post: postRouter });
export type AppRouter = typeof appRouter;             // the only thing the client imports (as a type)
```

**HTTP endpoint (fetch adapter, App Router)**
```ts
// app/api/trpc/[trpc]/route.ts
import { fetchRequestHandler } from "@trpc/server/adapters/fetch";
import { appRouter } from "@/trpc/routers/_app";
import { createTRPCContext } from "@/trpc/init";

const handler = (req: Request) =>
  fetchRequestHandler({ endpoint: "/api/trpc", req, router: appRouter, createContext: createTRPCContext });
export { handler as GET, handler as POST };
```

**Client usage with TanStack Query (v11 integration)**
```tsx
"use client";
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";
import { useTRPC } from "@/trpc/client";

export function PostTitle({ id }: { id: string }) {
  const trpc = useTRPC();
  const qc = useQueryClient();
  const post = useQuery(trpc.post.byId.queryOptions({ id }));            // typed key, input and output
  const rename = useMutation(
    trpc.post.rename.mutationOptions({
      onSuccess: () => qc.invalidateQueries(trpc.post.byId.queryFilter({ id })),   // targeted invalidation
    }),
  );
  return <button onClick={() => rename.mutate({ id, title: "New" })}>{post.data?.title}</button>;
}
```

**Server Component: direct caller, no HTTP**
```tsx
// app/(app)/post/[id]/page.tsx
import { trpc, HydrateClient, prefetch } from "@/trpc/server";

export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  prefetch(trpc.post.byId.queryOptions({ id }));         // fill the cache on the server
  return <HydrateClient><PostTitle id={id} /></HydrateClient>;
}
```

**Infer types without importing the server**
```ts
import type { inferRouterInputs, inferRouterOutputs } from "@trpc/server";
import type { AppRouter } from "@/trpc/routers/_app";

export type RouterInputs = inferRouterInputs<AppRouter>;
export type RouterOutputs = inferRouterOutputs<AppRouter>;
type Post = RouterOutputs["post"]["byId"];
```

### Rules of thumb
1. **Use tRPC only for a private, same-team, TypeScript-to-TypeScript contract.**
2. **Validate every input with a schema**; never trust the client even though types match.
3. **Authenticate in middleware, authorise in each procedure** by ownership.
4. **Return DTOs**, not database rows.
5. **Import the router type only** in client code (`import type`).
6. **Keep procedures backward compatible** during a deploy window.
7. **Use the TanStack Query integration** so principle 38 applies unchanged.
8. **Call procedures directly from Server Components** instead of making an HTTP hop.

### Industry best practices
- Organise **routers by domain** (`post`, `billing`, `team`) and merge them in one `appRouter`; keep resolvers thin and put logic in service functions that can be tested without HTTP.
- Use **Zod/Valibot schemas shared** with forms (React Hook Form resolver) so client and server validate the same shape.
- Use **`TRPCError` codes** (`UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `BAD_REQUEST`, `TOO_MANY_REQUESTS`) and an **error formatter** that adds a safe, structured Zod error for form mapping (principle 45).
- Add **middleware** for logging, tracing, rate limiting and timing per procedure.
- Use **batching** (`httpBatchLink`) to merge parallel calls into one request, and streaming batches (`httpBatchStreamLink`) for slow procedures, while keeping an eye on request size limits.
- Add **`superjson`** (or the built-in transformer support) only when you really need `Date`, `Map` or `BigInt` across the wire.
- **Set cache headers** for public queries via `responseMeta`, and revalidate with server-side tags where appropriate.
- Consider **OpenAPI generation** (`trpc-to-openapi`) if you later need a REST surface for a few endpoints.
- **Contract-test** critical procedures and run `tsc` in CI so type breaks are caught before merge.
- **Keep the router type light**: very large routers can slow the TypeScript language server; split packages or use project references in big monorepos.

### Things to avoid
- Exposing tRPC as a public or partner API.
- Using tRPC when the back-end is not TypeScript (you lose the whole point).
- Importing server runtime code (database client, secrets) into client bundles; import types only.
- Skipping input validation because "TypeScript already checks types" (types vanish at runtime).
- Returning ORM entities with internal or sensitive fields.
- Authorisation only in the UI or only in a single middleware with no per-resource checks.
- Treating every call as a procedure and recreating a god-router with hundreds of endpoints.
- Deploying client and server independently with breaking procedure changes and no compatibility window.
- Mixing tRPC and ad hoc `fetch("/api/...")` calls for the same feature.
- Leaving the error shape default and string-matching messages in the client.
- Relying on tRPC alone for file uploads or very large streaming payloads without checking how they are handled.

### Checklist
- [ ] The consumers are only this team's TypeScript clients; no public API need.
- [ ] Every procedure has an `.input()` schema and returns a DTO.
- [ ] `protectedProcedure` (or equivalent) authenticates; each procedure authorises by ownership.
- [ ] Client code imports `type AppRouter` only; no server code in the client bundle.
- [ ] TanStack Query integration is used; keys and invalidation follow principle 38.
- [ ] Server Components use the direct caller and hydrate the client cache.
- [ ] Errors use `TRPCError` codes and a formatter that exposes field errors safely.
- [ ] Rollouts keep procedures backward compatible for one deploy window.
- [ ] `tsc` and tests run in CI; large routers are split to keep type-checking fast.

### In this codebase
Measured with a quick scan:
- **tRPC is not used and is not a fit as things stand.** The back-end is a separate Python project (`back-end/` with `pyproject.toml`, `alembic` and an `openapi.yaml`), so there is no shared TypeScript to infer from. The cross-language contract is OpenAPI.
- The equivalent safety here comes from **types generated from the OpenAPI document** (for example `openapi-typescript`) plus Zod schemas at the boundary (`src/lib/api/*-schemas.ts`), see principle 37.
- tRPC could be considered only for a **TypeScript-only server layer inside the Next.js app** (for example a BFF composing several services for the web UI, principle 41), where the web client is the only consumer.
