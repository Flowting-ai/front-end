## 45. API-Layer Error Handling

> Handle network, HTTP and validation errors, each with a different strategy. 422 errors map back to specific form fields. Interceptors handle global 401s once.

### Definition
API-layer error handling is the part of the front end that turns **anything that can go wrong in a request** into **one predictable error model** the UI can act on. A request can fail in three different places, and each needs a different response:

| Class | What happened | Example | Strategy |
|---|---|---|---|
| **Network** | No response: offline, DNS, CORS, timeout, abort | `TypeError: Failed to fetch`, `AbortError` | Retry (idempotent calls), show offline/"try again", never show raw text |
| **HTTP** | A response arrived with a non-2xx status | `401`, `403`, `404`, `409`, `429`, `5xx` | Act on the **status**: re-auth, show permission message, retry later, show not found, report |
| **Validation** | The server rejected the *input* (often `400`/`422`) | `422` with `{ field: message }` list | Map to **specific form fields**; user fixes input; no retry |
| **Contract** | `2xx` but the body does not match the expected shape | Missing field, wrong type | Treat as a bug: report, show generic error; catch with schema parsing |

Errors are **expected** (a failed request is normal operation) or **exceptions** (a bug). Expected errors are modelled as data or typed errors and shown in the UI; only unexpected ones reach an error boundary (principle 19).

### Key properties

**1. One normalised error model**
- All failures become an `ApiError` (or a `Result`) with: `kind` (`network | http | validation | contract`), `status`, a stable machine **`code`**, a **user-safe `message`**, optional **`fieldErrors`**, a **`requestId`**, and `retryable`.
- UI code branches on `kind` and `code`, never on message strings or raw `Response` objects.

**2. Different strategy per class**
- **Network**: retry **idempotent** requests (GET, PUT, DELETE, or POST with an `Idempotency-Key`) with exponential backoff and jitter, a small cap, and respect for `AbortSignal`. Show "You appear to be offline" using `navigator.onLine` plus failed-request evidence.
- **`401`**: the session or token is invalid or expired. Handle **once**, in the transport layer (see interceptors).
- **`403`**: authenticated but not allowed; show a permission message; do not retry.
- **`404`**: resource missing; render `not-found`/empty state (`notFound()` in Server Components).
- **`409`**: conflict (stale edit, duplicate); offer reload or merge.
- **`422` / `400` validation**: map to fields (below).
- **`429`**: rate limited; honour `Retry-After`, back off, tell the user.
- **`5xx`**: server problem; retry limited idempotent requests, then show a generic "try again" with a reference ID; report.

**3. Validation errors map to fields**
- `422` bodies carry a list of problems with a **path** (`loc`, `pointer`, or field name). Convert them to `{ fieldName: message }` and call the form library's `setError` for each, so the user sees the message beside the exact input and focus moves to the first invalid field.
- Unmapped errors (no matching field) appear in a form-level alert (`role="alert"`).
- **Validate on the client for speed, and always on the server for truth.** Share the schema (Zod) where both sides are TypeScript.

**4. Interceptors handle cross-cutting errors once**
- A single transport wrapper (an `apiFetch`, an Axios interceptor, a `fetch` middleware or a tRPC link) adds auth headers, parses errors into the model, **refreshes the token on `401` and retries once**, and emits a global "session expired" event when refresh fails.
- Prevent a **refresh stampede**: many parallel requests that all get `401` must share **one** refresh promise (single-flight), then retry.
- Components never implement their own `401` handling.

**5. Never show raw errors to users**
- Map `code`/`status` to **friendly, localised messages**; keep technical detail in logs. Never expose stack traces, SQL, internal hostnames or upstream provider messages.
- Always show a **next step**: retry, fix a field, sign in, contact support with a reference ID.

**6. Validate responses at the boundary**
- Parse successful responses with a schema (Zod) in the data function. A shape mismatch becomes a `contract` error (and a Sentry event) instead of `undefined is not a function` deep in a component.

**7. Report with context**
- Send `kind`, `status`, `code`, `requestId`, route and release to your error tracker (principle 19). Do **not** report expected user errors (`401` redirects, `404`, validation) as exceptions; count them as metrics instead.

### Practical patterns in Next.js (TypeScript)

**Error model**
```ts
// lib/api/errors.ts
export type FieldErrors = Record<string, string>;

export class ApiError extends Error {
  constructor(
    public readonly kind: "network" | "http" | "validation" | "contract",
    message: string,
    public readonly opts: { status?: number; code?: string; fieldErrors?: FieldErrors; requestId?: string; retryable?: boolean } = {},
  ) {
    super(message);
    this.name = "ApiError";
  }
}
```

**Normalise any failure (network, HTTP, validation) in one place**
```ts
// lib/api/request.ts
export async function request<T>(path: string, init: RequestInit & { schema?: z.ZodType<T> } = {}): Promise<T> {
  let res: Response;
  try {
    res = await fetch(`/api/backend${path}`, init);
  } catch (e) {
    if (e instanceof DOMException && e.name === "AbortError") throw e;               // let cancellation through
    throw new ApiError("network", "Unable to reach the server.", { retryable: true });
  }

  if (res.ok) {
    const json = res.status === 204 ? undefined : await res.json();
    if (!init.schema) return json as T;
    const parsed = init.schema.safeParse(json);
    if (!parsed.success) throw new ApiError("contract", "Unexpected response.", { status: res.status });
    return parsed.data;
  }

  const body = await res.json().catch(() => null);                                    // body may not be JSON
  const requestId = res.headers.get("x-request-id") ?? undefined;

  if (res.status === 422 || res.status === 400) {
    throw new ApiError("validation", "Please check the highlighted fields.", {
      status: res.status, fieldErrors: toFieldErrors(body), requestId,
    });
  }
  throw new ApiError("http", messageFor(res.status, body?.code), {
    status: res.status, code: body?.code, requestId,
    retryable: res.status === 429 || res.status >= 500,
  });
}
```

**Map `422` to form fields (React Hook Form)**
```ts
// FastAPI-style: { detail: [{ loc: ["body","email"], msg: "invalid email", type: "..." }] }
export function toFieldErrors(body: any): Record<string, string> {
  const out: Record<string, string> = {};
  const items = Array.isArray(body?.detail) ? body.detail : body?.errors ?? [];
  for (const d of items) {
    const path = Array.isArray(d.loc) ? d.loc.filter((p: string) => p !== "body").join(".") : d.field;
    if (path && !(path in out)) out[path] = d.msg ?? d.message;
  }
  return out;
}
```
```tsx
const form = useForm<FormValues>({ resolver: zodResolver(schema) });
const save = useMutation({
  mutationFn: createProject,
  onError: (e) => {
    if (e instanceof ApiError && e.kind === "validation") {
      Object.entries(e.opts.fieldErrors ?? {}).forEach(([name, message]) =>
        form.setError(name as keyof FormValues, { type: "server", message }));
      form.setFocus(Object.keys(e.opts.fieldErrors ?? {})[0] as keyof FormValues);   // focus first invalid field
    } else {
      toast.error(e instanceof ApiError ? e.message : "Something went wrong.");
    }
  },
});
```

**Global `401`: single-flight refresh, retry once, then sign out (the interceptor)**
```ts
let refreshing: Promise<boolean> | null = null;

async function withAuth(path: string, init: RequestInit): Promise<Response> {
  const res = await fetch(path, init);
  if (res.status !== 401) return res;

  refreshing ??= refreshSession().finally(() => { refreshing = null; });   // all parallel 401s share one refresh
  const ok = await refreshing;
  if (!ok) {
    window.dispatchEvent(new Event("auth:session-expired"));               // one listener redirects to login
    return res;
  }
  return fetch(path, init);                                                // retry exactly once
}
```
Retry only requests that are safe to repeat; for non-idempotent writes, refresh first and let the user resubmit if the first attempt may have reached the server.

**Retry policy in React Query (principle 38)**
```ts
new QueryClient({
  defaultOptions: {
    queries: {
      retry: (count, error) =>
        error instanceof ApiError && error.opts.retryable && count < 2,         // never retry 4xx / validation
      retryDelay: (n) => Math.min(1000 * 2 ** n, 10_000) * (0.5 + Math.random() / 2),
    },
    mutations: { retry: false },                                                // writes are not retried by default
  },
});
```

**Global handlers for logging and toasts**
```ts
const queryClient = new QueryClient({
  queryCache: new QueryCache({
    onError: (error, query) => {
      if (error instanceof ApiError && error.kind === "http" && (error.opts.status ?? 0) >= 500) report(error);
    },
  }),
});
```

**Server Components and Server Actions**
```ts
// Server Component: expected failure rendered, missing resource → notFound()
const res = await fetch(url);
if (res.status === 404) notFound();
if (!res.ok) return <p role="alert">Could not load this section.</p>;

// Server Action: return validation errors as data
const parsed = Schema.safeParse(Object.fromEntries(formData));
if (!parsed.success) return { fieldErrors: z.flattenError(parsed.error).fieldErrors };
```

### Rules of thumb
1. **One error model, one place that creates it.** UI branches on `kind`/`code`.
2. **Different class, different strategy**; do not treat every failure as "show a toast".
3. **Map `422` to fields**, focus the first invalid one, and keep the user's input.
4. **Handle `401` once** in the transport layer with single-flight refresh and one retry.
5. **Retry only idempotent, retryable failures**, with backoff, jitter and a cap.
6. **Never show raw messages**; show friendly text and a reference ID.
7. **Parse responses with a schema** so contract drift becomes a clear error.
8. **Report unexpected errors, count expected ones.**

### Industry best practices
- Use **RFC 9457 Problem Details** (`application/problem+json`: `type`, `title`, `status`, `detail`, `instance`, plus extension members) as the server error format, and agree **stable error `code`s** with the back end instead of parsing messages.
- Include an **`x-request-id`/trace ID** on every response and show it in support-facing error UI.
- Honour **`Retry-After`** on `429` and `503`; cap total retry time; stop retrying when the user navigates away (`AbortSignal`).
- Use **timeouts** on every request (`AbortSignal.timeout(ms)`) and distinguish user-cancel from timeout.
- Use **idempotency keys** for payment and create operations so retries do not duplicate.
- **Localise** user messages and keep technical detail out of translations.
- Provide **inline, accessible errors**: associate with inputs via `aria-describedby`, announce with `role="alert"` or live regions, move focus to the first error (principle 20).
- **Degrade gracefully**: show cached data with a "could not refresh" banner when a refetch fails (React Query keeps stale `data` alongside `error`).
- **Offline UX**: detect offline, queue safe actions, and retry on reconnect.
- Add **contract tests** against the OpenAPI document so error shapes do not drift silently.
- **Test error paths** deliberately (MSW handlers returning `401`, `422`, `429`, `500`, timeouts, malformed JSON).

### Things to avoid
- Matching on `error.message` text to decide behaviour (brittle, breaks with copy or locale changes).
- A global toast for every error, including validation errors the form should show inline.
- Implementing `401` handling in individual components or hooks.
- Refreshing the token separately in every parallel request (refresh stampede and race conditions).
- Retrying `POST` payments or creates without idempotency keys.
- Retrying `4xx` errors (they will not succeed) or retrying forever.
- Showing raw server messages, stack traces or upstream provider errors to users.
- Swallowing errors (`catch {}`) so failed saves look successful.
- Clearing the form on error, or only showing "Invalid input" without field detail.
- Treating a `200` with an error body as success, or assuming a `2xx` body matches your types.
- Reporting every `401`/`404`/validation response to the error tracker as an exception.
- Logging request bodies, tokens or personal data in error reports.

### Checklist
- [ ] A single `ApiError` (or `Result`) model with `kind`, `status`, `code`, `message`, `fieldErrors`, `requestId`.
- [ ] One transport function normalises network, HTTP, validation and contract errors.
- [ ] A single interceptor handles `401` with single-flight refresh, one retry, and a global session-expired event.
- [ ] `422`/`400` validation errors map to form fields; focus moves to the first invalid field.
- [ ] Retries apply only to idempotent, retryable failures, with backoff, jitter, cap, `Retry-After` and abort support.
- [ ] User-facing messages are friendly, localised and include a reference ID; no raw server text.
- [ ] Responses are parsed with schemas; contract failures are reported.
- [ ] Unexpected errors are reported with context; expected errors are metrics, not exceptions.
- [ ] Error paths (`401`, `403`, `404`, `409`, `422`, `429`, `5xx`, offline, timeout) are covered by tests.

### In this codebase
Measured with a quick scan of `src/` (not a full audit):
- `src/lib/api/client.ts` already implements most of the pattern: an `ApiError` class (`status`, `code`, `message`, `rawMessage`), a central `apiFetch` with **one silent token refresh and retry on `401`**, a global `auth:session-expired` event plus toast when the second attempt fails, an onboarding/checkout exception that does not sign the user out, and parsing of the back-end's `detail` array (`loc` and `msg`) into a combined message.
- `friendlyApiError` (same file) and `getFriendlyHttpErrorText` map errors to friendly text by **matching message substrings** as well as status (for example "token expired", "rate limit", "fetch failed"). Status and an agreed error `code` are more robust than text matching, which breaks when back-end copy changes.
- Validation details (`422` with `loc`/`msg`) are **joined into one string**, so forms cannot highlight individual fields. Returning `fieldErrors` from the transport (see `toFieldErrors` above) would let forms call `setError` per field.
- Check that the refresh is **single-flight** across parallel requests (`src/lib/jwt-utils.ts` deduplicates in-flight token fetches, which is the same idea), and that non-idempotent writes are not blindly retried after a `401`.
- The error-reporting side (no tracker installed, boundary only logs to the console) is covered in principle 19.
