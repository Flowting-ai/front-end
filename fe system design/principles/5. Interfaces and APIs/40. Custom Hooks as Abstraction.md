## 40. Custom Hooks as Abstraction

> Wrap data-fetching logic so components stay clean and the source is hidden. Change REST to GraphQL to WebSocket in one place. Co-locate the hook with its feature.

### Definition
A custom hook is a function whose name starts with `use` and that calls other hooks. It packages **stateful logic** (fetching, subscriptions, form state, timers) behind a small, intention-revealing interface: `const { data, isPending, error } = usePosts(userId)`.

As an **architecture boundary**, a data hook is the seam between **UI** and **data source**. Components say *what they need* (`usePosts`), the hook decides *how to get it* (REST, GraphQL, WebSocket, cache). Swap the transport and only the hook changes.

```
Component  ──▶  useFeature()  ──▶  data function / client  ──▶  network
 (what)          (the seam)          (how, where, which protocol)
```

### Key properties

**1. Components depend on an interface, not a transport**
- A component never contains `fetch("/api/...")`, a query key, a URL, a WebSocket message type or a GraphQL document.
- It consumes a stable return shape, so migrating REST → GraphQL → WebSocket (or adding caching) is a change in one file.

**2. A narrow, stable return contract**
- Return what the UI needs: data, status flags, and a few actions (`refetch`, `create`, `remove`). Hide the library: components should not need to know React Query exists.
- Decide the contract once and keep it stable; changing it is a refactor of every consumer.

**3. Layering**
| Layer | Responsibility | Knows about |
|---|---|---|
| Component | Render, wire events | Hook interface only |
| Feature hook (`usePosts`) | Query keys, caching rules, mapping to UI model, optimistic updates | Data functions, cache library |
| Data function (`getPosts`, `createPost`) | HTTP/GraphQL call, auth header, parse and validate, throw typed errors | URL, protocol, schema |
| Transport client (`apiFetch`, socket provider) | Base URL, auth refresh, interceptors, retries | Network |

Each layer only calls the one below it.

**4. Co-locate by feature**
- Keep the hook next to the feature that owns it: `features/posts/use-posts.ts`, `features/posts/api.ts`, `features/posts/queries.ts`, `features/posts/PostList.tsx`.
- Promote a hook to a shared `hooks/` folder only when two or more features need it and it has no feature-specific knowledge (`useDebouncedValue`, `useMediaQuery`).

**5. Hooks share logic, not state**
- Each call to a hook creates its **own** state. Two components calling `useCounter()` do not share a counter. To share, put the state in a cache (React Query), a context, a store or the URL.

**6. Rules of Hooks apply**
- Call hooks at the top level, never conditionally, in loops or after early returns. The `eslint-plugin-react-hooks` rules enforce this and flag missing effect dependencies.

### What belongs in a hook, and what does not
| Put in a hook | Keep out of it |
|---|---|
| Fetching + caching + invalidation rules for a feature | JSX and styling |
| Subscribing/unsubscribing (WebSocket, observers, media queries) | Business rules that are not tied to React state (put in plain functions) |
| Form wiring (validation, submit, field errors) | Anything the server should decide (authorisation, pricing) |
| Mapping API shape to UI model (`select`) | Side effects at module load |
| Debounce, throttle, local persistence | Global singletons with hidden state |

Pure logic with no React state (formatting, sorting, mapping) is better as a **plain function**: easier to test, usable on the server.

### Practical patterns in Next.js (TypeScript)

**Feature folder**
```
features/posts/
  api.ts           // getPosts, createPost: the only place that knows URLs
  queries.ts       // query keys + queryOptions (principle 38)
  use-posts.ts     // usePosts, useCreatePost: the public interface
  PostList.tsx
  index.ts         // exports only what other features may use
```

**Data function: the "how"**
```ts
// features/posts/api.ts
import { apiFetch } from "@/lib/api/client";
import { PostSchema } from "./schemas";

export async function getPosts(userId: string, signal?: AbortSignal) {
  const res = await apiFetch(`/users/${userId}/posts`, { signal });
  return PostSchema.array().parse(await res.json());      // validate at the boundary
}
```

**Hook: the "seam"**
```ts
// features/posts/use-posts.ts
"use client";
import { useQuery } from "@tanstack/react-query";
import { postListOptions } from "./queries";

export function usePosts(userId: string) {
  const q = useQuery(postListOptions(userId, {}));
  return {
    posts: q.data ?? [],
    isLoading: q.isPending,
    error: q.error,
    refresh: q.refetch,
  };                                                       // stable, library-agnostic contract
}
```
Components import `usePosts`; the cache library is an implementation detail.

**Swapping the source later (one place)**
```ts
// Same contract, different transport: components do not change.
export function usePosts(userId: string) {
  const [posts, setPosts] = useState<Post[]>([]);
  useEffect(() => {
    const unsubscribe = socket.subscribe("posts", { userId }, setPosts);   // WebSocket instead of REST
    return unsubscribe;
  }, [userId]);
  return { posts, isLoading: false, error: null, refresh: () => socket.request("posts:refresh") };
}
```
In practice you would keep the REST read for the first page and use the socket to push updates into the same cache (principle 44).

**Generic utility hook (shared, no feature knowledge)**
```ts
export function useDebouncedValue<T>(value: T, ms = 250) {
  const [v, setV] = useState(value);
  useEffect(() => {
    const t = setTimeout(() => setV(value), ms);
    return () => clearTimeout(t);              // cleanup is part of the contract
  }, [value, ms]);
  return v;
}
```

**Effect cleanup and cancellation**
```ts
export function useEventStream(url: string, onMessage: (e: MessageEvent) => void) {
  const handler = useEffectEvent(onMessage);   // stable callback that sees latest props (React 19.2)
  useEffect(() => {
    const es = new EventSource(url);
    es.onmessage = handler;
    return () => es.close();                   // always release the resource
  }, [url]);
}
```

**Server vs client**
- Hooks only run in Client Components. For data the server can supply, fetch in a Server Component or a plain async data function (principle 6) and pass props; reuse the same `api.ts` functions in both places.

### Rules of thumb
1. **One hook per intent** (`usePosts`, `useCreatePost`), not one mega hook per page.
2. **No URLs, keys or protocol details in components.**
3. **Return a small, stable, library-agnostic object.**
4. **Co-locate by feature**; promote to shared only after the second use and when generic.
5. **Put pure logic in plain functions**, orchestration in hooks.
6. **Always clean up** subscriptions, timers and listeners.
7. **Memoise returned callbacks/objects only when consumers depend on identity**; with the React Compiler on, avoid manual noise.
8. **Test hooks** with `renderHook` and mocked data functions, not a real network.

### Industry best practices
- Follow the **`use` prefix** convention and the **Rules of Hooks**; enforce with `eslint-plugin-react-hooks`.
- Keep hooks **composable**: small hooks combined into larger ones (`useDebouncedValue` + `usePosts` = `useSearchPosts`).
- Return **objects for many values**, tuples only for two-value pairs like `useState`.
- Validate data at the boundary (Zod) in the data function so every hook returns trusted types.
- Make hooks **SSR-safe**: do not read `window` or `localStorage` during render; use effects or `useSyncExternalStore` with a server snapshot.
- Use **`useSyncExternalStore`** for external stores and browser APIs (online status, media queries, WebSocket state).
- Provide **typed generics** for reusable hooks (`useLocalStorage<T>`), and a stable cache key per instance.
- Expose **cancellation** (`AbortSignal`) and **error** state consistently across data hooks (principle 45).
- **Document the contract** with a short comment and an example; treat the return shape as an API.
- Prefer **dependency injection by arguments** (pass the client/function) when a hook must be testable without module mocking.

### Things to avoid
- Components that call `fetch` directly, build URLs or know query keys.
- "God hooks" returning 20 values and handling several unrelated concerns.
- Hooks that read global mutable state or perform work at import time.
- Hidden side effects: a hook named `useX` that also navigates, shows toasts and writes storage without saying so.
- Passing unstable inline objects/functions as dependencies, causing effect loops.
- Using a hook just to wrap one `useState` with no added meaning.
- Returning the raw library result (`UseQueryResult`) everywhere, leaking the dependency to the whole UI.
- Calling hooks conditionally to "skip" fetching; use `enabled` or a parent component instead.
- Forgetting cleanup, leaving sockets, timers and listeners alive after unmount.
- Sharing a hook between features by importing across feature folders; extract the generic part instead.
- Assuming two calls to a hook share state.

### Checklist
- [ ] No component contains a URL, a query key, or a transport detail.
- [ ] Every feature has a data layer (`api.ts`) and a hook layer (`use-*.ts`) with a stable contract.
- [ ] Hooks are co-located with their feature; shared hooks are generic and feature-agnostic.
- [ ] Data functions validate responses and throw typed errors.
- [ ] Hooks clean up subscriptions, timers and listeners; fetches accept `AbortSignal`.
- [ ] Hooks are SSR-safe (no `window` reads during render).
- [ ] `eslint-plugin-react-hooks` is on and has no suppressions without a reason.
- [ ] Hooks have tests using `renderHook` and mocked data functions.
- [ ] Swapping the transport for one feature would touch only that feature's data and hook files.

### In this codebase
Measured with a quick scan of `src/` (not a full audit):
- `src/hooks/` holds about 25 shared hooks (chat history, streaming chat, persona repos, credit status, model selection and more), plus `src/lib/queries/personas.ts` as a React Query hook. Most feature hooks live in the global `hooks/` folder rather than next to their feature; for data hooks, co-locating them with the feature would clarify ownership.
- `usePersonas` (`src/lib/queries/personas.ts`) is a clean example of the seam: it wraps `fetchPersonas`, hides the key, and bridges an existing window event into invalidation, so consumers did not need to change.
- Data functions already exist in `src/lib/api/*.ts` behind `apiFetch`, and Zod schemas sit next to them. The remaining work is mostly components that still fetch with local state or call API modules directly; moving those behind `use-*` hooks gives the one-place-to-change property.
- `use-streaming-chat.ts` and the SSE code are good candidates for the documented hook contract (principle 44), because the transport (SSE today) may change.
