## 38. React Query Patterns

> Three core hooks map cleanly to the three client-server interactions: `useQuery` (read and cache), `useMutation` (writes and optimistic UI), `useInfiniteQuery` (paginated feeds). Hierarchical query keys enable targeted invalidation. `['posts', userId, { filter }]` is the shape.

### Definition
TanStack Query (formerly React Query) manages **server state** on the client: data that lives on the server, is shared, and can become stale. It provides caching, request deduplication, background refetching, retries, mutation handling and cache invalidation, so components stop hand-rolling `useEffect` + `useState` + loading flags.

The key mental split: **server state** (owned by the server, cached copy in the browser) versus **client state** (UI state owned by the browser). Query manages the first; `useState`, URL and context manage the second (principle 13).

### Key properties

**1. Three hooks, three interactions**
| Interaction | Hook | What it gives you |
|---|---|---|
| Read | `useQuery` | Cached data, `isPending`, `isError`, `isFetching`, automatic refetch on mount, focus and reconnect |
| Write | `useMutation` | Imperative `mutate`/`mutateAsync`, status, callbacks for optimistic updates, rollback and invalidation |
| Paginated feed | `useInfiniteQuery` | `pages` array, `fetchNextPage`, `hasNextPage`, built for cursors (principle 39) |

**2. Hierarchical query keys**
- A key is an **array** that uniquely describes the data and its inputs: `['posts', userId, { filter, sort }]`.
- Order from **general to specific**. A prefix matches everything below it, so `invalidateQueries({ queryKey: ['posts'] })` refreshes every posts query, while `['posts', userId]` refreshes only one user's.
- Include **every variable the query function reads** in the key; if it changes, the key changes, and a new cache entry is fetched.
- Keys are compared by **deep equality of JSON-serialisable values**; object key order does not matter, array order does.

**3. Cache timing: two settings to understand**
- `staleTime`: how long data counts as **fresh** (no refetch on mount/focus). Default `0`, so data is stale immediately.
- `gcTime` (formerly `cacheTime`): how long **unused** data stays in memory before garbage collection (default 5 minutes).
- Tune `staleTime` per data type: seconds for live data, minutes for reference data, `Infinity` for immutable data.

**4. Mutations: optimistic UI and invalidation**
- After a write, either **invalidate** the affected keys (simplest, correct) or **update the cache directly** with the server response (`setQueryData`).
- For instant UI use an optimistic update: cancel in-flight queries, snapshot, write the guess to the cache, **roll back on error**, then **invalidate on settle** so the server's truth wins.
- In v5 there is a simpler option: render from `mutation.variables` while `isPending`, with no cache writes and nothing to roll back.

**5. Infinite queries**
- v5 requires `initialPageParam`; `getNextPageParam(lastPage)` returns the next cursor, or `undefined` when there is no more.
- The cache holds all loaded pages as one entry; use `maxPages` to cap memory for very long feeds.

**6. Server rendering with the App Router**
- Prefetch on the server (`queryClient.prefetchQuery`), `dehydrate`, and wrap a client subtree in `<HydrationBoundary>`; the client `useQuery` with the **same key** starts with data.
- Create a **new `QueryClient` per request on the server** and one per browser session on the client, never a module-level singleton on the server (it would leak data between users).
- Share the key and function with **`queryOptions`** so server and client cannot drift.
- Set a non-zero `staleTime` (for example 60 s) so the client does not refetch immediately after hydration.

### Where React Query fits in the App Router
| Need | Prefer |
|---|---|
| Initial page data, SEO, no client interactivity | Server Component `fetch` (principle 6) |
| Data that users refresh, poll, filter live, or mutate with instant feedback | React Query in a Client Component |
| Same data on server first paint and live updates after | Server prefetch + `HydrationBoundary` + `useQuery` |
| One-off form submit | Server Action (`useActionState`), no Query needed |

### Practical patterns in Next.js (TypeScript)

**Query key factory and `queryOptions`**
```ts
// features/posts/queries.ts
import { queryOptions, infiniteQueryOptions } from "@tanstack/react-query";
import { fetchPosts, fetchPostsPage } from "./api";

export type PostFilter = { status?: "draft" | "published"; q?: string };

export const postKeys = {
  all: ["posts"] as const,
  lists: () => [...postKeys.all, "list"] as const,
  list: (userId: string, filter: PostFilter) => [...postKeys.lists(), userId, filter] as const,
  detail: (id: string) => [...postKeys.all, "detail", id] as const,
};

export const postListOptions = (userId: string, filter: PostFilter) =>
  queryOptions({
    queryKey: postKeys.list(userId, filter),
    queryFn: ({ signal }) => fetchPosts(userId, filter, signal),   // signal enables cancellation
    staleTime: 30_000,
  });

export const postFeedOptions = (userId: string) =>
  infiniteQueryOptions({
    queryKey: [...postKeys.all, "feed", userId] as const,
    queryFn: ({ pageParam, signal }) => fetchPostsPage(userId, pageParam, signal),
    initialPageParam: null as string | null,
    getNextPageParam: (last) => last.nextCursor ?? undefined,
  });
```
One factory, one shape: invalidating `postKeys.lists()` refreshes every list; `postKeys.detail(id)` touches one.

**`useQuery` in a custom hook (principle 40)**
```ts
// features/posts/use-posts.ts
"use client";
import { useQuery, keepPreviousData } from "@tanstack/react-query";
import { postListOptions, type PostFilter } from "./queries";

export function usePosts(userId: string, filter: PostFilter) {
  return useQuery({ ...postListOptions(userId, filter), placeholderData: keepPreviousData });
}
```
`placeholderData: keepPreviousData` keeps the old list on screen while a new filter loads, so the UI does not flash empty.

**`useMutation` with optimistic update and rollback**
```ts
"use client";
import { useMutation, useQueryClient } from "@tanstack/react-query";
import { postKeys } from "./queries";

export function useRenamePost() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (v: { id: string; title: string }) => renamePost(v.id, v.title),
    onMutate: async (v) => {
      await qc.cancelQueries({ queryKey: postKeys.detail(v.id) });       // stop in-flight refetches
      const previous = qc.getQueryData<Post>(postKeys.detail(v.id));     // snapshot
      qc.setQueryData<Post>(postKeys.detail(v.id), (p) => (p ? { ...p, title: v.title } : p));
      return { previous };
    },
    onError: (_e, v, ctx) => qc.setQueryData(postKeys.detail(v.id), ctx?.previous),   // rollback
    onSettled: (_d, _e, v) => {
      qc.invalidateQueries({ queryKey: postKeys.detail(v.id) });         // server truth wins
      qc.invalidateQueries({ queryKey: postKeys.lists() });
    },
  });
}
```
Simpler alternative for a single visible list: show `mutation.variables` while `isPending` and skip the cache work.

**`useInfiniteQuery` feed**
```tsx
"use client";
import { useInfiniteQuery } from "@tanstack/react-query";
import { postFeedOptions } from "./queries";

export function Feed({ userId }: { userId: string }) {
  const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfiniteQuery(postFeedOptions(userId));
  const posts = data?.pages.flatMap((p) => p.items) ?? [];
  return (
    <>
      {posts.map((p) => <PostCard key={p.id} post={p} />)}
      {hasNextPage && (
        <button onClick={() => fetchNextPage()} disabled={isFetchingNextPage}>Load more</button>
      )}
    </>
  );
}
```
Trigger `fetchNextPage` from an `IntersectionObserver` sentinel for infinite scroll, and keep a visible button as a keyboard-accessible fallback.

**Server prefetch and hydration (App Router)**
```tsx
// app/(app)/posts/page.tsx   Server Component
import { dehydrate, HydrationBoundary, QueryClient } from "@tanstack/react-query";
import { postListOptions } from "@/features/posts/queries";
import { PostList } from "@/features/posts/PostList";

export default async function Page() {
  const user = await getSessionUser();                  // authenticate on the server
  const qc = new QueryClient();                         // new per request
  await qc.prefetchQuery(postListOptions(user.id, {}));
  return (
    <HydrationBoundary state={dehydrate(qc)}>
      <PostList userId={user.id} />                     {/* client component calls useQuery with the same key */}
    </HydrationBoundary>
  );
}
```
```tsx
// app/providers.tsx
"use client";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { useState } from "react";

export function Providers({ children }: { children: React.ReactNode }) {
  const [client] = useState(() => new QueryClient({
    defaultOptions: { queries: { staleTime: 60_000, retry: 1 } },
  }));
  return <QueryClientProvider client={client}>{children}</QueryClientProvider>;
}
```
Prefetched data is dehydrated into the HTML, so do not prefetch user-private data into a shared cache (principle 21).

**Dependent and parallel queries**
```ts
const user = useQuery(userOptions(id));
const projects = useQuery({ ...projectsOptions(user.data?.orgId ?? ""), enabled: !!user.data?.orgId });
```
Use `enabled` for dependent queries, and `useQueries` or separate hooks for parallel ones. For waterfalls you control, fetch both on the server instead.

### Rules of thumb
1. **Server state in Query, client state elsewhere.** Never copy query data into `useState`.
2. **One key factory per feature**; keys are hierarchical, general to specific, and include every input.
3. **Use `queryOptions`/`infiniteQueryOptions`** to share config between server prefetch and client hooks.
4. **Set `staleTime` deliberately**; the default `0` refetches more than most apps need.
5. **After a mutation, invalidate by prefix**; add optimistic updates only where latency matters.
6. **Pass `signal`** to `fetch` so cancelled queries stop network work.
7. **New `QueryClient` per request on the server**; one stable client in the browser.
8. **Wrap queries in domain hooks** (principle 40); components do not know keys or URLs.

### Industry best practices
- Prefer **`isPending`/`isError` + `data`** narrowing in TypeScript (v5 types are discriminated), and use **Suspense variants** (`useSuspenseQuery`) with error boundaries (principle 19) when you want loading and error UI out of the component.
- Use **`select`** to derive a slice of cached data so components re-render only when that slice changes.
- Use **`setQueryData` with the mutation response** for single-entity updates to avoid an extra refetch.
- **Throw typed errors** from query functions (principle 45), and decide retry per error: no retry for `4xx`, limited retry with backoff for network and `5xx`.
- Configure **global defaults** once (`staleTime`, `retry`, `refetchOnWindowFocus`), and a **global `onError`** via `QueryCache` / `MutationCache` for logging and toasts.
- **Poll sparingly** (`refetchInterval`) and pause when the tab is hidden (the default); prefer SSE/WebSocket for true real time (principle 44).
- Use **`persistQueryClient`** only for data safe to store on device, and clear it on logout.
- Install the **ESLint plugin** (`@tanstack/eslint-plugin-query`) to catch missing keys, unstable `QueryClient`s and `queryFn` dependencies not in the key.
- Use the **Devtools** in development to inspect keys, staleness and refetches.
- **Test** with a fresh `QueryClient` per test (`retry: false`) and a mocked network layer (MSW).

### Things to avoid
- Putting variables into the query function but not into the key (stale or shared cache bugs).
- Copying `data` into `useState` and editing it (two sources of truth).
- Creating `new QueryClient()` inside a component body without `useState` (a new cache every render).
- A module-level `QueryClient` on the server (data shared between users).
- Using Query to fetch data a Server Component could pass as props.
- Invalidating `[]` or everything after each mutation.
- `refetchOnWindowFocus` surprises on expensive endpoints left at defaults.
- Unbounded infinite lists with no `maxPages` or virtualisation.
- Using `mutateAsync` without `try/catch` (unhandled rejections), or `mutate` inside `useEffect` loops.
- Spreading complex objects with unstable identities into keys (new key every render).
- Storing sensitive data in a persisted cache.

### Checklist
- [ ] Each feature has one query-key factory; keys are hierarchical and include all inputs.
- [ ] `queryOptions` are shared between server prefetch and client hooks.
- [ ] `staleTime` and `retry` are configured intentionally (globally and per query type).
- [ ] Mutations invalidate by prefix; optimistic updates roll back on error and settle with invalidation.
- [ ] Infinite queries set `initialPageParam` and `getNextPageParam`, and cap pages for long feeds.
- [ ] `QueryClient` is created per request on the server and once per session on the client.
- [ ] Components consume domain hooks, not raw keys and URLs.
- [ ] Query functions accept `signal` and throw typed errors.
- [ ] ESLint plugin and devtools are enabled; tests use an isolated client.
