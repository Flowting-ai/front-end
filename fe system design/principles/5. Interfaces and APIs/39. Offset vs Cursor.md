## 39. Offset vs Cursor

> Page numbers break on live data; a cursor points to the last seen item. Offset shifts when items are inserted. Cursor is the only correct choice for feeds.

### Definition
- **Offset pagination** asks for "skip N, take M": `GET /posts?offset=40&limit=20` (or `?page=3&pageSize=20`). The server counts rows from the start of the result set.
- **Cursor pagination** (also called **keyset** or **seek** pagination) asks for "the items after this one": `GET /posts?after=eyJ…&limit=20`. The cursor encodes the **position of the last item seen**, usually its sort key.

Both return a page of items. They differ in what happens when the data **changes while the user is paging**, and in how well the database can serve deep pages.

### Key properties

**1. Offset shifts when data changes**
- A user is on page 2 (items 21 to 40). Meanwhile a new post is inserted at the top. When they load page 3 (`offset=40`), the item that used to be #40 is now #41, so it appears **again** at the top of page 3 (a **duplicate**).
- If an item is deleted, the opposite happens: an item slides from page 3 to page 2 and is **skipped**.
- On static, rarely changing data this is invisible. On a **live feed** it is a correctness bug.

**2. Cursor is stable**
- "Items older than the one with id X / timestamp T" does not change when new items are added at the top. No duplicates, no skips.
- The cursor is **opaque** to the client: it only sends back what the server gave it.

**3. Performance**
- Offset: the database must scan and discard `offset` rows. `OFFSET 100000` reads 100,000 rows to return 20, so deep pages get **slower linearly**.
- Cursor: a `WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 20` query uses an index and costs about the same on page 1 and page 10,000.

**4. What you give up with cursors**
- **No random access**: you cannot jump to "page 37". Only next and previous.
- **No cheap total count**: `COUNT(*)` on large tables is expensive; show "Load more" or "100+" instead of "page 3 of 87".
- Sorting must be **deterministic and unique**: sort by a column plus a **tiebreaker** (the id), or equal values will cause skips.

**5. Where offset is still fine**
- Small or mostly static datasets, admin tables where users want page numbers and a total, and search results ranked by a score where "page 3" is a meaningful concept. Cap the maximum offset and keep an index on the sort column.

### Decision table
| Situation | Use |
|---|---|
| Feeds, chat messages, notifications, activity logs, timelines | **Cursor** |
| Infinite scroll / "Load more" | **Cursor** |
| Data inserted or deleted while users browse | **Cursor** |
| Large tables, deep pages | **Cursor** |
| Small static list with numbered pages and a total count | Offset is acceptable |
| Admin grid needing "jump to page" and sort by any column | Offset, with limits (or hybrid) |
| Search results ranked by relevance | Offset with a cap, or a search engine's own cursor (`search_after`) |

### Practical patterns in Next.js (TypeScript)

**Response shape (a stable contract)**
```ts
type Page<T> = {
  items: T[];
  nextCursor: string | null;   // null means the end
  prevCursor?: string | null;  // only if backwards paging is supported
  hasMore: boolean;
};
```

**Opaque cursor encode/decode (server)**
```ts
// Cursor = base64url(JSON({ t: createdAtISO, id })). Sign or validate it; never trust it blindly.
const encode = (c: { t: string; id: string }) => Buffer.from(JSON.stringify(c)).toString("base64url");
const decode = (s: string) => {
  const parsed = JSON.parse(Buffer.from(s, "base64url").toString());
  return z.object({ t: z.string().datetime(), id: z.string().uuid() }).parse(parsed);
};
```
Validate the decoded value with a schema. A tampered cursor must produce `400`, not a SQL error.

**Keyset query (server, SQL idea)**
```sql
SELECT id, title, created_at
FROM posts
WHERE (created_at, id) < ($1, $2)          -- row comparison: after the cursor
ORDER BY created_at DESC, id DESC          -- unique, deterministic order
LIMIT $3 + 1;                              -- fetch one extra to know if there is more
```
Return the first `limit` rows; if `limit + 1` rows came back, `hasMore` is true and the cursor is built from the last returned row. Index `(created_at DESC, id DESC)`.

**Client: `useInfiniteQuery` maps one-to-one (principle 38)**
```ts
useInfiniteQuery({
  queryKey: ["posts", userId, "feed"],
  queryFn: ({ pageParam, signal }) => fetchPosts({ after: pageParam, limit: 20 }, signal),
  initialPageParam: null as string | null,
  getNextPageParam: (last) => last.nextCursor ?? undefined,   // undefined stops paging
});
```

**Newest items at the top of a live feed**
- Keep the cursor-based "older" pages, and fetch **newer** items separately (`?since=<newest id>`), merging them in on demand ("3 new posts" pill). Do not re-fetch page 1 and shift everything under the user.

**Chat history (load older on scroll up)**
- Page **backwards** with a `before` cursor, prepend the older page, and **preserve scroll position** (record `scrollHeight` before, adjust `scrollTop` after).

**Relay-style connections (GraphQL)**
```graphql
type PostConnection { edges: [PostEdge!]! pageInfo: PageInfo! }
type PostEdge { cursor: String! node: Post! }
type PageInfo { hasNextPage: Boolean! endCursor: String hasPreviousPage: Boolean! startCursor: String }
# posts(first: 20, after: "cursor")
```

**Server Component with URL cursor (shareable "next page" link)**
```tsx
export default async function Page({ searchParams }: { searchParams: Promise<{ after?: string }> }) {
  const { after } = await searchParams;
  const page = await listPosts({ after, limit: 20 });
  return (
    <>
      <PostList items={page.items} />
      {page.nextCursor && <Link href={`?after=${page.nextCursor}`}>Older posts</Link>}
    </>
  );
}
```
This gives crawlable, bookmarkable pagination for public lists with no client state. For private lists, avoid putting identifying data inside the cursor.

### Rules of thumb
1. **Feeds and chats use cursors.** Always.
2. **Sort by a unique, indexed key** (column + id tiebreaker).
3. **Cursors are opaque, validated, and sometimes signed.**
4. **Return `nextCursor` and `hasMore`**, and fetch `limit + 1` to know cheaply.
5. **Do not promise totals or page jumps** with cursors; design the UI around "load more".
6. **Cap `limit`** on the server (for example 100) and set a default.
7. **Handle empty and last pages** explicitly (`nextCursor: null`).
8. **Use offset only** for small or static data where page numbers add value.

### Industry best practices
- Use **keyset pagination** on any large table; add a **composite index** matching the `ORDER BY`.
- Make cursors **opaque and versioned** so the encoding can change without breaking clients; **sign** or encrypt them if they include data you do not want exposed or forged.
- Keep results **stable under writes**: for append-only data, include an upper bound or snapshot timestamp on the first request when strict consistency matters.
- **Combine filters and cursor**: the cursor belongs to a specific filter/sort; reject a cursor reused with a different sort.
- Provide **`Link` headers or `pageInfo`** following a standard (RFC 8288, Relay connection spec) rather than inventing field names.
- **Show approximate counts** (`~1.2k`) from an estimate or cached counter instead of exact `COUNT(*)` on hot paths.
- **Virtualise long lists** (`@tanstack/react-virtual`) and cap loaded pages (`maxPages`) to protect memory and scroll performance.
- Offer **both directions** (`before`/`after`) where users scroll up (chat) or browse around a deep link to an item.
- Document pagination behaviour in the OpenAPI/GraphQL schema, with examples.

### Things to avoid
- Offset pagination on live feeds, chat messages or notifications.
- `OFFSET` with very large values and no cap (slow, and a simple denial-of-service vector).
- Sorting by a non-unique column without a tiebreaker (skips and duplicates at page boundaries).
- Cursors that are raw row IDs or timestamps exposed as public, guessable, parseable values when ordering is not by that key.
- Trusting a client-supplied cursor without validation (injection, errors, data exposure).
- Using page numbers in the URL for infinite scroll lists, then breaking them when data shifts.
- Computing a total count on every request for large tables.
- Reusing a cursor across different sort orders or filters.
- Refetching page 1 to "refresh" and replacing the user's loaded pages, losing their place.
- Unlimited `limit` parameters.

### Checklist
- [ ] Every list that changes while being read uses cursor pagination.
- [ ] Order is deterministic: sort key plus unique tiebreaker, backed by a composite index.
- [ ] Cursor is opaque, validated server-side, and tied to its filter and sort.
- [ ] Response includes `nextCursor`/`hasMore` (or Relay `pageInfo`); the last page returns `null`.
- [ ] `limit` has a default and a server-side maximum.
- [ ] Client uses `useInfiniteQuery` (or equivalent) with `initialPageParam` and `getNextPageParam`.
- [ ] Newer items are fetched separately and merged without shifting the user's view.
- [ ] Long lists are virtualised and page count is capped.
- [ ] Offset pagination, where used, is justified (small, static) and capped.

### In this codebase
Measured with a quick scan of `src/` (not a full audit):
- The chat list and message history already use cursors: `listChats(cursor?)` in `src/lib/api/chat.ts` sends `?cursor=…` and reads `next_cursor` and `has_more`, and the messages endpoint takes a `cursor` too. This is the correct choice for feeds.
- `listChats` contains defensive handling for several response shapes (array, object with `chats`, and `next_cursor`/`has_more`). A single typed `Page<T>` contract, generated from the OpenAPI document, would remove that branching.
- The list pages are loaded with hand-written fetch state; moving them to `useInfiniteQuery` (principle 38) with `maxPages` and a virtualised list would remove most of the paging code in components.
- For chat history loaded upward on scroll, confirm scroll position is preserved when older pages are prepended.
