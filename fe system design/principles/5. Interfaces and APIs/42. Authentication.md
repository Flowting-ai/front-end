## 42. Authentication

> Sessions, JWTs or delegated OAuth: each with different trade-offs. Tokens in `localStorage`: one XSS owns all. Most apps should use a managed provider.

### Definition
**Authentication** answers "who is this?"; **authorisation** answers "what may they do?". They are separate, and authorisation must be enforced on the server at every data access (principle 21).

There are three common models:

| Model | How it works | Strengths | Weaknesses |
|---|---|---|---|
| **Server sessions** (opaque session ID in a cookie, state in a database or cache) | Cookie holds a random ID; server looks up the session | Instant revocation, small cookie, easy to reason about | Needs a shared store; one lookup per request |
| **Stateless sessions / JWT** (signed or encrypted token carries the claims) | Server verifies the signature, no lookup | No store, scales easily, good for service-to-service | **Hard to revoke** before expiry; larger; easy to misuse; claims go stale |
| **Delegated OAuth 2.0 / OpenID Connect** (sign in with an identity provider) | App redirects to a provider, gets an authorisation code, exchanges it for tokens | No password handling, SSO, MFA and social login, standard | Redirect flows, token management, provider dependency |

These are not exclusive: a typical modern setup is **OIDC login via a provider** → **an encrypted session in an `httpOnly` cookie** at the web app → **access tokens used server-side** to call APIs.

### Key properties

**1. Where the token lives decides the blast radius**
- **`localStorage` / `sessionStorage` / JS-readable cookies**: any XSS on your origin can read the token and exfiltrate it. One injected script owns every account that visits.
- **`httpOnly; Secure; SameSite` cookie**: JavaScript cannot read it. XSS can still make requests as the user while the page is open, but cannot steal the credential to use elsewhere.
- **In-memory only** (a variable): not persisted, not stealable from storage, but lost on reload and still reachable by XSS running on the page. Fine as a short-lived cache fed by a secure session.

**2. Prefer the BFF / "token handler" pattern for browser apps**
- The browser holds only an opaque session cookie. The **server** (your Next.js app) holds access and refresh tokens and calls APIs on the user's behalf (principle 41). No long-lived token ever reaches client JavaScript.
- This is the architecture recommended by current IETF guidance for browser-based OAuth clients.

**3. Use a managed provider unless you have a reason not to**
- Authentication has a long tail of hard problems: password hashing, breach detection, MFA, account recovery, session fixation, rate limiting, brute-force and credential-stuffing protection, social login quirks, passkeys, compliance.
- Managed options: Auth0, Clerk, WorkOS, Cognito, Firebase Auth, Supabase Auth, or open-source libraries (Auth.js, Better Auth, Lucia-style patterns). Choose one with first-class Next.js App Router support and server-side session helpers.

**4. OAuth 2.0 / OIDC, correctly**
- Use the **Authorization Code flow with PKCE** for every client (including confidential ones). The implicit flow and the password grant are deprecated.
- Validate `state` (CSRF) and `nonce` (replay) on the callback, validate ID token `iss`, `aud`, `exp` and signature, and use exact-match redirect URIs.
- Request **least-privilege scopes**; separate scopes and audiences per API.

**5. Session lifecycle**
- Short-lived access tokens (minutes) with **rotating refresh tokens**; absolute and idle timeouts for sessions; **re-authenticate for sensitive actions** (billing, email change).
- **Logout must end the session server-side** and, where supported, at the identity provider (single logout).
- Rotate the session identifier on login and privilege change to prevent fixation.

**6. Passwordless and strong auth**
- **Passkeys (WebAuthn)** resist phishing and remove passwords; offer them alongside or instead of passwords where the provider supports it. Support MFA (TOTP, push, passkey) and enforce it for admin roles.

**7. Authenticate in the right places in Next.js**
- **Proxy** (`proxy.ts`): optimistic redirects ("no session → go to login"), reading only the cookie. It is not the only line of defence.
- **Data access layer** and **each Server Action and Route Handler**: verify the session and authorisation again, close to the data.
- **Layouts do not re-run on every navigation**, so a layout check alone does not protect every child page.

### Practical patterns in Next.js (TypeScript)

**Stateless session in an `httpOnly` cookie (library-free sketch with `jose`)**
```ts
// lib/session.ts
import "server-only";
import { SignJWT, jwtVerify } from "jose";
import { cookies } from "next/headers";

const key = new TextEncoder().encode(process.env.SESSION_SECRET);   // 32+ bytes, server-only

export async function createSession(userId: string) {
  const expires = new Date(Date.now() + 8 * 60 * 60 * 1000);
  const jwt = await new SignJWT({ sub: userId })
    .setProtectedHeader({ alg: "HS256" })
    .setExpirationTime(expires)
    .sign(key);
  (await cookies()).set("session", jwt, {
    httpOnly: true, secure: true, sameSite: "lax", path: "/", expires,
  });
}

export async function getSession() {
  const token = (await cookies()).get("session")?.value;
  if (!token) return null;
  try {
    const { payload } = await jwtVerify(token, key, { algorithms: ["HS256"] });
    return { userId: String(payload.sub) };
  } catch {
    return null;                                   // expired or tampered
  }
}
```
This is the pattern the Next.js authentication guide shows. For production, prefer a vetted library or provider over maintaining this yourself, and add a database session when you need revocation.

**Data access layer re-checks on every call**
```ts
// data/auth.ts
import "server-only";
import { cache } from "react";
import { redirect } from "next/navigation";
import { getSession } from "@/lib/session";

export const requireUser = cache(async () => {
  const s = await getSession();
  if (!s) redirect("/login");
  return s;
});
```
```ts
// data/projects.ts
export async function getProjectDTO(id: string) {
  const { userId } = await requireUser();          // authenticate here, not just in the layout
  return db.project.findFirst({ where: { id, ownerId: userId } });   // and authorise by ownership
}
```

**Optimistic redirect in `proxy.ts` (cookie presence only)**
```ts
// proxy.ts
import { NextRequest, NextResponse } from "next/server";

export function proxy(req: NextRequest) {
  const hasSession = req.cookies.has("session");
  if (!hasSession && req.nextUrl.pathname.startsWith("/app")) {
    return NextResponse.redirect(new URL("/login", req.url));
  }
  return NextResponse.next();
}
export const config = { matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"] };
```
Proxy runs on every matched request, so keep it fast and do not query a database there. It is a convenience redirect, not an authorisation check.

**Managed provider (Auth0 SDK shape)**
```ts
// lib/auth0.ts
import { Auth0Client } from "@auth0/nextjs-auth0/server";
export const auth0 = new Auth0Client();           // session stored in an encrypted httpOnly cookie
```
```ts
// server code
const session = await auth0.getSession();                      // who is the user?
const { token } = await auth0.getAccessToken();                // access token for calling APIs, server-side only
```
The browser never sees the refresh token; the SDK handles login, callback, logout and token refresh routes.

**Server-side logout**
```ts
"use server";
export async function logout() {
  (await cookies()).delete("session");
  await db.session.deleteMany({ where: { userId: (await requireUser()).userId } });  // if using DB sessions
  redirect("/login");
}
```

### Rules of thumb
1. **Do not build your own auth** unless it is your product; use a managed provider or a vetted library.
2. **Tokens never in `localStorage`.** Use `httpOnly; Secure; SameSite` cookies.
3. **Browser holds an opaque session; server holds tokens** (BFF pattern).
4. **Authorise at the data layer** on every read and write; proxy and layouts are conveniences.
5. **Authorization Code + PKCE**, exact redirect URIs, validate `state`, `nonce`, `iss`, `aud`, `exp`.
6. **Short-lived access tokens, rotating refresh tokens, absolute session timeouts.**
7. **Re-authenticate for sensitive actions** and enforce MFA for privileged roles.
8. **Make logout real**: end the session on the server and at the provider.

### Industry best practices
- Follow **OWASP ASVS** (authentication and session management chapters) and the **OWASP Authentication and Session Management cheat sheets**.
- Offer **passkeys** and MFA; avoid SMS as the only second factor where better options exist.
- **Hash passwords** (if you must store them) with Argon2id or scrypt/bcrypt with a work factor; never encrypt or use fast hashes.
- **Rate limit and lock out** login, signup and reset endpoints; return generic messages to prevent account enumeration.
- Use **cookie prefixes** (`__Host-`) and `Secure`, `SameSite=Lax` or `Strict`, narrow `Path`, and the shortest lifetimes that work.
- **Rotate secrets** and signing keys; support key IDs (`kid`) and JWKS for verification.
- Keep **JWT payloads small and non-sensitive**; verify the algorithm explicitly (never accept `alg: none` or a client-chosen algorithm).
- Log authentication events (login, failed login, MFA changes, token refresh failures) and alert on anomalies.
- Plan **account recovery** as carefully as login; it is the usual weakest link.
- **Test the flows**: expired token, revoked session, tampered cookie, replayed callback, logout in another tab.
- Handle **multi-tab behaviour**: broadcast logout and session expiry so every tab reacts.

### Things to avoid
- Storing access tokens, refresh tokens or session IDs in `localStorage` or `sessionStorage`.
- Putting sensitive data in JWT payloads (they are signed, not secret, unless encrypted).
- Long-lived JWTs with no revocation strategy.
- Implicit flow, password grant, wildcard redirect URIs, or skipping PKCE.
- Authentication only in `layout.tsx` or only in `proxy.ts`.
- Trusting `userId`, role or tenant sent by the client.
- Decoding a JWT in the browser and treating its claims as proof of identity (decoding is not verifying).
- Rolling your own crypto, password storage or session scheme in a product that is not an auth product.
- Revealing whether an email exists in login and reset error messages.
- Leaving test or default credentials and unrestricted signup open in production.
- Forwarding the session cookie to downstream services instead of a purpose-issued token.

### Checklist
- [ ] A managed provider or vetted library handles login, MFA and account recovery.
- [ ] Browser holds only an `httpOnly; Secure; SameSite` session cookie; no tokens in web storage.
- [ ] Access and refresh tokens are used server-side only.
- [ ] Every data function, Server Action and Route Handler authenticates and authorises.
- [ ] OAuth uses Authorization Code + PKCE with validated `state`/`nonce`, exact redirect URIs.
- [ ] Session timeouts, token rotation, and logout (local and provider) are implemented and tested.
- [ ] Sensitive actions require recent authentication; privileged roles require MFA.
- [ ] Login, signup and reset endpoints are rate limited with non-enumerating messages.
- [ ] Auth events are logged and monitored; secrets and keys have a rotation plan.

### In this codebase
Measured with a quick scan of `src/` (not a full audit):
- Authentication is **delegated to Auth0** via `@auth0/nextjs-auth0` (`src/lib/auth0.ts`, `src/proxy.ts`), which keeps the session in server-managed cookies. This matches "use a managed provider".
- `src/lib/jwt-utils.ts` fetches the Auth0 access token on the client for the back-end's Bearer auth and keeps it **in a module variable (memory only)** with expiry tracking, a 60 s refresh buffer and a deduplicated in-flight refresh. No token write to `localStorage` was found in a text search. It is still reachable by XSS while the page is open, so the server-side proxy path (`/api/backend/...`, principle 41) is a good place to attach the token on the server instead and avoid giving client code the access token at all.
- `jwt-utils.ts` decodes the JWT `sub` and `exp` with `atob` without verifying a signature, which is acceptable for display and refresh timing only; the back-end must remain the verifier.
- `src/proxy.ts` uses the Auth0 session and a `/users/me` onboarding gate with a per-user cache; keep authorisation of data in the back-end and in server-side data functions rather than in the proxy alone.
