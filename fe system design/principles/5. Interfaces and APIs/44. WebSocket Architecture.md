## 44. WebSocket Architecture

> Open one connection per app in a provider; components subscribe to message types. Per-component sockets waste resources. Centralise reconnection and backoff.

### Definition
A **WebSocket** is a long-lived, full-duplex connection between browser and server over a single TCP connection (upgraded from HTTP). Either side can send messages at any time with little overhead. It suits **low-latency, bidirectional, high-frequency** traffic: chat, collaborative editing, presence, live cursors, multiplayer, trading feeds.

An **architecture** around it means three things: **one connection** owned by the app, a **typed message protocol**, and a **subscription layer** that components use without touching the socket.

```
        ┌───────────── Provider (one socket, reconnect, auth, heartbeat) ─────────────┐
Server ◀┤  messages ──▶ dispatcher ──▶ subscribers by message type / channel          │
        └────────────────────────▲──────────────────────────────┬─────────────────────┘
                                 │ useSubscription("chat:msg")  │ send(...)
                              Component A    Component B    Component C
```

### Key properties

**1. One connection per app, in a provider**
- A socket costs a TCP connection, TLS state, server memory, a file descriptor and often a licensed or metered connection slot. Ten components each opening a socket multiply all of that and can hit browser and server limits.
- A **provider** at a deep layout boundary owns the single instance, exposes `send` and `subscribe`, and shares connection status. Components subscribe by **message type or channel**; the provider routes.

**2. Centralise connection management**
- **Reconnection with exponential backoff and jitter**, a maximum delay, and a reset after a stable connection. Never reconnect in a tight loop.
- **Heartbeats** (ping/pong) detect half-open connections that the browser never reports closed.
- **Authentication** at connect time (short-lived ticket or first-message token, never a long-lived secret in the URL) and **re-auth on token refresh**.
- **Resubscribe** to channels after reconnect and **resync missed state** (fetch the gap with REST or request replay from a last-seen ID).
- **Pause when hidden or offline**: use `visibilitychange` and `online`/`offline` events to avoid wasted reconnects and battery drain.

**3. A typed, versioned message protocol**
- Use a **discriminated union** for messages: `{ type: "chat.message", payload: ... }`. Validate incoming frames with a schema (Zod) before dispatching.
- Include a message **ID**, optional **correlation ID** for request/response, and a protocol **version**.

**4. Sync WebSocket data into your cache, not into component state**
- Treat messages as **events that update the same cache** components already read (React Query `setQueryData` / `invalidateQueries`). The UI then has one source of truth, whether data arrived by REST or by push (principles 13 and 38).

**5. Choose the right transport**
| Need | Choose |
|---|---|
| Server → client only (notifications, progress, live feed, LLM token streaming) | **Server-Sent Events (SSE)**: plain HTTP, auto-reconnect, works through most proxies and with `fetch` streaming |
| Bidirectional, high-frequency, low latency (collaboration, games, presence) | **WebSocket** |
| Infrequent updates, simple | **Polling / refetch on focus** with React Query |
| Many-subscriber broadcast at scale, no infra to run | A managed realtime service (Ably, Pusher, PartyKit, Supabase Realtime) |
| New bidirectional streams with multiplexing (emerging) | WebTransport; not yet broadly dependable |

Start with the **simplest transport that works**; most "real-time" product features are one-directional and fit SSE.

**6. Next.js and hosting constraints**
- **Next.js Route Handlers cannot accept WebSocket upgrades** by themselves. Options: a **custom Node server** (`ws` or Socket.IO on the same port; you lose some platform optimisations), a community plugin that patches Next.js (fragile across versions), or, usually best, a **separate realtime service** (a standalone Node/Go/Python service or a managed provider).
- **Serverless platforms do not hold sockets open** (functions have time limits). Do not plan WebSockets on a pure serverless deployment without an external realtime service.
- **SSE through a Route Handler** works on the Node runtime: return a `Response` with a `ReadableStream` and `Content-Type: text/event-stream`. Mind proxy buffering, idle timeouts and `maxDuration`.

**7. Scaling and operations (server side)**
- Sockets are **stateful**: you need sticky sessions or a pub/sub backplane (Redis, NATS, Kafka) so a message reaches subscribers connected to other server instances.
- Limit **connections per user**, **message size and rate**, and **channel permissions**; authorise every subscription server-side.
- Monitor connections, reconnect rates, message latency and dropped frames.

### Practical patterns in Next.js (TypeScript)

**Typed message protocol**
```ts
// lib/realtime/protocol.ts
import { z } from "zod";

export const ServerMessage = z.discriminatedUnion("type", [
  z.object({ type: z.literal("chat.message"), id: z.string(), chatId: z.string(), text: z.string() }),
  z.object({ type: z.literal("presence.update"), userId: z.string(), online: z.boolean() }),
  z.object({ type: z.literal("pong") }),
]);
export type ServerMessage = z.infer<typeof ServerMessage>;
export type ClientMessage = { type: "subscribe" | "unsubscribe"; channel: string } | { type: "ping" };
```

**Single-connection provider with backoff, heartbeat and subscriptions**
```tsx
// lib/realtime/RealtimeProvider.tsx
"use client";
import { createContext, useContext, useEffect, useMemo, useRef, useState } from "react";
import { ServerMessage, type ClientMessage } from "./protocol";

type Handler = (m: ServerMessage) => void;
type Ctx = { status: "connecting" | "open" | "closed"; send: (m: ClientMessage) => void; subscribe: (type: ServerMessage["type"], h: Handler) => () => void };
const RealtimeContext = createContext<Ctx | null>(null);

export function RealtimeProvider({ url, children }: { url: string; children: React.ReactNode }) {
  const [status, setStatus] = useState<Ctx["status"]>("connecting");
  const ws = useRef<WebSocket | null>(null);
  const handlers = useRef(new Map<string, Set<Handler>>());

  useEffect(() => {
    let attempt = 0, closed = false, retry: ReturnType<typeof setTimeout>, beat: ReturnType<typeof setInterval>;

    const connect = async () => {
      setStatus("connecting");
      const ticket = await fetchSocketTicket();                         // short-lived token from your server
      const sock = new WebSocket(`${url}?ticket=${ticket}`);
      ws.current = sock;
      sock.onopen = () => { attempt = 0; setStatus("open"); beat = setInterval(() => sock.send(JSON.stringify({ type: "ping" })), 25_000); };
      sock.onmessage = (e) => {
        const parsed = ServerMessage.safeParse(JSON.parse(e.data));     // validate every frame
        if (parsed.success) handlers.current.get(parsed.data.type)?.forEach((h) => h(parsed.data));
      };
      sock.onclose = () => {
        clearInterval(beat); setStatus("closed");
        if (closed) return;
        const delay = Math.min(30_000, 500 * 2 ** attempt++) * (0.5 + Math.random() / 2);   // backoff + jitter
        retry = setTimeout(connect, delay);
      };
    };
    connect();
    return () => { closed = true; clearTimeout(retry); clearInterval(beat); ws.current?.close(); };
  }, [url]);

  const value = useMemo<Ctx>(() => ({
    status,
    send: (m) => ws.current?.readyState === WebSocket.OPEN && ws.current.send(JSON.stringify(m)),
    subscribe: (type, h) => {
      const set = handlers.current.get(type) ?? new Set<Handler>();
      set.add(h); handlers.current.set(type, set);
      return () => set.delete(h);                                       // unsubscribe on unmount
    },
  }), [status]);

  return <RealtimeContext.Provider value={value}>{children}</RealtimeContext.Provider>;
}

export const useRealtime = () => {
  const c = useContext(RealtimeContext);
  if (!c) throw new Error("useRealtime must be used inside RealtimeProvider");
  return c;
};
```

**Component-facing hook: subscribe to a message type**
```ts
// lib/realtime/use-subscription.ts
export function useSubscription<T extends ServerMessage["type"]>(type: T, onMessage: (m: Extract<ServerMessage, { type: T }>) => void) {
  const { subscribe } = useRealtime();
  const handler = useEffectEvent(onMessage);                            // latest callback without resubscribing
  useEffect(() => subscribe(type, handler as never), [subscribe, type]);
}
```

**Push into the React Query cache (single source of truth)**
```ts
function useChatLive(chatId: string) {
  const qc = useQueryClient();
  useSubscription("chat.message", (m) => {
    if (m.chatId !== chatId) return;
    qc.setQueryData<Message[]>(["chat", chatId, "messages"], (old = []) =>
      old.some((x) => x.id === m.id) ? old : [...old, toMessage(m)]);   // dedupe by id (replays happen)
  });
}
```

**Resync after reconnect**
```ts
// on status change to "open" after a gap:
qc.invalidateQueries({ queryKey: ["chat", chatId] });                   // fetch what was missed over REST
```

**SSE route handler (server → client streaming, no custom server)**
```ts
// app/api/stream/route.ts
export const runtime = "nodejs";
export const dynamic = "force-dynamic";

export async function GET(req: Request) {
  const stream = new ReadableStream({
    start(controller) {
      const enc = new TextEncoder();
      const timer = setInterval(() => controller.enqueue(enc.encode(`data: ${JSON.stringify({ t: Date.now() })}\n\n`)), 5000);
      req.signal.addEventListener("abort", () => { clearInterval(timer); controller.close(); });
    },
  });
  return new Response(stream, { headers: { "content-type": "text/event-stream", "cache-control": "no-cache, no-transform", connection: "keep-alive" } });
}
```

### Rules of thumb
1. **One socket per app**, owned by a provider; components subscribe by type or channel.
2. **Prefer SSE** for server → client; use WebSocket only for true bidirectional, high-frequency needs.
3. **Backoff with jitter, heartbeat, resubscribe, resync** are mandatory, not optional.
4. **Validate every frame** with a schema; the socket is untrusted input.
5. **Write incoming data into the cache** (principle 38), not scattered component state.
6. **Authorise at connect and per channel** on the server; use short-lived tickets.
7. **Do not host sockets on pure serverless**; use a custom server or a separate realtime service.
8. **Design for message loss and duplication**: idempotent handlers, message IDs, gap recovery.

### Industry best practices
- Use a **proven client library** for production (Socket.IO, `partysocket`/`reconnecting-websocket`, Ably, Pusher, or `graphql-ws`) rather than hand-rolling reconnection.
- **Multiplex** many logical channels over one socket; **batch and throttle** high-frequency updates (for example `requestAnimationFrame` or 50 to 100 ms buffers) before touching React state.
- **Use binary or compact encodings** (MessagePack, Protobuf) only when payload size or CPU measurements justify it; JSON is fine for most apps.
- **Compress** (permessage-deflate) selectively and cap **frame size**.
- **Close politely** with codes and reasons (`1000` normal, `1001` going away, `4xxx` app-defined, such as auth expired) and handle them differently on the client (do not retry on `auth failed`).
- Keep **WebSocket URLs free of long-lived secrets**; use `wss://`, validate `Origin` on the server to mitigate cross-site WebSocket hijacking, and apply rate limits.
- **Provide a fallback** (SSE or long-poll) for networks that block upgrades, or rely on a library that does.
- **Show connection state** in the UI ("Reconnecting…") and queue outbound messages with limits while offline.
- **Test** with network throttling, offline toggles, server restarts, and many tabs; load-test the server for concurrent connections and fan-out.
- **Observe**: connection counts, reconnect rate, send/receive latency, message error rate; alert on reconnect storms.

### Things to avoid
- Opening a WebSocket inside each component or hook instance.
- Reconnecting immediately and forever with no backoff (thundering herd after a deploy).
- Trusting incoming messages without validation, or rendering message content as HTML.
- Using WebSockets for data that updates every few minutes (polling or SSE is simpler).
- Authenticating with a long-lived token in the query string (it ends up in logs).
- Holding message state only in component `useState`, so a remount loses it.
- Assuming exactly-once, in-order delivery; not handling duplicates or gaps after reconnect.
- Deploying a socket server behind a load balancer without sticky sessions or a backplane.
- Leaking sockets: not closing on unmount, logout or token change.
- Sending large payloads or unbounded history over the socket instead of REST pagination (principle 39).
- Relying on the browser's `onclose` alone to detect dead connections.
- Choosing WebSockets for a pure serverless Next.js deployment without a separate service.

### Checklist
- [ ] Transport is chosen deliberately (SSE, WebSocket, polling, managed service) and the reason is written down.
- [ ] A single provider owns the connection; components use `useSubscription`-style hooks.
- [ ] Reconnect uses exponential backoff with jitter and a ceiling; heartbeat detects dead links.
- [ ] Incoming frames are validated against a schema and dispatched by `type`.
- [ ] Incoming data updates the shared cache; duplicates are ignored by ID; gaps are resynced over REST.
- [ ] Authentication uses short-lived tickets; server checks `Origin` and per-channel permissions.
- [ ] Socket closes on logout, unmount and token change; paused when offline or hidden.
- [ ] Server side has sticky sessions or a pub/sub backplane, limits, and metrics.
- [ ] Hosting supports long-lived connections (custom server or external realtime service).

### In this codebase
Measured with a quick scan of `src/` (not a full audit):
- **No WebSocket usage was found.** Real-time behaviour (chat and agent streaming) uses **Server-Sent Events** through the Node-runtime route handlers `src/app/api/chat/route.ts`, `src/app/api/persona-chat/route.ts` and the streaming proxy `src/app/api/backend/[...path]/route.ts` (`maxDuration` 800), with SSE parsing and schemas in `src/lib/api-client.ts` and `src/lib/api/sse-schemas.ts`. For one-directional model output this is the right transport and avoids the hosting limits of WebSockets.
- Before adding WebSockets (for example live collaboration or presence), confirm the hosting model supports long-lived connections, and prefer a provider-based `RealtimeProvider` with `useSubscription` hooks as shown above so components never touch the socket.
- The existing SSE client logic is a good candidate for the same provider-and-hook structure (one place for reconnect, validation and cancellation), see principle 40.
