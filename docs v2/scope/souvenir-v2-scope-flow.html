Perplexity reference — Search vs Computer
  • Two modes, one product. Search is quick, cited answers. Computer (launched 25 Feb 2026) is the agent mode: it splits a goal into subtasks and runs them in parallel with specialised sub-agents. Chat = Search, Task = Computer.
  • Models. Search lets the user choose a model. Computer coordinates about 19 models itself. Its Sept 2026 Effort Mode (Light / Standard / High / Ultra) lets users set how hard it works while Perplexity chooses the model. This supports P1.3.
  • Connectors in the composer. Selecting a connector once in the composer attaches it to the current thread. Pattern for P1.6.
  • Projects ≈ Spaces. Spaces are folders for threads with shared context, added via ⋯ → Add to Space. P1.5 goes further: attach before sending.
Possible extension: an effort control in Task mode instead of a model picker.

What it needs (from the scan).
  • No notification system exists today. No bell, inbox, unread count, /notifications endpoint or real-time channel (WebSocket or live event stream). Feedback is toasts to the person who did the action, in that tab. The settings page's switches aren't saved anywhere.
  • Backend work needed: a /notifications endpoint (list · unread count · mark as read), delivery by polling or a live stream, and saved preferences.
  • Sources that already exist: org audit log (/organizations/{id}/audit), Super Link dashboard (/persona-shares/dashboard), automation runs (/automations).
  • Front-end issues to fix along the way:
    1. The workspace credit status values don't match (paused vs grace|locked), so a paused workspace never shows the locked banner.
    2. Slack needs_reinstall and missing_scopes are read and then dropped.
    3. The souvenir:memory-updated signal has no listener.
    4. "Workflow invite" in settings points at unused /workflow/* endpoints.
Perplexity reference — notifications
  • The profile/account button sits at the bottom-left of the sidebar. Notification settings live in that menu (Profile → Notifications).
  • It notifies when long work finishes: Deep Research, Computer tasks, scheduled tasks, file creation. In-app, email and mobile channels can each be switched on or off.
Take from it: per-type, per-channel on/off settings, and "long task finished" as the main notification. Our visible bell feed goes a step beyond Perplexity's settings-only approach.

Perplexity reference — browser control
  • Computer can take full control of the Comet browser and work on any site or logged-in app with permission, without connectors or MCPs.

For Souvenir: a live view inside the P3 panel, a clear "Take control / Hand back" switch, and per-site permission before acting in a logged-in app.
Part B — New agents flow in detail

07Design principles

01Purpose in, agent outOne sentence from the user. Everything else is generated and editable later.
02Clarify in conversationAmbiguity (connector, data source, scope) is resolved with question cards, not settings screens.
03Workspace owns resourcesKnowledge lives in Library, connectors on the account. Agents use them.
04One agent, reusedCreated once, reused by chats and tasks. No duplicates.
05Owner edits, others use or copyNo shared edit rights, no half-locked agents.
06Nothing hidden or disabledOnly what works is shown. No dead or hidden controls.

15Open questions

  1. Versioning. Does V2 keep agent versions and a publish step, or is every save live? If versions stay, what does "publish" mean now that sharing creates copies?
  2. Test Chat and AI Suggestions. Kept (e.g. a "Try it" box on the editor page), or does the user just test the agent in a normal chat?
  3. Memories. Per user, per agent, or both? Do memories learned by a copied agent stay with that copy only?
  4. Reuse matching. How does a task decide an existing agent "matches"? Purpose similarity, name, or a question card?
  5. Library permissions. Can an agent be limited to part of Library (a folder or tag), or does it always see everything the user can see?
  6. Default model, tone and temperature. What are they, and who can change the defaults (workspace admin or user)?
  7. "Recommended for you" signals. Which data personalises the recommendations?
  8. Publish to workspace vs Share as template. Both hand out copies. Is the difference only discovery?
  9. Migration. What happens to existing V1.5 agents' knowledge files and blocked-connector lists: move them into Library, or drop them?
  10. Backend coverage. Which parts need new backend work (generation from purpose, Library, memories, templates, agent matching)? Needs a separate FE→BE handover doc.

16.2 Existing system (V1.5)

Pros
  • Precise, explicit control over every field
  • Per-agent knowledge and connector isolation; access tightly scoped by default
  • Version history with restore, plus a version limit that protects published and open versions
  • Test Chat and AI Suggestions beside the editor
  • Already built, with many race conditions fixed
  • Nothing auto-generated, so no AI surprises
Cons
  • Slow start: 4 screens before any value
  • Saving differs per tab; live agents can change without warning
  • Leaving never asks; autosave errors hidden
  • Test panels locked until first Save; lock screen has no Save button
  • Knowledge delete is a hard delete with no undo
  • Workspace agents missing in chat; Brain picker states false ownership
  • Lots of hidden, disabled or dead UI; fragile storage chains
  • Super Link recipients get a locked copy and land on the generic library

16.3 Proposed system (V2)

Pros
  • Fast: purpose in, agent out
  • Conversational: question cards only when needed
  • One editor page, one save behaviour
  • Knowledge and connectors managed once, at workspace level
  • Agents reused across chats and tasks, no duplicates
  • Memories make agents improve over time
  • Simple copy-based sharing; recipients can edit
  • Nothing hidden or disabled ships
Cons / risks
  • Generation quality: a weak name, model or prompt becomes the default if unreviewed
  • Broad access by default: every agent reaches all of Library and every connector
  • Too many question cards would feel like a form again
  • Clutter: auto-created agents could fill /agents
  • Wrong reuse: matching may pick an agent that's only roughly right
  • Memory privacy: users may not know what was learned
  • Lost V1.5 strengths (history, Test Chat) unless deliberately kept
  • Large rebuild: new backend work plus migration
16.3a Proposed fixes for the V2 risks

Shared rule: keep the fast default, and put a visible note with a one-click Undo / Swap / Edit right where it's used. No extra settings screens.

1 · Generation quality generate well, then let the user check it
  • Preview before create: built into Path B. The editor page shows every generated field pre-filled next to a live preview card, with Regenerate per field; nothing is saved until Finish. In Path A, the chat card has Edit, which opens the same page.
  • Structured prompt: generated instructions always follow one outline (role · goals · tools · output format · limits), so quality is consistent.
  • More context in: purpose + question-card answers + workspace context (industry, connected tools).
  • Model chosen by rules (type of work → model), not free-form AI choice. 2–3 name/avatar options to pick from.
  • Self-test: run 2–3 sample prompts before showing the agent. An Improve instructions button in Advanced, fed by 👍/👎 on replies.
2 · Broad access by default reading is open, writing needs permission, access can be narrowed
  • Read vs write: reading from Library and connectors is open. Sending / posting / editing / deleting asks the first time: Allow once / Always allow for this agent.
  • Access line in agent details and the editor page: "Can access: All Library · Gmail, Slack" with Edit to narrow it to folders, tags or connectors. Off by default.
  • Access follows the person using the agent: never more than the current user can access. Shared copies never carry the owner's access.
  • Sensitive Library items (HR, finance) are used only when the scope names them explicitly.
  • Activity log per run ("Read 3 docs · sent 1 email") in the task side panel.
3 · Too many question cards strict limit, smart defaults, never ask twice
  • Only ask when the answer changes the result. If there's a single or sensible default, use it and mention it: "Using Gmail (workspace) · change".
  • At most 3 cards per creation, shown together in one group.
  • Every card has a default selected + Skip, so pressing Enter moves on.
  • Remember answers as agent defaults and as workspace preferences.
  • Measure it: if more than about half of users skip a card, stop asking that question.
4 · Clutter task-created agents start temporary and are kept once useful
  • Temporary at first: tied to the task that created it, and not shown in the main /agents list.
  • Kept automatically after 2–3 reuses, or when the user clicks Keep in the task side panel.
  • Auto-archived after 30 days unused; archived agents can be restored.
  • Filters: Mine · Created by tasks · Shared with me · Archived.
  • Merge suggestions for look-alike agents.
5 · Wrong reuse match with a confidence score, show the choice, allow a swap
  • Match on more than the name: purpose similarity + tools needed + past success.
  • High confidence → reuse and show "Using Support Triage (reused) · Swap". Medium → one question card. Low → create a new agent.
  • Learn from swaps: stop suggesting that match for that type of task.
  • Reuse with small adjustments: add instructions for that run only, without changing the saved agent.
6 · Memory privacy visible, can be undone, never leaves the user
  • Say when it learns: a "Learned: prefers bullet summaries · Undo" note, never silent.
  • Memories page per agent: view / edit / delete, clear all, turn learning off.
  • Memories belong to a person and an agent, never shared in templates, workspace publishing or Super Links unless the owner picks specific ones.
  • Never saved: passwords, secrets, payment details, sensitive Library content.
  • Incognito chat: nothing from that conversation is learned.
7 · Lost V1.5 strengths keep the safety nets, drop the ceremony
  • History: automatic snapshot on every save; ⋯ → History → Restore; the user can pin a version so it's never removed.
  • "Try it" box on the editor page (next to the preview card), with no lock, because the agent exists as soon as it's created.
  • AI Suggestions → "Improve" button inside Advanced → Instructions.
  • Tight access comes back through the Access line (fix 2).
  • Keep the tested pieces: reuse V1.5's fixed save and race-condition logic where it still applies.
8 · Large rebuild build in phases, reuse what exists, make migration reversible
  • Start on the existing backend: POST /persona/starter already generates a prompt from name + purpose, and POST /persona already creates repo + version together. Purpose-only creation can use them first.
  • Phases: (1) new creation + panel over existing APIs → (2) Library + workspace connectors → (3) memories, matching, templates.
  • Feature flag per workspace, with V1.5 and V2 running side by side during rollout.
  • Migration (S10) with a dry-run report and rollback; existing agents behave exactly as before.
  • FE→BE handover doc early, listing new endpoints per phase.
16.4 Verdict — why V2 is better

V2 removes the cost of getting started and the inconsistency that cause most of V1.5's problems. Four ways of saving become one. Four setup screens become one sentence. Per-agent copies of files and connectors become shared workspace resources.

V1.5's real strengths are tight access scoping, version history and inline testing. They aren't reasons to keep V1.5, but V2 should carry them over deliberately. The fixes in §16.3a do exactly that while also reducing V2's own risks, and §17 sets out when to build them.

18.4 Resolve before building P0 — 🔴 summary
  1. Snapshot per run: editing a running agent never changes a run in progress.
  2. Generation failure and junk purposes: retry, manual fill, validation.
  3. Allowed models only: the rules never pick a blocked model.
  4. Delete, leave and orphan rules: dependency warning, soft delete, admin takes over.
  5. Automations protect their agents: never auto-archive an agent a schedule uses.
  6. Install-time checks: missing Library items or connectors; never carry personal connectors.
  7. Billing rules for each sharing type: who pays, clearly stated.
  8. Sign-in return link for share recipients.
  9. Task using a teammate's agent: copy on first use.
  10. Pause, don't fail: expired connector, credits running out, write approval with nobody around.
  11. No credential capture in take-control mode.
